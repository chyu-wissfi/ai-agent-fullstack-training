# 第四章 学习笔记

第三章解决了一个核心问题：一个需要搜索、阅读、修改和测试的任务，怎样通过 Loop 持续执行，通过 Planning 记录子目标，通过 Checkpoint 保存进度，再由 Harness 把工具、状态、审批和执行环境连接起来。



到第三章结束，我们已经有了一台能够连续工作的 Codebase Agent。

但能继续执行，不代表每一步都判断正确。



还是登录会话修复任务。Agent 明明运行了失败测试，下一轮却说“测试已经通过”；用户最早要求“不得修改现有测试”，任务执行十几轮以后，这条限制却不见了；几天后重新打开项目，Agent 又要从头搜索会话模块和测试命令。



这些问题不一定要靠换模型解决。我们首先要检查：

- 当前这一轮，模型实际看到了什么？

- 输入里的测试结果，测的是哪一版代码？

- 工具已经执行了，任务记录有没有更新？

- 新任务能不能读取上次留下的项目知识？

- 文档很多时，关键规则有没有被检索到？

- 原文变化以后，知识页、索引和缓存有没有一起更新？



所以第四章要回答的问题变成：

**怎样让模型每一轮拿到足够、适用、可核对的信息，并把后续任务仍然有用的知识保存下来？**



整章沿一条连续主线展开：

1. **4\.1 Context Engineering**：选择本轮材料，安排优先级，控制预算，并记录实际请求。

2. **4\.2 Working Memory**：把当前目标、约束、执行结果和未完成事项整理成准确的任务记录。

3. **4\.3 Memory**：筛选值得跨任务复用的信息，保存、召回、核对和维护。

4. **4\.4 RAG**：资料变多后，找到回答需要的证据，再检查回答是否受证据支持。

5. **4\.5 LLM Wiki**：把多份资料之间的关系整理成知识页，管理来源、更新、冲突和权限。

6. **4\.6 项目四**：把长期记忆和 RAG 接回 Codebase Agent，并沿真实执行链验收。

这六节不是六个独立知识点。



装配器要选择信息，首先得有准确的任务记录；当前任务结束以后，还要决定哪些信息值得留下；留下的资料越来越多，就需要检索；反复整理的结论可以形成 Wiki，但 Wiki 也必须跟着原文变化。最后，这些信息能力仍然要接回第三章的 Harness、Loop 和 Tool Runtime。

## 一、学习预期：这一章不要求你背什么？

本章不要求背诵 LlamaIndex、Milvus、OKF 或 pi 插件的全部 API，也不要求脱离 AI 手写一套完整检索系统。



真实工作中，AI 很适合帮助我们完成：

- 根据明确字段生成任务记录和元数据结构；

- 编写文档加载、分块、索引和检索适配代码；

- 实现记忆读写、索引同步和格式校验；

- 根据指定规则生成装配报告和评估脚本；

- 整理知识草稿、补来源链接、发现内容差异。



但下面这些判断必须由工程师完成：

- 哪些信息是当前决策必需的，哪些可以外存和按需读取。

- 哪些是用户要求、执行事实、历史经验或模型推断。

- 证据何时失效，恢复后怎样核对当前现场。

- 记忆保存什么，属于哪个项目，怎样更新和删除。

- 召回失败、排序失败、装配遗漏和生成错误分别怎样定位。

- 引用和自动检查到底证明了什么，哪些结论还没有检查。

- 来源变化或撤权后，哪些知识页、索引和缓存必须同步。

- 质量、成本和延迟按什么口径比较，什么证据支持启用一个方案。



掌握标准可以分成三层：

|能力层次|掌握标准|
|---|---|
|能解释|说清 Context、Working Memory、长期记忆、RAG 和 Wiki 各自负责什么|
|能追踪|沿一次任务找到材料来源、记录更新、检索候选、实际请求、回答引用和维护记录|
|能修复并验证|能发现丢约束、旧证据复用、跨项目记忆混用、召回遗漏、引用不支持结论和更新不同步，并用反例验证修复|

本章主要参考这些实现：

|参考实现|重点观察什么|
|---|---|
|pi 与 Codex 的上下文处理|历史压缩、近期消息保留、工具结果配对和实际请求记录|
|LiteLLM|模型路由、响应缓存、限流、重试与用量记录|
|OKF、pi\-okf、pi\-okf\-memory|知识文件组织、目录、更新记录和模型调用记忆工具|
|LlamaIndex、Milvus、BM25|文档到节点、向量索引、关键词检索、融合和来源追踪|
|LLM Wiki 实验|来源快照、草稿、发布、依赖维护、巡检和权限验收|
|project3/v2 的阶段四扩展|两件记忆工具、RAG 工具与既有治理链的组合|

这些实现不是标准答案。读代码的目标，仍然是找到稳定职责，再迁移到自己的工程。



## 本章贯穿的登录会话案例

第一阶段是修复到期边界：

> 请修复登录会话已经到期，却仍被判为有效的问题。当前时间小于到期时间时允许访问，等于或大于到期时间时拒绝访问。先定位和复现，再新增回归测试、修复实现并验证。不得修改现有测试，不得通过延长有效期绕过问题。

这个阶段重点看：模型有没有拿到当前源码和失败证据，任务记录有没有把“建议修改”“修改成功”“测试通过”分开。



第二阶段是新会话中的退出登录任务：

> 为 login\_demo 增加退出登录功能。先查项目知识，确认修改位置、业务规则和验证入口，再读取当前源码。

这个阶段重点看：长期记忆和检索有没有减少重复调查，返回的知识能不能追到来源，需求草稿有没有被误写成已完成功能。



第三阶段是知识更新实验：把已批准的教学规则从 30 分钟改为 60 分钟，但保留原始源码仍为 30 分钟的现场。

这个阶段重点看：系统能否同时说明“当前规则要求什么”“源码实际做什么”“旧版本曾经是什么”，而不是全局替换一个数字。



不同小节的演示工程、函数名和模型配置可能不同。阅读时以对应代码和运行记录为准，不把某个示例路径或一次输出当成所有工程的统一事实。

# 4\.1 Context Engineering：把模型每一轮需要的信息组织好

## 一、Prompt 写清楚以后，为什么还要管理 Context？

**Prompt 主要规定怎样做，Context Engineering 管理这一轮实际给模型什么。**

用户要求“到期立即失效，不修改现有测试”，属于指令。但模型要判断错误在哪里，还需要当前源码、失败断言、任务进度和可用工具。



模型会写比较运算符，不代表它知道这个项目恰好到期时算不算有效。Loop 能继续调用模型，也不能把遗漏的业务规则自动补回来。



一次模型请求至少包含这些对象：

|对象|登录修复中的作用|
|---|---|
|系统规则|规定角色、材料处理和执行纪律|
|当前用户目标与约束|说明修复什么，允许和禁止什么|
|历史消息|保留此前交互和工具结果|
|当前任务状态|说明已定位、未修改还是待验证|
|源码与证据|支持本轮判断|
|工具快照|告诉模型本轮可以申请哪些动作|



下面只看请求的组成，不展开模型调用代码：

```Python
request = {
    "messages": [
        {"role": "system", "content": "项目规则与材料处理规则"},
        {"role": "user", "content": "当前目标、限制和必要材料"},
        # 选中的历史、工具调用与对应结果、当前任务记录
    ],
    "tools": tool_snapshot,
}
```

`tools` 和 `messages` 都属于本轮输入。程序不能只统计用户那一句话，也不能把所有已存材料都当成模型已经看到了。



**Prompt 是 Context 中的指令部分；Context Engineering 管理进入模型的指令、材料、历史、工具说明和状态视图。**



## 二、上下文窗口解决容量，不能保证判断正确

输入管理同时面对两个问题：信息能不能放下，放进去后是否适用。

读源码、搜索和测试会产生大量文本。全部发送，可能超过窗口，也可能挤占输出空间。

即使没有超限，大量支付文档、旧版测试通过记录和已废弃规则，也会干扰登录到期判断。



因此，判断错误时先分流：

|现象|优先检查|
|---|---|
|请求超出窗口|输入预算、工具定义、输出预留和计数方法|
|当前失败没进入请求|材料选择与装配|
|旧版通过记录被使用|证据版本与失效规则|
|输入充满无关文档|相关性与优先级|
|有当前证据仍答错|原始请求、响应与生成行为|

长窗口提供更多容量，不能代替信息筛选；盲目删减也可能删掉必要的调用方或类型定义。目标是在预算内保留足够支持当前判断的信息。



## 三、Context Packing：选择材料，也安排材料去向

**装配不是全部拼接，而是围绕下一步决策，确定直接提供、外部保存和按需读取的内容。**



登录边界排查阶段，可以这样安排：

|去向|内容|原因|
|---|---|---|
|本轮直接提供|到期立即失效、不得修改现有测试|决定正确行为与修改边界|
|本轮直接提供|当前比较条件、失败输入、预期和实际结果|决定本次错误怎样复现和修复|
|外部保存|完整测试日志|保留核对依据，避免每轮复制全部内容|
|请求中提供引用|完整日志路径与执行编号|缺细节时能够补读|
|暂缓读取|无关模块与早期探索全文|当前动作不依赖它们|

装配后的材料可以写成：

```JSON
{
  "规则": "now >= expires_at 时会话失效",
  "限制": "不得修改现有测试，可新增回归测试",
  "当前代码": "return now <= expires_at",
  "失败证据": {
    "输入": {"now": 100, "expires_at": 100},
    "预期": false,
    "实际": true
  },
  "完整日志": "artifacts/session_tests.log"
}
```

这是一份教学输入，不表示本段执行了测试。模型要补读完整日志，可以提出 `read_file`；真实读取仍由 Loop 和 Runtime 完成。



文件路径必须真实存在，并位于允许访问的范围内。一个不能读取的引用，不能承担恢复证据的作用。



## 四、Context Prioritization：先判断有效，再分配空间

只保留最近 N 条历史，有两个明显问题。

最早的“不得修改测试”可能被删；刚出现的一句旧版“测试通过”，也可能挤掉当前失败证据。



所以选择材料时，先问三件事：

1. 它现在是否仍然有效？

2. 它是否与当前步骤相关？

3. 缺少它，模型会不会选错动作或判断错进度？

在排查阶段，规则、当前源码和失败证据优先；补丁完成后，当前 Diff、修改结果和新测试状态优先。优先级要随任务阶段变化。



看下面的代码，只关注“分配空间的顺序”：

```Python
def allocation_order(blocks):
    return sorted(
        range(len(blocks)),
        key=lambda i: (
            not blocks[i].required,
            -blocks[i].priority,
            i,
        ),
    )
```

必须项优先，随后按优先级分配。它没有完成预算检查，也没有授权任何工具。



这里有两个边界：

- 必须保留的是必要信息，不一定是原文全文。失败断言和准确引用可以替代几千行日志。

- 空间分配顺序不是历史消息发送顺序。工具调用仍在结果之前，调用与结果保持配对。

约束还可以保留理由。比如“继续使用现有 session 中间件，因为所有客户端共用它”，比只有一个禁止句更容易让模型理解影响范围。



上下文帮助模型选择方案，执行权限仍由 Runtime 强制检查。



## 五、Context Budget：先留输出，再算完整输入

输入预算按这个公式计算：

$B_{input}=W_{context}-R_{output}-M_{safety}$

同时还要满足模型和 Provider 各自的输入、输出限制。



假设窗口为 16,000 Token，输出预留 3,000，安全余量 1,000，输入预算就是 12,000。系统规则、用户要求、工具定义和消息格式开销占去 3,000 后，材料才有约 9,000 的空间。



**输出预留不能被输入借走。**模型还要生成回答或工具参数，输入占满窗口，后续动作也可能无法正常产生。

安全余量覆盖计数误差，但不能代替校准。统计时要检查整个请求，不能只把几个正文字符串的长度相加。



### 5\.1 教学预算实验怎样读

原稿主动设置课堂容量 1,000、输出 128、余量 150，因此输入预算是 722 Token。这是教学限制，不是实际模型窗口。

|材料|本次处理|
|---|---|
|业务规则和修改限制|必须保留|
|完整失败日志|放不下，改为断言和原文引用|
|当前源码与任务状态|能放下，保留|
|旧版测试记录|已失效，排除|
|支付文档|优先级低且超限，本轮跳过|

全部材料的估算约为 17,183 Token，装配后约为 220–222。几次记录略有差异，来自临时日志路径变化。

其中一次实际输入为 131 Token，本地估算为 221，差了 90。只能说明这次计数口径不同，不能以后固定减去 90，也不能认定本地估算永远偏大。



发送前用估算检查预算，发送后用服务端 `usage` 核对，多次运行后再调整计数方式与余量。

日志里的“当前失败/完整：12,137 / 722”表示加入这份材料后的整个输入预计占用，不是该材料单独的大小。



### 5\.2 关键内容放不下，就停止发送

原稿还验证了两个拒绝场景：预算小到基本规则和工具说明都放不下；必要证据压缩后仍超出预算。两种情况都停止发送。



对应处理顺序是：

1. 规则与工具说明重复，就精简重复内容，只提供本轮需要的工具，并保持执行快照一致。

2. 必要代码或证据太长，就缩小读取范围或拆成多步。

3. 必须项仍放不下，就拒绝发送，不能静默删掉关键限制继续调用。

4. 切换到更小窗口的模型，重新检查并装配。



还要分清两个预算：本轮请求是否放得下，整个 Run 是否还有 Token、费用和时间额度。前者由装配入口检查，后者由 Harness 累计管理。



## 六、Context Compression：缩短内容，保留核对依据

工具结果和任务历史不是同一种压缩对象。

|对象|优先处理方式|必须保留|
|---|---|---|
|结构化测试结果|程序提取关键字段|状态、失败断言、版本、异常、完整记录位置|
|长任务历史|生成交接摘要|目标、约束、已完成、未完成、失败方案和下一步|
|长源码|搜索定位，再读取必要范围|当前函数及必要调用方、类型和配置|
|无关材料|本轮不提供|不必先花模型调用生成摘要|



### 6\.1 工具结果不能只截开头

只截前 500 字符，可能保留下来的全是启动信息，失败断言却在末尾。

到期边界需要保留：`now=100`、`expires_at=100`、预期 `False`、实际 `True`，以及测试对应的代码版本。

下面是原稿压缩函数的核心做法，只展示关键字段：

```Python
summary = {key: result[key] for key in (
    "revision", "status", "tests_run", "failure_count",
    "error_count", "errors", "output_ref",
)}
summary["failures"] = result["failures"][:max_failures]
summary["omitted_failures"] = (
    len(result["failures"]) - len(summary["failures"])
)
```

字段缺失应该报错，不能当作测试通过；至少保留一条失败证据；总失败数和省略数量都要在。

实际执行三个边界检查，只有恰好到期失败。人为加入的重复启动信息让完整记录约为 3\.6 万字符，短结果约为 459 字符。

这个结果证明本次程序提取保留了失败依据。它不表示所有日志都适用同一个压缩规则。短结果也仍要通过总预算检查。



`revision` 用内容哈希标识受测代码；完整记录保存到文件，缺细节时通过工具补读。



### 6\.2 模型摘要也要核对

交接摘要至少要说清：

> 目标是到期立即失效；不得修改现有测试；当前 `<=` 导致边界失败；补丁尚未应用；下一步修改并验证；源码版本和日志位置可核对。



pi 的默认会话压缩会整理较早历史、保留近期消息，并结合已有摘要更新；Codex 会根据配置与 Provider 能力采用相应压缩路径。阅读重点是摘要与原始记录的关系，不是记住内部类名。



摘要可能漏约束，也可能把“怀疑时区问题”写成“已确认”。因此：

- 关键约束由程序保留；

- 测试状态以执行记录为准；

- 更新摘要要结合新增记录和可核对事实；

- 生成摘要本身计入 Token、费用和时间；

- 路径、版本和工具调用 ID 保持准确。



压缩后的输入更短，且关键判断仍有依据、缺细节还能补读，才算达到目的。



## 七、上下文污染：结构完整与内容可信要分别检查

**错误、过期或不适用的信息进入请求并影响判断，就是上下文污染。**

|类型|登录案例|处理动作|
|---|---|---|
|过期信息|旧版通过结果用于新代码|标记受测版本，重新验证当前代码|
|信息冲突|旧宽限期规则与当前立即失效要求冲突|标明来源，核对采用规则|
|摘要失真|猜测被改成确定根因|回看执行记录与原文|
|外部指令混入|源码注释要求上传环境变量|当作材料内容，执行仍走权限边界|

装配和裁剪还可能破坏工具消息：保留结果却删掉调用，或留下调用却没有结果。



发送前至少检查：

1. 工具调用由 assistant 消息提出，调用 ID 合法且不重复。

2. 每条结果对应待完成的调用 ID。

3. 一批调用的结果配齐后，再进入后续交互。

4. 没有孤立结果，也没有未说明状态的缺失结果。

正式工程也可以根据执行记录补齐中断状态，但必须保留原 ID，部分内容要明确标记不完整。



**补齐消息是在修复历史；重新读取是一次新的工具调用。**不能补造成功结果，也不能借补齐历史重放结果不明的写操作。



消息配对正确，只证明协议结构完整。合法的“测试通过”消息仍可能来自旧版本。



## 八、Context Debug Report：查清模型实际收到了什么

只记录本轮 Token 数，无法解释当前失败为什么没有进入请求。



一份装配报告至少应记录：

|范围|要记录的内容|
|---|---|
|每份材料|身份、来源与版本、处理方式、选择或排除原因、处理前后占用|
|整个请求|输入预算、最终估算、计数方法、请求哈希、实际请求位置|
|运行关联|Run ID、轮次、策略版本、实际模型、工具快照|
|压缩过程|原始历史、摘要、重建历史、触发原因和耗时|
|调用结果|响应、实际 usage、首文字延迟、总耗时和错误状态|

单份材料占用用于观察变化，最终总数从完整请求重新计算。



### 8\.1 真实摘要与恢复实验

运行入口：

```Bash
python 4-1-8-Report.py
```

配套文件在运行记录中也出现小写 `report`，以实际工程文件名为准。



本次流程是：读取并确认失败 → DeepSeek 生成摘要 → 摘要替换早期交互 → 比较输入 → 恢复后核对源码 → 应用补丁 → 运行真实测试 → 独立验收。

|观察|原稿记录|能支持的结论|
|---|---|---|
|摘要状态|已定位，未应用补丁，未重跑测试|没有把方案写成已修复|
|相同探测问题的输入|637 → 262 Token|本次实际输入减少 375，约 59%|
|摘要调用|总计 848 Token|压缩有额外调用成本|
|恢复后行为|重读源码并核对版本，再修改和复测|没有直接把摘要当当前现场|
|最终验收|三个测试通过，测试文件未修改|对应修复任务本次验收通过|

这里使用 DeepSeek 重现模型摘要和历史重建，没有调用 OpenAI 远端压缩接口。



本次实验也没有验证“排除旧通过”“跳过支付文档”和“必须项超限”，不能把前面装配实验的结果混进来。

压缩后后续输入又从 677 增加到 1,472 Token，说明新工具结果仍会继续累积。一次压缩不是永久控制上下文。



### 8\.2 判断错了，按四个位置找信息变化

1. `original-history.json`：原始结果是什么。

2. `summary.md`：摘要有没有漏约束、改状态或把推断写成事实。

3. 恢复后的 `*-request.json`：正确摘要和用户要求是否真正发送。

4. 对应响应：模型看到正确信息后是否仍判断错误。

先找到第一个出错的位置，再修对应规则。请求哈希只能帮助核对请求身份，仍要打开实际内容。



**报告证明程序发送了什么，不能证明模型内部怎样理解。**



接入时，在 Harness 模型入口保存请求、结束后关联响应与消耗。pi 继续负责 Loop，Runtime 继续负责工具执行。



## 九、Retrieval Context：缺什么，通过工具补什么

资料不在当前记录中，就通过工具寻找：需要堆栈时读取日志，找不到函数时搜索定义，再读取相关范围。

这已经属于按需检索上下文，不一定先建向量数据库。

补回来的内容仍要检查来源、版本、范围和预算。检索成功不意味着全文直接进入下一轮，也不意味着其中的文字变成指令。

分块、Embedding、混合检索与重排放到 4\.4 深入。这里先掌握：依据不足，就明确缺什么并补读，拿到材料后再判断。



## 十、长上下文的成本与延迟：统计整个任务

压缩后的一个请求变短，不能直接推出整个任务更便宜。

比较方案至少看五件事：任务完成率、总 Token、总费用、首文字延迟、端到端耗时。

摘要、重试和探测请求也要计入。模型等待与生成、工具执行分别计时；工具跑五秒，不能全部算成模型慢了五秒。

缺失 usage 记录为未知，缺单价就不能给出确定费用。



## 十一、KV Cache：复用计算，不能证明信息正确

KV 是注意力计算中的 Key 与 Value。单次生成时缓存前面内容的计算结果，可以避免生成下一个 Token 时全部重算。

部分服务还支持跨请求的前缀复用。稳定规则尽量保持内容和顺序一致，变化状态放在后面，有机会提高复用；是否命中看实际服务和统计。

规则、权限或工具变化，必须更新。不能为了缓存命中继续使用过期内容。



## 十二、LiteLLM：接回 Gateway，分清缓存与重试

**Harness 整理输入，LiteLLM 按配置发送、路由、限流和重试。**网关不会自动补回失败证据，也不会修正错误摘要。

|类型|复用的对象|
|---|---|
|KV 与前缀缓存|已完成的模型计算|
|Gateway 响应缓存|已生成的回答|

响应缓存要让代码版本、权限、工具变化进入请求或隔离规则。不能只根据“修复登录”几个字返回旧答案。

演示入口：

```Bash
python 4-1-12-Gateway.py
```



直接使用 LiteLLM 库与 `DEEPSEEK_API_KEY`，代码配置 `agent-default` 路由并关闭 thinking。它不要求另起网关服务，也不应与其他版本的网关地址配置混淆。

|实验|原稿结果|结论范围|
|---|---|---|
|首次与相同输入|1,514 ms → 缓存命中 8 ms|本次响应缓存生效|
|版本、源码和测试描述变化|未命中缓存，重新调用|本次未复用旧回答；材料是预设，未真实改代码或跑测试|
|限流|第二次返回 429|本次限流生效；跨分钟边界时结果可能不同|
|两个并发请求|都成功|不能据此证明并发限制或串行行为|
|有限重试、模型回退|配置重试，只有一个模型|本次没有重试过程和回退证据|

缓存命中的 `usage` 来自原响应，不能再算一次新的模型消耗。流式中途失败时记录错误与已接收内容，再由 Harness 判断下一步，不直接重放整个请求。



SDK 与网关的重试要统一管理，避免倍增。模型重试不能顺带重放已经执行的补丁。输入超限回到装配器；切模型重新检查窗口与能力。

原稿记录还指出两项问题：价格配置缺失导致显示零，不代表免费；`acompletion` 未 await 的警告需要修复，不能因为报告生成就宣布代码完全正确。



### 本节重点与验收

**重点掌握**：Prompt 与 Context 边界；装配、优先级、预算、压缩、污染与报告；按需补读；本轮与整次任务预算；KV 与响应缓存；网关路由和重试边界。



**了解即可**：框架内部压缩类名、模型分词器全部细节和 LiteLLM 所有配置项。



验收时至少证明：

1. 当前限制、当前源码和失败断言进入实际请求。

2. 旧版本测试不会被当作当前验证结果。

3. 工具调用与结果配对完整。

4. 必须项压缩后仍超限，模型请求没有发出。

5. 原始历史、摘要、请求与响应能够相互关联。

6. 成本统计包含摘要等额外调用，并明确未知值。

# 4\.2 Working Memory：把当前任务的信息组织起来

## 一、为什么有了对话历史，还要工作记忆？

4\.1 的装配器负责选择信息，但它首先要有一份准确的任务记录。

登录修复进行到一半：Agent 已经读源码、取得边界失败，建议把 `<=` 改成 `<`。此时真正的进度是“已定位，未修改，未验证”。



下一轮用户只说“继续”。如果输入没有明确进度，模型可能重新搜索，也可能误把修复建议当作代码已经修改。

完整历史能帮助判断，但其中同时有计划、失败尝试和后来的结果。历史越长、压缩越多，每轮重新推断进度越容易出错。



**工作记忆，就是围绕当前任务保存目标、约束、执行事实和未完成事项的记录。**它让装配器直接取出当前进度，也让程序检查当前版本是否真的完成验证。

|记录方式|回答的问题|
|---|---|
|历史|每一步发生过什么？|
|工作记忆|现在什么已完成，什么失败，什么还没做？|
|本轮 Context|这次决策需要看到其中哪些内容？|

工作记忆可以包含在已有 State 中，不要求另建一套数据库。



## 二、最少保存哪些信息？

先从四类开始：目标、已完成步骤、关键工具结果、未解决问题。再补充约束、风险、来源和版本。

|字段|当前登录修复记录|
|---|---|
|目标|恰好到期时返回 `False`|
|已完成|读取源码、运行边界测试、定位比较条件|
|关键结果|`test_at` 预期 `False`，实际 `True`|
|未完成|补丁尚未应用，修改后尚未测试|
|约束|不得修改现有测试，不得延长有效期|
|风险|改变边界可能影响调用方，待搜索和测试|
|下一步|准备并应用符合范围的补丁|

这里最重要的不是字段名，而是状态依据：



**提出方案、修改成功、测试通过，是三个不同阶段。**

模型建议修改，只能保存候选方案；修改工具确认成功，才能写“已修改”；测试实际通过，才能保存对应版本的通过结果。



### 2\.1 工具结果保存摘要，原文保留核对入口

几千行日志不必全部复制到工作记忆。当前记录可以保存失败用例、输入、预期、实际、版本和原文位置。

```JSON
{
  "summary": "test_at 失败：预期 False，实际 True",
  "source": "run_test",
  "execution_id": "test-001",
  "code_version": "v1",
  "status": "current",
  "reference": "logs/test-v1.txt"
}
```

这是完整字段的教学示例。原稿前面的简化字典未列出所有字段，正式实现要补齐后再引用。

摘要让模型快速知道边界问题；原文与执行 ID 让程序能够核对。不能删掉失败断言，也不能把未测试写成通过。



## 三、约束与风险怎样记录，谁负责执行？

**约束是必须遵守的要求，风险是需要检查的影响。**



“不得修改测试”是约束；“修改后是否影响调用方”是风险；“我准备只改一个文件”是 Agent 的计划，不能冒充用户要求。

|对象|至少保存什么|更新方式|
|---|---|---|
|约束|内容、来源、适用范围|用户或有效项目规则调整后更新；无法判断冲突时澄清|
|风险|可能的问题、依据、具体检查动作|搜索或测试后记录已排除、已确认或仍待核对|

约束写进工作记忆，只能帮助模型准备方案。违规方案仍要在执行前拦住。



“不得修改现有测试”的完整链路是：

1. 工作记忆保存要求及来源。

2. 装配器把要求放进模型输入。

3. Runtime 在写入前检查补丁目标。

4. Harness 根据允许、拒绝或执行结果更新进度。



如果补丁涉及禁止文件，Runtime 拒绝后，记录必须变成“补丁被拒绝，代码未修改”，下一步重新准备补丁。不能沿原计划直接进入“修改后验证”。



## 四、临时事实要有来源，也要能失效

工具读取到的源码、测试结果和修改状态，都是某个现场下的执行事实。“临时”指它们可能随代码或环境变化失效。

下面这些内容要分开：

|内容|性质|可以证明什么|
|---|---|---|
|工具返回 `<=`|源码观察|当时读取的版本使用这个表达式|
|工具返回边界失败|执行事实|对应版本该用例未通过|
|模型说改成 `<` 应该有效|候选判断|有一个待验证方案|
|工具确认补丁应用|修改结果|文件已发生对应变更|
|新版本测试通过|验证结果|本次覆盖的测试在该版本通过|

代码从 v1 改为 v2，v1 的失败仍然是真实历史，但不能证明 v2 仍失败；v1 的通过同样不能证明 v2 正确。

相关旧证据要按规则标记 `stale`，当前版本重新测试。源码、任务要求和运行环境变化，都可能触发失效。

`status=current` 需要程序维护。写一个标签，不会让证据永久有效。

分支也要隔离：方案 A 与 B 的代码不同，不能用 B 的通过记录证明 A 完成。



## 五、Scratchpad：把计划和下一步接到执行事实后面

失败事实说明发生了什么，但不一定说明准备怎样处理。

Scratchpad 是工作记忆中的任务便签，保存计划、观察、简短决策和下一步。它不要求保存模型内部的隐式思维链。



看下面的便签，重点看证据引用与状态：

```JSON
{
  "plan": ["修改比较条件", "运行边界测试"],
  "observation": "恰好到期仍返回 True",
  "evidence_id": "test-001",
  "status": "已定位，尚未修改",
  "decision_summary": "拟将 <= 改为 <，效果尚未验证",
  "next_step": "应用补丁"
}
```

`evidence_id` 对应失败执行记录，说明为什么提出这个方案。下一轮知道准备做什么，同时知道还没执行。

补丁失败，就记录失败并检查原因；测试通过，就核对是否覆盖全部要求，再决定能否完成。

**计划可以由模型提出，执行状态必须根据真实结果更新。**



## 六、工作记忆生命周期：创建、更新、保存、恢复、归档

|阶段|输入与动作|结果|
|---|---|---|
|创建|读取目标、约束和初始现场|建立当前任务记录|
|更新|收到每次工具结果|调整已完成、失败、风险和下一步|
|保存|到达暂停或恢复边界|记录不随进程退出而丢失|
|恢复|读取记录并核对当前代码|确定从哪一步继续，哪些证据需重做|
|归档|核对完成条件|保留执行记录，筛选后续有用知识|

补丁成功后暂停，要保存新版本、修改结果和“尚未测试”。恢复时确认当前文件仍匹配，再继续测试。

暂停期间别人改了代码，就先检查差异，重新决定验证范围。存档说明上次做到哪里，不能证明外部文件一直没变。

### 保存与发送是两个动作

完整日志可以持久化，本轮只发送失败断言和引用。工作记忆可以保存多个风险，本轮只提供影响当前动作的部分。

**持久化保证记录能再读；上下文装配决定模型这次实际看到什么。**



## 七、Agent State、执行记录和工作记忆怎样分工？

Agent State 可以保存消息、模型、工具和运行标记，也可以包含业务字段。这里单独讲工作记忆，是为了明确目标、证据和进度怎样更新。

|保存位置|主要职责|
|---|---|
|执行记录|原始工具返回、调用关联、退出码和日志|
|工作记忆|提取后的关键结果、当前目标和进度|
|模型请求|本轮选中的信息|

它们可以存于同一个文件或数据库，但语义要能区分。



### 原稿 JSONL 演示证明了什么？

演示依次写入用户要求、预设工具调用、真实边界表达式结果，再写入 `customType=working_memory` 记录。恢复时重新读取，取出最新工作记忆，装配进下一轮消息。



这里关注两件事：

- 调用 `id` 与结果 `toolCallId` 相同，说明结果对应哪次执行。

- 自定义工作记忆保存下来后，不会自动成为模型消息，还需要装配器读取并加入请求。

演示中的 `isError=False` 表示计算工具正常获得结果。结果为 `True`，与预期 `False` 不符，业务验证仍然失败。



**工具正常返回，不等于任务验证通过。**

这段代码没有调用模型、没有修复源码，也没有核对恢复后的版本；临时目录退出后删除。它证明记录写入、重新读取和装配路径成立，正式工程仍需持久存储与现场核对。



### 本节重点与验收

**重点掌握**：历史与当前记录的区别；目标、约束、风险、事实与下一步；来源和版本；Scratchpad；结果驱动状态更新；保存与发送分离；工作记忆与 State 的边界。

**了解即可**：JSONL 每个内部字段的具体名字。



验收至少覆盖：

1. 仅提出方案时，状态仍为未修改、未验证。

2. 补丁失败或被拒绝后，不会记录修改成功。

3. 修改版本后，旧通过记录不再支持完成。

4. 新进程能读取进度，核对现场后继续未完成步骤。

5. 工具执行成功与业务断言通过分别记录。

# 4\.3 Memory 体系：从当前会话走向长期复用

## 一、短期与长期，按用途区分

工作记忆帮助完成这一次修复。任务结束后，“正在准备补丁”通常已经没用，但模块位置、项目边界要求、测试入口和核验过的修复经验，下次增加退出登录还会用到。

不保留这些信息，新任务就要重新搜索，用户也可能再次说明同一条约定。



**长期记忆，是跨会话、跨任务保存并复用信息的能力。**程序从外部记录取回相关知识，再放进模型输入，没有修改模型参数。

|信息|当前任务用途|后续任务用途|
|---|---|---|
|补丁尚未应用|当前进度|通常没有|
|当前失败断言|分析和修复|可整理为有版本范围的故障经验|
|会话模块路径|本次定位|新任务的定位线索|
|测试命令|本次验证|下次修改的验证入口|
|到期立即失效的项目规则|本次约束|范围内后续功能仍需遵守|

短期说的是服务当前任务，不是只能放内存。一个任务持续两天，工作记忆保存到数据库，仍然主要服务这个任务。

长期说的是跨任务复用，也不保证永远正确。代码和约定变化后，记录仍要维护。



## 二、长期记忆保存什么？先筛选，再写入

写入前问三件事：

1. 以后哪类任务还会用到它？

2. 来源能不能核对？

3. 什么变化会让它失效？

模块和测试入口有明确用途，可以保留；“退出登录可能与缓存有关”只能作为推断；已删除的临时打印通常留在本次日志即可。

凭证、登录令牌、密码和完整用户请求载荷，不作为本案例的长期知识。真正需要留下的是模块、规则与经验。



### 2\.1 要求、事实、推断和证据分别保存

|性质|例子|使用时怎样判断|
|---|---|---|
|要求|维护者规定到期立即失效|核对提出者权限和适用范围|
|事实|实际读取确认模块位置|核对版本和当前文件|
|推断|退出故障可能与缓存有关|作为排查线索，不能直接定根因|
|证据|命令回执、源码哈希、测试日志|支持核对对应结论|

用户说“不要修改测试”是要求；用户说“文件应该在 session 目录”仍可能只是待核对线索。

保存内容时，记录项目、来源和检查时间。涉及执行事实，再补版本或文件哈希。

一次任务的限制不能不加范围地变成全项目永久规则。



## 三、记忆生命周期：写入、检索、更新与失效

### 3\.1 写入后，新任务还必须真正读取

输入是本次确认的模块位置与测试入口；动作是连同项目和来源写入；结果是形成外部记录。

几天后，输入变成“退出登录任务 \+ 项目标识”；程序检索相关记录、装配进请求；模型才能根据路径读取当前源码、确认测试，再实施功能。

只看到回答提及熟悉文件名，不足以证明记忆被读取。要看工具回执或确定性加载记录。

### 3\.2 更新定位到原记录，避免相似内容误覆盖

测试移动到新目录，就依据当前文件和运行回执更新原入口，同时保留来源与检查时间。

更新、删除以前，先确认项目和准确的记录 ID 或路径。搜索只能返回候选，不能因为两条内容相似就任意覆盖。

错误推断曾被写成确定结论，应纠正或删除，防止它反复影响后续排查。

### 3\.3 冲突先核对范围，再比较来源

旧记录是 `pytest ...`，新说明是 `python -m pytest ...`，两条可能都能运行，差别可能在入口约定和环境。

不能只因新消息更晚就覆盖。它可能来自模型建议，也可能属于另一个分支。

处理顺序：同一项目、同一对象和环境吗 → 来源是否适用 → 谁有权调整要求或提供新证据 → 决定替换内容。

**要求看谁有权提出，事实看证据是否适用。**同样可靠却矛盾，就查配置或让维护者确认。

### 3\.4 过期、废弃与删除分别处理

“旧版本用 `<=`，改为 `<` 后测试通过”可以保留为历史经验；“当前源码仍用 `<=`”在修改后就不能当现行事实。

|动作|用途|
|---|---|
|标为过期或历史|保留追溯价值，退出当前事实使用|
|废弃|不再作为推荐入口或有效规则|
|删除|移除错误、不应保存或无保留价值的活动记录|

删除活动记忆不自动证明备份和缓存都已清除，清除范围需要单独定义。



## 四、OKF：先解决知识组织，再选择检索技术

**长期记忆不等于向量数据库。**保存、分类、来源、更新和使用规则，不能由向量相似度替代。

OKF（Open Knowledge Format）用 Markdown 目录树组织知识，顶部 YAML 保存元数据，链接连接相关概念，`index.md` 提供目录，`log.md` 记录更新。

OKF的 v0\.2 规范中，概念文件的 `type` 始终必填。课程使用的 `~/.pi/agent/okf-memory` 是路径约定；`~` 是用户目录，实际跨项目隔离仍要确认配置的根目录，不能只靠标签。

工作顺序可以是先读索引，再读当前任务相关概念，不必把整套知识全文自动塞进请求。



### 4\.1 元数据组织了记录，不能单独证明内容正确

实际展示的文件被标记为 `type: Fact`，带标题、描述、标签、时间和 `source: session`。

但正文同时包含：

- 会话模块路径线索；

- 教学项目的到期要求；

- 按原相对路径没有找到文件的说明；

- 使用前读取源码和检查边界测试的清单。



描述直接写“实现在 `app/session.py`”，正文却承认原路径未找到，摘要比正文更确定。这是需要核对的信号。

|字段或内容|不能直接推出什么|
|---|---|
|`type: Fact`|全文每条内容都已验证|
|`source: session`|哪句话来自用户，哪句话来自实际读取|
|时间戳|测试就在这个时间执行|
|标签和项目名|存储根目录已隔离|
|文件路径线索|当前文件一定存在|

使用这份知识，要先找到当前源码、核对比较条件与边界测试。记忆给定位入口和检查步骤，没有证明当前实现正确。



## 五、pi 插件实操：安装、建立、召回、更新

本节涉及两个用途：pi\-okf 辅助建立和维护项目知识；pi\-okf\-memory 在对话中让模型调用工具保存与召回。

原稿提醒两套插件声明的 OKF 版本不同，不能直接混写。以对应插件支持的格式与实际回执为准。



### 5\.1 终端安装与会话命令分开

先在终端安装原稿使用的版本：

```Bash
pi install npm:pi-okf@0.4.0
cd /path/to/your-project
pi
```

安装成功后再进入 pi 会话。`pi install` 是终端命令，`/okf-init` 是会话命令。

本笔记保留原稿版本，命令作为课程操作记录，不代表它是最新发布版本。



### 5\.2 基于证据建立知识

在 pi 会话中先说明任务，再调用初始化命令：

```Plaintext
请基于当前源码、项目说明和实际测试记录建立知识。
重点记录会话模块位置、到期规则和测试入口。
不要修改业务源码，不保存凭证，不把推断写成验证事实。
没有执行证据的测试结果标为待验证。

/okf-init
/okf-validate
```

执行后检查实际文件清单、索引与相关概念文件。名字与讲义不同，就采用真实路径。

`/okf-validate` 校验格式，不能证明登录行为正确，也不能证明测试通过。



### 5\.3 全新会话验证外部读取

关闭旧会话，在同一项目启动新 pi 会话，要求先读索引、再读会话与测试概念、最后读当前源码。

```Plaintext
我要为 login_demo 增加退出登录，先不要修改代码。
先读取配置中的 OKF 根目录索引，再读取会话与测试相关概念。
核对来源和状态，读取当前源码。
输出需要检查的文件、适用约定和建议测试入口。
每项说明来自哪个知识文件，以及与当前代码是否一致。
```

原稿记录中，索引 → 概念 → 源码三步都出现在工具回执，可以确认外部知识进入了新会话。

此时只完成定位与核对，没有实现退出登录，也没有运行建议命令。



### 5\.4 更新原概念，核对格式与实际含义

维护者调整测试入口后，先更新项目说明，实际运行新命令，再让 Agent 更新原测试概念。

```Plaintext
/okf-update session
/okf-validate
```

检查当前入口、来源和验证范围是否更新，旧命令是否只保留于历史说明。

也可基于差异提供更新线索：

```Plaintext
/okf-update diff origin/main
```

Diff 说明哪些文件变化，Agent 仍需阅读内容。不能只凭文件名生成知识结论。

删除临时或错误记录时，同样先定位准确项目与记录，再检查实际删除结果，不把搜索结果数量当删除成功。



### 5\.5 “自动记住”具体怎样发生？

适配层在会话启动时准备记忆库和目录摘要，在 `before_agent_start` 注入记忆纪律、目录摘要与读取指引。

模型根据这些指引决定是否调用工具。新背景、稳定偏好、明确决策和用户纠正出现时，先搜索避免重复，再调用 `okf_remember`；后续问题先 `okf_search` 找候选，再 `okf_read` 读全文。

原稿提到六件记忆工具，但正文没有完整列出名称。本节只使用已经明确给出的名称，其余以安装版本提供的工具列表为准。



**自动指模型在指引下选择工具，不是后台无条件保存每句话。**也不是每次任务都会确定性地读入全部记忆。

是否实际写入、召回或删除，看回执。目录摘要不等于全文；关键项目约束仍由 Harness 精确加载，再交执行层检查。

图谱查看入口：

```Plaintext
/okf graph
```

原稿描述 macOS 会打开生成的 HTML，其他平台按回执路径打开。建立关联使用真实概念 ID 并检查 `related` 与图谱边。

图谱显示关联，不能直接证明因果。



## 六、当前任务丢失上下文，长期记忆能恢复全部进度吗？

不能只查长期知识就宣布恢复。

长期记忆能告诉模型模块在哪里、曾用什么办法；当前任务到底应用补丁没有、审批是否有效、测试对应哪个版本，仍要读工作记忆、Checkpoint 和执行回执，再核对现场。

|信息|恢复入口|为什么这样安排|
|---|---|---|
|当前目标、约束、步骤状态|工作记忆与 Checkpoint|要精确知道哪些动作已执行|
|模块线索与历史经验|按项目召回长期记忆|先取候选，再核对是否仍适用|
|完整日志与补丁细节|执行记录引用|需要细节时再读|
|当前文件与环境|实际工具读取|判断旧状态能否继续使用|

不要把这几类信息混在一次相似度检索里。否则模型可能把经验当约束，把旧测试当当前通过结果。



## 七、记忆策略怎样比较？

|策略|可能收益|需要承担的代价|
|---|---|---|
|无记忆|简单，没有记忆查询开销|重复搜索和重复询问|
|完整历史|细节多|输入增长，夹带旧状态，可能超限|
|摘要记忆|输入集中|可能漏约束、改条件；生成有开销|
|按需检索|控制输入规模|查询、维护成本与漏召回风险|

这些是取舍，不是本项目已测出的性能结果。不能只因接了插件就宣布成功率提高或延迟降低。

本项目先采用组合方案：精确状态走工作记忆和 Checkpoint，必要约定按项目读取并强制检查，经验按需检索，完整日志留引用。

比较时固定任务与起点，记录完成率、总 Token、费用、查询耗时和端到端耗时，再检查失败原因。



### 本节重点与验收

**重点掌握**：短期与长期按用途区分；保存标准；要求、事实、推断与证据；记忆生命周期；OKF 的组织作用；新会话读取；模型自动记忆的真实路径；项目隔离；长期知识与任务恢复边界。

**了解即可**：插件全部命令与图谱展示细节。



验收至少完成三步：

1. 真正写入一条带项目、来源与适用范围的持久记录。

2. 关闭会话，新会话实际读取记录并核对当前源码。

3. 制造一次项目变化，更新原记录，确认旧入口退出当前使用。

另外检查：推断没有变成验证事实，格式通过没有变成业务通过，跨项目记录没有混用。

# 4\.4 RAG：先找到证据，再检查回答

## 一、项目知识已经保存，为什么还要 RAG？

资料少，可以先读索引、再打开几个概念。资料积累到几百份文档、大量源码和多年故障记录以后，按文件名查找容易遗漏，全部发送又超预算。

用户问“增加退出登录，需要改哪些文件、怎样验收”，需要同时找到修改位置和验收要求。只检索到需求背景，模型仍缺少关键依据。

**RAG（Retrieval\-Augmented Generation）先从资料中检索相关证据，再把证据放进模型输入，让模型据此回答。**知识更新通过修改资料与索引完成，不要求改变模型权重。



整条链路分两个阶段：

|阶段|动作|结果|
|---|---|---|
|离线准备|解析 → 清洗 → 分块 → Embedding → 存储文本、向量与元数据|可检索的资料索引|
|在线回答|问题处理 → 检索 → 融合与筛选 → 重排或压缩 → 装配 → 生成 → 校验|带来源且能够核对的回答|

资料更新后，要同步对应分块和索引。找到话题相关的段落，也不等于找到了答案；模型拿到证据，也可能补出资料里没有的内容。

所以这一节主要检查数据准备、检索与证据使用，而不是一开始就换更贵的模型。



本节使用 LlamaIndex 组织文档、节点和检索，用 Milvus 实操向量存储，再加入 BM25、融合、查询处理和后处理。原稿 RAG 演示使用 MiniMax 与本地 BGE，不能把其他小节的 DeepSeek 配置写成本节已运行配置。

## 二、第一步：最小检索闭环，先留下每个环节的结果

先用两道题观察：

- 简单题：登录会话的有效期是多少分钟？

- 复杂题：退出登录需要改哪些文件，验收标准是什么？



运行入口：

```Bash
pip install -r rag44/requirements.txt
python scripts/step1_min_loop.py
```

`demo.py`，用 `VectorStoreIndex.from_documents()` 跑文档、Embedding 与流式回答。最小 Demo 用来理解链路，分步骤脚本用来观察质量与问题。



### 2\.1 Document 与 Node 分别是什么？

加载时，一份文档包装为 `Document`，正文之外保留路径、类型等元数据。

分块后，每个检索单位是 `Node`。后续返回节点与分数，程序才能追到具体文件和小节。

第一步读取 9 个对象：4 份文档、3 个源码文件、2 份历史记录，按标题等逻辑得到 30 个节点。

数量可以发现漏读，不能证明正文完整。还要抽查关键规则与需求。



### 2\.2 Markdown 按标题，再控制长小节

看下面两层分块器的职责：

```Python
parser = MarkdownNodeParser()
inner = SentenceSplitter(chunk_size=384, chunk_overlap=0)
```

第一层利用标题组织小节，第二层拆过长内容。384 是分块器的 Token 口径，不是 384 汉字，也不是整次模型请求大小。

第一步源码示例仍按整文件保留，没有证明采用 AST。AST 属于后面的数据准备实验。

**节点入库只说明它能被查询；只有最终进入本轮请求的内容，模型这次才看得到。**



### 2\.3 Embedding 配置要匹配，维度相同还不够

Embedding 把问题与文本转为向量，让“登出”和“退出登录”这类不同表达有机会匹配。

原稿最小闭环使用 MiniMax `embo-01`，记录维度为 1536。文档和查询分别走文本与查询入口，使用相互匹配的模型和处理方式。

同为 1536 维，不代表来自不同模型的向量能比较。模型变了，通常要重建文档向量，并确认集合维度与配置。

Milvus Lite 保存到本地数据库文件，集合为 `login_demo_chunks`，示例使用余弦度量。库配置的 `dim` 要与实际输出长度一致，重建前确认 `overwrite` 的影响。



### 2\.4 不看分数猜质量，直接看答案证据有没有出现

简单题 Top\-3 中，包含答案的“有效期长度”排第三。模型最后回答“30 分钟 \[3\]”，能够追到对应规则。

复杂题 Top\-3 却主要是需求标题、有效期长度和背景，没有修改清单。

|观察|判断|
|---|---|
|答案证据排第三但保留|仍可用于回答|
|分数很高，只有需求背景|仍然缺修改范围依据|
|几个分数接近|不能单独证明排序不稳定|
|分数超过固定阈值|不能当作事实可信度|

原稿 `score >= 0.30` 一条也没删掉。这个阈值在本次没有区分作用，阈值要靠标注问题集校准。



### 2\.5 装配编号与引用，先保证能够反查

每条证据给编号，附路径、标题和正文。模型回答中的 `[n]` 对应本轮第 n 条证据。

提示词要求依据材料回答、结论带引用、证据不足时明确说明。

但程序不能只靠提示词。原稿复杂题给出“登录页面、JavaScript 文件、路由文件”等建议，没有列出资料明确要求的修改文件，编号检查却通过，因为编号都在范围内。

**编号合法说明它指向一条存在的证据，不能说明证据支持结论。**

超预算时也不能直接截断整个拼接字符串，可能切掉规则条件和来源。优先保留完整证据单元或受控摘录，再检查总输入。



### 2\.6 一致性检查是本项目代码的能力，不是完整正确性保证

检查器通过正则提取路径、常量、数字与单位、命令和布尔值，再做字面核对。这是应用层实现的校验规则，不能因为使用 LlamaIndex，就认为框架自动完成了项目结论的全面验证。

“30 分钟”可以被提取并找到依据；笼统的“修改路由文件”可能没有被识别，自动检查就没覆盖它。

要区分：无引用、引用越界、无可核对实体、存在无依据实体、局部检查通过。

第一步暴露了三种独立问题：关键证据没召回，模型在不足材料上生成建议，检查器又没覆盖这些建议。必须分别改对应环节。



## 三、第二步：数据准备，避免答案在入库前丢失

运行入口：

```Bash
python scripts/step2_data_prep.py
```

先确认资料读到了、关键关系保留了、分块完整了，再调检索。没加载的文件或已被删掉的条件，不会靠调高 Top\-K 自动恢复。



### 3\.1 解析要保留关系，不只是提取字符

|格式|本节处理|核对重点|
|---|---|---|
|Markdown|标题、正文与 YAML 元数据|限定条件、小节和来源|
|Python|读取源码，后续比较 AST|函数结构、变量、行号|
|PDF|pypdf 逐页抽取文本|页码、表格对应、符号；扫描件另需 OCR|
|HTML|提取标题、段落与列表，标题转 Markdown|测试命令、代码块和限制是否漏掉|
|CSV|每行绑定列名和值，转为文本|服务、会话类型与时长是否对应|

例如“到期前 True、恰好到期 False、到期后 False”是一张有关系的表，不能解析成条件和结果各自堆在一段里。

原稿新增 PDF、HTML、CSV 后共 12 份资料。PDF 抽到文本、HTML 去掉标签、CSV 转成四条数据句，只能说明有输出，完整性仍需对照原件。

PDF 清洗若删除页码注释，要先将页码写入分块元数据，避免只能定位文件不能定位页面。

HTML 从 532 字符变为 272，不证明减少的全是无用内容。CSV 的“可续期是是”保留值但表达不自然，可以优化为键值形式。

正文写“服务是 login\_demo”，不等于节点已经具备可过滤的 `service` 元数据。



### 3\.2 清洗不能删掉决定含义的词

可以去掉多余空格、重复空行和格式噪声，不能删“不得”“仅限”“草稿”“旧版本”等词。

这些词决定规则对谁适用、是否批准、是否已实现。



资料类型与格式也要区分：`doc_type=doc` 和 `source=md` 可以同时出现在规则和历史记录里，不能据此认定两者都代表当前规范。

|内容性质|说明什么|不能替代什么|
|---|---|---|
|当前规则|应当怎样实现|当前代码事实|
|历史故障|过去发生什么|当前测试回执|
|需求草稿|希望做什么|已上线状态|
|测试回执|某次执行结果|所有版本的正确性|

原稿部分元数据还没有展示 `record_type` 和版本字段，应列为待完善，不能写成已实现。



### 3\.3 分块同时看完整性和粒度

固定长度、带重叠、按段落、按标题、按句子与 AST 等方案，要用同一批资料观察。完整性高，不等于单位合适；块少，也不一定效果好。

原稿中几个具体结果：

|方案观察|结果|怎样解释|
|---|---|---|
|长度切分，重叠 0 与 24|函数完整均为 6/10|本次增加重叠没有改善该指标|
|按标题方案|函数完整 10/10，最长节点 2460 字符|源码整文件保留，完整但可能太粗|
|AST，仅统计源码|3 文件、14 节点、10 函数完整，均长约 180 字符|更细且保留结构，不能与全语料节点总数直接比|
|标签称段落不超过 200|实际最长 383 字符|不是严格上限，要检查二次拆分|

AST 识别语法结构，不会自动恢复调用链。检索到函数以后，仍可能补读调用者、存储和配置。

建议按资料结构选初始方案：规范和需求优先标题，源码优先结构；然后用同一问题集验证召回，不能只用分块表宣布检索提高。



### 3\.4 Overlap 缓解边界断裂，也增加重复

原稿短窗口例子中，重叠 15 让“不要写成 `now <= expires_at`”完整进入一块，但块开头仍是半个符号，不代表语义完整。

另一份正文从 7 块增加到 10 块，说明重复与索引工作可能增加。脚本的“块数 × 窗口”不是实际存储量，更不是数据库大小，不能据此直接宣布存储增长比例。

调整顺序：定位被切断的关键条件 → 增加适量重叠或改变边界 → 检查完整性 → 统计实际重复、Embedding 用量与索引大小。

字符演示的参数不能直接套到 Token 分块。



### 3\.5 Chunk Metadata 决定过滤和追溯能力

规则节点示例含 `file_path`、`heading`、`header_path`、`service`、`topic`、`owner`、`updated` 与节点 ID；源码节点还能有 `kind` 和 `lines`。

路径与小节用于引用，行号用于回源，项目字段用于范围过滤，ID 用于关联和去重。维护人和更新时间不能单独证明内容正确。

一个节点带字段，不证明全部文档都覆盖；代码赋值节点，也不能讲成函数节点。源码变化后，位置要重新核对。

第二步验证了部分解析、结构和元数据过程，没有测召回率和答案质量，也没有展示本步骤的入库结果。进入下一步前，确认修改清单与验收要求完整存在于待索引节点。



## 四、第三步：检索，先把需要的证据找回来

运行入口：

```Bash
python scripts/step3_retrieval.py
python scripts/step3b_query_rewrite.py
```

本组比较固定使用 9 份 Markdown 与源码、30 个节点、8 道题。第二步新增格式和 AST 没有接入这组实验，不能把两个实验混成同一配置。



### 4\.1 先分清召回率、命中率与完全命中

工程师为每道题标出正确证据位置，代码称 `gold`。本节按路径和小节匹配，最终保留 Top\-3。

一道题有两处 gold，只找回一处：召回率 0\.5，命中为是，完全命中为否。

$Recall_q=\frac{\text{找回的 gold 数}}{\text{该题 gold 总数}}$



|指标|本节口径|
|---|---|
|召回率|先算每题找回比例，再对问题取平均|
|命中率|至少找到一处 gold 的题占比|
|完全命中|所有标注证据都找到的题数|

这些检查资料位置，没有直接检查答案。gold 也需要维护：其他原文同样支持结论时，标注可能不完整。



### 4\.2 更换 Embedding，要重建并固定其他条件

分块与问题不变，原稿比较 MiniMax、BGE 和维度处理配置。

|配置|召回率|命中率|完全命中|
|---|---|---|---|
|初始 MiniMax 向量|0\.312|0\.375|2/8|
|BM25|0\.625|0\.750|4/8|
|BGE 向量|0\.688|0\.750|5/8|

BGE 更适合本次问题集，后续采用它。256 维截断没有测出汇总下降，只说明这批题没显示差异，不证明其余维度没有价值。

原稿部分“建库秒”实际包含建库与八题检索评估，不能全部解释成建库速度。模型和向量配置变化，要重新生成文档向量，不能只改查询侧。



### 4\.3 向量存储：建库与打开已有库分开

|方案|定位|本节关注的边界|
|---|---|---|
|FAISS|向量搜索库|持久化、元数据和服务治理需要应用配套|
|Chroma|集成式向量存储|便于原型，选择时看数据与工程要求|
|Milvus|向量存储与检索系统|集合、向量与标量字段、索引和过滤|

本节实操 Milvus Lite，集合配置模型维度和距离度量。更大规模时索引避免每次全量比较，但具体索引和部署要按实际规模选择。

Lite 便于本地验证，Standalone 或集群用于相应服务化需要。原稿没有实测这些部署的吞吐，不能给出本节已证明的规模结论。

日常查询用 `load_index()` 打开已有库，不再提交节点。当前 `build_index(overwrite=False)` 仍会提交节点，新 ID 可能造成重复。

**不覆盖集合，不等于不重复入库。**要把稳定 ID、更新和删除策略明确写进工程。



### 4\.4 BM25：补精确词匹配，中文要有一致分词

向量适合跨措辞的语义匹配；常量、路径和正式术语可以让关键词检索直接定位。

BM25 综合词频、词的区分度和文档长度等因素评分。它是评分方法，不是一个完整存储系统。

本节用 `rank_bm25`，对节点与查询使用一致的 jieba 分词与归一化。中文没有空格，不能把整句直接当成一个词；代码符号也要核对分词后是否仍能匹配。

同样的“退出登录”问法可能适合向量，`SESSION_TTL_SECONDS` 则体现关键词价值。哪个更好仍要按问题集比较。



### 4\.5 Elasticsearch 是检索系统，与 BM25 不在同一层

Elasticsearch 承载倒排、全文评分、字段分析、过滤和聚合等工程能力。它可以承担关键词一路，也可根据版本与配置组织向量检索。

可以由 Milvus 与 Elasticsearch 分担两路，在应用融合；也可以评估一个支持混合能力的引擎。

课程没有部署 Elasticsearch，也没有调用 Milvus 内置全文检索。小型实验先在进程内跑 BM25，是否服务化看已有基础设施、数据量和运维成本。

不能把“用了 BM25”直接写成“已接入 Elasticsearch”。



### 4\.6 Hybrid Search：两路分数不能直接相加

余弦相似度与 BM25 的量纲和分布不同，直接相加会让结果受尺度支配。

RRF（Reciprocal Rank Fusion）按排名贡献融合：

$score(d)=\sum_r\frac{w_r}{k+rank_r(d)}$


同一节点按稳定 ID 汇总，每路权重决定贡献。`k=60` 是融合平滑参数，不是最终 Top\-K。



初始向量的混合结果：

|配置|召回率|命中率|完全命中|
|---|---|---|---|
|MiniMax \+ BM25，等权，候选 3|0\.375|0\.500|2/8|
|等权，候选 10|0\.500|0\.625|3/8|
|加权，候选 10|0\.562|0\.625|4/8|

融合还不如 BM25 单独，说明混合不保证提升。最终只留三条，某一路也可能把另一路的有效证据挤出去。



换 BGE 后：

|配置|召回率|命中率|完全命中|
|---|---|---|---|
|BGE \+ BM25，等权，候选 10|0\.750|0\.875|5/8|
|等权，候选 20|0\.750|0\.875|5/8|
|BGE 70% \+ BM25 30%，候选 20|0\.812|0\.875|6/8|

后续采用最后一组：每路取 20，再融合留 3。权重与候选数来自当前问题集，不能当通用配置。



### 4\.7 Metadata Filter：对象确定以后再过滤

问题明确属于 login\_demo，可以排除支付会话。原稿过滤返回五条，排除了原第四条支付内容，前三未变。

本次证明范围过滤生效，没有证明 Top\-3 召回提高。

比较登录与支付时，两边都要保留；只说“会话”且无项目上下文，就先确定对象。

本次过滤是独立演示，尚未接入混合。正式融合时两路使用相同范围与权限，否则 BM25 可能把已排除资料带回来。



### 4\.8 查询处理：原意不变，重新查库

漏证据不一定是算法问题，用户的“验证命令”与资料的“测试入口”也可能不匹配。

|方法|动作|必须检查|
|---|---|---|
|Query Rewrite|改成更适合检索的表达|对象、限制与不确定性保留|
|Query Decomposition|多个需求拆成子问题|原问题的对象和比较维度全部覆盖|
|多路改写|同一需求换多个表达|最终排名是否改善，增加多少开销|
|术语扩展|原问题后补项目词表|不改变需求，不重复添加|
|查询澄清|范围仍不明确时追问|先利用已有项目和符号信息判断|

针对 q4“退出登录改完，用哪条命令验证”的结果：

|处理|召回率|完全命中|观察|
|---|---|---|---|
|原问题加权混合|0\.812|6/8|q4 缺测试入口|
|单条重写，或原问题与重写融合|0\.812|6/8|表达变化，覆盖未提高|
|查询分解|0\.812|6/8|汇总未提高，示例还漏一项续期比较|
|多路改写，或加原问题|0\.750|5/8|覆盖下降|
|项目术语扩展|0\.938|7/8|q4 测试入口进入结果|

术语扩展将“命令”补为“测试入口、python \-m pytest”，将“登出”补为“退出登录、logout”。本次不需要模型生成查询。



第一名仍是验收标准，q4 却从没命中变成命中，说明有效证据进入了第二或第三位。检查全部返回结果，不只看第一名。

分解比较两种会话的时长与续期，要覆盖四个组合；原稿示例漏“支付会话能否续期”，需要检查再使用。

多路脚本标题写并行，代码实际循环执行，不能当作已实现并发。单条重写约增加 0\.8–1\.9 秒，也要纳入取舍。

“可能是缓存问题”不能改成“Redis 故障怎么修”，否则猜测变成确定前提。

澄清脚本只输出判断，没有接收用户补充再检索。符号在当前项目能唯一定位时，也不必机械追问。

**改写以后要重新执行检索。**只在旧候选上重排，找不回原来漏掉的资料。

本次术语表有效，仍需独立新问题验证，不能把当前调参题集作为泛化证明。



## 五、第四步：检索后处理，选好证据再检查回答

运行入口：

```Bash
python scripts/step4_postprocess.py
python scripts/step4b_rerank_limit.py
python scripts/step4c_cross_encoder.py
```

本组仍为 9 份资料、30 节点、8 题，BGE 与 BM25 加权融合。先保留 20 候选，再选 3 条给回答模型。

它没有接第三步的术语扩展，因此基线召回是 0\.812，不是 0\.938。



### 5\.1 Rerank 能改排序，不能补回候选之外的内容

q4 的测试入口在 20 条候选中排第 20，前三没有。

|情况|定位|下一步|
|---|---|---|
|候选中没有正确证据|召回遗漏|回到解析、分块、查询与检索|
|候选有，最终没有|排序或筛选问题|查重排输入与选择规则|
|最终选中，请求中没有|装配问题|查预算、截断与格式化|
|请求中有，回答用错|生成或证据理解问题|对照结论与引用|

“不在候选里”是重排做不到；“在候选里但没选中”是本次没排好。排第 20 不代表重排无法访问。



### 5\.2 LLM 重排：看它收到什么，不只看排序结果

提示词要求模型按“能直接回答问题”排序，只返回候选编号 JSON，不生成答案。

程序解析编号、过滤越界、补齐遗漏，最后取三条。原稿存在几个具体边界：

- 重复编号没有去重，可能让同一节点占多个位置。

- JSON 解析失败恢复原顺序，但这段兜底没有覆盖模型请求异常。

- 每段只提供正文前 220 字符，答案相关句子可能没有被送进去。

所以正确来源在候选里，也不代表重排模型看到了完整证据。要保存重排实际输入。

本次 q4 选择了验收标准、关键用例和忘记命令的 FAQ，没有选中 gold 指定的测试入口。它找到相关资料，仍未完成该证据目标。



### 5\.3 Cross Encoder：把问题与候选成对打分

与预先分别生成向量不同，Cross Encoder 同时输入问题和候选正文，给出相关性分数，再排序。

原稿调用重点是问题与候选文本两个输入：

```Python
from fastembed.rerank.cross_encoder import TextCrossEncoder

ce = TextCrossEncoder("BAAI/bge-reranker-base")
scores = list(ce.rerank(question, [h.node.text for h in hits]))
```

按分数选前三。这个分数不是答案正确概率。

本次找齐的标注证据更多，但 q4 仍把“关键用例”放前面，没有命中“测试入口”。文件相关，不等于需要的小节被选中。

|方法|原稿重排计时|比较限制|
|---|---|---|
|LLM 重排|合计约 31\.0 秒，约 3\.9 秒/题|每段前 220 字符|
|Cross Encoder|合计 137\.10 秒，约 17\.14 秒/题|调用传入候选正文，模型加载 2\.1 秒另计|

本地模型本次更慢，具体原因要检查硬件、推理和候选长度。两种输入范围也不完全相同，不是纯粹相同输入下的模型能力对照。



### 5\.4 上下文压缩：少给内容，也可能删掉证据

当前压缩让模型逐段摘出相关句子，要求逐字、不补充，并保留标题与代码符号。

程序丢弃“无相关内容”和少于八字符的输出，其他摘录保留元数据。

这两个规则还要验证：短常量也可能是有效答案；要求逐字，不表示实际没有改写。

q6 从 3,022 字符压到两段、136 字符，但无依据实体从 1 增加到 2。只能确认变短，不能宣布更可靠。需要查看原文、摘录和最终回答，才能定位错误发生在哪一步。

压缩尤其不能删掉否定、范围、版本和条件。删掉“旧版本”，会把历史缺陷变成当前事实。

存在冲突先核对版本和适用范围，无法判断就保留冲突。原稿没有自动解决全部冲突。



### 5\.5 后处理要同时看质量与开销

主脚本比较：A 直接取三条；B 重排后取三条；C 复用同一重排结果再压缩。

原稿几个结果：

|观察项|结果|能支持什么|
|---|---|---|
|答案检查|三组都 8/8|通过当前必备与禁用关键词检查|
|无依据实体数|A 4、B 1、C 3|重排减少这类问题，压缩后部分增加|
|最终回答输入|7,721 → 5,926 Token|压缩后最终输入约少 23%|
|计入的生成与后处理时间|62\.0 → 93\.5 秒|当前实现增加等待|

这里的 8/8 没检查完整回答：q3 只要求一个修改文件，q7 未完整检查续期比较。

表中也没有包含重排和压缩全部 Token，不能说总费用节约 23%；时间不包括完整建库、检索和校验。

是否开启一个环节，必须看完整口径。不能因最终输入变短就默认启用压缩，也不能因多一层模型就认定效果提升。



### 5\.6 Citation 至少分三层检查

|层次|检查什么|未覆盖什么|
|---|---|---|
|编号合法|存在、范围正确、能反查本轮证据|证据是否支持结论|
|实体核对|路径、常量、数字、命令等有字面依据|否定、条件和完整语义|
|结论支持与完整性|每条关键结论有依据，用户要求已覆盖|仍受标注和核对方法限制|

“可以修改测试”和“不能修改测试”出现相同词，字面检查不能判断方向。

证据写 30 分钟，答案写 1,800 秒，字面未匹配不一定错误。需要区分：

1. 原文事实：30 分钟。

2. 可靠推导：30 × 60 = 1,800 秒。

3. 项目判断：当前某个常量为 1,800，需要源码证据。

单位换算成立，不代表当前代码配置也成立。

“无可核对实体”不是通过；“未发现无依据实体”也不是答案全面正确。

如果使用压缩，还要核对摘录与原始节点。只检查答案与摘录，可能放过压缩时生成的错误。



### 5\.7 校验失败以后怎么办？要定义发布行为

本节检查器由项目代码实现，可以继续增加结论级检查、覆盖率要求和失败处理。原稿当前只是打印检查结果，没有自动修正，也没有发布门禁。

接产品时可以定义：证据不足就拒答或标缺口；引用越界就修复引用后重检；重要结论不受支持就不发布确定答案，必要时补检索或转人工。

这些是需要补充的工程规则，不能写成原稿已经执行的能力。

流式输出还要考虑时机：如果边生成边展示，校验结束前用户已经看到内容。可先生成检查后发布，也可展示待校验状态并更新最终结果。

**事后发现错误，不等于已阻止错误展示。**



## 六、第五步：固定问题集，按相同口径比较

运行入口：

```Bash
python scripts/step5_evaluate.py
```

四组仍使用相同 9 份资料、30 个节点和 8 道题，分块与最终回答提示词保持一致。

|组别|比较位置|

|V0|初始 MiniMax 向量方案|

这里比较整套配置，不能把多处同时变化归因给单一算法。单项实验则尽量一次只改一个变量。



### 6\.1 总览先看三条变化

V0 → V1 的标注证据覆盖提高，答案关键词检查从 4/8 变成 8/8；V1 → V2 加重排，召回下降；V2 → V3 仍为 8/8，部分引用检查改善，但全链费用未统计完整。

**组件增加不是提升证据，固定条件下的比较结果才是。**



### 6\.2 q2：命中、召回与答案检查可以不一致

q2 问到期瞬间是否有效，gold 包含当前规则“到期边界”和历史记录“结论”。

V1 找一处，召回 0\.5；回答关键词检查通过；引用状态是无可核对实体。

因此，V1 总命中率 1\.0、平均召回 0\.938 可以同时成立：每题至少找到一处，不代表每题全部找齐。

V0 的 q2 为“0\.0 / 答案通过 / 引用通过”。可能有其他有效证据，也可能补出了结论，仅凭这格不能认定一定正确或一定错误，要回看上下文和答案。



### 6\.3 q4：重排后没有保住指定测试入口

|配置|q4 召回|答案关键词检查|引用检查|
|---|---|---|---|
|V0|0\.0|未通过|通过|
|V1|1\.0|通过|通过|
|V2|0\.0|通过|通过|
|V3|0\.0|通过|通过|

V2、V3 写出了必备命令，却没有 gold 指定的小节。要确认其他节点是否支持这条命令。

若支持，完善可接受证据标注；若不支持，关键词通过不能替代依据。还要查候选、重排实际输入和最终装配，不只看结果猜原因。



### 6\.4 q6：找到来源，也可能用错或核对不到

V1、V2、V3 都命中 `SESSION_TTL_SECONDS` 的标注来源，也出现“1800”等必备内容，但判为存在无依据实体。

要打开回答、抽取实体和证据，确认是换算表达、引用范围、资料不足还是模型补充。原稿没给具体实体，不能替它编一个原因。



### 6\.5 汇总数字按检查器口径解释

|观察|原稿记录|注意事项|
|---|---|---|
|答案检查|V0 4/8；V1–V3 8/8|关键词验收，不是全面正确率|
|引用检查|V1 6/8；V2 5/8；V3 6/8|无可核对实体也不计通过|
|含无依据实体回答|V2 2/8|这是回答数占比，不是实体数或全部幻觉率|
|平均召回|V1 0\.938；V2 0\.812|逐题变化造成，不能只看一个平均数|

V1 → V2 中，q4 从 1 降 0，q2 从 0\.5 升 1，q7 从 1 降 0\.5；后两项抵消，整体主要损失 q4 的指定证据。

失败归因代码先看是否任意 gold 进入结果，再看关键词检查。没有 gold，即使关键词通过也标检索失败；有 gold 且答案检查失败才标生成失败。

“生成失败为空”只说明这套规则未检出，不能推导“检索到了就一定答对”。



### 6\.6 Token、费用与计时必须对齐

V3 比 V2 最终输入少 2,308 Token，约 27%。这是回答输入节省，不是总费用节省，因为没有计入完整后处理用量。

V2 与 V3 都约 8\.3 秒/题，计时范围却不同：

- V2：检索、融合、重排和最终回答。

- V3：复用 V2 已选结果，只计压缩、装配和最终回答。

不能说加压缩没有增加端到端等待，也不能直接相加，两边都包含最终回答，会重复计算。

公平比较从接收问题开始，各方案独立计时，分别记录检索、融合、重排、压缩、生成、校验和发布。

建库也单独统计：原稿 V0 6\.0 秒，BGE 索引 2\.8 秒，不含此前读取、分块和 BM25 初始化。MiniMax 14 次、38 文本、9\.1 秒跨建库与查询，不能全算成每题在线开销。

本地模型没有远程 API 费，也有计算资源成本。usage 缺失填 0 是原脚本待修正项，正式报告记录未知。



### 6\.7 本次结果支持什么选择？

V1 在这八题上证据覆盖最好、答案检查全部通过、记录的在线时间较短，可先作为候选默认方案。

V2 没提高答案验收，部分指标下降；V3 缩短输入并改善一项引用结果，但完整成本和延迟尚不够比较。

下一步用新问题验证 V1，补齐完整答案要求、无答案题和候选到请求的记录。

八题都有答案，不能直接推断系统会拒答。新增无答案题时，单独检查是否正确说明资料不足，也要调整空 gold 的召回统计，不能沿旧分母机械平均。



## 七、出问题时，先找到第一个丢失证据的环节

|检查顺序|核对对象|失败时改哪里|
|---|---|---|
|1|原文是否有答案，状态是否适用|补可靠来源或说明缺口|
|2|解析与分块是否保留关键条件|加载、清洗、分块和元数据|
|3|候选中是否有答案证据|查询、模型、分词、过滤与召回|
|4|最终节点和请求是否保留|重排、压缩、预算与装配|
|5|回答结论是否受引用支持|提示词、生成与结论核对|
|6|检查结果是否如实表达覆盖|标注、检查器与发布规则|

一次只修一个具体问题，再用原失败题复测，并用新题检查。不要同时换模型、分块、提示词后，只凭最终结果宣布某个方法有效。



### 本节重点与验收

**重点掌握**：离线与在线链路；Document 与 Node；多格式解析；清洗和分块；Overlap 与元数据；Embedding 一致性；向量存储；BM25、Elasticsearch、RRF；范围过滤；查询处理；LLM 与 Cross Encoder 重排；证据压缩；引用与一致性检查；评估口径；无答案题与失败归因。

**了解即可**：所有向量数据库的部署参数、重排模型结构和 BM25 的完整数学推导。



验收至少证明：

1. 正确规则、修改位置与验收要求真实存在于节点中。

2. 同一问题能查看向量、关键词、融合候选与最终请求。

3. 正确证据不在候选时，系统能定位为召回问题。

4. 来源编号有效，关键结论仍逐条核对内容支持。

5. 重排、压缩没有被单凭“更复杂”“更短”认定有效。

6. 比较记录包含完整调用成本和相同范围的延迟。

7. 无答案题能够说明资料不足，未知 usage 不填零。

# 4\.5 LLM Wiki：把整理结果变成可维护的知识资产

## 一、RAG 已经能查资料，为什么还要 Wiki？

新人问登录模块，往往需要同时读规则、源码和测试指南，再整理出：有效期多少，到期怎样判断，实现在哪里，怎样验证。

如果每次问都重新建立这些关系，重复工作就会增加。

**LLM Wiki 让模型根据原始资料生成、组织和维护知识页，把可复用的总结、关联和分析保存下来，并随着来源变化更新。**



但保存后的页面会被重复使用，错误、过期和受限内容也可能重复传播。

知识资产治理因此要回答：结论有没有依据，来源变化能不能同步，冲突有没有隐藏，谁可以生成、发布和阅读。



### 1\.1 LLM Wiki 是工作模式，不是装上就自动成立的系统

传统 Wiki 由人整理和维护，LLM Wiki 将部分阅读、提取、补链接与更新工作交给 Agent。

维护方式变化，版本、审核、来源与权限要求仍然要由工程师规定。还需要用户指令或调度触发，不能因为目录叫 Wiki 就认为它会自动保持最新。

例如 PRD 提出退出登录，当前 `logout()` 却仍抛 `NotImplementedError`。页面必须分开写需求目标和源码状态，不能把“希望实现”变成“已经上线”。



### 1\.2 Wiki、RAG、Memory 各管什么？

|能力|本案例中的用途|
|---|---|
|工作记忆与 Checkpoint|接着完成当前退出登录任务|
|长期记忆|召回过去定位的模块和核验经验|
|Wiki|阅读整理后的规则、实现和验证关系|
|RAG|为当前问题寻找相关原文或知识页|

测试入口可以同时出现在记忆与 Wiki，区别是组织、维护和使用方式。

**Wiki 维护知识，RAG 为本次问题找到知识。**可以先检索 Wiki，再沿引用核对原文。



## 二、最小结构：依据、草稿、发布内容和维护记录分开

|位置|用途|修改规则|
|---|---|---|
|`raw/`|原始资料版本快照|不由模型改写，新来源新增快照|
|`staging/`|尚未通过发布检查的草稿|可修改，不能默认作为现行依据|
|`wiki/`|检查后发布的知识页|按发布规则更新|
|`schema.md`|来源、版本、冲突和权限规则|由工程师明确规范|
|`manifests/`|来源清单、哈希与页面依赖|与页面版本同步|
|`logs/`|生成、校验、发布和失败记录|保留实际操作事实|
|`reports/`|影响分析、巡检与验收|写清证据和未验证项|

用 `corpus.zip` 做实验输入，先检查压缩包路径，拒绝绝对或越界路径，再原样导入 `raw/v1/`，保留相对目录。

已有实验目录先检查，不能直接覆盖。

来源清单登记 source ID、相对路径、实际 SHA\-256、资料类型和原文提供的日期状态。原文没写的信息记未知，不能把本次导入版本当资料业务版本。

先准备规则、来源和空索引，不等于已经生成或发布知识页。



## 三、知识页至少回答三个问题

**适用于哪里，结论是什么，依据在哪里。**

页头管理身份、版本、状态和来源；正文组织规则、实现与核对入口。

|记录|作用|
|---|---|
|`page_id`、项目与页面版本|稳定定位同一页及其修订|
|草稿、发布或待复核状态|决定是否可当当前依据|
|来源 ID、版本、实际哈希|核对生成依据|
|权限策略引用|关联宿主访问规则，不能代替鉴权|
|关键结论与具体引用|逐句核对内容支持|
|待核对事项|保留缺资料、实现差异和冲突|

登录会话页可以包括：30 分钟、到期无效、请求触发续期、时间判断位置、令牌生命周期入口、测试入口，以及本次测试回执是否存在。

这是目标结构，实际值必须来自对应来源。

正文引用了 `app/auth.py`，页头和依赖清单也要登记它，不能只登记部分来源。

没有本次执行回执，就写“资料未提供本次测试结果”。测试指南说明怎么验收，历史记录说明过去通过，都不能替代当前测试。



## 四、生成与发布分开，由程序控制提交

### 4\.1 先固定合法输入，再生成草稿

宿主确定项目与执行身份，检查来源读取权限，固定来源版本和哈希。

模型输出三类内容：正文、结论到证据映射、待核对事项。



生成四页：

|草稿|整理内容|
|---|---|
|`technical/login-session.md`|登录规则、实现、续期和测试入口|
|`technical/token-lifecycle.md`|签发、签名校验、检查、续期、清理和退出|
|`comparisons/session-types.md`|登录、支付、匿名浏览、记住我令牌的区别|
|`project/logout-plan.md`|退出需求、当前实现、验收与未决问题|

生成时重点核对：时间判断与令牌管理分工；PRD 草稿和 `logout()` 未实现状态；测试指南不等于已通过；环境变量声明是否真的进入有效期调用链；历史缺陷不等于当前实现。

`config.py` 声明或读取配置，不能直接证明配置生效，要沿实际调用关系核对。

草稿使用标准 Markdown 相对链接，按未来发布目录计算；另外生成依赖清单，记录来源 ID、哈希、位置、知识页依赖和结论映射。

这一阶段不改 raw、不发布、不运行业务测试。



### 4\.2 程序查结构，内容核对查含义

|检查层|核对内容|
|---|---|
|结构|来源存在、实际哈希、页面 ID、路径边界、引用位置、发布后链接|
|内容|引用支持结论，否定与条件完整，需求与执行分开，配置与生效分开|
|发布策略|哪些可自动发布，哪些需负责人确认，可见范围是什么|

检查失败，保留草稿和原因。可以按原文修正草稿，不能改原文迎合结论。

流程示意中，`validator.check` 和发布策略通过以后，才进入 `commit_if_current`。这是职责示意，不是随文件创建就拥有的完整生产程序。



### 4\.3 提交前为什么还要再次检查？

生成期间可能发生三种变化：原文更新、身份撤权、别人修改同一页。

草稿仍写“退出未实现”，开发者却已经提交实现，就不能继续按旧源码发布。

提交前再次核对来源哈希、权限和页面基线。变化时停止覆盖，重新读取并核对。

页面正文、依赖清单和导航索引要协同生效；日志记录实际发布结果。工程里需要保证这几个更新一致，不能把本地复制文件说成已经实现事务或原子发布。

**模型整理内容，程序管理草稿、有效条件与发布。**



## 五、来源追踪：整页参考资料不够，关键结论要具体对应

“读过哪些文档”与“这句话由哪一段支持”不同。

30 分钟引用有效期长度，到期无效引用到期边界，实现位置引用函数，测试入口引用测试指南。

作者、机构和时间存在就登记，不存在记未知，不能编造权威身份。



### 5\.1 派生页也要追到原文

会话对比页根据登录页生成，仍需追到登录与支付各自原始规则和版本。

可以沿“对比页 → 知识页 → 原文”，重要结论也可直接引用原文。程序保存直接和间接依赖，来源变化时才能找齐受影响页。



### 5\.2 问答归档不把模型输出自动变成事实

新人问答有复用价值，可以归档，但先核对来源、范围和重复。

原稿归档页是 `wiki/queries/login-onboarding.md`，回答时先读 schema、来源和索引，再读相关页，涉及代码回看源码，不只引用 AI 总结。

已有同类页优先更新；没有证据的猜测列待研究。归档后同步依赖、索引和日志，并抽查关键结论到原文的链路。



## 六、来源更新：沿依赖传递，不能全局替换数字

实验中批准登录有效期从 30 分钟改成 60 分钟，生效条件从本次激活开始；附件原规则仍为 30 分钟。

这个实验不代表公司真实审批，也不代表业务源码已修改。



### 6\.1 新快照先登记，再找直接和间接影响

保留 `raw/v1/`，新增 `raw/v2/docs/session-rules.md`，记录实际哈希、替代关系和激活时间。

沿依赖找登录页、令牌页、会话对比页和归档问答。先标待复核，输出 `update-impact.md`，再重读与更新。

未同步期间，当前规则查询可以回到新原文，并说明 Wiki 待更新，不能继续无提示使用旧页。



### 6\.2 按结论含义改，区分规则与实现

|信息|更新后表达|
|---|---|
|当前已批准教学规则|登录 60 分钟，请求触发续期|
|到期边界|仍为恰好到期无效|
|原始源码|若仍为 1,800 秒，就说明实现还是 30 分钟|
|FAQ、表格等未改原文|说明尚未同步，不擅自改来源|
|支付与其他会话|原规则保持各自范围|
|历史记录|保留当时 30 分钟|
|退出登录状态|不因时长规则变化而变成已实现|

不能全局替换 30 或 1800。必须能分别回答当前批准规则、当前源码行为与 v1 历史规则。



### 6\.3 页面更新后，索引和缓存也要同步

页面保留稳定身份，内容用版本区分。来源更新沿页面、分块、检索索引、摘要和缓存传播。

同步失败要标状态，并回退当前原文。没接向量索引或缓存，就标未接入，不能声称已同步。

旧来源与页面历史保留供历史查询。版本、生效时间、导入时间分别记录，Git 提交时间不能自动替代业务生效时间。



## 七、重复、过期和冲突不是一个动作

|类型|处理方式|
|---|---|
|重复|同项目、版本和范围核对后合并，保留各来源与背景|
|过期|退出默认当前查询，保留历史用途与适用时间|
|冲突|比较范围、状态、权威与生效期，无法解释时留双方依据并确认|

30 分钟源码、60 分钟规则和未批准的 90 分钟建议，不是三个同地位的规则投票。

90 是讨论建议；60 是当前实验规则；30 是尚未同步的实现或历史状态。

两份同范围、同生效期间的已批准规则真正矛盾，才需要负责人确认。新导入不一定新内容，多篇转述也可能来自同一个错误来源。

巡检检查重复页、旧规则、冲突、孤立页、坏链接和依赖遗漏。报告先列页面、问题、证据、影响与建议，不直接删除或合并。

“本次未发现问题”不等于永久正确。



## 八、权限贯穿读取、生成、发布和使用

维护 Agent 同时读公开说明与内部安全设计，生成的综合页不能因为经过总结就公开。

|环节|谁检查什么|
|---|---|
|来源读取|宿主按执行身份检查正文、附件、图片、标题与元数据|
|生成|只给模型已授权来源，保留派生依赖|
|发布|可信程序决定可见范围和发布权限|
|页面使用|检索、文件读取、导航、导出和缓存执行相同限制|
|来源撤权|沿依赖调整页面权限，使索引、摘要、缓存及相关长期记忆失效|

最小整页方案是：读者满足所有来源的访问条件，才可读该页。公开介绍单独用公开来源生成，受限内容对外使用按规定脱敏与审批。

`access_policy` 字段和提示词不是鉴权。模型不能自行把页面改为公开。

搜索有权限检查，直接 `read_file` 没有，也会形成绕过。因此要从多个入口验证同一限制。

原稿权限实验先确认已有机制：有可执行身份控制，就分别用授权与未授权身份测试；没有就如实标未实现，列接入点和用例，不能伪造拒绝日志或假装切换身份。



## 九、质量验收：检查四个维度，再比较收益

|维度|验收动作|
|---|---|
|完整性|登录时长、边界、续期、实现、退出状态、测试入口有依据；缺项明确|
|可信度|抽查至少六条关键结论，核对原文支持，分开事实、推导、建议和执行|
|时效性|分别问当前规则、当前源码、旧规则，检查版本与状态不混用|
|可检索性|用会话过期、登录状态老是掉、退出后令牌还能用等问法实际定位|

只有索引导航就记录导航结果，不虚报召回率。将 Wiki 接入 RAG 后，重新维护证据标注，不能沿用已变化的旧节点 ID。

程序检查来源、链接、版本、依赖和权限；模型辅助检查语义冲突与条件遗漏。缺资料先补可靠来源，没有就保留缺口。

比较“直接检索原文”和“先查 Wiki、必要时回原文”，固定同一问题集，统计回答质量、来源支持、维护费用与端到端耗时。

未实际比较，就不能说 Wiki 一定更准或更便宜。页面正确，回答仍可能误读，回答侧检查继续保留。



### 本节实验的操作顺序

|步骤|交付物|检查结果|
|---|---|---|
|导入与规则|raw/v1、schema、来源清单、空索引和日志|真实资料与哈希，不生成业务结论|
|生成四页|staging 草稿与 dependencies|来源完整，缺口与差异保留|
|校验发布|prepublish 报告、wiki 页面、索引与日志|分别记录已发布和仍草稿|
|新人问答归档|login\-onboarding 与来源依赖|结论能追到原文|
|60 分钟更新|raw/v2、影响报告、页面版本|新规则与旧源码分开|
|90 分钟建议巡检|lint 报告|未批准建议不覆盖现行规则|
|权限检查|access\-review|已实现与未实现清楚区分|
|最终验收|acceptance|每项为通过、未通过或未验证，并附证据|

这些是练习流程和目标产物，不是本笔记已经执行的实验结果。



### 本节重点与验收

**重点掌握**：Wiki 的工作模式；与 RAG 和 Memory 的关系；来源快照、草稿与发布分离；结论到证据映射；依赖更新；提交前复核；重复、过期和冲突；派生权限；四维质量验收。

**了解即可**：示例每个目录的具体命名和发布器的内部实现。



验收至少证明：

1. 原文没被模型修改，未核对内容仍为草稿。

2. 关键结论能定位到原文版本和位置。

3. 60 分钟规则、30 分钟源码和 90 分钟建议不会混成一个当前事实。

4. 来源变化能找到直接和间接依赖，更新失败有明确状态。

5. 有权限机制就测试真实拒绝，没有就标未实现。

6. 当前测试结果缺失时，不写“测试已经通过”。

# 4\.6 项目四：给 Codebase Agent 装上记忆和检索



## 一、项目目标：信息能力要回到同一个 Agent

前面几节分别解决输入、任务记录、长期知识、检索和知识维护。项目四把其中长期记忆与 RAG 接回 project3/v2。

**长期记忆帮助复用之前核对过的项目知识；RAG 帮助从资料库查当前任务需要的业务规则。**两者为动作提供依据，真正读取、修改和测试仍走既有 Loop、Runtime 与 Sandbox。

不能再写一条绕过治理的执行路径，也不能把检索答案直接当成代码已修改的结果。



最后收敛到五件事：

|目标|要证明什么|
|---|---|
|找得到|新会话能取得相关记忆，RAG 能找到回答证据|
|装得下|新增内容仍通过本轮输入预算|
|记得准|要求、事实、推断、来源和版本不混用|
|恢复得了|当前任务进度能恢复，旧证据经现场核对后使用|
|解释得清|回答和操作能追到记忆、资料、源码与执行记录|

这一节的直接接入对象是长期记忆与 RAG；前面 4\.1、4\.2 的装配和任务记录规则作为共同验收条件。不能因为新增了两个工具，就宣布六节全部能力已经生产化。



## 二、接长期记忆：模块、工具、加载和测试一起补

### 2\.1 六处修改分别负责什么

|接入位置|动作|结果|
|---|---|---|
|`config/platform.yaml`|增加记忆开关与配置|平台能够明确启用或关闭|
|`src/memory.ts`|实现 list、search、read、remember、digest、validate|文件组织、读写与校验能力|
|`src/tools/memory.ts`|暴露 recall 与 remember 工具|模型通过受控能力申请读写|
|`renderSystemPrompt`|运行前读取配置的长期记忆摘要|本次运行得到相关知识入口|
|`config/prompts.yaml`|在 `codebase.agent` 中补使用规则|模型知道先召回、核对、再应用|
|`tests/unit/kg_memory.test.ts`|增加持久化、索引、召回与边界测试|接入能够用反例检查|

启动摘要与按需读取配合使用：摘要帮助发现相关知识，具体结论还要读全文和当前源码。

记忆内容是项目材料。即使模板把材料追加到系统提示词，也要明确其中引用文本的性质，不能让外部记忆里的指令覆盖可信规则。



### 2\.2 两件工具继续走 Tool Runtime

|工具|风险|作用|
|---|---|---|
|`memory_recall`|read|按 query 或 ID 找回记忆|
|`memory_remember`|write|写入合法 OKF 概念并同步维护记录|

与十件仓库工具一样，它们注册进 `ToolRegistry`，经过白名单、RBAC、参数契约和 `ToolRuntime`，留下审计。

记忆写入不是修改业务源码，但仍然是持久副作用。原稿操作中需要审批，批准只针对对应写入。



### 2\.3 先写入，再用新进程召回

下面保留原稿的 CLI 操作方式，把破损的换行整理为一个 JSON 参数。内容是教学概念，不表示本笔记执行过该命令：

```Bash
node --import tsx src/cli.ts invoke memory_remember '{"id":"concepts/login-flow","type":"Code Concept","title":"登录调用链","description":"登录入口与服务层调用关系","tags":["auth"],"body":"# 调用链\n路由→Service→仓储。使用前核对当前源码。"}'
```

从实际回执取审批 ID，写入变量后批准与执行：

```Bash
APPROVAL_ID='替换为本次回执中的审批ID'
node --import tsx src/cli.ts approvals decide "$APPROVAL_ID" --decision approve --actor trainer-1 --roles maintainer
node --import tsx src/cli.ts approvals execute "$APPROVAL_ID"
```

角色与执行身份采用本地示例配置，批准后仍要看写入回执。

然后在新进程中读取：

```Bash
node --import tsx src/cli.ts invoke memory_recall '{"query":"登录"}'
npm test
```

需要核对的结果是：概念文件真实落盘、索引和日志同步、新进程取得同一记录。CLI 召回证明跨进程读取；业务新会话是否自动加载，还要检查实际模型请求。



### 2\.4 单元测试至少覆盖什么

1. remember 写入合法 OKF，文件内容与请求相符。

2. `index.md` 与 `log.md` 同步。

3. recall 按 query 和 ID 能找回。

4. `..` 路径穿越在写入前被拒绝。

5. 新进程或新会话能读到持久记录。

还要结合第三章验收：拒绝或未批准不写入；错参数不执行 handler；写结果保留调用关联；记忆开关关闭时行为符合配置。

这些是验收要求，实际是否通过以测试报告为准。



## 三、RAG 后端先独立跑，再接成只读工具

### 3\.1 为什么先保留独立查询入口？

RAG 查询要先确认索引、答案和引用都正确，再接 Agent。这样失败时能分清是后端检索问题，还是工具适配与结果回写问题。

后端职责：

|文件|职责|
|---|---|
|`ingest.py`|资料入库，建立向量与 BM25 索引并写 storage|
|`query.py`|查询模式、Top\-K、生成开关与 JSON 输出|
|`rag/hybrid.py`|jieba 分词、BM25、向量与 RRF|
|`rag/local_embed.py`|BGE 中文本地向量，示例为 512 维|
|`rag/answer.py`|编号证据装配与回答提示词|
|`rag/llm.py`|原稿使用的 MiniMax chat 适配|

这里使用 `BAAI/bge-small-zh-v1.5` 与对应维度，不把第一步 MiniMax 的 1536 维配置沿用过来。



### 3\.2 入库与查询分开执行

```Bash
python ingest.py --overwrite
python query.py -q "会话的有效期是多少分钟？" --json --top-k 3
python query.py -q "登录会话有效期" --json --mode bm25 --top-k 2 --no-llm
```

首次或资料更新后入库。查询使用已有存储，避免每次提问重复向量化整套资料。

`--json` 提供机器可读答案与来源；`--no-llm` 只观察检索结果和引用，不把它说成已经由回答模型综合生成结论。

`--overwrite` 用于明确重建的实验，执行前确认目标，不能把它当所有日常查询的前置动作。



### 3\.3 把查询封装为 `rag_query`

|契约|原稿要求|
|---|---|
|风险|`risk=read`，不修改知识库和工作区|
|权限|`rag:read`|
|角色|reviewer、developer、maintainer|
|审批|本例只读查询无需人工确认|
|执行路径|Registry → 白名单与 RBAC → Runtime → 后端 → 结果回写与审计|
|输出|回答 \+ 带编号的来源追溯|

只读不等于任何人都可以读。范围和权限依然检查，后端结果也继续受输出预算与审计规则控制。

原稿接入规格来自 `RAG提示词.md`，其中 `formatRag` 把 JSON 排成模型可读文本：回答在前，引用逐条编号。

**答案里的 ****`[n]`**** 必须与来源追溯一一对应。**格式化不能重新编号后忘记同步答案，也不能丢掉路径和小节。

若检索文本进入模型，要保留材料边界，不能把文档中的指令当宿主授权。



## 四、用真实业务 Run 验证接入

先在 RAG 目录入库，再回 Agent 工程运行真实模型路径。目录切换按实际项目位置进行。

```Bash
python ingest.py --overwrite
```

回到 `project3/v2` 后：

```Bash
node --import tsx src/cli.ts agent "登录会话有效期是多少？给我带出处的答复" --no-route --decider real
```

从实际回执取 Trace ID，再查看记录：

```Bash
TRACE_ID='替换为本次运行的TraceID'
node --import tsx src/cli.ts trace "$TRACE_ID"
npm test
```

这里要看模型是否实际调用 `rag_query`，不是只看最终回答有没有“30 分钟”。`--decider real` 表示让真实模型决策，但仍要靠 Trace 证明本次走了查询工具。

如果本次没有调用，先检查工具快照、使用指引、启动注入和实际请求，不伪造工具记录。

完整链路应能追到：用户问题 → 模型调用 → Runtime 校验与授权 → RAG 后端结果 → 编号格式化 → 下一轮输入 → 最终回答。



## 五、记忆、资料与源码冲突时，先说清各自证明什么

例子：RAG 规则写 30 分钟，源码实际计算为 20 分钟。

不要让模型直接选择看起来更权威的一份，更不能靠更新文档掩盖代码问题。

|来源|证明的对象|
|---|---|
|已批准项目规则|应当实现的业务要求|
|当前源码和配置调用链|当前实现的行为|
|当前测试回执|本次测试范围内的运行结果|
|历史记忆|过去核对的事实或经验|

先指出差异，再读取当前规则状态、代码和相关测试，判断是记忆过期、资料滞后，还是实现不符合规则。

原稿“以代码为准并更新记忆”，适用于核对当前实现事实；不能理解为源码可以自行改写已批准业务要求。4\.5 的 60 分钟规则与 30 分钟源码，也需要同时保留。

**源码说明现状，规则说明目标，测试验证指定版本的实际行为。**

修复代码仍需要用户目标、当前证据、授权和修改后测试，RAG 答案不能替代这些条件。



## 六、项目验收：五个目标分别拿什么证据？

|目标|验收动作|通过依据|
|---|---|---|
|找得到|新会话召回；真实 Run 查询规则|读取或工具调用记录，相关来源进入请求|
|装得下|使用长记忆和长检索结果|总请求受控，关键证据保留，必须项超限停止|
|记得准|混入推断、旧入口和另一项目记录|性质与范围明确，不直接当当前事实|
|恢复得了|修改后未测试时暂停再恢复|找回状态，核对现场，继续当前版本验证|
|解释得清|抽查答案与源码判断|引用编号、原文位置、版本和 Trace 对应|

再主动制造几类反例：

1. 未批准写记忆：没有概念文件写入。

2. 路径穿越：Runtime 或记忆模块拒绝，目标外文件不变。

3. 新会话：不继承旧聊天，仍能实际取得持久记录。

4. 资料更新：旧规则不继续作为默认当前答案。

5. 资料与源码冲突：回答保留差异，不假装已经一致。

6. 引用编号错位：格式或检查失败，不宣布可追溯性通过。

7. RAG 或记忆失败：结构化错误进入下一轮，不伪装成空结果成功。



### 工程师负责什么，AI Coding 可以承担什么？

|工作|AI 可以辅助|工程师必须核对的证据|

|信息结构与模块边界|编写模块和接口|数据样例与真实链路|

# 复习题答案

1. **问：Prompt 与 Context Engineering 分别管理什么？**
答：Prompt 规定模型要做什么、遵守什么规则。Context Engineering 管理每轮实际发送的规则、材料、历史、任务状态和工具定义。例如，“不得修改测试”属于指令，而当前源码和失败断言属于判断所需的材料。

2. **问：为什么只保留最近 N 条消息可能丢掉最重要的限制？**
答：重要限制可能出现在最早的用户要求中，后续消息没有重复它。只按时间裁剪，可能留下最新日志，却删掉“不得修改现有测试”。因此，关键约束要单独保留，再按相关性和有效性选择其他历史。

3. **问：输入预算为什么要扣掉输出预留和安全余量？**
答：模型读完输入，还需要空间生成回答或工具调用参数，因此必须预留输出容量。安全余量用于覆盖本地估算与服务端实际计数的误差。否则，输入看似放得下，实际调用仍可能超限或无法完成输出。

4. **问：工具定义是否计入输入？为什么不能只算正文长度？**
答：工具名称、描述和参数 Schema 都会占用输入 Token。系统规则、历史消息和消息格式也有开销。因此，预算检查要覆盖完整请求，不能只统计用户问题和资料正文。

5. **问：必须项压缩后仍超限，程序应该怎样处理？**
答：停止发送，缩小源码或证据的读取范围，或者把任务拆成多步。调整后重新检查完整请求的预算。不能静默删除关键约束和失败证据，再让模型在信息不足时继续判断。

6. **问：工具日志压缩与任务历史压缩为什么采用不同方法？**
答：工具日志通常有明确字段，适合由程序提取执行状态、失败断言、版本和原文位置。任务历史包含目标、尝试、决策和进度，适合整理成交接摘要。模型生成的摘要可能遗漏信息，因此关键约束和执行状态仍要与原始记录核对。

7. **问：怎样证明当前测试结果对应当前代码？**
答：测试时记录被测代码的版本或内容哈希，并关联执行编号、测试命令和日志。使用结果前，核对当前代码是否仍与被测内容一致。代码变化后必须重新测试，旧通过记录不能证明新版本正确。

8. **问：Context Debug Report 能证明什么，不能证明什么？**
答：它能记录本轮发送了哪些材料、怎样压缩，以及为什么保留或排除。结合实际请求，可以检查关键约束和当前证据有没有进入模型输入。它不能证明模型内部怎样理解，也不能单独证明最终答案正确。

9. **问：KV Cache 与响应缓存复用了什么？**
答：KV Cache 复用模型已经完成的部分注意力计算，减少重复计算。响应缓存复用此前生成的回答，命中后可以不再调用模型。两者都不能保证内容仍然适用，规则、代码或权限变化时仍要更新。

10. **问：为什么一次压缩输入减少 59%，不代表整次任务更省钱？**
答：59% 描述的是某次请求输入的减少，不包含生成摘要的额外消耗。整个任务还可能产生检索、核对、重试和后续模型调用。是否省钱，要比较完成同一任务时的全部调用费用。

11. **问：工作记忆与聊天历史、Agent State、Checkpoint 怎样协作？**
答：聊天历史保留交互过程，工作记忆把其中的目标、约束、执行事实和未完成事项整理成当前记录。Agent State 承载运行状态，也可以直接包含工作记忆。Checkpoint 保存恢复所需状态，恢复时再核对文件和执行现场，决定从哪一步继续。

12. **问：工具正常返回，为什么业务验证仍可能失败？**
答：正常返回只说明工具执行完成并取得了结果，不说明结果符合业务要求。例如测试工具返回“预期 False，实际 True”，工具链路正常，但被测功能仍然错误。因此，要分别记录工具执行状态和业务验证结果。

13. **问：长期记忆为什么不等于模型参数更新或向量数据库？**
答：长期记忆通常保存在模型外部，使用时读取相关记录并加入输入，没有修改模型参数。向量数据库只是可选的存储与检索组件，也可以使用文件或普通数据库组织记忆。记忆是否可靠，还取决于保存标准、来源、适用范围以及更新和删除规则。

14. **问：一条信息写入前，怎样判断后续价值、来源和失效条件？**
答：先说明以后哪类任务会用到它，避免保存没有复用价值的临时过程。再核对它来自用户要求、实际执行还是模型推断，并保存对应依据。最后明确什么变化会让它失效，例如文件迁移、代码更新或项目规则调整。

15. **问：OKF 格式通过为什么不能证明项目事实正确？**
答：格式检查验证文件结构、必填字段等组织要求，不验证业务结论是否成立。一份格式正确的文件，也可能保存错误路径或过期测试结果。事实正确性还要通过读取来源、核对当前代码和实际执行确认。

16. **问：pi 的“自动记忆”具体由哪些动作组成？**
答：插件先向模型提供记忆目录和使用指引，模型根据任务决定是否搜索、读取或写入。需要保存时先查重，再调用记忆写入工具；需要使用时检索候选并读取相关内容。实际成功与否要看工具回执，“自动”不意味着每句话都会无条件保存。

17. **问：关闭旧会话以后，怎样证明知识确实从外部记录读入？**
答：启动不继承旧聊天的新会话，查看它读取索引和知识文件的工具记录或加载记录。再核对读取内容是否进入本轮模型请求。只看到回答出现熟悉的文件名，不足以证明外部记忆被使用。

18. **问：资料解析怎样保留表格条件与结果的对应关系？**
答：按行保留记录，并让每个值带上列名，例如“情况：恰好到期；期望：False”。分块时尽量让同一行的条件和结果保持在一起，同时保存表格来源和位置。不能把条件与结果分别堆成两段，否则模型可能对应错误。

19. **问：AST 分块为什么不能代替调用链分析？**
答：AST 分块识别函数、类和赋值等语法结构，帮助保留完整代码单元。它不会自动说明业务请求经过哪些模块，也不能完整确定运行时的调用关系。理解实际行为仍要追踪入口、调用方、配置和数据流。

20. **问：换 Embedding 后，为什么不能只改查询侧？**
答：文档向量与查询向量必须来自匹配的模型和处理方式。只改查询侧，两边可能处于不同向量空间，即使维度相同也不能可靠比较。因此，更换模型时要重新生成对应文档向量，并核对索引配置。

21. **问：BM25、Elasticsearch 与向量库分别处于什么层次？**
答：BM25 是关键词相关性评分方法。Elasticsearch 是承载全文检索、过滤和聚合等能力的系统，可以使用 BM25 评分。向量库主要负责向量存储和相似度检索，可以与关键词检索配合形成混合方案。

22. **问：RRF 的融合参数与最终 Top\-K 有什么区别？**
答：RRF 的融合参数控制排名贡献怎样衰减，权重控制不同检索路的贡献。最终 Top\-K 决定融合后保留多少条结果。比如融合参数 `k=60` 不表示返回 60 条，最终仍然可以只保留三条。

23. **问：对象没明确与用词不匹配，分别应该怎样处理？**
答：对象不明确时，先结合项目上下文确定范围，仍无法判断再向用户澄清。对象明确但用词不同，可以补充项目术语或改写查询，再重新检索。例如“会话多久过期”可能需要确认服务，“验证命令”则可以扩展为“测试入口”。

24. **问：正确证据没有进入候选，为什么重排补不回来？**
答：重排只能对已经收到的候选重新评分和排序，不能选择输入中不存在的证据。正确证据缺失时，要回到查询、过滤或召回环节重新查找。只有证据已进入候选却排名靠后，才适合尝试重排。

25. **问：引用编号合法、实体有依据与结论受支持分别检查什么？**
答：编号合法检查引用是否对应本轮存在的证据。实体有依据检查路径、数字、命令等是否能在证据中找到。结论受支持检查证据是否真正证明整句话，包括否定、条件、版本和适用范围。

26. **问：30 分钟换算成 1,800 秒，为什么不能直接证明当前代码常量？**
答：换算只能证明两个时长数值等价，不能证明源码采用了这个值。当前常量可能不同，也可能被配置覆盖或没有参与实际计算。因此，要读取常量定义和相关调用关系，才能说明当前实现。

27. **问：无答案题为什么要单独设计验收与统计？**
答：无答案题检查系统能否识别证据不足并说明缺口，而不是生成猜测。没有正确证据时，普通召回率不适合直接沿用原来的计算方式。应单独统计正确拒答、错误作答等结果，并明确判断标准。

28. **问：需求草稿、历史修复和当前源码状态怎样在 Wiki 分开？**
答：分别标明内容性质、适用版本、状态和来源。需求草稿写期望行为，历史修复写过去发生的结果，当前源码状态写实际读取到的实现。不能因为需求提出了退出登录，就写成当前功能已经上线。

29. **问：原文变化以后，为什么还要更新派生页、索引与缓存？**
答：这些位置可能仍然保存旧结论，后续任务会继续读到过期内容。要沿来源依赖找到直接和间接受影响的页面，再同步分块、索引、摘要和缓存。同步未完成时应标明待更新，必要时回到当前原文回答。

30. **问：受限来源经过总结，为什么不能自动扩大阅读范围？**
答：总结仍可能包含受限事实，改变表达方式不会消除信息限制。派生页面的可见范围要由可信程序根据来源权限确定。需要公开时，应按规定使用公开来源，或完成脱敏和审批。

31. **问：60 分钟规则、30 分钟实现和 90 分钟建议应该怎样表达？**
答：当前已批准规则要求 60 分钟，当前源码仍实现 30 分钟，说明实现尚未同步。90 分钟属于未批准建议，不能覆盖现行规则。回答时分别标明规则、实现和建议的来源与状态，不把三者混成一个当前事实。

32. **问：****`memory_remember`**** 与 ****`rag_query`**** 为什么都必须经过 Runtime？**
答：写记忆需要检查参数、路径、权限和审批，读资料也需要检查访问范围。统一经过 Runtime，才能执行治理、回写结构化结果并留下审计。否则，记忆或检索适配层就可能成为绕过既有边界的新入口。

33. **问：怎样沿 Trace 找到记忆或 RAG 接入中的第一个断点？**
答：按工具可见性、模型调用、校验授权、后端执行、结果回写、实际请求和最终回答依次核对。找到第一个缺失、错误或不一致的位置，例如后端有结果，但下一轮请求没有证据。修复对应模块后，用原失败任务复测，确认整条链路恢复。
