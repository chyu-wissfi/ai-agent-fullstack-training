Context Engineering——模型答错之前，先查它实际看到了什么

本课定位：Week04 第一课。第三章让 Agent「能持续推进任务直到完成或停止」；但能继续执行，不代表每一步判断正确。本课回答第四章的核心问题的第一半：怎样让模型每一轮拿到足够、适用、可核对的信息——装配、优先级、预算、压缩、污染防护与调试报告。后五课（工作记忆、长期记忆、RAG、Wiki、项目四）都建立在这条输入链上。

第一部分：精讲（先读，测验在后）

0. 开篇：三个事故与第四章地图

笔记开篇（行 15）给了三个事故现场，全部发生在「Agent 能继续执行」之后：

  1. Agent 明明运行了失败测试，下一轮却说「测试已经通过」——旧证据或摘要失真。
  2. 用户最早要求「不得修改现有测试」，十几轮以后这条限制不见了——装配裁剪丢约束。
  3. 几天后重新打开项目，Agent 又要从头搜索会话模块和测试命令——知识没有跨会话保存。

这些问题不一定要靠换模型解决。先检查六件事：模型这一轮实际看到了什么？输入里的测试结果测的是哪一版代码？工具执行了任务记录有没有更新？新任务能不能读到上次留下的知识？关键规则有没有被检索到？原文变化后知识页、索引和缓存有没有一起更新？——正好对应本章六节：

为什么「能执行」之后还要专章讲信息？ 因为 Loop 只保证「继续调用模型」，不能把遗漏的业务规则自动补回来（笔记行 162）。模型会写比较运算符，不代表它知道这个项目恰好到期时算不算有效。替代方案是「换更强模型 / 更长窗口」，代价是成本与延迟上升，且容量解决不了适用性——旧版通过记录、已废弃规则照样干扰判断。当前约束下选「管理输入」：让每一轮的判断材料足够、适用、可核对，这是比换模型更便宜也更可验收的路径。

1. Prompt 与 Context：一次请求到底由什么组成

Prompt 主要规定怎样做，Context Engineering 管理这一轮实际给模型什么（笔记行 156）。「到期立即失效，不修改现有测试」是指令；但模型要判断错误在哪里，还需要当前源码、失败断言、任务进度和可用工具。一次模型请求至少包含六个对象：

上下文窗口解决容量，不能保证判断正确（笔记 4.1 二）。即使没有超限，大量支付文档、旧版测试通过记录和已废弃规则也会干扰登录到期判断。所以判断错误时先分流，而不是先换模型：

现象优先检查
请求超出窗口输入预算、工具定义、输出预留和计数方法
当前失败没进入请求材料选择与装配
旧版通过记录被使用证据版本与失效规则
输入充满无关文档相关性与优先级
有当前证据仍答错原始请求、响应与生成行为
为什么长窗口不能代替信息筛选？ 窗口是容量约束，判断需要的是适用性约束——两者正交。把全部材料塞进去，除了可能超窗、挤占输出空间，还会让过期与无关内容参与判断（污染，第 6 节）。反过来，盲目删减也可能删掉必要的调用方或类型定义。取舍点：目标是「在预算内保留足够支持当前判断的信息」，不是「越多越好」也不是「越少越省」。这一分流表与 0008 的门禁漏斗同构：先定位问题属于哪一层，再修那一层。

2. Packing：装配不是拼接，是安排材料去向

装配围绕下一步决策，确定直接提供、外部保存和按需读取的内容（笔记行 226）。登录边界排查阶段的安排：

去向内容原因
本轮直接提供到期立即失效、不得修改现有测试决定正确行为与修改边界
本轮直接提供当前比较条件、失败输入、预期和实际结果决定本次错误怎样复现和修复
外部保存完整测试日志保留核对依据，避免每轮复制全部内容
请求中提供引用完整日志路径与执行编号缺细节时能够补读
暂缓读取无关模块与早期探索全文当前动作不依赖它们
为什么「外部保存 + 引用」而不是「全文进请求」或「直接丢掉」？ 全文进请求：每轮复制几千行日志，预算被吃掉且失败断言可能被启动信息淹没；直接丢掉：缺细节时无法核对，压缩就成了不可逆的信息销毁。取舍后的第三条路：完整记录持久化，请求里只放断言、版本和真实路径，模型缺细节时提出 read_file，真实读取仍由 Loop 和 Runtime 完成（权限边界不变）。这与 0016 审计「存截断 + 全量哈希」是同一个取舍：请求里放判断所需的摘要，核对依据留在可反查的外部记录里。

3. Prioritization：先判断有效，再分配空间

只保留最近 N 条历史有两个明显问题（笔记行 266）：最早的「不得修改测试」可能被删；刚出现的一句旧版「测试通过」也可能挤掉当前失败证据。所以选择材料先问三件事（图 3）：现在是否仍然有效 → 是否与当前步骤相关 → 缺少它会不会选错动作或判断错进度。优先级随任务阶段变化：排查阶段规则、当前源码和失败证据优先；补丁完成后当前 Diff、修改结果和新测试状态优先。

分配空间的顺序由 allocation_order 决定（4-1-4-Prioritization.py）：必须项优先，随后按优先级数值，同级保持原顺序。它只回答「先给谁空间」，没有完成预算检查，也没有授权任何工具。两个边界必须分清：

  • 必须保留的是必要信息，不一定是原文全文——失败断言和准确引用可以替代几千行日志。
  • 空间分配顺序不是历史消息发送顺序——工具调用仍在结果之前，调用与结果保持配对（第 6 节的协议检查）。

约束还可以保留理由：「继续使用现有 session 中间件，因为所有客户端共用它」比只有一个禁止句更容易让模型理解影响范围。但记住分工：上下文帮助模型选择方案，执行权限仍由 Runtime 强制检查（笔记行 312）——写进请求的约束只是「让模型知道」，不是「强制执行」。

为什么必须项优先，而不是按时间或按优先级数值一刀切？ 按时间裁剪（最近 N 条）会把最早的用户限制裁掉——限制通常只说一次，后续消息不会重复它；按数值一刀切则可能让高分的旧证据挤掉当前失败。必须项优先的代价是低优先级材料可能本轮缺席，收益是「缺了就会判错」的信息永不缺席。这与 0008 门禁「拒绝压过放行」同构：关键不变量不参与排序竞争。另注意 must ≠ 全文：必须项也可以给压缩版，只要断言、版本与引用还在。

4. Budget：先留输出，再算完整输入

输入预算公式（笔记行 320）：

B_input = W_context − R_output − M_safety

同时还要满足模型和 Provider 各自的输入、输出限制。输出预留不能被输入借走：模型读完输入还要生成回答或工具参数，输入占满窗口，后续动作可能无法正常产生。安全余量覆盖计数误差，但不能代替校准——发送前用估算检查，发送后用服务端 usage 核对，多次运行后再调整计数方式与余量。

关键内容放不下时的处理顺序（笔记行 366–374）：① 规则与工具说明重复就精简，只提供本轮需要的工具并保持执行快照一致；② 必要代码或证据太长就缩小读取范围或拆成多步；③ 必须项仍放不下就拒绝发送，不能静默删掉关键限制继续调用；④ 切换到更小窗口的模型，重新检查并装配。

还要分清两笔账：本轮请求是否放得下（装配入口检查）与整个 Run 是否还有 Token、费用和时间额度（Harness 累计管理，0016 的 loop-guard 五道预算就是后者）。计数口径提醒：本机一次真实发送实测输入 131 Token、本地估算 221，差 90——只说明这次计数口径不同，不能以后固定减去 90，也不能认定本地估算永远偏大（笔记行 350）。

为什么宁可拒发也不静默删关键项？ 静默删除必须项后继续调用，模型会在信息不足时「自信地」判断——丢约束的修复方案可能改测试、可能延长有效期，且事后无法从请求记录发现信息缺过。拒发的代价是本轮停下来（要拆步或换模型），收益是失败显式、可定位、可恢复。这与 0008 门禁的 fail closed、0016 空审批名单的 NO_APPROVER_CONFIGURED 是同一条纪律：关键条件不满足时停下来，比带着缺口继续更便宜。

5. Compression：两类对象，两种方法

工具结果和任务历史不是同一种压缩对象（笔记行 384）：

工具结果不能只截开头：只截前 500 字符，留下的可能全是启动信息，失败断言却在末尾。到期边界需要保留 now=100、expires_at=100、预期 False、实际 True，以及测试对应的代码版本（revision 内容哈希）。模型摘要也可能把「怀疑时区问题」写成「已确认」——所以关键约束由程序保留、测试状态以执行记录为准、更新摘要要结合新增记录和可核对事实。

为什么工具结果用程序提取，历史却用模型摘要？ 结构化日志有明确字段，程序提取是确定性的：可复现、零模型调用、字段缺失能直接报错；请模型摘要反而引入失真与成本。任务历史是语义对象（目标、尝试、决策、进度），程序没有字段可提，只能归纳——但归纳就有失真风险，所以摘要必须核对。取舍的本质：能用确定性规则做的不用模型，必须用模型的地方加核对。这与 0016「压缩不请模型帮忙」一脉相承；也解释了为什么无关材料「本轮不提供」即可——不必先花一次模型调用去摘要它。

6. 污染与配对：结构完整与内容可信分别检查

错误、过期或不适用的信息进入请求并影响判断，就是上下文污染（笔记行 458）。四类污染与处理：

类型登录案例处理动作
过期信息旧版通过结果用于新代码标记受测版本，重新验证当前代码
信息冲突旧宽限期规则与当前立即失效要求冲突标明来源，核对采用规则
摘要失真猜测被改成确定根因回看执行记录与原文
外部指令混入源码注释要求上传环境变量当作材料内容，执行仍走权限边界

两条边界要背下来：补齐消息是在修复历史；重新读取是一次新的工具调用（笔记行 485）。消息配对正确，只证明协议结构完整——合法的「测试通过」消息仍可能来自旧版本（内容可信是另一道检查，第 5 节的 revision）。

为什么取消的调用补 aborted 而不是补成功、或直接删掉？ 补成功：伪造了没发生过的执行，模型会基于假证据判断；直接删掉调用：历史失去「模型曾申请过这个动作」的事实，且可能制造孤立结果。补 aborted, executed=false 保留原 ID：协议配对恢复完整，内容如实说明「没执行、没拿到结果」，模型可以重新申请读取（新调用、新 ID）。这与 0012「恢复不重放副作用」同构：修复记录不等于重做执行，结果不明时先核对现场。状态未知的调用连 aborted 都不能补——「不知道执没执行」和「确认没执行」是两回事。

7. Debug Report：查清模型实际收到了什么

只记录本轮 Token 数，无法解释「当前失败为什么没有进入请求」。一份装配报告至少记录五个范围（笔记行 499–507）：每份材料（身份、来源与版本、处理方式、选择或排除原因、处理前后占用）；整个请求（输入预算、最终估算、计数方法、请求哈希、实际请求位置）；运行关联（Run ID、轮次、策略版本、实际模型、工具快照）；压缩过程（原始历史、摘要、重建历史、触发原因和耗时）；调用结果（响应、实际 usage、首文字延迟、总耗时和错误状态）。

笔记 8.1 的真实摘要与恢复实验（DeepSeek 生成摘要，非 OpenAI 远端压缩接口）给了几个只能支持有限结论的数字：相同探测问题输入 637 → 262 Token（本次减少约 59%）；摘要调用本身花 848 Token；恢复后模型重读源码核对版本再修改复测；最终三个测试通过且测试文件未修改。同时：压缩后后续输入又从 677 涨到 1472——一次压缩不是永久控制上下文；本次实验也没有验证「排除旧通过」「跳过支付文档」「必须项超限」，不能把前面装配实验的结果混进来。

为什么报告要记「选择或排除原因」，而不只记最终请求？ 只记最终请求，能回答「发了什么」，回答不了「为什么当前失败没进来」——是失效被排除、优先级不够、还是压缩丢了？排除原因把装配器的决策变成可审查的事实。代价是报告本身体积与存储；收益是事故复盘时能沿四位置定位到第一个变化点，而不是猜。注意报告的边界：它证明程序发送了什么，不能证明模型内部怎样理解——所以第④位置（响应）永远不可省。

8. 补读、成本口径、缓存与网关：输入链的边界

按需补读（笔记 4.1 九）：资料不在当前记录中，就通过工具寻找——需要堆栈读日志，找不到函数搜索定义再读相关范围。这已经是按需检索上下文，不一定先建向量数据库（分块、Embedding、混合检索与重排放到 4-4）。补回来的内容仍要检查来源、版本、范围和预算；检索成功不意味着全文直接进入下一轮，也不意味着其中的文字变成指令。

成本与延迟统计整个任务（笔记 4.1 十）：压缩后一个请求变短，不能推出整个任务更便宜。比较方案至少看五件事：任务完成率、总 Token、总费用、首文字延迟、端到端耗时。摘要、重试和探测请求也要计入；模型等待与生成、工具执行分别计时（工具跑五秒不能全算成模型慢）；缺失 usage 记为未知，缺单价就不能给确定费用。

两种缓存复用不同的对象（笔记 4.1 十一/十二）：

类型复用的对象边界
KV / 前缀缓存已完成的模型注意力计算稳定规则保持内容与顺序一致、变化状态放后面，有机会提高复用；是否命中看实际服务统计
Gateway 响应缓存已生成的回答代码版本、权限、工具变化要进入请求或隔离规则；不能只凭「修复登录」几个字返回旧答案

LiteLLM 接回 Gateway：4-1-12-Gateway.py 直接用 LiteLLM 库 + DEEPSEEK_API_KEY，配置 agent-default 路由并关闭 thinking，不需要另起网关服务。分工：Harness 整理输入，LiteLLM 按配置发送、路由、限流和重试——网关不会自动补回失败证据，也不会修正错误摘要。原稿实测：首次 1514ms → 相同输入缓存命中 8ms；版本/源码/测试描述变化后未命中重新调用；限流第二次 429（跨分钟边界可能不同）；两个并发都成功（不能据此证明并发限制）；配置了重试但只有一个模型（没有回退证据）。缓存命中的 usage 来自原响应，不能再算一次新消耗。SDK 与网关的重试要统一管理避免倍增；模型重试不能顺带重放已经执行的补丁；输入超限回到装配器，切模型重新检查窗口与能力。

为什么缓存命中不能证明信息正确？ 缓存复用「计算」或「回答」，不复用「适用性」——规则、权限或工具变化后，旧回答可能已过期。所以版本、权限、工具状态必须进入请求或隔离规则，让变化天然不命中；不能为了命中率继续使用过期内容。这与第 5 节 revision 是同一条纪律：复用必须绑定版本，否则省下的钱会以错误判断的形式还回来。另注意原稿自己记录的两个问题：价格配置缺失显示零不代表免费；acompletion 未 await 的警告要修复——报告生成了不等于代码完全正确。

9. 面试视角：两分钟主链 + 追问链

如果面试官问「你们的 Agent 怎么管理上下文」，按这条链讲：

  1. 边界：Prompt 规定怎样做，Context Engineering 管理本轮实际给模型什么——指令、材料、历史、任务状态、工具快照都计入输入。
  2. 装配：围绕下一步决策安排三种去向（直接提供 / 外存+引用 / 暂缓）；先问有效性、相关性、必要性，必须项优先；分配顺序不是发送顺序，工具调用与结果保持配对。
  3. 预算：B = W − R − M，输出预留不可借；估算发送前检查、usage 发送后核对；必须项压缩后仍超限就拒绝发送，不静默删关键限制。
  4. 压缩：结构化结果程序提取（revision 哈希绑定版本、至少一条失败证据、字段缺失报错），长历史模型摘要加核对；压缩本身计入成本，一次压缩不是永久控制。
  5. 核对：配对检查保证协议结构完整，revision 与失效规则保证内容适用；判断错了沿四位置（原始历史→摘要→实际请求→响应）找第一个变化点。
  6. 边界：缓存复用计算或回答，不证明适用；网关管路由限流重试，不补证据；本轮预算与整次 Run 预算两笔账分开。

常见追问与回答方向：

  • 「窗口 128k 了为什么还要压缩？」→ 容量≠适用；无关与过期材料干扰判断；成本延迟随输入增长；压缩还要保留核对依据。
  • 「怎么保证压缩不丢关键约束？」→ 必须项程序保留不参与竞争；字段缺失报错；至少一条失败证据；必须项超限拒发；摘要与原始记录核对。
  • 「模型说测试通过了，你信吗？」→ 先查消息对应哪个 revision，再核对当前代码哈希；旧通过不能证明新版本（与 0014 完成契约同构）。
  • 「一次压缩省 59%，任务就省钱了吗？」→ 不能；摘要调用 848 Token 另计，后续输入还会累积；整次任务看五件事口径。
  • 「KV cache 和响应缓存什么区别？」→ 前者复用已完成的注意力计算，后者复用已生成的回答；两者都要让版本/权限/工具变化进入请求或隔离规则。

工作对应点：你在 OpenViking 做 VikingDB 与 local 后端的检索质量对比——本课的「固定口径五件事」「原稿数字只是那次运行的证据」「未知 usage 不填零」正是 benchmark 报告的口径纪律；4-4 的 V0–V3 评估会把这条纪律展开成完整方法。

实验 ④：配对——self-test 五项 + 四发探针

    预期（本机实测）：发送前拦截 MISSING_TOOL_RESULT、取消补齐 aborted（executed=false）、孤立结果移除、幂等修复、未知状态停止——五项离线验收通过。
  • 四发探针（脚本名带横杠不能直接 import，用 importlib 加载；在 4-1 目录执行）：
    ./.venv/bin/python - <<'EOF'
import importlib.util
spec = importlib.util.spec_from_file_location("chk", "4-1-7-check.py")
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
probes = [
  ("孤立结果", [{"role":"user","content":"hi"},
               {"role":"tool","tool_call_id":"call_1","content":"test passed"}]),
  ("批次未齐", [{"role":"assistant","tool_calls":[{"id":"a"},{"id":"b"}]},
               {"role":"tool","tool_call_id":"a","content":"ok"},
               {"role":"user","content":"继续"}]),
  ("重复ID",   [{"role":"assistant","tool_calls":[{"id":"a"},{"id":"a"}]}]),
]
for name, msgs in probes:
    try: m.check(msgs)
    except ValueError as e: print(name, "→", e)
try: m.normalize([{"role":"assistant","tool_calls":[{"id":"x"}]}], set())
except ValueError as e: print("未知状态 →", e)
EOF
    先写预期：四发各报什么？「批次未齐」和「缺失结果」的区别在哪？
    预期（本机实测）：ORPHAN_TOOL_RESULT: call_1 / INCOMPLETE_TOOL_BATCH: ['b'] / INVALID_TOOL_CALL_ID: a / 调用尚未结束或状态未知，不能补结果：x。区别：批次未齐是过程中被后续交互打断；缺失结果是序列结束时仍有 pending。

实验 ⑤：主动改造 A——把边界修对，看证据怎样跟着版本走

  • 把 4-1-6 的故意错误改对，重跑，再恢复：
    sed -i '' 's/return now <= expires_at/return now < expires_at/' 4-1-6-Compression.py
./.venv/bin/python 4-1-6-Compression.py
git checkout -- 4-1-6-Compression.py   # 恢复课程原样（故意保留的边界错误）
    先写预期：status 变成什么？revision 会变吗？为什么 revision 必须变？
    预期（本机实测）：status=passed、failure_count=0、failures 为空；revision 哈希变了（它是脚本内容哈希）。这就是「证据绑定版本」的现场：改代码前那次 failed 记录是真实历史，但不能证明新代码仍失败；改代码后的 passed 也不能反过来证明旧代码正确。恢复后 git diff -- 4-1-6-Compression.py 应为空。

实验 ⑥：主动改造 B——让失效证据「复活」，看污染怎样进入请求

  • 不改原文件，用 heredoc 把旧测试的 valid 改成 True 重跑装配（在 4-1 目录执行）：
    ./.venv/bin/python - <<'EOF'
import importlib.util, tempfile
from pathlib import Path
spec = importlib.util.spec_from_file_location("budget", "4-1-5-Budget.py")
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
from tokenizers import Tokenizer
tok = Tokenizer.from_file("tokenizer.json")
count = lambda r: len(tok.encode(m.dump(r), add_special_tokens=False).ids)
with tempfile.TemporaryDirectory() as d:
    failure = "test_at_expiry：now=100，expires_at=100；预期 False，实际 True。"
    log = "启动信息和依赖检查通过\n" * 2000 + failure
    p = Path(d) / "session_tests.log"; p.write_text(log)
    blocks = [
        m.Block("业务规则和限制", "到期立即失效；不得修改现有测试。", 100, True),
        m.Block("当前源码", "return now <= expires_at", 90, True),
        m.Block("当前失败", log, 100, True, compact=failure + f"\n完整日志：{p}"),
        m.Block("当前状态", "失败已复现，补丁未应用。", 80),
        m.Block("支付文档", "无关支付模块说明\n" * 1000, 10),
        m.Block("旧测试", "旧版本全部通过。", 95, valid=True),  # 改造点
    ]
    req = m.pack(blocks, m.Budget(), count)
    print("旧测试进入请求:", "旧版本全部通过" in m.dump(req), "估算:", count(req))
EOF
    先写预期：「旧版本全部通过」会进入请求吗？预算检查拦得住它吗？
    预期（本机实测）：进入请求，估算约 222→236（临时日志路径长度不同会有 ±2 浮动）。它短、优先级 95、预算放得下——预算检查拦不住污染，有效性检查才能。这就是 valid=False 那道排除的 why：失效证据不是「占地方」，是「会误导」。模型可能据此认为「测试已经通过」——开篇事故一的现场复现。
