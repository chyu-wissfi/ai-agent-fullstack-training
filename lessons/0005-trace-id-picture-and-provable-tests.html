第一部分：trace_id 的画面

1. 先把场景立起来：一次报障

周五 16:32，业务方报障：「客服 Agent 的退款任务跑了 40 秒，最后失败了，用户还在页面上等」。你面对的是三个服务（API 入口、Agent Harness、LLM Gateway），每秒几千行日志，分部署在多台机器上。翻日志是不可能的。

你手里只有一样东西：前端在发请求时，把响应头里的 trace_id 记了下来，值是 tr_9f2c41。你 grep 它：

$ grep tr_9f2c41 logs/*     ← 你手里唯一的钥匙
16:32:01 api       tr_9f2c41                     请求进入，解析用户消息「查订单并退款」
16:32:01 harness   tr_9f2c41  run_a1             启动任务：查询订单状态
16:32:01 harness   tr_9f2c41  run_a1 step_01     模型规划：需调用订单查询工具
16:32:01 gateway   tr_9f2c41  run_a1 step_01 call_c1   路由到 provider-a，请求发出
16:32:03 gateway   tr_9f2c41  run_a1 step_01 call_c1   429 限流，退避 2s 后重试（attempts=2）
16:32:08 gateway   tr_9f2c41  run_a1 step_01 call_c1   成功，TTFT 487ms
16:32:09 harness   tr_9f2c41  run_a1 step_01 tool_t1  订单查询返回：ORD-8817 已发货
16:32:10 harness   tr_9f2c41  run_a1 step_02     模型总结，run_a1 完成（2 calls / 1 tool）
16:32:11 harness   tr_9f2c41  run_b2             启动任务：提交退款
   …（run_b2 的 step_01 至 step_04 正常）…
16:32:39 gateway   tr_9f2c41  run_b2 step_05 call_c9   5xx，重试耗尽，Run 预算 deadline 到期
16:32:40 harness   tr_9f2c41  run_b2             失败：BUDGET_EXCEEDED（40s / 9 calls / 3 retries）

这就是「整条追踪链」的画面：这次用户请求从进入系统到最终失败，跨了三个服务、两个任务、五个步骤、九次模型调用。trace_id 是把这一切缝成一条故事线的那根线。没有它，16:32:01 的请求和 16:32:40 的失败，在你眼里毫无关系；有了它，一次 grep 就是完整的因果链。

顺着这条线你还能回答业务方的问题「40 秒花在哪了」：call_c1 被限流退避吃掉 6 秒、run_b2 里的三次重试（attempts 字段）和最终 5xx 各占多少，一数便知--这是「延迟不能只记一个数字」能落地的前提。

2. 每行日志的四级家谱

笔记 13.3 的原图，配上每级「回答的问题」--ID 体系存在的意义就是让任何一行日志能回答五个定位问题：

trace_id = tr_9f2c41 ← 属于哪次用户旅程？（你 grep 用的钥匙，跨所有服务） └─ run_id = run_a1 ← 是哪个任务？（一次 Agent Run，含多轮模型与工具调用）    ├─ step_id = step_01 ← 任务走到第几步？（一个 Loop Step）    │  ├─ call_id = call_c1 ← 这一步的哪次模型调用？（attempts=2 是它内部的事）    │  └─ tool_call_id = tool_t1 ← 哪次工具调用？    └─ step_id = step_02 ← ……任务可以有很多步 └─ run_id = run_b2 ← 同一次旅程的第二个任务

注意树里最容易漏的一点：重试不产生新的 call_id。call_c1 下 attempts=2，指的是这一次模型调用的第二次尝试。而 Structured Output 校验失败后的修复调用会拿一个新的 call_id、并关联原调用--它是「又一次调用」，不是「同一次调用的重试」。

3. trace_id 和 run_id 什么时候是两回事

你背的口径「trace_id 标识整条追踪链；run_id 标识一次 Agent Run」之所以模糊，是因为在简单系统里两者恰好重合：笔记 1.6 阶段（单文件 gateway.py）就是这么用的--行 6078 写「trace_id：一次 Agent Run」，那时一个请求就是一个任务，分不出两层。1-7 接入完整 Harness 后才拆成四级。

分开后，trace 比 run 大的典型情形：一次用户旅程触发多个任务--上面的例子里「查订单并退款」被拆成 run_a1、run_b2；主 Agent 派发子 Agent、并行 Run、一个任务跨会话续跑，都是同一个 trace 下多个 run。反过来不成立：一次 Run 只属于一个 trace。更本质地说，trace_id 是分布式追踪的标准概念（OpenTelemetry / W3C traceparent 请求头），它跨服务、跨进程传播--请求每进入一个新服务，那一行的日志继续带着它。课程四级链是这套工业标准在 Agent 栈上的领域化投影。

4. 谁生成谁：Gateway 与 Harness 的分工

Q13 后半问「谁负责把 call_id 放进完整的因果链」，答案是那句口诀：Gateway 负责 call_id 内部细节，Harness 负责把它放进完整 Run 的因果链。翻译成画面：run_id / step_id 由 Agent Loop 所在的 Harness 生成，随 CallContext(trace_id=…, run_id=…, step_id=…) 传给 Gateway；Gateway 只在这些字段下补充自己这层的细节--call_id、attempts、fallback、provider_request_id。Gateway 不知道也不需要知道任务拆了几步；Harness 不知道也不需要知道一次 call 重试了几次。两层各自加自己那层的坐标，日志才能拼出完整家谱。

5. ID 对照排查动作表（背这张就够了）

你拿到能回答典型动作
trace_id这次旅程的全部grep 一次，拿到跨所有服务的完整故事线
run_id某个任务的全部聚焦单任务日志，统计它的总 calls / tokens / 成本
step_id第几步出的事定位失败发生在哪个 Loop Step
call_id哪次模型调用看 attempts、延迟分解、错误码；与 Cost Ledger 对账
provider_request_id供应商侧的那次请求提工单时附上--供应商唯一能对上号的编号
业务 ID（工单号）领域对象查业务库；不能拿来关联模型调用

工作对应：你 8 月排查 AISphere 空间管理搜索不生效时，沿着「前端 → llmops_app → IAM 服务」的链路走通了一次微型追踪--那条链路上的日志能串起来，靠的正是这类贯穿 ID。Agent 平台的 trace 只会更长：OpenCode → plugin-daemon → OpenViking → VikingDB，每一跳都该带着同一个 trace_id。

第二部分：Q19--有证明力的断言

6. 心法一句话：给「不发生的坏事」开收据

Q19 问的是：审查一份「能返回 200」的 AI 生成 Gateway 实现，哪组测试断言最有证明力？心法只有一句：测试的证明力不在于证明「能跑」，而在于证明「不允许发生的行为确实不会发生」。

「能返回 200」为什么没证明力，你其实亲身经历过：AISphere 空间管理那次故障里，ListAllWorkspace 接口一直正常返回 200--前端请求组装时没读取搜索框字段，接口照样 200，搜索就是不生效。200 证明的只是「没崩」，不证明「行为正确」，更不证明「边界守住了」。

这在你审查 AI 生成代码时尤其致命：AI 生成的代码恰恰 happy path 写得最流畅、失败边界写得最潦草。所以审查每条测试时问一句：「这条断言证明了什么不会发生？」答不上来，它就只是「能返回 200」。

7. 正确项的每条断言 ↔ 它堵住的坏事

断言堵住的坏事对应纪律（主题课 4 精讲）
未知模型 / 非法请求 / 缺模板变量时，Provider 调用次数为零确定性错误被白白重试，烧钱且无效入口处拒绝；模板校验先于模型请求
一次失败一次成功时 attempts == 2SDK 隐式重试掩盖真实调用量max_retries=0
非法 JSON 不产生 parsed未复验的 Structured Output 流进下游本地两层校验（语法 + Schema）
流式首块后失败不调备用模型重复文本、双倍计费、无法对账首块为界
取消后只有一个 cancelled 终态、用量只落一次用量对不上账compare_and_set 唯一终态
Trace 不含 API Key、堆栈、完整 Prompt密钥扩散、数据治理事故不默认落敏感数据

8. 三个误导项为什么诱人

覆盖率 90%、类型注解完整、静态检查零告警、README 完整、Docker 能启动--这些都是代码卫生指标：它们描述「代码长什么样」「项目好不好上手」，不描述「运行时守不守边界」。90% 覆盖率可以全部由 happy path 提供；类型注解一个不少的代码照样可以无限重试、密钥写进日志。卫生值得要，但卫生不是证明力--这正是把正确选项和其他三个区分开的唯一标尺。
