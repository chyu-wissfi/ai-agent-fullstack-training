第一部分：精讲（先读，测验在后）

0. 开篇：四个追问

先看一个具体任务：修复登录会话过期后仍能访问的问题，并完成修改、测试和交付说明。

假设模型找到 session-policy.ts，把日期比较改成完整时间比较，跑完测试，最后回复「问题已修复」。任务结束了吗？课程要求继续追问四件事：

  1. 它跑的是不是任务要求的测试范围？只跑 target，还是 target / boundary / regression 都跑了？
  2. 测试通过以后，它有没有再次修改代码？旧测试还能证明当前文件吗？
  3. 如果中途等待过审批，真正执行的还是批准过的那个补丁吗？
  4. 如果运行被打断，恢复后会不会把已经完成的修改再做一遍？

这四个问题分别落在模型调用、工具执行、状态管理和运行环境之间。每个模块单独看都可能正确，但连接处的事实一旦不一致，整个任务就会错。这正是本课的主题：单个模块正确 ≠ 整个 Agent 能正确完成任务（PPT 开篇原话）。

本课主线只有一句：把准备、修改、验证、异常处理、恢复和交付串成完整闭环，并让每一步都有可核对的证据。

1. Harness：连接，不是新模块

课程给出的定义是：围绕模型组织工具、状态、上下文和执行环境的支撑程序，合在一起就是 Harness。 一句话：Agent = Model + Harness。

Model 负责理解、推理和生成动作；Harness 负责让动作真正发生，并组织整个执行过程。Harness 连接六样东西：Agent Loop、Context、State / Checkpoint、Tool Runtime、Governance、Sandbox。

同一个模型，接入不同的 Harness，表现可能完全不同。比如测试失败后，一个系统只返回「执行失败」，另一个返回失败用例、断言差异和代码位置；后者让模型知道哪条行为没满足，前者可能让它反复修改不相关的代码。

所以 Agent 工程优化不能只看模型和 Prompt，还要检查四个问题：模型看到了什么？动作是否真正执行？执行结果是否正确返回？失败后能否继续处理？

为什么 Harness 不是「再包一层」：如果只是在模型外面堆模块，而不把同一份执行事实接进模型、状态、审批和完成检查，每个模块都可以局部正确，系统仍然会交付一个失败的任务。代价是要维护更多连接和一致性；收益是模型决策有真实依据，程序也能独立判断完成。课程材料没有把 Harness 当成第七个模块，而是把它定义为「把已有能力接成完整执行系统」。

2. 分工与唯一执行入口

Harness 不是重新写一个大类，而是把已有模块按职责连接起来。课程的分工表：

模块本例中的职责
Tool提供读取文件、应用补丁、运行测试等具体能力
Tool Runtime检查调用，管理执行，记录并返回结果
Loop组织模型与工具之间的多轮交互
State保存计划、执行事实、验证证据和未完成事项
Sandbox限制操作实际能够触及的文件、进程或其他资源
任务运行层协调启动、等待、取消、恢复和收尾

顺着一次补丁调用看，基本链路是：

Model → Loop → Runtime → Tool / Sandbox → Result → Loop

三条原则必须记住：

  1. 执行约束放在执行入口。路径、权限、参数检查不能只写在某个 Loop 分支；换一条调用路径就可能漏掉。
  2. 「是否继续下一轮」属于运行控制，不交给 Tool 决定。工具只回答「这次动作的结果」，Loop 和 Harness 才决定继续、等待、停止还是转人工。
  3. Agent Runtime 负责更高层的启动、等待、取消、恢复和收尾。这些语义不能混进某个工具的 handler。
为什么检查必须在唯一入口：如果检查写在 Loop 的某个分支，模型换一种调用方式、宿主直接调用、审批按钮直接写后端，都可能绕过它。唯一入口的代价是所有调用都要经过同一层，可能多一次间接调用；收益是规则只需要维护一份，所有写入路径都受同一组条件约束。这与 0013 的「Runtime 检查放行、Sandbox 限制影响范围」是同一条主线。

2.5 读工程：先分清 Harness 与待测应用

作业要写的是 Harness，不是把框架再实现一遍。课程工程里，src/ 是 Harness，fixtures/demo-app/ 是被修改、被测试的目标应用。两类测试也不能混：fixtures/demo-app/tests/ 证明登录行为；harness_agent/tests/ 证明门禁、证据、取消与恢复。目标应用全绿，不证明 Harness 正确；Harness 全绿，也不证明它真的修好了目标应用。

代码位置它拥有的事实与职责阅读时盯住的不变量
main.ts / cli.ts进程入口、工作区、AbortController、启动或恢复恢复检查先于模型构造；待批动作未决时不启动模型
agent-runner.ts装配全部协作者，配置 pi Loop，累积真实历史并组织存档新跑与恢复共用一条执行链；不是课程自己重写 Loop
pi-tools.ts模型可见工具、参数适配、Runtime 结果转换modelView 给模型；details.evidence 给程序

loop-guard.ts重复动作、计划门禁、结果观测、完成检查、缺项回写先落执行记录，再登记证据；缺项变 follow-up，不信模型收尾

一条新任务的阅读顺序是：main/cli → agent-runner → pi Loop → pi-tools → runtime → loop-guard → plan-store/task-record → completion-contract。恢复则先从 cli → resume.prepareResume 读，确认模型还没有被创建，再看业务对象怎样还原。不要按文件名字母顺序读，那会看见很多正确函数，却看不见事实怎样跨边界。

为什么先画「事实归属图」再写代码：同一个词「状态」在这里至少有三种含义：pi 的会话历史、计划与证据、业务任务与执行记录。若不先指定谁拥有哪份事实，很容易出现模型文本被当成执行证据、计划步骤完成被当成任务完成、存档 JSON 被当成工作区快照。课程代码把三者分开，代价是对象和转换更多；收益是每份事实都有明确来源和验证者。

本工程的证明边界也要说清：它组合 pi 的 Loop，不是手写 Loop；Checkpoint 只保证 JSON 原子替换，不是文件系统事务；executeTestProcess 支持超时参数，但 runTest 当前未传默认 timeoutMs（runtime.ts:415–419）。因此课程测试证明的是特定连接与反例，不等于生产级 Sandbox、完整时间治理或工作区回滚能力。

3. 一个结果，两个消费者

一次工具执行结果有两个消费者：

  • 给模型：提供下一步判断依据，比如失败用例、断言差异、日志位置。
  • 给程序：更新状态、证据、计划进度和完成条件。

只返回给模型：模型知道失败了，但程序可能仍认为任务已经完成。只更新程序：状态正确，但模型不知道为什么失败、下一步怎么修。

因此课程把结果写成：执行结果 → Model Context + State / Evidence。状态与上下文职责不同：

  • State：保存程序可核对的事实。
  • Context：提供模型当前需要的信息。

模型可以只看到简短的测试摘要，程序仍然保留完整测试记录。还有一条容易漏掉的不变量：代码变化后，旧测试证据必须失效，并告诉模型哪些检查需要重新执行。 这不是「多写一条日志」，而是完成判断的前提。

这条原则在课程代码里不是一个抽象要求，而是同一个 ManagedToolResult 的两个投影（runtime.ts:24–30、pi-tools.ts:94–109）：

export interface ManagedToolResult {
  ok: boolean;
  code: string;
  modelView: unknown;       // 给模型看的内容
  artifact?: string;
  evidence?: ToolEvidence;  // 给程序补全并保存的证据草稿
}

// pi-tools.ts：同一次结果，content 与 details 分别服务两个消费者
content: [{ type: "text", text: JSON.stringify(result.modelView) }],
details: { ok: result.ok, code: result.code, evidence: result.evidence, ... }

模型没有直接填写 evidence。Runtime 先产生证据草稿，LoopGuard.observeToolResult 再补入 stepId、toolCallId、artifactVersion 和证据 ID（loop-guard.ts:168–227）。这决定了证据的来源是执行侧，而不是模型的一段自我汇报。

这张图还解释了四种「成功」为什么必须分开：

层级看什么不能推出什么
工具调用结果ok / code，测试进程是否得到明确结果run_test 可以 ok: true 而测试 exitCode: 1
测试行为passed、真实退出码、前后内容摘要测试通过不等于计划步骤或任务已完成
计划步骤步骤证据与 verifier；默认 verifier 可能只作宽松接收步骤 completed 不等于最终交付成立
任务完成当前 Diff、每组最新有效结果、交付物与当前现场模型说完成或 Loop 结束都不能替代它
为什么必须双写：两个消费者拿到的必须是同一次执行事实。只给模型，程序会被模型的说法带着走；只给状态，模型会在缺少依据的情况下盲目重试。代价是双写一致性和更多状态字段；收益是模型与程序不会一边说成功、一边说失败。后面 commerce-agents 的 ToolOutcome 就是把这两条去向做进同一个返回值。

4. 正常路径：先红后绿，再交付

本例缺陷在 fixtures/demo-app/src/auth/session-policy.ts：isSessionExpired() 只比较 UTC 日期，没有比较完整时间。同一天内，即使会话已经到期，函数仍可能判断它有效。

只说「把日期比较改成时间比较」可以引导修改，却没有说清修改后要满足什么行为。至少要覆盖四个边界：

  • 到期前；
  • 恰好到期；
  • 到期后；
  • 同一天但已经超过到期时刻。

测试传入固定 now: Date，不需要真的等待会话过期。任务完成需要两层检查：

  1. 第一层：测试验证行为——target、boundary、regression 三组测试。
  2. 第二层：Completion Contract 验证交付证据——当前代码存在目标 Diff；三组验证全部通过；指定交付产物存在。
测试回答「代码行为对不对」；Completion Contract 回答「交付证据齐不齐」。

本例的契约由 createLoginFixContract({ targetSource, targetArtifact, requiredScopes }) 创建；它只认当前版本上的目标 Diff、三组最新有效测试结果和真实交付产物。

准备工作区，给模型足够的起点。执行前先确认：工作区已有修改、本次允许修改的范围、测试运行目录、Runtime 与依赖、后台服务是否真实存在。不要依赖隐含环境状态：上一次 cd 不代表下一次 Shell 仍在该目录；历史记录写着「服务已启动」，不代表进程仍然存在。

首轮 Context 只需要四类信息：

内容模型需要知道什么
目标修复什么行为，哪些情况必须满足
入口从哪个文件、函数和测试开始检查
边界允许修改什么，哪些动作需要审批
验收必须完成哪些验证，生成什么交付产物

原则是：给模型足够开始工作的上下文，而不是把整个仓库塞进去。代码、日志和其他信息后续通过 Tool 按需读取。

先确认失败，再应用补丁。证据链是：读取代码 → 读取测试 → 复现失败 → 修改 → 再验证。先确认三件事：缺陷是否真实存在？当前测试是否真正覆盖缺陷？调用方怎样使用这个函数？如果应该失败的测试却通过，先检查测试覆盖，不要立即修改代码。

补丁执行仍必须经过 Runtime 检查 → Sandbox 执行；所有写入路径都受同样约束。补丁失败时：返回真实失败原因；让模型重新读取文件；程序不能猜测模型想修改的位置。 成功后保存 Diff、保留 toolCallId、更新任务状态。

让测试结果决定下一步。修改后先做类型 / 语法 / Lint，再跑三组测试。失败先分两类：

  • 环境失败：测试没有真正运行 → 代码行为尚未验证。
  • 行为失败：测试正常运行但断言失败 → 把失败用例、预期值、实际值和日志位置交回模型。

最重要的证据原则：测试结果必须对应实际受测代码。 测试通过后如果相关代码再次变化，旧测试记录仍然真实，但已经不能证明当前代码正确。

核对最终改动，再宣布完成。测试通过后还要看最终 Diff：是否真正修复目标问题？是否保留原有行为？是否删除失败测试？是否放宽断言？是否绕过验证？exit_code = 0 只是执行证据，不等于需求已经满足。最终由 Completion Contract 判断：当前 Diff + 当前有效测试证据 + 交付产物 → completed。

交付说明说清四件事：改了什么、验证了什么、什么没有验证、还有什么限制。

为什么必须先确认失败：如果测试在修改前就通过，后面的绿色不能证明修复有效——它可能根本没覆盖缺陷。先红后绿才让「修复」有比较对象。代价是多跑一次基线测试；收益是避免「改了一个不相关的地方，测试本来就会过」的假修复。同理，测试通过也不等于交付完成：测试只覆盖行为，契约还要核对当前 Diff 和产物。

5. 完成检查：只认当前最新事实

现有完成契约已经从证据中查找测试结果，而不是根据模型最终回复判断。但它还可能接受两类不可靠证据。

第一类：版本编号没变，内容却变了。 Runtime 在受控补丁成功后把 revision 从 r0 推到 r1，这能跟踪经过该入口的修改；但同一次运行中，如果文件被外部编辑，计数不一定变化。因此验证记录要关联实际受测内容 / 内容指纹，而不是只关联逻辑版本号。

第二类：早先成功掩盖后续失败。 同一内容、同一 boundary 范围，第一次通过、第二次失败；如果仍以「存在某个通过记录」为条件，早先的成功会掩盖最新失败。正确做法是：按验证范围取最后一次尝试，最新失败不能被更早的成功覆盖。

交付文档也一样：已有写入记录只证明当时写过；收尾时还要检查文件是否存在、是否包含要求内容、内容哈希是否与最后写入一致。

完成契约里的核心判断可以压缩成这段代码（src/completion-contract.ts:110）：

for (const scope of requiredScopes) {
  // 先取最后一次尝试，再判断其有效性。取消或未知不能跳过后沿用旧通过。
  const latest = evidence.findLast(
    (item) => item.kind === "test" && item.payload.scope === scope,
  );
  let reason: string | undefined;
  if (!latest) reason = "尚未执行";
  else if (latest.payload.resultCode !== "OK") {
    reason = `最近一次结果 ${String(latest.payload.resultCode ?? "未知")}，不能作为通过证据`;
  } else if (latest.payload.exitCode !== 0 || latest.payload.passed !== true) {
    reason = `最近一次未通过（exit=${String(latest.payload.exitCode)}）`;
  } else if (latest.payload.stable !== true
    || latest.payload.beforeDigest !== latest.payload.afterDigest) {
    reason = "测试期间输入变化或缺少前后指纹";
  } else if (!current || latest.artifactVersion !== revision
    || latest.payload.verificationDigest !== current.verificationDigest
    || latest.payload.beforeDigest !== current.verificationDigest) {
    reason = "源码、测试或配置与受测内容不一致";
  }
  if (reason) missing.push(`当前版本缺少通过的测试范围：${scope}；${reason}，请重新运行 run_test`);
}

Runtime 在每次测试前后各算一次 verificationDigest，覆盖源码、测试与配置；两次不一致就返回 TEST_INPUT_CHANGED，即使退出码是 0 也不能作为通过证据。测试记录同时保存 beforeDigest、afterDigest、stable 与 resultCode，完成契约再拿它与当前现场比较（src/runtime.ts:405–453）。

内容指纹只能证明「被纳入摘要的内容」。verificationPaths 与恢复时的 digestFiles 都是任务契约的一部分；漏掉关键源码、测试或配置，所谓「当前有效」就只是对这份清单有效。写自己的 Harness 时，先列验证范围，再谈哈希，不要只复制一个 digest 函数。

为什么是「最新结果」而不是「曾经通过」：完成检查回答的是「现在这份代码是否已经被验证」，不是「历史上有没有出现过一次成功」。版本号便宜但会漏掉绕过受控入口的外部编辑；内容指纹更贵，却能发现真实文件变化。课程的选择是：完成时读取当前可核对的事实，必要时重新计算摘要，而不是相信历史记录。注意它与 0010 的停止原因 write-once 方向不同：停止原因防止后来的成功覆盖先到的终局失败；测试证据要求最新一次失败压过更早的通过——两者共同的目标都是「不能让方便的历史叙事掩盖当前事实」。

6. 异常路径：继续不是默认动作

课程把异常处理统一为五个判断：

  1. 判断失败：动作到底有没有发生？
  2. 结果不明：先核对现场。
  3. 用户取消：停止必须传到真实执行层。
  4. 再次恢复：重新检查旧状态和旧证据。
  5. 持续无进展：主动停止。

核心原则：继续执行不是默认动作，而是一个需要证据支持的决定。

错误处理首先不是决定「要不要重试」，而是确认「刚才的动作到底有没有发生」。三类情况：

  • 明确未执行 → 可以按原因处理 / 有限重试。
  • 明确失败 → 根据具体原因调整动作。
  • 执行结果不明 → 先检查现场，不能直接重试。
发生了什么程序应怎样处理
临时模型请求故障按调用层规则有限重试
补丁明确未匹配、未写入返回原因，让模型读取后调整
缺少授权保存待批动作，进入等待
写操作结果不明查执行记录与现场，再决定下一步
相同动作持续失败且无进展达到限制后停止，保留未完成事项

错误必须足够具体，能够推动下一步发生变化。不要只返回「修改失败」；应该说「目标文件存在，但待替换片段没有匹配，请重新读取当前内容」。同时守住事实边界：不知道有没有写入，就记录「结果不明」，不能伪装成普通失败。

写操作结果不明为什么不能直接重放：典型情况是「补丁提交 → 文件已写入 → 程序退出 → 结果尚未保存」。此时 Checkpoint 认为修改还没完成，实际文件可能已经改成功。直接 Replay 可能重复写入、再次失败或扩大副作用。恢复时先核对：原动作涉及什么对象？执行前是什么状态？当前现场发生了什么变化？只有三种结论：

  • 确认已经执行 → 恢复真实结果，不重复执行。
  • 确认没有执行 → 满足条件后重新执行。
  • 部分执行 / 无法确认 → 保留未决，继续核查或人工处理。

不能仅凭文件里出现了某段预期代码，就认定整个动作成功；多文件补丁可能只完成一部分。核心原则：写操作恢复不是 Replay，而是先恢复执行事实。

没有进展时怎样停止：区分局部 Retry（一个动作最多尝试多少次）与任务 Budget（整个任务最多运行多少轮、多久）。不能因为一次局部重试成功，就重置整个任务预算。停止后保存已有修改、测试结果、未决动作、停止原因。核心判断：程序运行结束 ≠ 任务完成。

为什么「继续」需要证据：模型可以一直说「我再试一次」，但如果动作已经产生副作用、只是结果没保存，重试就是把一次不确定变成两次副作用。代价是要先查执行记录与现场，可能多花时间甚至转人工；收益是避免重复写入和扩大故障。课程把「结果不明」单独列为一类，而不是塞进「失败」，就是为了不让程序用错误码掩盖未知。

7. 取消、暂停、恢复：三种语义

Cancel 解决「怎样真正停下来」，不是「怎样恢复到原状态」。 UI 停止输出，不代表任务真正停止。取消信号必须沿调用链传播：任务入口 → Model / Runtime → Executor → 实际进程。还要确认：模型请求是否停止？测试进程是否退出？文件写入是否已经发生？取消不会自动撤销已经产生的副作用，因此取消后的状态应该记录「实际上发生了什么」，而不是统一标记为 failed。

课程实现用 AbortSignal 把取消传到 executeTestProcess；POSIX 下子进程以 detached: true 启动，拥有自己的进程组，取消时对 -pid 发送 SIGTERM，宽限期后升级 SIGKILL，并在返回前确认进程组已经消失。这样停的是整棵进程树，而不只是 Node 的测试运行器父进程。

const child = spawn(command, [...args], {
  cwd: options.cwd,
  detached: grouped,   // POSIX: own process group
  stdio: ["ignore", "pipe", "pipe"],
});
...
if (grouped) process.kill(-child.pid, signal);

暂停与取消是两种语义，不能都叫「暂停」：

方式语义
--pause-after保存后停止，任务仍是 running，允许恢复
SIGINT / ABORTED当前 runner 转为 cancelled 终态

Resume 之前，重新检查旧结论。 Checkpoint 保存的是上一次运行结束时的事实，它不能证明这些事实现在仍然有效。恢复前检查三类信息：当前工作区与存档相比相关文件是否变化；未决动作上次执行到了哪里、是否可能已经产生修改；旧测试和待批动作是否仍适用于当前现场。恢复顺序是：现场核对 → 修正状态 → 失效过期证据 → 构建 Context → 继续 Loop。模型必须最后启动，因为前几步任何一步失败都意味着现场不可信或不允许继续。

恢复不必一律从头开始。没有受变化影响的步骤，其有效证据可以保留；只重新验证变化涉及的部分。

「内存里已经登记」不等于「已经落盘」。课程在轮次 / 收尾边界保存 Checkpoint；待批动作与存档之间仍可能存在崩溃窗口。恢复时用 journal、调用闭合记录与现场摘要把这种窗口判成 unknown，正是为了补上「存档还没写到」的事实缺口，而不是假设每次状态变化都已同步持久化。

退出码方向不要记反：进程退出码 0 表示成功，非 0 表示失败；被信号终止时 exitCode 可能是 null，要结合 signal、cancelled、timedOut 判断。0012 的 A8 就曾在这里出过错。

为什么三种语义不能合并成一个「停止」：Pause 要保留可恢复的 running 状态；Cancel 要进入终态并记录真实副作用；Resume 要在启动模型前核对现场。把它们都叫「暂停」，要么会把已取消的任务重新跑起来，要么会把可恢复的任务当成终态丢掉。代价是状态机和入口分支更多；收益是每种停止都有明确的所有权和后续动作。

8. 接进 pi：三个容易接错的位置

先沿一次 run_test 读工程：main / cli → agent-runner → pi Loop → pi-tools → Runtime → State / Evidence → Completion Check。

读 Harness 的重点不是「有没有 Hook」，而是规则有没有覆盖实际调用路径。三个容易接错的位置：

  1. 首轮与后续轮次不同。首轮 Context 由应用准备；后续 Context 才由 prepareNextTurn 更新；完成判断必须读取最新业务状态。
  2. 不是所有调用都会经过 afterToolCall。工具不存在、参数校验失败、beforeToolCall 拒绝，都可能提前结束。拒绝记录不能只放在 afterToolCall；否则这些调用会漏记。
  3. 模型输出 approved: true ≠ 获得授权。真正批准必须来自宿主审批流程；批准后仍要重新核对条件，并走同一个执行器。
// src/agent-runner.ts:467
// pi 参数校验失败、未知工具、beforeToolCall 拦截都跳过 afterToolCall。
// 从真实结束事件补齐记录，不伪造执行，也不把阻塞步骤激活。
if (pending && !observedToolResults.delete(event.toolCallId)) {
  ...
  guard.observeToolResult({
    ...pending, args, result: event.result, isError: event.isError, context,
  });
}

Completion Contract 拒绝完成以后，不能只返回「任务未完成」。要明确：哪组测试没执行、哪条证据已经过期、最新结果为什么失败、哪个动作正在等待批准。Runtime 的结构化错误不能在 Tool Adapter 中被压缩成模糊错误。状态记录事实，Context 告诉模型下一步缺什么。

模型可以根据失败调整动作，但不能修改规则：Patch 失败可以重新读取；权限不足不能换工具绕过；测试失败可以修代码，不能删除验收条件。

为什么用事件流补齐而不是再加一个 Hook：在 afterToolCall 里加分支最省事，但它天然覆盖不到「还没走到 handler」的拒绝路径。代价是要观察真实事件流、处理去重和顺序；收益是未知工具、参数错误、前置拒绝、真实执行四类结果都能进入同一份记录。课程在 agent-runner.ts 里用 observedToolResults 去重，再从 tool_execution_end 补齐，正是为了不伪造执行、也不漏记拒绝。

9. 手写 Harness：commerce-agents 解剖

commerce-agents 是 Anthropic 开源的电商 Agent，用 Python 和 Claude Messages API 手写模型与工具之间的循环。课程只看最典型的 runtime-messages-api 路径：应用自己组织 Loop 与 Harness，业务规则仍放在独立的 core。

工程可以理解为三部分：业务核心（gates.py 门禁、executor.py 执行器、changes.py 变更账本、backend.py 后端协议）由三条运行路径共用；模型循环每条路径一份（Messages API / Agent SDK / Managed MCP）；循环与执行器之间只有一个连接点：把「工具名 + 参数字典」交给 BaseToolExecutor.execute()，拿回一个 ToolOutcome。

业务要求是：把这件商品的价格下调 10%，执行前先给我确认。 基本流程：查询 → 暂存 → 展示 → 审批 → 执行 → 返回结果。

同一结果给模型和宿主。 ToolOutcome 有四个字段：

字段给谁含义
result_text模型继续判断所需的文本
events宿主界面和业务事件
is_error双方工具执行失败
blocked宿主被哪道业务门禁拦下
@dataclass
class ToolOutcome:
    result_text: str
    events: list[AgentEvent] = field(default_factory=list)
    is_error: bool = False
    blocked: str | None = None

tool_result_block 只读 result_text 和 is_error；界面事件全部来自 outcome.events。两个函数接收同一个 outcome，因此不可能出现一边说成功、一边说失败。模型一次查询两个商品，一个成功、一个失败时，只合成「一个成功，一个失败」不够；必须用原 tool_use_id 逐个配对，模型才能判断重试谁。

手写 Loop 的顺序：准备身份、状态、Context 和 Tools → 请求模型 → 获取 tool_use → 交给 Executor → 使用原 tool_use_id 构造 tool_result → 进入下一轮。收尾时还要处理尚未配对的 tool_use：settled 里有真实结果就按真实结果回答；确实被打断且没有结果，才写「需要重试」。

轮次上限怎么收尾。 range(max_tool_iterations + 1) 多出的那一轮，force_text 为真、tool_choice 是 none，模型只能给出自然语言回答，随后 break。到达上限时 stop_reason 是模型这次返回的 end_turn，不是「超限」；宿主如果只看这个字段，会以为任务正常收尾。所以循环结束以后，还得由宿主判断业务究竟走到哪一步。

调价先暂存，批准由宿主提供。 执行 apply_change 前依次检查三道门禁：

  1. Provenance：这个 change_id 是否真实存在于本会话的来源记录？
  2. Guardrail：当前业务规则是否允许？护栏读取的是 state.seen_changes 中的暂存内容，不是本次调用传进来的描述。
  3. Approval：开启 require_host_approval 时，宿主是否真实记录了批准？

顺序有实际意义：未知 ID 没有可信内容可供检查；护栏读取已经暂存的方案，模型不能在本次调用中换一段描述就改变被检查的内容；批准是宿主对一个「存在且合规」的变更作决定，所以放在最后。

known = state.seen_changes.get(change_id)
if known is None:
    return ToolOutcome.held(PROVENANCE_GATE, ...)
if violations := check_guardrails(known.kind, known.items, config):
    return ToolOutcome.held(GUARDRAIL_GATE, ...)
if config.require_host_approval and change_id not in state.approved_change_ids:
    return ToolOutcome.held(APPROVAL_GATE, ...)
return None

宿主批准后，不必再让模型决定是否执行。 点击预览卡就是宿主的批准或驳回：先在 state.approved_change_ids 标记，再通过同一个 executor.execute("apply_change", ...) 执行，最后无论成败都撤销标记。标记不能留在状态里被后面某一轮对话消费。如果批准按钮绕过门禁直接访问后端，模型路径上的规则就没有覆盖全部写入入口。

防止重复写入 ≠ 恢复第一次执行结果。 第一次 Apply 成功但响应丢失，第二次请求被拒绝为「已经应用」，可以避免重复写入，却不能把第一次的完整结果交还给调用方；调用方仍然需要查询真实业务状态。这与代码补丁已经写入、回执尚未保存完全对应：结果不明 → 先查副作用 → 再决定下一步。

还要区分 Loop Complete（本轮模型运行结束）与 Business Complete（业务状态证明任务真正完成）。商品调价可能处于 Staged、已批准但 Apply 失败、Apply 结果不明、明确 Applied、因轮次上限结束但任务未完成；这些状态必须从业务记录读取，而不是从模型最后一句话推断。

为什么业务规则要放在 core、循环可以替换：pi 版本由框架负责通用 Loop；Messages API 版本由应用自己处理 Tool Use、Tool Result 和下一轮请求。如果业务门禁、执行器和变更账本跟着循环重写，三条运行路径就会有三套规则，迟早分叉。把业务核心抽出来，代价是循环与执行器之间要定义清楚一个连接点；收益是模型循环可以替换，业务规则仍然只有一份。课程反复强调：真正不变的是「依据从哪里来 → 动作在哪里检查 → 实际执行了什么 → 结果怎样记录 → 为什么允许继续」。

10. 作业迁移：你的 Guarded Harness 怎样挂进 smolagents

你的作业要求很具体：不改 src/smolagents/ 一行，只用新增文件给 ToolCallingAgent 加可恢复的 Guarded Coding Harness。这比「从零写 Loop」更接近真实工程：框架已经有自己的校验、记忆和异常路径，设计的第一问不是「我的类怎么写」，而是我能挂在哪里、每个切点之前框架已经做了什么。

完成验收是「两道闸」，不是一次函数调用。第一道在模型给出 final answer 时：Harness.final_answer_check 重新读取当前证据和现场，缺项就抛 AgentError；smolagents 把错误写入当前 step 的 memory，再进入下一轮（harness.py:322–353）。第二道在 agent.run 返回以后：宿主调用 Harness.finish，按审批拒绝、预算、未闭合动作和完成证据推导 RunOutcome（harness.py:270–320）。前一道负责「别让模型停错」，后一道负责「程序到底怎样收尾」。

审批复用同一执行器，但不是复用同一个调用。你的实现里，第一次 Invocation 因缺少批准停在 WAITING_APPROVAL；宿主调用 Harness.approve 后，重试是新的 tool_call_id，由同一个 approval_id 把「请求 → 宿主批准 → 重试 → 执行」串起来。第二次进入 Gate 时仍核对参数摘要与目标文件摘要，再消费一次性批准：

Invocation #1 → PendingApproval(args_digest + target_digest)
             → 宿主 approve（不是模型工具）
Invocation #2 → 同一 approval_id → 重核现场并消费批准
             → journal intent → tool.execute → journal result

这里同时守住三件事：模型不能伪造宿主批准；旧批准不能用于已经变化的目标文件；审计仍能还原跨两次调用的完整决定链。自动批准也是宿主显式开启的机器路径，记录 actor=system，不是绕开门禁。

摘要是同一原则，不是同一个字段包打天下。作业说明里「同一套指纹让旧证据与旧审批失效」需要按代码拆准：

机制实际保护什么不能过度声称什么
repo_digest（选定的源码 + 测试文件）C4 工作区漂移、H2 测试证据是否对应当前输入只覆盖 digest_files 清单，不自动覆盖配置或任意文件
Gate.workspace_digest（目标文件）审批后目标内容是否仍与批准时一致不是联合 repo_digest；run_test 无目标路径时摘要为空
content_hash / 写入前后哈希Diff 是否对应当前源码、交付文件是否与写入证据一致不能单独证明测试通过或任务完成

恢复时工作区漂移检查还先于未闭合 journal 检查。因此「写入已发生但结果未保存」若改变了摘要覆盖的文件，可能先报 WORKSPACE_DRIFT，不一定报 UNKNOWN_RESULT。结果码取决于检查顺序，不取决于你希望演示哪一种事故。

T2 暴露的两个问题，恰好说明为什么要找第一个断开的连接：

  1. 空计划让契约永远拒绝。模型第 4 步已经修好且测试通过，契约却要求一份模型根本无法通过工具创建的计划。修复不是换模型或改 Prompt，而是宿主定义计划、由证据推进状态（e2e_real.py:89–123）。还要记住：sync_plan 只是进度视图，最终仍由读取当前证据的完成契约兜底。
  2. 供应商拒绝 tool_choice="required"。这是框架默认请求参数与 DeepSeek thinking 模式的兼容问题，不是 Harness 门禁问题。用 Model.kwargs 覆盖为 auto，无需修改 smolagents 核心。
为什么作业复盘必须保留「尚未证明」的部分：当前 Checkpoint 主要保存 task + workspace，恢复的是 Harness 业务状态，不是完整 smolagents 会话；step_callbacks 只同步步号，存档由宿主显式调用；崩溃用例在 journal.begin 后直接 os._exit，证明的是 write-ahead 能识别未闭合动作，并没有执行一次真实写 handler 后再崩溃。承认这些边界不会让作业变差，反而能防止把「设计文档写了」误当成「代码已经证明」。这也是面试里最可信的回答方式：已实现什么、用什么测试证明、还剩什么不能声称。

11. 验收：看决定，也看实际后果

验收有两个对象：Agent Harness 与 目标登录应用。前者检查 Planning、Approval、Completion、Cancel、Resume；后者检查会话过期是否真正失效、原有登录行为是否正常。两条核心区别：

Harness 测试通过 ≠ 登录缺陷修复成功。
登录测试通过 ≠ Harness 的取消与恢复正确。

第一层：用固定输入验证确定的程序规则。 脚本化实验用 faux 模型产生固定动作，检查暂停时是否留下可读取 Checkpoint、恢复后是否保留计划 / 执行记录 / 进度、已完成修改是否重复执行、最终状态是否与完成检查一致。它证明的是固定输入下机制符合预期，不能证明真实模型能够自主定位并修复缺陷。

第二层：用真实模型完成登录任务。 复用真实 Gateway 和模型配置运行任务；运行结束后不只看模型回复，还要核对实际 Diff、三组测试记录、交付文件、测试之后有没有新的相关修改。没有执行的检查记为未执行；环境问题导致测试无法启动，记为尚未验证。真实运行结果来自执行记录，不来自模型对执行过程的描述。

主动制造反例，不等待模型偶然犯错。 一次成功不能证明控制规则可靠。课程给出的五个反例：

反例要同时检查的结果
测试通过后再修改相关文件任务不能直接完成，旧证据失效
同一范围先通过后失败最新失败不能被旧成功掩盖
待批期间修改目标文件旧批准不能直接执行旧补丁
运行中取消测试相关进程真实退出，进度和结果被保存
模型输出「已完成」缺少证据时不能绕过完成契约

在你的 smolagents 作业上，还要补一组「切点是否真的生效」的验收：

  • 拒绝 final answer 后还有下一次真实工具调用，并且拒绝原因进入 memory；只断言 AgentError 被抛出，不能证明 Loop 没停。
  • 正常跨进程恢复后，轮数、步号、Checkpoint 序号和重复动作计数保留，文件没有被重写；只证明「能 new 一个 Harness」不够。
  • 摘要覆盖文件漂移与无关缓存文件变化要分开：前者拒绝恢复，后者不应制造假漂移。
  • G1 两条路径分别验收：直接 Harness.invoke 有自定义审计，真实 agent 路径没有；两者都必须证明 handler 没执行。
  • 崩溃测试说清崩溃点：intent 后立即退出，只证明未闭合动作检测；若要声称「真实写入后恢复」，必须把崩溃点放到真实写 handler 之后，并预期检查顺序可能先报工作区漂移。

只检查日志里有没有「拒绝」或「取消」不够，还要检查真实后果：文件有没有被修改？子进程有没有退出？任务有没有错误进入 completed？控制规则验收 = 检查程序决定 + 检查实际后果。

失败后，找到第一个断开的连接。 沿链路定位：Runtime → Tool Adapter → Message / Context → State → Completion Contract。模型没看到失败，查 Runtime 结果 → Tool Adapter → 消息回写；状态已记录失败但任务仍完成，查 Evidence → Completion Contract。不要第一反应修改 Prompt。修复后重跑原失败场景，再检查相邻行为，保存配置、结果、失败原因和未验证项。

为什么一次成功不能证明控制规则可靠：成功路径可能只是模型碰巧没有触发边界；取消、恢复、审批、证据失效这些规则只在失败或中断时才生效。代价是要主动构造反例、跑更多场景；收益是你能拿出「程序决定 + 实际后果」的证据，而不是一句「我测过了」。这也是面试里区分「用过 Agent」和「做过 Agent 工程」的地方。

12. 面试视角：把连接讲成一条链

主问题：「模型说完成了，你凭什么交付？」 不要按模块背，按一条链回答：

  1. 完成判定：Completion Contract 读当前 Diff、当前有效测试证据和交付产物，不读模型最后一句。
  2. 证据有效性：证据绑定内容指纹，每个验证范围取最新结果，测试前后摘要一致；旧证据在代码变化后失效。
  3. 双消费者：同一执行结果同时进入模型 Context 和 State / Evidence，模型能修、程序能判。
  4. 异常语义：Cancel 传到真实进程；Resume 先核对现场；写操作结果不明不重放。
  5. 授权：宿主批准才有效，批准后仍走同一个执行器；门禁顺序 provenance → guardrail → approval。
  6. 验收：控制规则看程序决定 + 实际后果，主动构造反例，不靠一次成功。

常见追问与回答锚点：

  • 「测试通过了不就行了吗？」——测试只证明行为；还要当前 Diff、三组最新有效结果、交付产物，且测试后改代码旧证据失效。
  • 「模型说 approved: true 呢？」——模型参数不是授权；批准必须来自宿主审批入口，并在执行前重新核对文件状态与补丁内容。
  • 「重复 apply 被拒，不就恢复了吗？」——防重复写入不等于恢复第一次丢失的结果；还要查业务状态，区分 staged / applied / unknown。
  • 「为什么不用更强的 Prompt？」——Prompt 不能让程序看到真实进程、文件和证据；完成判定必须由程序依据当前事实作出。
  • 「pi 和手写 Harness 有什么区别？」——Loop 谁来写不同；不变的连接是依据来源、检查位置、执行事实、记录方式和继续条件。
  • 「你的作业为什么不改 smolagents 核心？」——核心已有 Loop、schema 校验和 memory；新增 Harness 只挂真实切点。代价是要接受框架前置路径的边界，收益是升级与维护时不用长期维护一个框架分叉。
  • 「G1 没有自定义审计，是不是审计丢了？」——它在 Tool.forward 之前被框架 schema 校验拒绝，handler 没执行；当前作业选择明确记录这个限制。若需求是全量拒绝留痕，就必须接更早的调用路径，不能声称 Tool.forward 已覆盖所有提议。
  • 「模型修好了却一直被拒，是模型不行吗？」——先查契约是否要求模型根本无法产生的事实。空计划问题就是宿主契约与工具能力不匹配，应该修宿主编排，而不是先改 Prompt。
  • 「你的恢复能接着完整对话吗？」——当前恢复的是 Harness 业务状态与工作区事实，不是完整 ReAct 会话。把这句话说清楚，比笼统声称「支持恢复」更工程化。

2 分钟复述骨架：

Agent = Model + Harness
Harness 把 Loop / Context / Runtime / State / Governance / Sandbox 接起来
一次结果 → 模型 Context + State/Evidence
完成 = 当前 Diff + 最新有效证据 + 交付产物（不是模型说完成）
异常 = 先判断动作有没有发生；结果不明先查现场；Cancel 到进程；Resume 先核对

smolagents 作业 = Tool.forward 执行治理 + final_answer_checks 拒绝续跑 + finish 独立结算
恢复 = intent/result 判未闭合 + 现场摘要 + 业务状态；不冒充完整会话恢复
验收 = 程序决定 + 实际后果 + 明确尚未证明的边界
