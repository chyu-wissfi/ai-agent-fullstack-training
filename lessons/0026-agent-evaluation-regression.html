第一部分：精讲（先读，测验在后）

0. 开篇：一次做好不等于稳定变好

Agent 在库存重构后报告「已经增加幂等判断，测试全部通过」。这句话最多是一个待核验主张。如果初始库存 10，同一业务编号、相同商品和数量各预占 2，连续提交两次后库存却变成 6、有效预占记录有 2 条，业务结果就明确失败；报告再完整也不能抵消（笔记行 879–895）。

即便这次真的修好了，也只能说明这一份最终产物在这个验证范围内通过。要证明新版 Agent 更值得采用，还要从原始缺陷工程、新会话和相同配置重新运行，观察同一任务多次 Trial、同类变化和旧能力回归。

为什么不能把「验收一次任务」和「比较 Agent 版本」混为一谈？前者只需判断这份交付是否满足当前要求；后者还要控制模型、Prompt、Skill、工具、环境、题目与评分标准，并观察波动和旧能力。后者多出环境隔离、重复 Trial 和统计解释的成本，但没有这些成本，就只能得到一次演示，不能得到稳定改进的证据。

1. 评测对象：完整系统与四层验收

本课评的是指定配置下的完整执行系统：模型根据输入决定动作，Agent Harness 组织上下文与 Loop，工具真正读写和运行，环境提供代码、数据、依赖与资源。缺少并发验证，既可能是模型遗漏，也可能是规则没进入实际请求、执行权限不足或数据库没启动（笔记行 894–911）。

材料能证明不能单独证明
Trace模型收到什么、调用了什么、工具实际返回什么最终服务一定满足业务规则
Outcome最终代码、库存、预占记录与接口行为所有未来场景都可靠

Trace 出现「运行测试」，先证明发起了调用；还要看真实执行、测试内容、退出状态与当时代码指纹。先测通过后把实现改坏，旧测试记录不能验收最终文件。越权尝试被拦截也保留两条事实：Agent 有越权尝试，治理机制成功阻止实际影响。

为什么过程验收不能强制唯一搜索路线？先读规则再定位代码、先找入口再回读规则都可能有效；强制唯一顺序会误拒绝合理实现，也让 Agent 学会表演路径。只强制业务或治理本身要求的顺序，例如审批先于执行；其余检查必要信息、关键动作和证据是否充分。

2. 标准：先人人对齐，再人机对齐

2.1 指标从业务目标往下设计，失败从证据往上解释

业务层关心故障、人工返工与总交付时间；Agent 任务层关心能否稳定完成、恢复和准确接管；组件层用检索、装配、工具参数等事实解释任务表现。Agent 十分钟生成代码，工程师再花两小时补测和修接口，不能只报「生成提速」（笔记行 927–941）。

旧规则被召回，只支持检索层判断；当前规则找到却没进请求，要查装配；进入请求却未使用，再看后续决策。组件指标是定位线索，不自动成为端到端业务收益。

2.2 背靠背标注：分歧是标准缺口，不是噪声

先把同一份 Diff、请求、数据库状态和测试材料交给研发与测试独立判断。若库存只扣一次但重复请求返回服务器错误，研发可能说通过，测试可能说失败。不要平均；拆成「业务效果是否重复」与「重复请求响应是否符合契约」，分别判定，再把统一规则写回 Rubric（笔记行 943–963）。

本教学案例约定：同编号同参数只能一次有效预占；同编号不同参数按接口契约拒绝；不同编号是不同请求。真实项目必须由业务与研发确认，不能把课程约定当普遍业务事实。

2.3 Rubric 三态：未知不能被静默消灭

把「重构质量高」拆成正常预占、相同请求重试、编号参数冲突、不同请求、并发竞争、异常回滚、接口兼容与修改边界。每项写清输入与动作、必须核对的结果、证据来源、通过/失败/未知和整体合成规则（笔记行 965–998）。

情况「并发行为正确」「必要材料齐全」
有证据证明满足通过通过
有证据证明违反失败失败
缺并发记录未知若记录是交付要求，则失败

只查「没有负库存」不够，还要核对成功承诺总量；只查「不超卖」也不够，拒绝全部请求会满足前者却破坏正常服务。既检查不该发生的事，也检查应当正常发生的事。

为什么不把所有质量都强行二元化？库存数量、记录和退出码适合确定判断；维护性、方案取舍仍有语义维度。强行二元会减少主观漂移，却可能把复杂质量变成无意义打勾。课程选择「核心事实尽量明确，开放质量保留分维度与人工判断」，代价是仍需校准和复核。

3. 资产：Task、Trial、Grader 与题集

第一批任务从发布前人工检查、历史故障、Agent 真实失败与高质量完成样本开始。优先高频与高风险；20–50 个失败相关任务只是冷启动参考，不是门槛。同一道题换十种措辞，不自动增加十种业务风险覆盖（笔记行 1024–1043）。

一道合格 Task 至少有：稳定 ID/版本/来源/负责人、任务说明、初始工程、必要上下文、操作约束、成功条件、评分配置、参考与反例、用途标签。交给 Agent 的部分必须包含目标、规则和边界；评测端另存初始数据、参考方案、独立检查与初始化方法。隐藏函数名或隐藏报告字段不能突然成为强制条件。

题集标签是可交叉维度：重复预占题可以同时是历史错题、能力题、黄金样本与发布必过项；修复稳定后再成为持续回归项。未修复问题先进入候选池，不能等修好才保存；也不能伪装成稳定通过的回归项。满分仍要抽查评分器是否过松、答案是否泄漏、环境是否残留。

为什么参考方案和已知缺陷都要先跑？正确实现通过，说明题目可解、环境和评分器基本可用；目标缺陷失败，说明检查确实能抓住问题。只做前者，可能出现「谁都能过」的空评分器；只做后者，可能把有效方案也全部错拒。两者仍不证明真实 Agent 得分。

4. 运行：两种 Harness、隔离与证据包

Agent Harness 负责做任务，Evaluation Harness 负责规定条件、启动、取证、验收与汇总。两者可复用基础设施，但独立验收不能由被评 Agent 修改。一次 Trial 应从规定缺陷工程、新会话和初始数据开始；第二次要恢复起点，而不是把上次修改和答案留给下一次（笔记行 1125–1169）。

4.1 哪些状态必须恢复或记录？

源码、未提交文件、生成报告、数据库、索引、会话历史、工作记忆、长期记忆、任务缓存都要处理；模型、Prompt/Skill、工具、权限与预算也要固定或记录。任务本来测长期记忆，就给每次相同初始记忆，不继承上一轮正确答案。基础设施冷热缓存可能改变延迟与计价，要说明条件，不能把缓存收益归给策略。

环境还要贴近真实使用：SQLite 局部测试不证明另一种数据库的事务与并发；绕过真实工具网关并放大 Shell 权限，也不再是同一配置。受控服务适合稳定比较局部能力，真实调用适合观察实际集成，二者分别标记。

4.2 完整运行包与三条独立状态

证据至少保存回答
任务与配置题目、初始快照、版本、权限、预算比较条件是否相同
模型请求/响应实际消息、工具定义、错误与流式状态规则是否进入输入，响应是否完整
工具与检索调用 ID、参数、结果、重试、来源及后续使用请求与真实执行能否对上
最终产物与测试最终文件、Diff、指纹、命令、退出码、断言测试是否验证最终版本
实际状态库存、预占记录、接口行为业务要求是否实现
计量与停止各阶段耗时、用量、费用、停止原因资源与完成判断是否可信

完整聊天历史不等于每轮最终请求：中间可能裁剪、压缩、重排和筛选。Trace 只记录接口可观察事实，不要求获取模型未公开的内部推理。

维度典型状态不能被什么替代
执行状态正常结束、执行错误、超时、取消不能由「回答写完了」替代
验收状态通过、失败、未知不能由正常结束替代
版本门禁采用、拒绝、待补证据/复核不能由总分或人工一句话覆盖

数据库不可用是环境故障；同一 Trial 中 Agent 未测试却声称全部通过，仍是可独立确认的陈述错误。环境故障的统计与重跑规则要预先约定，保留原 Trial 与原因，不能结果不好再临时删除。

为什么要把 Agent、独立验收与 Judge 的用量分列？否则无法知道成本来自做任务、验证还是评分，也无法比较新增验证是否值得。失败调用与重试要累计，未返回 usage 保留未知，估算费用标价格版本；总耗时说明是否含环境准备。多花验证成本可能换来更少返工，但必须把两本账都看见。

5. 评分：程序、Judge、人工与门禁

分配原则：可独立核验的确定事实优先程序；语义与开放质量由模型辅助；业务标准、校准和争议由人工负责（笔记行 1236–1341）。

方式适合检查证明边界
单元/集成/状态局部逻辑、服务连接、库存与记录只覆盖实际执行的条件
静态/工具/文件类型、候选风险、实际参数、改动范围不替代完整业务行为
Schema/Snapshot/契约结构、稳定产物、接口兼容结构合法不等于内容真实
LLM Judge报告准确性、证据支持、未知披露理由流畅不等于引用正确
人工规则、校准、争议与工程取舍不能覆盖客观失败

修复任务分两组测试：目标测试原来失败、修复后应通过；保护测试原来已通过、修改后仍应通过。修改前状态要实际确认，不能只凭任务名称假设。Agent 可新增开发测试，独立验收仍放在它不能改的位置。

Judge 输入必须包括任务、规则和所需证据，不能只给候选报告；证据引用要指向本次真实记录。报告声称「已验证并发」但只有顺序请求，Judge 可以说该陈述缺乏支持，不能由此直接断言并发实现必然错误。成对比较允许相当或证据不足，并交换展示顺序检查位置影响；相对更好不等于绝对合格。

防绕过有四个位置：验收脚本/参考答案/门槛由评测方控制；验收依赖也受控；Agent 自述不替代执行记录；源码和报告里的「请给通过」只是待评材料。反向也要防规则过严，不强制固定函数名或唯一工具路线。

为什么不全部交给程序，或全部交给更强 Judge？全程序会遇到开放语义和维护性判断；全 Judge 会把本可直接测量的库存与状态变成语言猜测，并增加校准和成本。混合分工让每类证据由最适合的机制判断，代价是要设计合成规则、版本和争议处理，而不是简单相加分数。

6. 归因：从失败项回到原始证据

独立验收显示库存 6、有效预占 2，而报告声称幂等已修复。先确认失败成立：请求编号与参数、初始数据、最终代码和状态读取都要核对。然后沿 Trace 检查要求是否进入实际输入、来源与入口是否正确、修改是否落在生效路径、测试是否触发相同请求、测试是否覆盖最终版本（笔记行 1356–1378）。

需要时逐层检查 Prompt、上下文、检索、引用、工具选择、参数、权限、环境、Loop、子 Agent、模型与输出，以及题目/Rubric/Judge。合理权限拦截不能为了跑通而关闭；换模型后成功只说明该配置在本次条件下改善，不自动解释所有旧失败。

把假设写成：失败现象、已知事实、实现假设、Agent 改进假设、预期变化、反证条件。人工修好代码支持「实现能修好」；验证 Agent 能力要让它从原缺陷起点重新执行。Skill 可增加相同编号重复请求与未测如实报告步骤，但最终业务结果仍交独立验收。

为什么一次只改一个因素？同时改 Prompt、检索和 Skill，即使整体变好，也不能把收益归给其中某一项。单因素便于归因，但可能慢且漏掉交互效果；组合方案可以评价，却只能先声称「组合有效」。需要单独验证时复制策略，只改目标因素，并保持其他条件与评分一致。

7. 比较：多次 Trial、回归与采用

比较前固定四组条件：题目与标准、起点与环境、执行配置、统计与决策。采用要求在看结果前写：目标问题改善、报告与证据一致、正常功能和接口保持、没有越权、开销可接受。外部服务波动可交错运行新旧版本，但仍要保存环境状态（笔记行 1428–1450）。

2/3 是观测通过比例，不是 pass@3；一组三次出现成功，也不能推断真实 pass@3=100%。允许生成多个候选再用独立测试选择时，pass@k 更有参考价值，但选择器本身也要验证。用户每次都要稳定完成时，更关注单次表现和连续稳定性，同时报告 k、每次预算和总消耗。

教学例中合计由 13/15 到 14/15，但接口兼容由 3/3 降到 2/3。先查原始证据：确认新版退化就暂缓采用；确认评分器误判就修评分器，并同样重查相关新旧结果。总体提高不能抵消核心失败。

门禁要接实际 CI/CD 或采用动作。提交时跑快速检查与代表性任务；采用新模型、Prompt、Skill 时跑能力与回归集并重复 Trial；评分器变更额外验证正确、错误、边界样本；离线通过后再验证真实使用条件。只有报告、没有阻断或复核出口，不叫门禁。

8. 日常研发：五步测试与双闭环

8.1 人先定范围与风险，AI 再辅助展开

专家先圈定预占入口、幂等、事务与数据访问，AI 搜索调用链、状态转换、循环查询、提交位置和异常分支，产出带位置、触发条件、证据、影响与待验证点的候选清单；人再按业务影响和成本排优先级。Rule 保存工程普遍要求，Skill 保存特定场景方法，执行策略继续强制权限与预算。

五步测试设计是：建立范围 → 风险分级 → 设计分组 → 生成可执行步骤 → 验证覆盖（笔记行 1584–1637）。

  1. 范围：从 Diff、调用链与实际使用确定纳入和排除理由；共用事务变化也可能影响确认与释放。
  2. 风险：按业务影响而非修改行数确定深度；一行提交位置变化可能高于大量重命名。
  3. 分组：用判定表区分新编号、同编号同参数、同编号不同参数、库存不足；并发与异常另列。
  4. 步骤: 明确初始库存、固定编号、两次提交、异常注入位置，以及响应/库存/有效记录断言。
  5. 覆盖：风险→用例→证据矩阵运行后再关联代码指纹和真实结果。

已设计、已执行、已通过是三个状态。测试矩阵生成完毕只能写已设计；计划运行的测试不能写成已通过。

离线评测回答固定条件下新旧版本怎样；影子模式用真实输入对应快照在独立环境观察候选，不直接合并或发布；A/B 比较实际使用中的验收、返工、总时间与成本；巡检检查代表性能力；监控提供可用性、错误、耗时、用量与分布信号。影子重放不是线上 A/B，监控正常也不证明任务正确。

Case 流程要有负责人和后续动作：采集→清洗→评测→质检→归因→修改→复测→回归。历史失败先进入候选池，真实修复验证与项目确认后才进入活动回归。长期红色结果需要治理状态，避免团队习惯忽略失败。

为什么不一开始建设完整评测平台？冷启动最需要的是核心种子、明确规则、规定起点、基础评分和可归因记录；平台看板再多，Case 无人处理仍没有闭环。先跑通一个核心场景能暴露真实证据缺口，再按「发现不了什么、解释不了什么、哪些修改无法验证」扩量。代价是早期人工较多，但避免为尚未确认的需求建设复杂组件。

9. 代码解剖：本课实际证明什么

9.1 数据契约落在文件，不是五个抽象基类

eval_lab 是库存专用教学 Harness，不是通用强类型评测框架。Task 是 JSON 字典，要求 id/name/kind/prompt/checks/references/forbidden_paths/version；Trial 以运行目录和 manifest.json 为锚；Trace 是 trace.jsonl 与 provider_trace.jsonl；程序与语义结果分别写入 program_grades.json 和 judge_grades.json。

Task JSON + 独立 fixture
  → runs/<run_id>/manifest.json       # 配置、版本、起止指纹、run_status
  → trace.jsonl + provider_trace.jsonl # RPC 与消毒后的 provider 证据
  → initial/ + workspace/ + patch.diff # 起点与最终产物
  → development_tests.json + metrics.json
  → program_grades.json + judge_grades.json
  → gate.json                          # accept / reject / pending

run_status=completed 要求收到 agent_settled 且没有记录的模型错误；prompt 接受或进程退出本身不够。程序检查用新子进程和新临时 SQLite 数据库加载候选实现，不读 Agent 自述来代替行为。Judge 校验检查项集合、理由、状态和真实证据键；非法 JSON、虚构引用、不完整 SSE 都进入错误而不是通过。

9.2 门禁矩阵与比较口径不是同一个字段

本机合成输入release_gate原因
live 声明 + completed + 所有检查通过accept仅说明门禁分支接受这些输入
程序业务检查 failreject明确失败
run_status=timeoutreject执行未正常完成
source=protocol_testreject协议测试不能冒充真实 Agent 成功
必需语义检查 unknownpending证据不足，待补或复核
评分后源码再变化pending代码与取证/Judge 版本不一致

版本比较又把 accept/reject 映射为 outcome=true/false，把 pending 或未完成执行映射为 null。因此同一个非 completed Trial 在单次门禁中是 reject，在统计 outcome 中可为 unknown；字段服务不同问题，不能只看一个词。

statistics.summarize 支持从 n 次已知结果估计 k 次至少一次/全部成功；但 CLI compare 固定 k=min(3,trials) 且 n=trials，所以实际 CLI 主要是该组 any/all 观察，并未利用一般 n>k 估计，也没有置信区间或显著性检验。

9.3 已核实的实现边界

  • 字段没有自动成为规则：Task 必须声明 forbidden_paths，但当前 boundary_check 没有读取它，而是硬编码允许修改 inventory.py 和新增 tests/test_*.py。本机把该字段改为禁止 inventory.py 后，修改仍被判 pass。应把任务规则接回检查器，并用反例验证。
  • 不是 OS Sandbox：文件/工具边界是教学治理，独立程序评分会执行候选 Python；不能把它当恶意代码隔离。运行包 JSON 与 source=pi_live 也是可编辑声明，哈希帮助核对内容，但不构成签名或防篡改证明。
  • Judge 有截断与职责边界：单字段超过 24,000 编码字符会截断；缺失证据不应变通过。普通 release gate 没有强制人工批准，人工主要出现在标准校准、争议和回归准入。
  • 诊断默认是确定规则：step_08 提取非通过检查、选定事件和过期测试指纹，验证计划是固定模板；--llm 才新增引用证据的假设，仍要求人工复核。它不会自动找出所有根因。
  • 测试设计只生成计划：step_11 是 live 只读生成，输出 designed_not_executed；它既不实现也不执行测试。影子重放只标 isolated_replay_not_online_ab。

9.4 本机基线与历史材料必须分开

本机用 Python 3.12.14 运行 validate_local.py：23 项中 1 失败、2 跳过。失败是影子重放测试把 /var/... 与实现规范化后的 /private/var/... 直接比较；最小探针证实两者 resolve 相等、samefile 为真、原始运行包未变。这是 macOS 路径表示导致的现有测试问题，不是本课修复后的结果；2 项跳过是因为解压副本未安装本地 pi npm 依赖。

包内 README 声明制作环境没有真实供应商端到端验证，但后续归档又含 pi_live、校准和比较材料。它们只能作为未由本课独立复现的历史记录。两份历史比较里，同一 v2 在一次为 2/3 + 1 未知并 hold，另一次为 3/3 并 accept，恰好说明小样本波动；不能改写成「v2 永远更好」。本机只离线审阅这些记录，没有发起真实模型请求。

为什么把课程代码本身的缺陷也纳入教学？评测基础设施同样需要评测。一个未接线的 forbidden_paths 字段、一处路径表示误比较、一个过小的样本都可能制造错误结论。保留这些反例能训练双闭环：不只问 Agent 哪错了，也问 Task、Grader、证据采集和统计解释哪错了。

10. 面试视角：两分钟主链

我会先明确评测对象是指定模型、Harness、上下文、工具和环境的完整系统，结果看最终产物与业务行为，过程看必要动作，效率看包含人工返工的总成本，风险看越权尝试与真实影响。标准先由业务、研发、测试背靠背对齐，再下钻成带证据的 Rubric；程序、Judge、人工分别处理确定事实、语义质量和争议，校准分别看误放行、误拒绝与未知。Task 定义一道工作，Trial 是从固定起点的一次完整尝试，多个 Grader 共享这次 Trace 与 Outcome。每次 Trial 重置或记录源码、数据、会话、记忆、缓存和配置，保存实际模型请求与最终代码指纹。失败沿 Trace 区分事实、假设和验证计划。版本比较固定题目、环境、配置和统计规则，多次 Trial 后检查原问题、同类变化、旧能力和成本；总分提升不能抵消核心退化。最后让真实 Case 同时驱动 Agent 改进与评测资产改进，验证有效后进入持续回归。

常见追问链

  1. 「测试都通过了，为什么还不能验收？」——要确认测试是否实际执行、是否触发目标业务条件、是否覆盖最终代码；还要检查接口、边界、并发与真实状态。
  2. 「Judge 与人工 90% 一致，为何仍不可信？」——样本分布可能让始终通过也得高分；要看高风险误放行、误拒绝和未知处理，并跑保留样本。
  3. 「一次 Trial 多跑十条测试，能否当十次 Trial？」——不能，它们共享一次 Agent 尝试；新 Trial 要恢复规定起点和新会话。
  4. 「失败为什么不直接改模型？」——结果还受规则装配、工具参数、权限、环境、Loop、题目和评分器影响；先沿原始证据找第一个断点。
  5. 「pass@3 接近 100%，能否说明稳定？」——它表示至少一次成功；若每次都要可靠，需看单次分布和 pass^3，并注意独立同概率假设。
  6. 「总分提高为何仍拒绝新版？」——核心接口或边界可能是硬门槛；关键旧能力退化或关键未知未解决时，平均提升不能换放行。
  7. 「人工修好失败产物，是否验证 Skill 有效？」——没有。要让使用新 Skill 的 Agent 从原缺陷工程与干净会话重新执行，再比较同类、回归与成本。
