Working Memory——建议不是完成，旧测试不是当前验证

本课定位：Week04 第二课，4-1 装配器的上游。上一课解决「本轮信息怎样装进请求」；但装配器负责选择信息，它首先要有一份准确的任务记录。本课回答：这份记录保存什么、凭什么更新、怎样失效、怎样恢复——核心一句话：状态必须符合执行事实。
材料定位：第四章 学习笔记.md 4.2 节（行 668–905，本课第一材料，术语以此为准）+「本章复习问题」Q11–Q12（行 2584–2586，参考答案行 2664–2668，本课测验换形式覆盖）+ week04/README.md 4-2 目录说明 + 教师 PDF 4-2.pdf（补充）。
代码定位：course_code/week04/4-2/——四个演示脚本：4-2-2.py（结构化记录+装配）、4-2-3.py（取一条事实）、4-2-4.py（Scratchpad）、4-2-6.py（JSONL 保存与恢复）。全部纯标准库、离线可跑，复用 0017 建的 4-1/.venv（Python 3.12），不需要 tokenizers，也不需要 API key。
预计用时：精讲 40 分钟 + 测验 25 分钟 + 第二层动手练习 45 分钟
本课验收标准（笔记「本节重点与验收」行 893–903，五条）：① 仅提出方案时，状态仍为未修改、未验证；② 补丁失败或被拒绝后，不会记录修改成功；③ 修改版本后，旧通过记录不再支持完成；④ 新进程能读取进度，核对现场后继续未完成步骤；⑤ 工具执行成功与业务断言通过分别记录。第三部分六个实验与这五条一一对应。

三层定位：第一层能默画三张图——三层信息分工（图 1）、三阶段闸门（图 2）、约束四步链路（图 3）；第二层跑通四个离线脚本（实验①②），再主动改造四种失真（实验③–⑥）；第三层始终追问「这条状态凭什么写进记录」「这份证据对应当前哪个版本」「恢复时现场还是不是存档时那个现场」。

第一部分：精讲（先读，测验在后）

0. 开篇：「继续」两个字的事故

登录修复进行到一半：Agent 已经读源码、取得边界失败，建议把 <= 改成 <。此时真正的进度是「已定位，未修改，未验证」（笔记行 674）。下一轮用户只说「继续」。如果输入没有明确进度，模型可能重新搜索，也可能误把修复建议当作代码已经修改（行 678）。

完整历史能帮助判断，但其中同时有计划、失败尝试和后来的结果。历史越长、压缩越多，每轮重新推断进度越容易出错（行 680）。这正是 0017 开篇事故一（「明明运行了失败测试，下一轮却说测试已经通过」）的上游原因之一：装配器再能干，也没有一份准确的当前状态可选。

所以本课的位置在 4-1 的上游：工作记忆，就是围绕当前任务保存目标、约束、执行事实和未完成事项的记录（行 684）。它有两个消费者——装配器直接取出当前进度；程序用它检查当前版本是否真的完成验证。

1. 历史、工作记忆、本轮 Context：三层各回答一个问题

为什么不让模型每轮从全量历史自己重推进度？ 替代方案确实存在：全量历史直发、或最近 N 条、或让模型自己总结。代价是：历史里计划与事实混杂，长度和压缩都在放大推断错误率（行 680）；「最近 N 条」会丢掉最早的用户约束（0017 复习 Q2）；模型总结可能把推断写成确认（0017 两类压缩）。当前约束下选「程序维护的派生状态」：取出即用、可核对、可检查。代价是要遵守更新纪律——记录本身也会失真，本课后面五节全是这条纪律。

2. 最少保存什么：字段不重要，状态依据才重要

先从四类开始：目标、已完成步骤、关键工具结果、未解决问题；再补充约束、风险、来源和版本（行 698）。登录修复的当前记录（行 700–708）：目标「恰好到期时返回 False」；已完成「读源码、跑边界测试、定位比较条件」；关键结果「test_at 预期 False 实际 True」；未完成「补丁未应用、修改后未测试」；约束「不得修改现有测试、不得延长有效期」；风险「改变边界可能影响调用方，待搜索和测试」。

笔记强调：这里最重要的不是字段名，而是状态依据（行 710）——

工具结果保存摘要，原文保留核对入口（行 720–737）。几千行日志不必全部复制进工作记忆：当前记录保存失败用例、输入、预期、实际、版本和原文位置。笔记给的完整教学示例是六个字段：summary / source / execution_id / code_version / status / reference。

材料与代码的口径差（实验①会现场核对）：4-2-2.py 里的简化字典只有四个字段（summary / code_version / source / reference），缺 execution_id 和 status。笔记行 735 自己声明了这一点：「原稿前面的简化字典未列出所有字段，正式实现要补齐后再引用」。摘要让模型快速知道边界问题；原文与执行 ID 让程序能够核对。不能删掉失败断言，也不能把未测试写成通过（行 737）。

为什么摘要+引用，而不是全文或纯摘要？ 全文进记忆：每轮装配预算爆炸，噪声稀释关键断言（0017 预算与污染两课的直接后果）。纯摘要不留原文：失去核对入口，摘要错了无法回查。当前方案是取舍后的中间点——摘要服务模型判断，execution_id + reference 服务程序核对，与 0017「程序提取 + output_ref 补读」同一条设计线。

3. 约束、风险、计划：三种东西，以及约束的四步链路

约束是必须遵守的要求，风险是需要检查的影响（行 743）。「不得修改测试」是约束；「修改后是否影响调用方」是风险；「我准备只改一个文件」是 Agent 的计划，不能冒充用户要求（行 747）。记录方式也不同（行 749–752）：约束至少保存内容、来源、适用范围，用户或有效项目规则调整后更新，无法判断冲突时澄清；风险至少保存可能的问题、依据、具体检查动作，搜索或测试后记录已排除、已确认或仍待核对。

关键一句：约束写进工作记忆，只能帮助模型准备方案。违规方案仍要在执行前拦住（行 754）。「不得修改现有测试」的完整链路是四步（行 758–766）：

为什么约束写进了记忆，还要 Runtime 再拦一道？ 因为记录与提示词一样，只能「劝」模型，不能「强制」模型。替代方案「只靠 prompt 写约束」的代价：模型一旦提出违规方案，没有任何东西在执行前拦住它，事故直接落盘。当前约束下选「记录 + 装配 + 执行前拦截 + 结果回写」四层：每一层回答上一层失效后还剩什么（与 0008 的递推防线同一思路）。拒绝后的回写同样不可省——否则记录说「已修改」、事实是没改，后续每轮都建立在分叉的状态上。

4. 临时事实：有来源，也要能失效

工具读到的源码、测试结果和修改状态，都是某个现场下的执行事实。「临时」不是说它们不可信，而是说它们对应当时的代码和环境，可能随代码或环境变化失效（行 776；PDF p5 同口径）。五类内容要分开（行 780–786）：

内容性质可以证明什么
工具返回 <=源码观察当时读取的版本使用这个表达式
工具返回边界失败执行事实对应版本该用例未通过
模型说改成 < 应该有效候选判断有一个待验证方案
工具确认补丁应用修改结果文件已发生对应变更
新版本测试通过验证结果本次覆盖的测试在该版本通过
为什么按规则标 stale，而不是「全部重测」或「继续沿用」？ 全部重测最安全但最贵——每次代码变化都重跑全部测试，长任务里成本不可接受；继续沿用最便宜但失真——旧证据对新版本没有证明力。当前方案是精准失效：只有「相关」旧证据标 stale、只重测受影响范围。代价是要维护失效规则本身（什么变化触发哪些证据失效），这就是「status=current 需要程序维护」的含义——标签不是写完就永远有效的护身符。

5. Scratchpad：把计划和下一步接到执行事实后面

失败事实说明发生了什么，但不一定说明准备怎样处理（行 800）。Scratchpad 是工作记忆中的任务便签，保存计划、观察、简短决策和下一步；它不要求保存模型内部的隐式思维链（行 802）。看结构，重点看证据引用与状态（行 808–817）：

为什么不保存模型的隐式思维链？ 思维链是模型内部过程，冗长且不可核对——存下来也无法验证它说的推理是否真实发生。便签只存「可核对的决策摘要 + 证据引用」：丢失推理细节，换来可审计、可装配、可恢复的进度。这是取舍不是偷懒：恢复任务需要的是「准备做什么、凭什么、做到哪」，不是「当时怎么想的」。补丁失败就记录失败并检查原因；测试通过就核对是否覆盖全部要求，再决定能否完成（行 821）——便签跟着实际结果变化，不能一直保留最初的计划（PDF p6）。

6. 生命周期：创建、更新、保存、恢复、归档

阶段输入与动作结果
创建读取目标、约束和初始现场建立当前任务记录
更新收到每次工具结果调整已完成、失败、风险和下一步
保存到达暂停或恢复边界记录不随进程退出而丢失
恢复读取记录并核对当前代码确定从哪一步继续，哪些证据需重做
归档核对完成条件保留执行记录，筛选后续有用知识
为什么恢复必须先核对现场？ 存档是「上次做到哪里」的证据，不是「外部世界没变」的证据。暂停期间别人改了代码，就要先检查差异、重新决定验证范围（行 839）——与 0012 恢复五步「存档→工作区→任务状态→业务对象→最后启动模型」同构：现场不可信时继续执行，等于在别人的代码上沿用你的旧验证范围。为什么保存与发送分离？ 两个动作服务两个目的：持久化保证记录能再读；上下文装配决定模型这次实际看到什么（行 845）。全量保存不妨碍本轮只发相关部分——这正是 4-1 三去向里「外部保存+引用」在记录侧的落点。

7. 与 Agent State 的边界，以及 JSONL 演示到底证明了什么

Agent State 可以保存消息、模型、工具和运行标记，也可以包含业务字段；单独讲工作记忆，是为了明确目标、证据和进度怎样更新（行 851）。三个保存位置语义要区分（行 853–859）：

保存位置主要职责
执行记录原始工具返回、调用关联、退出码和日志
工作记忆提取后的关键结果、当前目标和进度
模型请求本轮选中的信息

它们可以存于同一个文件或数据库，但语义要能区分。4-2-6.py 的 JSONL 演示就是这个结构：依次写入用户要求、预设工具调用、真实边界表达式结果，再写入 customType=working_memory 记录；恢复时重新读取，取出最新工作记忆，装配进下一轮消息（行 865）。这种 message / custom 分型与 pi 会话存档同构（见 pi-agent-core 的 session/types.d.ts：type:"message" 与 type:"custom" + customType）。

演示里还有一个容易误读的字段：isError=False 表示计算工具正常获得结果；结果为 True、与预期 False 不符，业务验证仍然失败（行 875）。一句话：工具正常返回，不等于任务验证通过（行 879）——执行状态与业务断言要分别记录（验收第 5 条）。

这段演示证明了什么、不能证明什么？ 它证明：记录写入、重新读取和装配路径成立（行 881）。它没有调用模型、没有修复源码、也没有核对恢复后的版本；临时目录退出后删除。正式工程仍需持久存储与现场核对。这与 0017 的口径意识一致：演示数字与演示路径是「那次运行的证据」，不是普适结论——你的 benchmark 工作里，单次跑批的指标同样不能外推成系统结论。为什么不另建一套数据库？ 物理分离不是重点，语义区分才是：同一 JSONL 里 message 与 custom 各有消费者；另建存储反而引入「两处记录谁同步谁」的一致性问题。当前约束下「State 内含工作记忆」更便宜（行 692）。

工作对应点：结构化任务记录（目标/约束/事实/下一步分性质保存）与你熟悉的 de-test fact 族输出协议同构——都是「先定性质与来源，再谈检索与使用」。工作记忆与长期记忆的边界（当前会话 vs 跨会话复用）是下一课 4-3 的主题，也是 OpenViking 记忆系统的核心问题之一。

8. 面试视角：两分钟主链 + 追问链

两分钟主链（不看稿讲清）：历史回答「发生过什么」，工作记忆回答「现在什么状态」，本轮 Context 回答「这次看哪些」→ 记录最少保存目标、已完成、关键结果、未完成，再补约束、风险、来源、版本 → 状态依据是三阶段：建议只存候选、工具确认才写已修改、当前版本测试通过才存验证结果 → 约束走四步链路，Runtime 执行前拦截，拒绝必须回写 → 事实绑定版本，旧证据标 stale、分支隔离 → 便签接 evidence_id，结果驱动更新 → 保存与发送分离，恢复取最新记录并核对现场 → 工具正常返回≠业务验证通过。

工作记忆
├── 为什么：历史≠当前状态（长+压缩 → 重推易错）
├── 存什么：目标 / 已完成 / 关键结果 / 未完成 + 约束 / 风险 / 来源 / 版本
├── 凭什么写：三阶段（方案→修改→验证），只认执行证据
├── 怎样拦：约束四步链（记忆→装配→Runtime→Harness），拒绝回写
├── 怎样失效：code_version 绑定 + stale 程序维护 + 分支隔离
├── 怎样继续：Scratchpad 接 evidence_id；恢复取最新 + 核对现场
└── 边界：保存≠发送；执行成功≠业务通过；演示≠正式工程

面试官追问链：

  • 「模型说改完了，你怎么确认？」→ 三阶段：只认修改工具回执与当前版本测试执行，不认模型自述。
  • 「约束写在 prompt 里不就行了？」→ 四步链路：记录只帮助准备方案，违规方案靠 Runtime 执行前拦截；拒绝后还要回写状态。
  • 「旧测试通过记录为什么不能用了？」→ 证据绑定版本：v1 通过不证明 v2 正确；stale 要程序维护，分支也要隔离。
  • 「恢复会话就恢复进度了吗？」→ 存档≠现场没变：先核对当前代码，再决定从哪继续、哪些证据重做。
  • 「工具返回正常，为什么任务还失败？」→ 执行状态与业务断言分开：isError=False 只说明拿到了结果，不说明结果符合预期。

import json
from pathlib import Path
p = Path("/tmp/wm-session-demo.jsonl")
entries = [
  {"type":"message","message":{"role":"user","content":"修复会话到期判断，不得修改测试。"}},

实验 ③：主动改造 A——把建议写成完成（证明验收①）

  • 探针：伪造「已应用补丁」，看装配器会不会拦（在 4-2 目录执行）：

mem["completed_steps"].append("应用补丁")   # 改造点：没有任何执行证据
mem["unresolved"] = []

print("已完成含补丁:", "应用补丁" in mem["completed_steps"])
print("未完成已清空:", mem["unresolved"] == [])
print("tool_results 有执行ID吗:", [r.get("execution_id") for r in mem["tool_results"]])
print("请求里还有「尚未应用补丁」吗:", "尚未应用补丁" in ctx["messages"][1]["content"])
EOF
    先写预期：装配器会检查「应用补丁」有没有执行证据吗？请求里的进度变成什么？
    预期（本机实测）：已完成含补丁 True、未完成清空 True、执行 ID 全是 None、「尚未应用补丁」从请求消失——装配器照单全收。它只管选择与预算，不管状态真假；状态依据要靠更新纪律（三阶段）保证。这就是开篇事故的上游现场：记录失真，装配再正确也是在传播失真。

实验 ④：主动改造 B——恢复取错记录（证明验收④）

  • 探针：两次保存后，reversed 取最新 vs 正序取最早（在 4-2 目录执行）：
    ../4-1/.venv/bin/python - <<'EOF'
entries = [
  {"type":"message","message":{"role":"user","content":"修复会话到期判断，不得修改测试。"}},
  {"type":"custom","customType":"working_memory","data":{"code_version":"v1","status":"已获得失败证据，尚未修改","next_step":"定位并修改比较条件"}},
  {"type":"custom","customType":"working_memory","data":{"code_version":"v2","status":"补丁已应用，尚未测试","next_step":"运行修改后的边界测试"}},
]
pick = lambda es: next(e["data"] for e in es if e["type"]=="custom" and e["customType"]=="working_memory")
latest = pick(reversed(entries)); first = pick(entries)
print("reversed 取到:", latest["code_version"], "|", latest["status"])
print("正序取到:  ", first["code_version"], "|", first["status"])
EOF
    先写预期：去掉 4-2-6 里的 reversed() 会取到哪条？模型恢复后可能做什么危险动作？
    预期（本机实测）：reversed → v2「补丁已应用，尚未测试」；正序 → v1「尚未修改」。取到旧记录，模型以为还没改过，可能重复应用补丁。注意演示只做到「取最新」，还没做「核对现场」——恢复时确认当前文件仍匹配 v2，是正式工程要补的另一半（验收④的完整含义）。

实验 ⑤：主动改造 C——版本变了，旧证据还标 current（证明验收③）

  • 探针：代码已到 v2，对比「原样沿用」与「标 stale + 要求重测」两种记录（在 4-2 目录执行）：
    ../4-1/.venv/bin/python - <<'EOF'
import importlib.util, copy
spec = importlib.util.spec_from_file_location("wm", "4-2-2.py")
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
bad = copy.deepcopy(m.working_memory)   # 错误版：v1 失败记录原样进 v2 的请求
bad_text = m.assemble_context(m.system_prompt, m.user_prompt, bad)["messages"][1]["content"]
good = copy.deepcopy(m.working_memory)  # 正确版：标 stale + 对 v2 重测
good["tool_results"][0]["status"] = "stale"
good["unresolved"].append("代码已变为 v2：对 v2 重新运行边界测试")
good_text = m.assemble_context(m.system_prompt, m.user_prompt, good)["messages"][1]["content"]
print("错误版 含stale:", "stale" in bad_text, "| 含重测要求:", "重新运行" in bad_text)
print("正确版 含stale:", "stale" in good_text, "| 含重测要求:", "重新运行" in good_text)
EOF
    先写预期：错误版的请求里，模型能看出「这条失败证据测的是旧版本」吗？
    预期（本机实测）：错误版 stale=False、重测要求=False；正确版两者 True。错误版里 v1 失败摘要原样出现，模型可能误判当前代码仍失败、或把旧失败当成已验证的现状。失效标记与重测要求必须显式写进记录——与 0017 实验⑥「预算拦不住污染，有效性检查才能」同构：这里装配器同样拦不住，要靠记录侧的版本纪律。

实验 ⑥：主动改造 D——拒绝分支不回写（证明验收②）

  • 探针：给一个「只看计划、不看结果」的更新函数，补上拒绝分支（在 4-2 目录执行）：
    ../4-1/.venv/bin/python - <<'EOF'
import json
def update_bad(mem, result):
    mem["completed_steps"].append("应用补丁")
    mem["next_step"] = "运行修改后的测试"
def update_good(mem, result):
    if result["status"] == "applied":
        mem["completed_steps"].append("应用补丁")
        mem["status"] = "已修改，尚未测试"
        mem["next_step"] = "运行修改后的测试"
    else:
        mem["status"] = "补丁被拒绝，代码未修改"
        mem["next_step"] = "重新准备符合约束的补丁"
rejected = {"status":"rejected","reason":"补丁目标含 tests/，违反约束"}
a = {"completed_steps": ["读取源码", "运行边界测试"]}
b = {"completed_steps": ["读取源码", "运行边界测试"]}
update_bad(a, rejected); update_good(b, rejected)
print("错误版:", json.dumps(a, ensure_ascii=False))
print("正确版:", json.dumps(b, ensure_ascii=False))
c = {"completed_steps": ["读取源码", "运行边界测试"]}
update_good(c, {"status":"applied"})
print("正确版·成功分支:", json.dumps(c, ensure_ascii=False))
EOF
    先写预期：Runtime 拒绝后，错误版的 completed_steps 和 next_step 变成什么？为什么「沿原计划进入修改后验证」是事故？
    预期（本机实测）：错误版 completed_steps 多出「应用补丁」、next_step 指向「运行修改后的测试」——代码根本没改；正确版「补丁被拒绝，代码未修改」+ 重新准备补丁；成功分支才写「已修改，尚未测试」。拒绝不回写，状态与事实分叉，后续每轮都建立在谎报上（图 3 的拒绝分支）。
