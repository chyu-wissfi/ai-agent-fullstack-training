第一部分：精讲（先读，测验在后）

0. 开篇地图：第三章在解决什么问题

第三章的核心问题（笔记开篇）：一个需要搜索、阅读、修改、验证和纠错的长任务，Agent 怎样持续推进，并在中断、审批和异常之后仍然知道自己做到了哪里。整章沿一条连续主线展开，七个小节各管一段（这张表建议记在脑子里，后面每课都会在其中推进一格）：

3.1 Agent Loop       Tool Result 回来以后怎样继续？什么时候停止？   ← 本课，重点展开
3.2 Planning         复杂目标怎样拆步骤，计划怎样修订？
3.3 State/Checkpoint 任务状态怎样持久化，中断以后怎样恢复？
3.4 Sandbox          文件、Shell、网络和凭证能力怎样划定执行边界？
3.5 Agent Harness    模型、工具、状态、上下文、环境、审批怎样连成完整系统？
3.6 LangGraph        分支、并行、人工中断、循环、可视化怎样显式编排？
3.7 Codebase Agent v2 仓库工具与真实任务怎样组成完整项目闭环？

七节不是七个独立知识点：Loop 解决「怎样继续」，但没有计划就容易忘记目标；计划和证据需要保存（State/Checkpoint）；Agent 能真正操作文件和进程后需要 Sandbox；组件分别正确不等于接起来正确（Harness）；流程出现复杂分支、长时间等待人工和循环时需要显式编排（LangGraph）；最终所有能力汇到 Codebase Agent，由两类真实仓库任务验收。本课先让 Agent 真正循环起来；后面每课在这条线上推进一格。3.1 自己只预留接口（Snapshot、prepareNextTurn），不实现。

1. 为什么需要 Loop：不是步骤多，是新事实

Chatbot 问一次答一次；Agent 可能连续执行几十步——但「步骤多」不是需要 Loop 的理由。真正的理由（PDF p6）：代码理解任务开始时，Agent 不知道代码是什么语言、路由文件在哪、登录函数叫什么、有没有中间件、用的 ORM 还是裸 SQL。它不能一开始就制定完全可靠的固定计划，只能通过观察逐步获取事实，而下一步依赖上一步产生的新事实。

一句话锚点：复杂任务需要 Loop，不是因为步骤多，而是因为下一步依赖上一步产生的新事实。

控制权从用户移交给了模型，人的工作方式也变了——PDF p1 引用 Peter Steinberger 的「You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents」：不是不再写提示词，而是人的关注点从「逐轮提示」上移到「设计触发、反馈和验收系统」。同时注意边界：Loop 不替代 Prompt、Context 和 Harness，而是在它们之上增加控制层。

什么样的任务适合自主 Loop（PDF p3）？三个条件：目标清晰、结果可验证、过程能持续产生新证据并逐步收敛。「把 CLI 迁移到另一种语言并用功能清单+编译+测试验收」适合；「把 UI 做得更好看」没有客观完成标准，不适合。另外区分两层含义：任务内循环（一次 Run 内部观察→决策→调用→读结果→再决策）和任务外循环（什么事件触发 Run、结束后何时再启动、谁判断目标真正完成）——分清两层，就不会把定时任务、Sub-agent、Memory、Workflow 全混进 Agent Loop 里。

2. 五个对象：面试的第一张必答题

教师 PDF p6 给的是四层区分（Function Calling / Tool Runtime / Agent Loop / LoopGuard）；学习笔记把它扩成五个对象，补上 Harness——因为 3.5 整节都在讲 Harness，从第一课就把它放进地图，后面每课都在给这一行添内容。这张表是本课最核心的地图，也是面试官区分「调过 SDK」和「理解架构」的第一题：

对象              负责回答的问题                    示例
─────────────────────────────────────────────────────────────────────
Function Calling  模型怎样表达下一步动作？           「调用 search_code，搜索 auth」
Tool Runtime      这一次动作能否执行，怎样执行？     校验路径、权限、超时并运行搜索
Agent Loop        Tool Result 回来以后怎么办？      把命中结果交给模型，继续读文件
LoopGuard         整个 Run 还能不能继续？           最大轮数、重复动作、总时间
Harness           这些组件怎样围绕同一任务协同？     装配模型、工具、状态、上下文和执行环境
─────────────────────────────────────────────────────────────────────
一次工具调用的边界：Tool Call → 校验 → 授权 → 执行 → Tool Result
一次任务的执行边界：Run 开始 → 多轮模型与工具交互 → 完成/停止 → Run 结束

Why（怎么记）：Function Calling 管「表达」，Runtime 管「执行」，Loop 管「衔接」，Guard 管「刹车」，Harness 管「装配」。Loop 增加的是连续执行能力，但每一步仍然走第二章建好的 Runtime——循环不能绕过参数校验、权限、超时、审计和结果治理。这是第二章不变量 I3（唯一执行入口）在 Loop 时代的延续。

笔记还给了这张表的另一个视角——LoopEngine 管什么：它不替模型思考，负责让模型的连续思考和行动能够启动、反馈、收敛并安全停止，至少管理五件事：① 组装本轮 Context；② 调用模型；③ 分发 Tool Call；④ 回写 Tool Result；⑤ 决定继续还是结束。本课的主角 LoopGuard（最大轮数、重复动作检测、取消信号、完成契约）全部属于第⑤件事下的控制机制——面试里这句「不替模型思考」是加分点：宿主控制循环的安全，模型决定循环的内容。

3. pi 的最小循环：两种判断 + 工程保护

不需要从头写 Loop（PDF p6）：复用 pi、Codex 等成熟框架，只有适配特定基础设施时才自己实现。pi 的核心判断只有两种（PDF p7）：

async function runAgentLoop(context, config) {
  while (true) {
    const assistant = await streamAssistantResponse(context, config);
    context.messages.push(assistant);

    if (["error", "aborted"].includes(assistant.stopReason)) return;   // 判断②异常停止

    const calls = assistant.content.filter(x => x.type === "toolCall");
    if (calls.length === 0) return;                                    // 判断①协议停止

    const results = await executeToolCalls(calls, config);
    context.messages.push(...results);                                 // 写回 Context

    if (await config.shouldStopAfterTurn?.({ assistant, results })) return;
  }
}

即：Assistant Message 有 Tool Call → 执行工具并进入下一轮；没有 → 当前工具循环结束。真正有价值的不是这个 while，而是循环中的工程保护——长循环最容易错的地方（PDF p8）：内外两层循环混淆、流式占位消息顺序、执行前准备缺失、执行后收尾缺失、事件与取消缺失。后面 LoopGuard 和钩子装配就是在补这些保护。

4. Turn 与 Run：事件让循环可观测

一轮 Turn（PDF p8）：turn_start → Assistant 流式生成 → 零或多个 Tool Call → Tool 执行 → Tool Result Message → turn_end。一次 Run 包含多个 Turn，事件序列是：

agent_start
 ├─ turn_start
 ├─ message_start / update / end
 ├─ tool_execution_start
 ├─ tool_execution_end
 ├─ Tool Result message_start / end
 ├─ turn_end
 ├─ turn_start ……（下一轮）
 └─ agent_end

Why（事件有什么用）：Loop 决定循环能否运行，事件决定运行过程是否清晰、可观测、可干预。统计轮数、记录工具动作、观察模型和工具是否卡住、支持 Trace/UI/Checkpoint/人工接管，全都挂在事件上。对应代码：装配层 observeEvent()（src/agent-runner.ts:126）只记录不改推进——观察者不干预，是 Loop 和事件系统的分工。

5. 协议停止 ≠ 业务完成：本课最重要的分层

模型不再调用工具，只说明协议层准备停止，不等于业务层任务完成（PDF p9）。它可能是：已经完成 / 没找到目标 / 忘记写交付物 / 只读了部分代码 / 调用出错后提前结束。所以业务完成要由上层判断，分三层（PDF p14–16）：

第一层：协议停止信号    Assistant Message 无 Tool Call（pi 原生，只代表"模型不打算再调工具"）
第二层：最大轮数        max_turns——安全边界，不是完成条件；到上限必须明确报告
                        stopped / MAX_TURNS_EXCEEDED / completed:false，不能伪装成成功
第三层：业务完成条件    Completion Contract——由可验证的工程事实组成，写成可测试的代码
第四层：不可继续的运行  aborted / 用户取消 / 超轮数超时 / 不可恢复权限拒绝 /
                        重复动作 / 需人工确认但拿不到确认 → 不应继续调模型

完成契约的真实实现（src/loop-guard.ts:161 verifyCompletion()）：读取源码 ≥ 3 个 + 目标产物已写入，返回缺失项列表而不是布尔值——为什么？缺失项会被 Follow-up 消息逐条带回给模型，模型知道具体补什么；布尔值只能拒绝，模型会盲试。证据规则也在这层：证据只能来自成功的工具结果（observeToolResult，`loop-guard.ts:103`），模型在文本里声称「已读取」「已写入」不构成证据——和 Week02「调用成功 ≠ 目标完成」是同一句话。

当模型提前 Final 但证据不足：Host 拒绝 Final，注入一条用户角色的 Follow-up（稳定标识 FINAL_REJECTED + 缺失项清单），让 Agent 继续补证据。关键：Follow-up 属于同一个 Run，不重置轮次与动作计数——否则模型可以用「提前结束再重来」刷掉计数，保护全部失效。

停止的最后一级是把原因讲清楚（笔记 6.3）：至少区分三类结果——完成（契约通过、交付物存在且证据有效）、等待用户（需要补充信息、审批或决策）、主动停止（预算耗尽、取消、权限阻断或不可恢复错误）。锚点：停止自动执行不等于失败，更不等于成功——界面和日志都要说清具体是哪一种，调用方才能决定重跑、等待还是放弃。注意「等待用户」是一类：3.3 的人工接管和 3.5 的审批门禁都会落在这一格。

6. LoopGuard 走读：Run 级停止决策中心

src/loop-guard.ts 只做四件事（PDF p27）：①第三次相同动作不执行；②达到最大轮数停止；③从成功工具结果收集证据；④证据不足时拒绝 Final 并 Follow-up。边界：不调模型、不执行工具、不碰文件系统、不实现 Planner/状态机/Checkpoint/Sandbox。

停止判定顺序，不可调换（loop-guard.ts:123 afterTurn()）：

1) 已存在停止原因      → 立即停止
2) 达到最大轮数        → 以最大轮数原因停止
3) 本轮无工具结果      → 模型准备自然结束 → 执行完成校验
   ├─ 契约满足         → COMPLETED 结束
   └─ 契约不满足       → 生成 FINAL_REJECTED Follow-up，继续
4) 本轮有工具结果      → 允许继续

Why（顺序为什么不能换）：①放最前——一旦发生过 REPEATED_ACTION，后续任何判定都不能把 Run 拉回来，刹车踩了就是踩了；②在③前——轮数是硬预算，完成校验是软判断，硬边界必须先于软判断，否则超限的 Run 会多跑一轮；③只在「无工具结果」时触发——有工具结果说明模型还在干活，此时打断它做完成校验没有意义。停止原因一旦设置不得被后续覆盖（stop() 私有方法的 if 守卫，`loop-guard.ts:194`）：先触发停止的事实必须被如实保留，否则事故复盘会看到被覆盖过的假原因。

动作指纹去重（`loop-guard.ts:202`）：动作 = 工具名 + 规范化参数（递归排序对象字段后 sha256）。规范化复用第二章「审批参数摘要」的实现——字段顺序不同但语义相同的参数必须得到同一指纹，否则换序就能绕过检测。第一次与第二次允许执行，第三次在 Runtime handler 之前被阻止（beforeToolCall 钩子里先累加计数再判断，`loop-guard.ts:85`），并设置 REPEATED_ACTION 停止原因。为什么必须在 handler 前：重复动作的代价不只是浪费 token——如果工具带副作用（写文件、提交代码、触发外部操作），执行了才有「拦住」的意义就晚了。验收证据也由此而来：证明拦截真生效的唯一证据是 handler 实际只执行了两次，而不是错误码出现了（错误码可以伪造，执行次数伪造不了）。

相同动作一定是死循环吗（PDF p18）？不一定：run_test("pytest tests/test_login.py") 第一次失败、第二次通过——同一动作在不同上下文产生不同结果。所以动作指纹只是保守的入门保护，真正判断进展要问六个问题（笔记 7.2）：文件版本有没有变化、测试结果有没有变化、已验证事实有没有增加、计划步骤有没有推进、错误原因有没有变化、是否出现 A、B 两种动作来回切换的振荡。确认停滞时的处理也不是立刻杀掉：先给明确反馈，允许有限次调整策略；仍然没有新证据，就结束并报告卡在哪里。3.1 只实现最小去重，为 Plan 和 State Machine 打基础。

7. 装配与时序：Guard 怎么接进 pi 原生 Loop

src/agent-runner.ts 是纯装配层：创建运行状态 → 创建 LoopGuard → 创建 Runtime 与执行上下文 → 把 Runtime 适配成 pi 工具 → 构造 Context（System Prompt + 工具列表）→ 构造用户任务 → 接入钩子 → 调用 pi 的 runAgentLoop()。禁止自建循环（不变量 I5）：底层循环完全由 pi 提供，全工程只有一条模型循环和一条工具执行路径。钩子接入表：

pi 钩子                  接的 Guard 方法            职责
────────────────────────────────────────────────────────────────
beforeToolCall           guard.beforeToolCall       重复动作保护（handler 前拦截）
afterToolCall            guard.observeToolResult    收集成功证据
shouldStopAfterTurn      guard.afterTurn            停止判定（四步顺序）
getFollowUpMessages      guard.drainFollowUps       自然停止时注入 FINAL_REJECTED
prepareNextTurn          （空实现）                 为 3.3 Checkpoint 预留位置
getSteeringMessages      返回空集合                 运行中转向（本课不用）

pi 的实际调用时序（PDF p30，安装版本 0.84.4，课件按 0.83.0 描述）：

turn_end → prepareNextTurn → shouldStopAfterTurn → getSteeringMessages
         → （若自然停止）getFollowUpMessages

Why（这个时序为什么值得记）：完成校验发生在 shouldStopAfterTurn，而它排在 prepareNextTurn 之后——所以证据必须在本轮 Tool Result 更新之后完成校验才能读到（本课证据在 afterToolCall 收集，天然满足；将来证据若挪到 prepareNextTurn 更新，这个顺序就是坑）。这也是 PDF 反复要求「核对实际安装版本的钩子顺序，与 readme 描述比对，差异写进报告」的原因：钩子顺序是框架实现细节，不实测就会踩。

steering 与 follow-up 不是一回事（笔记 4.4）：运行中用户补充一句「这次只看移动端入口」，属于 steering——pi 在当前轮次与工具处理结束后的安全边界接收它，影响后续决策；用户说「分析完再补一份接口清单」，更适合排进 followUp——当前工具循环准备自然停止时再接着处理。本课的 FINAL_REJECTED 走的正是 follow-up 通道（getFollowUpMessages 只在自然停止时被调用，与上面时序图对上）。两者都属于本次执行的消息处理，不等同于定时调度（那是任务外循环的事）。

工具执行前后 Hook 的准确位置（笔记 4.5）：执行前 prepare——pi 先找工具、兼容参数、校验 Schema，然后才调用 beforeToolCall（所以本课的重复动作拦截发生在 Schema 校验之后、真实 handler 之前）；执行后 finalize——调用 afterToolCall，允许截断、脱敏或标记错误。两条容易忽略的规则：① 准备失败会形成错误 Tool Result（不会静默丢掉这次调用）；若要提前终止请求，只有当前批次所有工具结果都设置 terminate: true 才触发批次终止；② 即使工具并行执行，回写也按原 Tool Call 顺序组织——模型看到的结果顺序与它发起调用的顺序一致。另外，模型、Hook 和工具收到同一个 AbortSignal——中断才能沿整条执行链传播，而不是只停止界面输出。

另外注意两个装配细节：convertToLlm 只把用户/助手/工具结果消息转换给模型（System Prompt 与内部消息不混入）；maxRetries: 0——重试由 Gateway 负责（Week01 的分工），Agent 进程不重复实现。

8. ReAct 与 Plan-and-Execute：Loop 是发动机，Plan 是导航

ReAct（PDF p10）是「观察—决策—行动」闭环：观察当前结构和已有工具结果 → 判断还缺什么证据 → 提出 Tool Call → 读 Tool Result → 继续或 Finalize。它的价值不是展示模型完整思维，而是让每一步行动都有可追溯的观察依据。分工一句话：Loop 决定「要不要继续」，ReAct 决定「下一步往哪走」。

Plan-and-Execute 关注总目标拆成哪些阶段。二者可结合：Plan 管整体路线，ReAct 管执行中的局部决策。「找登录逻辑并写说明」适合 ReAct 起步（文件与调用关系未知）；「给指定函数补测试并修复」适合轻量计划 + ReAct（目标明确但要经历定位→补测试→运行→修正→回归多阶段）。本节不引入完整 Planner，3.2 再把局部决策升级为结构化、可跟踪、可修订的计划。

工程上保存什么（PDF p12）：保存可审计的动作记录（工具、参数、Runtime 是否放行、返回、新增事实、为什么继续或停止），即 ToolCall + Runtime 结果 + Tool Result + Observation + 停止依据；不保存模型完整推理过程——推理可能含隐私与无关试错、模型自述不如工具结果客观、恢复任务只需要事实和状态。这份记录结构就是第 4 节 TraceEvent 的雏形。

9. 中断与恢复：不是同一件事

中断 = 停止正在运行的模型和工具；恢复 = 从可信状态继续任务（PDF p19）。AbortSignal 把取消信号从入口传到模型流、工具和 Hook。但中断时系统可能正处于模型生成中/工具执行中/结果写回中/文件已产生部分副作用——所以中断必须配合保存点设计。重新发送原 Prompt 只是重新开始，不是恢复：重跑会重复写文件、重复提交代码、重复触发外部操作、覆盖已有结果。真正的恢复必须知道已经发生了什么，从可信保存点继续。本课只预留 Snapshot 接口（runId / messages / turn / evidence / stopCode），持久化到 3.3 实现。

10. 从 SOP 拆 Loop：五问对应表

业务 SOP 怎么变成 Agent（PDF p33–35）？依次问五个问题：

稳定规则        → System Prompt / Completion Contract   必须生成 Markdown 文档
动态决策        → LLM + Loop                            下一步搜哪个符号、读哪个文件
真实动作        → Tool Runtime                          搜索、读取、写入
硬边界          → LoopGuard                             最大轮数、重复动作
人机决策        → HITL（3.5 展开）                       修改源码前确认

Why（不要把 SOP 写成固定脚本）：直接把 SOP 翻成顺序执行程序，得到的是 workflow 而不是 Agent——它无法应对未知路径（文件位置不知道、调用链要现查）。Agent 的价值恰恰在「动态决策」那一格。本课只接四个工具（list_files / search_code / read_file / write_file），笔记给了它们的后续增强路线：list_files/write_file 的完整文件边界与 Sandbox 在 3-4、search_code 的搜索策略在 3-7、read_file 的 Context 管理在第四章——工具清单跟着任务走，每个工具的「最小版」和「完全版」在这张路线图上对号入座。

11. TDD 验收：怎么证明规则不是摆设

只看最终生成的 Markdown，只能证明模型会写字；要证明 Loop 按预期运行，需要两层测试（PDF p36）：脚本化测试（稳定复现边界条件）证明机制存在，真实集成测试（真实 Gateway + 模型）证明机制能工作。六个行为验收场景（tests/loop.test.ts:86 起）：

场景一 · Tool Result 回写    第二轮 Context 有 toolResult 消息，toolCallId 与原 Call 对应
场景二 · 拒绝提前完成        无证据 Final → 注入 FINAL_REJECTED → 补齐后成功结束
场景三 · 重复动作拦截        三次相同调用，第三次在 handler 前被阻止，handler 恰执行 2 次
场景四 · 最大轮数            maxTurns=3，模型调用恰 3 次，无第四次
场景五 · 取消传播            abort 后以取消原因结束，之后不再开始任何工具执行
场景六 · 完整闭环            搜索→读 3 文件→写产物→引用路径真实存在，轨迹可按
                             runId/turn/toolCallId 还原

注意断言的口味：全部指向可观测的行为事实（调用次数、消息内容、handler 执行次数），而不是内部状态或模型自述——这是 Week01「有证明力的断言」在 Loop 层的延续。

12. 面试视角：这一课怎么被问

  • 「Agent Loop 的停止条件怎么设计？」——答分层：协议停止（无 Tool Call）只是信号；业务完成靠 Completion Contract 校验，不足则 FINAL_REJECTED Follow-up；最大轮数是安全边界不是完成条件，到限必须如实报告 stopped。追问「为什么不直接信模型」→ 模型可能没找到目标/忘记交付物/出错早退，且 Follow-up 不重置计数，防止刷保护。
  • 「怎么防 Agent 死循环？」——动作指纹（工具名+规范化参数）计数，第三次在 handler 前拦截；追问「相同动作一定是死循环吗」→ run_test 二次通过的反例，生产级要看新事实是否产生。追问「怎么证明拦截生效」→ handler 执行次数=2，不是看错误码。
  • 「Agent Loop 和 Function Calling 什么关系？」——五个对象表：表达/执行/衔接/刹车/装配；强调 Loop 不绕过第二章治理（I3 唯一入口在循环里继续生效）。追问「宿主侧的 Loop 控制层替模型思考吗」→ 不替：LoopEngine 只管启动、反馈、收敛、安全停止（组装 Context、调模型、分发 Tool Call、回写结果、决定继续还是结束），模型决定循环的内容。
  • 「中断以后怎么办？」——中断≠恢复，重发 Prompt 会重复副作用；恢复要从可信保存点（Snapshot）继续，3.3 展开。
