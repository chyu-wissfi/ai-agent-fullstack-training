State Machine 与 Checkpoint：中断之后，凭什么接着做

本课定位：Week03 第三课。0010 让 Agent 循环起来并停得住，0011 让任务有了可验收的计划；这一课回答更硬的问题——进程死了、人工暂停了、审批卡住了之后，下一个进程凭什么知道做到哪、哪些动作真的发生了、现在允许做什么。会话历史只记录「聊过什么」，计划只记录「准备做什么」，两者都不等于「实际发生了什么」。本课补上任务状态机、步骤执行记录、业务 Checkpoint、人工审批与恢复判定。

0. 开篇：一个「差一点就对了」的事故

Agent 正在修一个登录模块的会话过期边界问题。它已经读完源码、复现了失败测试、生成了补丁，并且把补丁写进了 session-policy.ts。就在工具返回之后、这一轮的 Checkpoint 还没写下去的时候，进程被杀了。

重新启动后，恢复程序看到两个互相矛盾的事实：磁盘上是修改后的代码，存档里却还写着「补丁尚未完成」（笔记 3.3 二 2.1）。如果相信存档、直接按旧进度继续，Agent 可能重复打补丁；如果相信磁盘、直接把修复步骤标成完成，又拿不出当前代码版本上的测试证据。两种做法都在猜。

这一课要建立的，就是「不猜」的能力。恢复不是把聊天记录加载回来接着聊，而是从持久化的事实和重新核对过的现场里，推导出下一个可辩护的动作（图 1）。

为什么不能只靠会话历史：大模型的上下文是「对过去对话的压缩重建」，不是数据库事务日志。它可能记得自己说过「我要改文件」，但不能证明文件真的改了；可能记得工具返回「成功」，但不能证明测试通过。把会话历史当恢复依据，等于用「叙述」替代「事实」——叙述会漏、会错、会被压缩掉。恢复必须让程序能独立核对：计划到哪一步、动作有没有闭合、工作区是不是原来那个。

1. pi 的会话持久化：它恢复的是「聊过什么」

pi 自带会话持久化和续接能力（笔记 3.3 一）：启动时指定会话目录，运行结束后目录里会生成 JSONL 文件，一行一条记录，可能包含消息、会话信息和其他会话条目。结束进程后，用同一个工作目录和会话目录，通过 -c / --continue 就能续接；-r / --resume 打开会话选择器，--session-id 精确指定会话，--fork 派生新会话，--session-dir 指定存档目录，--no-session 关闭持久化。

两个容易被忽略的事实：① --fork 复制的是会话，不会自动还原代码工作区；② 会话发生过压缩时，续接重建的是「压缩摘要 + 保留下来的消息」，不是把全部历史原样塞回去。也就是说，连「聊过什么」都不保证逐字还原，更不用说业务现场。

所以笔记给了一句很重的话：它能找回之前聊过什么，暂时不能证明业务任务恢复到了可靠现场。会话持久化解决的是「模型别忘了上下文」，业务恢复解决的是「任务别做错、别重做、别漏做」——两个问题，两套记录。

2. 为什么存档会和现场对不上：两次写之间的空当

补丁工具的典型执行顺序是（笔记 3.3 二 2.1）：

修改文件
    ↓
更新内存版本计数
    ↓
工具返回
    ↓
轮次边界保存 Checkpoint

这四步不是原子的。补丁已经写进 session-policy.ts，新的执行结果和版本信息还没保存，进程就可能退出。恢复时于是看到：磁盘上是修改后的代码，存档里仍记录「补丁尚未完成」。

由此得到两条必须分开的命题：

  • 「存档里没有成功记录」不等于「动作没有发生」——动作可能已经落盘，只是结果没来得及写进存档。
  • 「动作发生了」也不等于「结果已知」——可能只写了一半文件、只启动了一半子进程，或者写成功但工具结果丢了。
为什么不能把 Checkpoint 当数据库事务：文件系统和存档文件是两个独立的存储，没有一个横跨两者的原子提交。即使你「每轮都存」，每轮内部仍有窗口；即使你「每个工具调用都存」，写文件和写存档之间仍有窗口。既然无法消除窗口，正确的设计就不是「假设同步」，而是让不同步可被发现：存档里记工作区摘要与代码版本，恢复时重新计算并比对；对不上的动作记为结果不明，禁止自动重放。这样窗口不会消失，但不会变成静默的错误。

3. 中断信号：能停下什么，不能回滚什么

AbortSignal 把「本次执行需要停止」的信号传给模型调用、循环和工具，相关组件在能响应的位置检查信号并结束自己的工作（笔记 3.3 二 2.2）。但有三点必须分清：

  1. 信号是一次性的：同一个信号一旦中止，不能恢复为未中止；下一次执行要用新信号。
  2. 停止能否及时生效，取决于执行环节是否支持取消：信号传给工具，工具内部还要配合处理；一个正在写文件或跑子进程的工具，未必能立刻停下。
  3. 停止过程需要收尾消息和工具结果：突然断电或强制杀进程时，不能保证收尾完成。

所以笔记有一句关键判断：中断不是回滚。已经写入的文件不会因为发出中断信号就自动恢复，已经启动的子进程也需要明确的终止或隔离策略。更细一层，要区分三件事（笔记五 5.3）：用户已经请求停止、Agent 不再发起新操作、已经启动的操作确实结束。页面不再输出日志，只能证明第一件或第二件，不能证明第三件。Promise.race 可以提前结束等待，但它不会自动停止另一个 Promise 背后的操作。

为什么这会影响恢复设计：如果误把「收到停止信号」当成「世界已经回到停止前」，恢复时就会在一个半修改的工作区上继续。正确做法是把「停止请求」「停止原因」「哪些操作已启动 / 已闭合」都落进业务记录，让恢复程序自己判断现场，而不是相信「停过了，应该没事」。

4. 业务层至少要补的四类信息

除了会话历史，业务层至少还要保存或关联四类信息（笔记 3.3 二 2.3）。这四类正好对应恢复时必须回答的四个问题：

  • 计划与步骤进度——哪些步骤已经完成，下一步准备做什么（我现在在哪？）。
  • 工具执行记录与证据——动作是否成功，测试结果是否完整可信（到底发生了什么？）。
  • 工作区标识与代码版本、摘要——现在的代码是否与保存时一致（世界还是那个世界吗？）。
  • 待审批动作与人工决定——哪些动作仍在等待确认，已有批准是否适用（我现在允许做什么？）。

注意一个边界：保存工作区标识和摘要，不等于把整个工作区备份下来。前者用于核对现场；如果需要回到旧代码，要另外准备 Git 提交、快照或独立工作区。把「摘要」当「备份」，是恢复设计里最常见的概念混淆之一。

5. 任务状态机：九个状态，不是九个步骤

最直接的做法是给任务加一个 status 字段，例如准备修改代码但还没批准时写 status = "waiting_approval"。但只有一个状态字段，还不算状态机；还要规定发生什么事情之后，状态才能改变（笔记 3.3 三 3.1）。笔记给出九个状态：

created            收到任务，还没开始处理
planning           正在建立或整理计划
running            正在分析结果、决定下一步
waiting_tool       已发起工具调用，正在等待结果
tool_failed        某次工具调用失败，需要判断如何处理
waiting_approval   某个动作尚未获批，等待人工决定
completed          修复和约定验证均已完成
failed             本次任务无法继续，未完成交付
cancelled          用户决定结束本次任务

这九个状态不是必须依次走完的九个步骤。不需要审批的任务不会进入 waiting_approval；一个任务调用多次工具，会多次进入和离开 waiting_tool。两个最容易混淆的问题：

工具失败，是不是整个任务就失败了？不一定。读取文件路径写错，可以先记 tool_failed，再搜索正确路径重新读取；只有达到停止条件——重试预算耗尽、缺少权限且无法解决——才把整个任务记为 failed。还要区分「测试工具执行成功」和「测试通过」：测试命令正常运行并拿到失败日志，说明成功获得了测试结果，但代码仍然有问题。

暂停了，是不是应该记为 cancelled？不是。暂停表示这次先停、之后还要继续；取消表示这个任务不做了。本例把两件事分开：任务状态记录中断前处于什么阶段（例如 running），停止原因记录为什么停下来（例如 INTERRUPTED）。「任务状态：running，停止原因：INTERRUPTED」表示任务在执行阶段被打断，目前没有继续运行，但任务还没有结束。

状态由程序根据实际事件和业务规则修改：工具开始执行、工具返回结果、用户批准、验收通过，都是更新依据。模型可以提出建议，但不能仅凭一句「我完成了」把任务改成 completed（笔记 3.3 三 3.1）。

对照代码时要注意一个差异：笔记给的是九态，本节的 RunStatus 只有七个值（task-record.ts:21-28）：running、waiting_tool、waiting_approval、suspended、completed、failed、cancelled。映射关系是：

  • created / planning 在 demo 里不表现为 RunStatus——任务记录创建时就是 running，计划通过 create_plan 工具建立；
  • tool_failed 被记在步骤层：StepRecord.failures、ToolCallRecord.ok=false、nextDecision，Run 本身仍可以是 running，是否停由重试/停止规则决定；
  • suspended 是 demo 对「不是失败的暂停」的收口：APPROVAL_REJECTED、RESULT_UNKNOWN、REPEATED_ACTION、MAX_TURNS_EXCEEDED、MODEL_ERROR 都落在这里（task-record.ts:171-181）。

笔记没有逐条解释 demo 为什么合并状态；这是从代码可以读出的实现映射。考试和面试以笔记九态为准，读代码时要能说出「哪一态被放到了哪一层」——这本身就是比背状态表更深的考点。

为什么「带显式迁移规则的状态机」比「只有一个 status 字段」更好：这里比较的是两种任务状态管理方式，不是「类 vs 字符串」。方式 A：只保存一个 status 字段，任何代码都能改、改成什么都行；方式 B：状态集合固定、迁移由事件触发、迁移路径有约束、每次迁移留痕、终态有明确语义、状态可存档恢复。status 字段两种方式都有，而且都可以是字符串——状态机不是另一种数据结构，而是对字段怎么变化的一组约束。方式 A 只能回答「现在是什么」，方式 B 还能回答「怎么变成这样的、接下来允许变成什么」：模型一句「完成了」不能把 failed 改成 completed，等待审批、暂停、失败、取消也不会被混成一个状态。

6. 步骤执行记录：换一个人接手也能看懂

任务状态说明当前阶段，步骤执行记录说明具体做过什么、结果怎样、还差什么（笔记 3.3 三 3.2）。一次工具调用至少记录：属于哪个计划步骤、调用哪个工具、传入什么参数、toolCallId、返回结果或错误、失败后的下一步决策、重试次数与预算消耗。代码里的 ToolCallRecord（task-record.ts:63-79）与 StepRecord（task-record.ts:82-95）就是这些字段的实体。

为什么要保存具体参数？因为「修改会话判断」只是意图，具体补丁才说明它准备改什么；审批、排障和恢复都要查看具体内容（笔记 3.3 三 3.2）。工具执行后要保存返回结果，包括失败；比如补丁没有应用成功，工具返回「找不到需要替换的原文」。后面如果再试成功，也不能覆盖前面的失败记录——这和 0010「再试成功也不能覆盖前面的失败记录」是同一条不变量，只是从停止原因下沉到了步骤记录。

更重要的是区分两种情况：

  • 已知失败：工具明确返回「补丁未应用」——有闭合结果，记录失败原因，可以按决策重试或换路径。
  • 结果不明：工具发起后进程退出，没有拿到结果——不能直接写成「执行失败，所以可以重试」。文件可能已经改了，只是成功结果没来得及保存。
为什么记录必须在执行前落：如果等工具返回后再写记录，进程在返回前死掉就什么都不剩——恢复时无法区分「这个动作从没开始」（可以安全执行）和「动作已经开始了但结果丢了」（绝不能盲目重放）。beginToolCall() 先落一条 startedAt、endedAt 为空的记录，才让「结果不明」成为可判定状态（task-record.ts:367-396）。这是整课最重要的一个实现细节：可恢复性不是恢复时补出来的，是执行时提前留下的。

7. Checkpoint：存档里到底装什么

Checkpoint 可以理解成任务存档：把当前进度和恢复依据保存下来，让下一个进程知道从哪里接着处理（笔记 3.3 三 3.3）。一份可用存档至少要回答七个问题：原始目标和约束是什么；当前计划、步骤状态和修订历史是什么；哪些工具已经执行、结果如何、有没有结果不明；当前工作区、代码版本或内容摘要是什么；有哪些待审批动作和人工决定；已用轮数、重试次数、Token、费用和时间预算还剩多少；会话记录对应哪个引用。

代码把它收进一个带元数据的信封（checkpoint.ts:45-71）：

CheckpointEnvelope {
  schemaVersion: 2          // 存档结构版本
  runId                     // 恢复的是哪次运行
  createdAt
  seq                       // 第几份存档，跨进程延续
  payload: {
    task: TaskRecord        // 状态、步骤记录、计数、待审批、决定、迁移历史
    plan?: PlanSnapshot     // 计划与修订历史
    evidence: Evidence[]    // 工具执行留下的证据
    session: {
      messages              // 会话历史（恢复时回灌给 pi）
      sessionId?            // pi journal 中的会话引用
      lastOperationId?      // 上次已闭合的操作
    }
    workspace: {
      id / repoRoot / projectRoot
      codeRevision          // 上次存档时的代码版本
      repoDigest            // 目标源码 + 相关测试的摘要
    }
  }
  checksum: sha256(stableStringify(payload))
}

几个字段的 why 值得单独说：

  • schemaVersion 与 codeRevision 不是一回事：前者说明存档用哪种数据结构、当前程序是否支持读取；后者说明工作区代码是哪个版本。格式版本不兼容要拒绝读取，代码版本不一致要核对现场，两个判断不能合并。
  • checksum 防的是「看起来合法」的损坏：JSON 能解析、字段也在，不代表内容没被截断或改写；loadCheckpoint 用稳定序列化重算摘要，不匹配就按损坏处理（checkpoint.ts:225-231）。
  • seq 是跨进程的存档序号：恢复后写出的第一份存档接着旧编号，不重置为 1；读取时还要校验它和 payload.task.counters.checkpoints 一致（checkpoint.ts:219-224），否则说明信封和业务对象不是同一次写的。
  • repoDigest 只覆盖目标源码 + 相关测试，不是全仓摘要。代码注释给了理由：全仓摘要会被 node_modules、临时文件干扰，导致恢复时误判（checkpoint.ts:102-109）。这是一个「摘要范围要跟恢复判断相关」的设计取舍。
为什么存档不能只存「任务状态 + 最后一条消息」：恢复需要同时回答「我在哪」「发生过什么」「世界变没变」「我允许做什么」。只存状态，你不知道哪些证据可用；只存消息，你不知道动作有没有闭合；只存工作区，你不知道计划与审批。Checkpoint 的价值不在于「存了很多」，而在于每一类信息都对应一个恢复判断。这也是为什么信封要分 task / plan / evidence / session / workspace 五块，而不是揉成一个大对象。

8. 什么时候保存，怎样避免半份存档

不能只在程序退出时保存——进程突然崩溃，就没有机会执行退出前的保存（笔记 3.3 三 3.3）。本例主要在完整轮次结束后保存；准备停下来等待审批时，也要先保存待确认动作和任务状态。保存越频繁，通常进度越新，但写入和一致性处理也更复杂；教学版本采用明确保存边界，不追求任意时刻中断都能原样接上。

尤其注意：修改代码和保存 Checkpoint 是两次操作。补丁可能已经写进文件，但新的存档还没保存，进程就退出了。因此，即使有 Checkpoint，也不能保证存档永远与实际代码同步——这正是第 2 节那条时间线的来源。

为了避免写出半份存档，代码采用「先写临时文件，再 rename 替换正式文件」（checkpoint.ts:156-164）：rename 是原子的，读者要么看到旧档，要么看到完整新档，不会看到写了一半的 JSON。存档还带两个信息：格式版本（说明数据结构，当前程序是否支持读取）和校验和（检查内容是否损坏）。保存和校验还要遵守同一套数据表示规则：没有值的可选字段统一省略或统一写成 null，不要两边不同；否则同一份内容会算出不同摘要。

如果新存档保存失败，应停止继续推进任务，报告原因，并保留最近一份有效存档（checkpoint.ts:165-172）。不能一边提示保存失败，一边继续修改代码——那会把「最后一个可恢复点」也毁掉。

为什么「保存失败」必须升级为停止条件：很多人会把存档当日志：写失败就打一行 warning，任务继续跑。但日志丢了可以补，恢复点丢了不能补。继续修改代码意味着工作区与最后一份有效存档的差异越来越大，之后即使想恢复，也无法判断哪些改动是存档之后发生的。正确策略是「保存失败 → 停止推进 → 保留旧档 → 报告」，把一次可恢复的失败变成一次明确的暂停，而不是一次不可恢复的继续。

9. 恢复五步：先把模型挡在门外

恢复流程固定五步（笔记 3.3 三 3.3、代码 resume.ts:103-119）：

  1. 检查存档能不能用：文件可读、格式支持、字段齐全、校验通过。
  2. 检查工作区对不对：目录还在吗，相关文件变了吗，上次有没有结果不明的操作。
  3. 检查任务是否允许继续：已完成或取消的任务不再续跑，等待审批的任务不能因重启绕过审批。
  4. 还原业务对象：计划、步骤记录、执行证据、审批信息和运行计数。
  5. 再让 pi 继续执行：准备有效上下文后，调用续跑能力。

顺序可以压成一句话：先读存档，再核对现场，确认允许继续，还原业务状态，最后启动模型。恢复不是把程序搬回上次暂停的那一行代码；启动的是新进程，它根据保存的信息重新判断下一步，上一次测试命令的调用栈或子进程不会自动恢复（笔记 3.3 三 3.3）。

为什么模型必须最后启动？因为模型一启动就可能发起工具调用。如果存档损坏、工作区不一致、任务已经终结或还有待审批动作没决定，先启动模型意味着它可能在程序发现这些问题之前就写出新的副作用——本来只是「恢复不确定」，变成「又改了一轮」。把模型放在最后，是把「检查」变成「前置条件」，而不是「事后告警」。

恢复时还要对「上次动作」做三态判定（笔记五 5.4）：

  • completed：有闭合记录（operation_finished / 步骤已 completed）——恢复真实结果，继续后续验证，不重复修改。
  • not_started：没有任何该动作的启动记录——满足原有条件后，才可以重新执行。
  • unknown：有启动记录但没有闭合记录（含「补丁已落盘、存档未写」）——保留未决事项，继续核查或交给人处理。

代码里的 inspectResumeState（resume.ts:103-252）把这几类检查落成具体判断：存档摘要与工作区不一致 → unknown；journal 里有 tool_started 但没有完成记录 → 写操作 unknown（读操作 replay:"safe" 可重放）；测试已启动但没有完整退出码 → 不得记为通过。最危险的是在第三态里随便补一个「失败」或「成功」状态——不能为了让流程「看起来完整」而伪造结论。

为什么「恢复」不是「回到上次暂停的那一行」：进程的调用栈、内存对象、子进程都不会随存档复活。新进程能做的是：读事实、核对现场、重新决定下一步。这也是为什么恢复入口要先跑 inspectResumeState 再跑 prepareResume（resume.ts:258-282）：前者只检查、不还原、不执行；后者只有在 canResume 为真时才还原业务对象。把「检查」和「执行」分成两个函数，是为了让「检查不通过时绝不启动模型」成为代码结构上的保证，而不是调用方的自觉。

10. 人工审批：批准的必须是一份具体补丁

审批必须发生在写入之前（笔记五 5.2）。补丁已经写进文件，再弹出「是否同意修改」，就失去了审批作用。本节的接入方式是：beforeToolCall 里拦住需要审批的动作，返回 { block: true }，工具调用不会执行，模型会收到相应错误结果；业务层保存待确认动作、设置 waiting_approval，并通过运行控制结束本次执行。等待期间，其他需要审批的写操作也必须继续被拦住（笔记 3.3 二 2.4）。

ApprovalGate（approval.ts）守住了几条不变量：

  • 同一时刻只允许一个待审批动作（approval.ts:85-112）：否则第二个写操作可以排在第一个后面，绕过「等待审批」的语义。
  • 批准只对对应 actionId 生效（approval.ts:136-151）：不允许拿一个批准去执行另一个动作。
  • patchHash 绑定补丁参数与目标文件内容（approval.ts:46-79）：path、search、replace 或文件内容任一变化，哈希都会变；执行前重算，不一致就抛 APPROVAL_STALE（approval.ts:172-190）。
  • 进程重启不默认获得批准：approved 只存在于做出决定的进程；TaskRecorder.restore 和 ApprovalGate.restore 都会强制把它清成 false（task-record.ts:225-231、approval.ts:123-130）。
  • 模型侧没有批准入口：批准只能来自人工 --approve 或显式的 --auto-approve；后者仍走暂存、哈希校验与落盘，只在 decisions[].by 里记成 auto（approval-flow.ts:1-9）。
为什么批准必须绑定哈希，而不是绑定一句话：如果审批只记「用户同意修改 session-policy.ts」，那么批准之后模型可以换一份完全不同的补丁、或者文件被外部改过，仍然拿旧批准去执行——人批准的是 A，落盘的是 B，审批就成了形式。patchHash 把「参数 + 目标文件当时的内容」绑成一个值：参数变了、文件变了，哈希都变；执行前重算，不一致就拒绝。这样「批准」才是一份可核对的具体授权，而不是一张空白支票。再加上进程重启强制 approved=false，才堵住「上次点过同意，这次重启直接继承」的绕过路径。

11. 接进 pi：四个接缝，不写第二套 Loop

3.3 不重写循环，只在 pi 的接缝上补业务记录（笔记 3.3 二 2.4）：

  • beforeToolCall：执行前决定是否放行；审批拦截放在这里，返回 { block: true }，handler 不执行。
  • afterToolCall：根据执行结果补充记录、审计信息和步骤证据；它返回的 terminate 要看批次语义——pi 会检查整个工具批次，只有所有最终结果都设置终止提示，才提前结束。
  • 事件订阅：agent_start、turn_start、tool_execution_start、tool_execution_end、agent_end 说明框架运行到了哪里，业务层再把这些事件关联到具体任务和计划步骤。
  • 续跑接口：runAgentLoopContinue 或 agent.continue() 提供继续执行的机制；使用前要先还原计划、证据、审批状态和运行计数，并完成工作区校验。

代码里有一个非常值得记的坑：会话历史不能存 context.messages。pi 的 Loop 内部是 {...context, messages: [...]} 的副本，从不回写调用方的这个数组；如果存档直接写 context.messages，恢复时历史可能是空的。本节的实现单独维护 history，存档写它，恢复时再回灌给续跑入口（agent-runner.ts:383-422）。测试 A8 专门断言：暂停存档里的 session.messages 非空、包含 assistant 消息；恢复后历史累积、任务输入只出现一次（checkpoint-resume.test.ts:377-441）。

续跑入口的选择也有讲究：history.length === 0 时用 prompt 重新发任务；否则用 continue 回灌历史。若最后一条恰好是 assistant，续跑前还要补一条推进提示，否则 pi 的续跑入口会直接抛错（agent-runner.ts:408-422）。这些细节说明：「恢复」不是调用一个 resume() 就完事，而是把上下文、计数、审批和现场都装配回可继续的状态。

12. TDD 验收：A1–A11 证明「恢复不是演出来的」

本节验收全部通过子进程真实执行 scripts/child-run.ts，断言落在真实产物上：存档、源码文件、交付物、状态迁移与退出码（checkpoint-resume.test.ts:1-11）。重点不是「返回了某个错误码」，而是「文件到底改了几次、轮数有没有保留、历史有没有累积」。几条主干：

  • A1 存档后崩溃：after-checkpoint:3 杀进程后，恢复保留 read 已完成、证据与轮数；续跑从后续步骤继续，已完成的 read 不被重做（test:47-94）。
  • A2 补丁已落盘、存档未写：摘要不一致 → RESULT_UNKNOWN，恢复入口 exit 3；源码中修复片段仍然只出现 1 次——没有第二次写入（test:96-143）。
  • A3 测试已启动但没有完整结果：步骤不得为 completed，恢复必须明确拒绝并给出 run_test 未决信息（test:145-173）。
  • A4 / A5 审批门：未批准时 APPROVAL_REQUIRED；拒绝后不能执行；文件被外部改动后 APPROVAL_STALE，恢复后人工批准也不落盘，源码保持不变（test:175-244）。
  • A6 存档损坏 / 任务终结：CHECKPOINT_CORRUPT / RUN_TERMINAL，入口 exit 3（test:246-303）。
  • A7 多次失败后暂停：暂停不是失败；失败历史、工具计数与预算在恢复后原样保留（test:305-334）。
  • A8 优雅暂停：--pause-after 6 后 stopCode=INTERRUPTED、状态仍是 running、read/reproduce 完成、fix 仍 pending、补丁 0 次；恢复走 continue，turn 从 6 继续，迁移序号接续，测试退出码序列 [1,1,0,0,0]（0 = 通过，非 0 = 失败），证据 ID 唯一且旧证据仍在，历史累积且任务输入只出现一次（test:339-443）。
  • A9 人工审批：停在 waiting_approval，前面的诊断与证据保留、待确认的是具体补丁、源码未被修改；没有决定时恢复只报告不启动模型；批准后 manual:1、补丁只落一次；拒绝后停在 suspended 而不是 failed（test:448-553）。
  • A10 独立工作区重跑：新运行有独立工作区与 runId，原存档字节级不变，且不继承旧批准——新运行照样停在等待审批（test:563-609）。
  • A11 同 runId 新运行：拒绝覆盖未终结存档（exit 3），原存档字节不变；换 runId 或 --resume 不受影响（test:614-665）。
为什么这些断言比「错误码正确」更有证明力：错误码是程序打印出来的，可以被错误的实现「碰巧」打印；但补丁片段出现次数、源码字节、turn 数、历史长度与顺序、证据 ID 是否重号是副作用的直接痕迹，伪造不了。A2 断言 patchCount === 1，A10 断言原存档字节级不变，A8 断言 resumedFrom.turn === 6 且任务输入只出现一次——这些才是「恢复没有重放、没有重做、没有覆盖」的证据。这也是 0005/0010/0011 一路下来的同一条验收纪律：断言真实产物，不断言叙述。

13. 面试视角：这一课怎么被问

  • 「能继续对话，为什么不算恢复了任务？」——会话是 transcript，不是 transaction：它记录说过什么，不证明工具执行过、文件改过、审批还有效。业务恢复要补四类信息：计划进度、工具记录与证据、工作区版本/摘要、待审批决定；再用摘要核对现场。
  • 「Checkpoint 保存什么、什么时候保存？」——七类内容（目标约束、计划与修订、工具记录与证据、工作区与版本、待审批与决定、预算、会话引用）；不能只在退出时存，崩溃没有退出；完整轮次结束存，进入等待审批前必须存；先写 tmp 再 rename，带 schemaVersion 与 checksum；保存失败就停止推进，保留旧档。
  • 「恢复前为什么要核对工作区？」——存档是快照，不是事务；补丁写入与存档保存有窗口，可能「磁盘已改、存档未写」。重新计算 repoDigest 与 codeRevision，不一致就判 unknown，不能拿旧进度继续，也不能直接重放写操作。
  • 「文件已修改但结果未保存，为什么不能直接重放？」——因为「没有成功记录」不等于「动作没发生」；写操作可能已经落盘，重放会造成重复修改。beginToolCall 在执行前落记录，endedAt 为空就是 unknown；unknown 只保留未决、交人工核查，不自动重放写操作。
  • 「暂停、取消、等待审批有什么区别？」——暂停是「先停，之后继续」，任务状态仍是 running，停止原因是 INTERRUPTED；取消是任务不做了，终态 cancelled；等待审批是任务在等人，waiting_approval 非终态，重启不能绕过。三者混成一个 failed，重试、计费、审计都会错。
  • 「审批怎么防止重启绕过或旧授权复用？」——approved 只在内存，恢复时强制 false；批准绑定 actionId 与 patchHash（参数 + 文件内容）；执行前重算哈希、校验锚点唯一；同一时刻只允许一个待审批；模型侧没有批准入口，auto 与 manual 只在 decisions[].by 上区分。
  • 「怎么证明恢复不是演出来的？」——A2 补丁只落一次；A8 turn 从 6 继续、退出码序列 [1,1,0,0,0]、历史累积且任务输入只出现一次；A10 原存档字节级不变、独立工作区不继承旧批准。断言真实产物，而不是断言错误码。
