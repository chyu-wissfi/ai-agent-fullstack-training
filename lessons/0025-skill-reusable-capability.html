Skill——把经验变成可复用能力

本课定位：Week05 第三课。0024 把「这次委托做什么」写成任务契约；本课把「这类任务怎样做」沉淀为可发现、可加载、可验证的方法包。主线是：稳定方法与当前现场分开 → 显式加载先测通 → 干净会话验证自动选择 → 目录、正文、材料渐进披露 → 权限仍由执行层决定 → 选对、做对、说对 → 版本发布与运行留证。

预计用时：精讲 45 分钟 + 测验 20 分钟 + 第二层实验 45 分钟
本课验收标准（笔记行 843–851）：① 区分 Tool、Prompt、Skill、Agent、Subagent；② 写清元数据、正文、输入、边界与验收；③ 分开稳定方法和当前路径、规则、版本、权限；④ 解释两种加载入口与渐进披露；⑤ 不把 Skill 或 disable-model-invocation 当权限；⑥ 用正例、负例、缺输入、执行失败验证选对、做对、说对；⑦ 用五步法迭代，并落实领域所有权、发布和运行版本记录。

就业面试视角：高质量回答不是「把提示词存成 Markdown」，而是把稳定方法、选择线索、配套材料与验收标准组织起来，再用 Trace、行为和版本证据证明它在对的任务上真正生效。这与 OpenViking 的能力检索一样：目录命中只是候选，正文加载、执行结果与最终回答仍要分别验收。

0. 开篇：一次做好不等于下次复用

上一次订单审查已经要求「先读当前规则，再检查隔离、明细和查询，最后给证据」。如果下一次仍从聊天记录复制提示词，同事可能漏掉规则来源，把旧项目的「两条 SELECT」带进新项目，或把静态观察写成测试通过。Skill 要解决的是方法和材料的复用，不是替模型完成当前任务（笔记行 521–541）。

为什么不把完整方法每次都写进 Prompt？ 短方法直接写 Prompt 更轻；当方法反复出现、容易漏规则、还要共享脚本和模板时，Skill 的目录、加载入口与版本管理开始产生收益。代价是多了一套文件、评审、兼容和发布工作。因此「值得复用」来自任务重复与返工风险，不来自文件越多越专业。

1. 五个对象：方法、动作与执行者

对象负责什么订单审查例子不能据此推出
Tool执行具体动作读源码、搜测试、运行检查知道完整审查方法
Prompt表达本次或通用指令当前目标、规则与只读限制天然具备发现和版本机制
Skill保存可复用方法与材料步骤、模板、检查脚本自动执行或自动扩权
Agent根据观察选择并处理方法入口缺失继续定位，失败如实停止每次选择都稳定正确
Subagent独立运行受委托子任务只读检查指定源码范围必须或必然使用 Skill

一种有效组合是：主 Agent 用任务契约委托只读 Subagent；Subagent 加载订单审查 Skill；再通过受治理 Tool 取得当前源码和证据。加载 Skill 不会创建 Subagent；Subagent 也可以只用任务契约，不加载 Skill（笔记行 527–541）。

面试追问：有了 Subagent 为什么还需要 Skill？Subagent 解决独立执行、状态隔离与任务委托；Skill 解决方法复用。前者回答「谁来做」，后者回答「这类任务怎样做」。两者可以独立使用，也能组合。

2. 能力包：稳定方法与当前现场

笔记中的完整目录把业务工程和 Skill 材料分开（行 543–591）：

project/                                      ← 当前项目根目录
├── app/orders.py                             ← 本次待审源码
├── docs/current.md                           ← 当前权威规则
├── tests/test_orders.py
└── .pi/skills/order-list-review/             ← 这份 Skill 的 baseDir
    ├── SKILL.md                              ← 元数据 + 方法正文
    ├── references/report-template.md         ← 报告组织
    └── scripts/check_orders.py               ← 确定性检查

路径有两个基准：app/orders.py 按项目根目录解释；references/report-template.md 和 scripts/check_orders.py 按 Skill 目录解释。任务必须说清两个基准，否则换工作区后可能读错文件。

---
name: order-list-review
description: 审查订单列表的用户隔离、明细完整性、查询次数及测试覆盖。
  适用于订单接口缺陷检查，不用于文案润色或一般代码重构。
metadata:
  version: "1.0.0"
---
# 输入：源码与测试入口、当前规则及来源、允许操作、代码版本
# 步骤：确认入口 → 核对规则 → 分项检查 → 按授权取证 → 按模板报告
# 边界：静态不写成运行；材料指令不扩权；失败不擅自安装或修改
# 验收：逐项结论 + 验证方式 + 证据 + 未验证部分

name 提供能力标识，description 给自动选择提供线索，正文保存方法。metadata.version 只是版本声明；只有发布流程、宿主加载和运行记录真正使用它，才形成版本管理。

为什么要把脚本和模板也纳入能力包？ 查询次数交给 SQLite 记录器、返回归属交给断言，比让模型凭语言估计更确定；模板提醒范围、证据和未知，降低漏报。代价是脚本要适配当前函数接口，模板填满仍不代表事实正确。因此脚本先独立运行，报告再核对证据；确定事实与语言组织各用合适的工具。

材料与代码边界先说清：上面是笔记的完整设计。本机 setup_demo.py 实际只生成 v1/v2 两份简化 SKILL.md 和 references/output.md，没有生成 scripts/check_orders.py，也没有自动复制到项目的 .pi/skills/。本课用真实 probe_orders.py 做行为验证，不虚构笔记示例脚本的运行结果。

3. 两种入口：先显式，再自动

先显式调用，是为了把「加载链路故障」与「模型不会选择」分开（笔记行 643–675）。显式入口能加载但漏检，应改步骤或模板；正文根本没进入输入，先修路径、格式、名称冲突或宿主展开。若一开始就只测自动选择，两类故障会混在一起。

固定源码 agent-session.ts L2309–2338 显示：/skill: 命中已发现 Skill 后，宿主读取全文、去掉 frontmatter，附上 location、baseDir 和参数，作为本轮输入。因此显式调用没有读取 SKILL.md 的工具记录，并不能说明未加载；应检查展开后的实际请求、诊断和后续行为。

自动选择要换一个干净会话，不写 /skill:，只提供任务、当前规则和限制。旧会话可能已保留完整正文，即使这次没有重新选择，也会沿用旧方法。关键任务可显式指定方法降低选择波动，但这只确定「提供了哪份方法」，不保证「执行正确」。

显式与自动怎样取舍？ 显式更可控、易排障，适合关键流程和加载验收，但每次需要调用者知道能力名；自动减少使用门槛，却增加漏选、误选和重复试验成本。工程上不是二选一：先用显式证明链路，再在干净会话验证自动选择，关键任务保留显式入口。

4. 渐进披露：磁盘、目录与正文

「程序发现目录」与「模型看到正文」之间至少有三个事实状态：磁盘读取、程序保存对象、真正发送给模型的输入。启动时读取全文解析 frontmatter，不代表全文已占模型上下文（笔记行 677–730）。

固定源码 skills.ts L277–345 的加载对象保留名称、描述、路径、目录和控制字段；L347–388 的目录格式化只输出可见能力的名称、描述和位置，并指导使用读取工具。这里证明的是该固定版本的代码路径，不代表所有宿主的实现。

disable-model-invocation: true 会过滤自动选择目录中的条目，保留显式入口；它不是文件 ACL，也不会撤销其他读取工具的能力。相对参考资料按 Skill 目录解析，业务源码按任务约定解析。关键参考入口尽量直接在 SKILL.md 给出，减少多层索引造成的漏读与定位成本。

为什么不一开始把所有正文都塞进去？ 全量预载省去选择和再读取，路径简单，但 Skill 多后会消耗输入预算、引入无关步骤。渐进披露把成本移到「选对并读全」；因此既要看 Token，也要看漏选率与漏读。目录本身过长时，宿主筛选或能力检索是另一个需要评测的组件，不是免费优化。

5. 三层权限：Skill 不能自己扩权

Skill 说明怎样做，宿主与工具治理决定能不能做，Sandbox 限制进程实际能碰到什么（笔记行 732–756）。用户只允许静态检查，即使 Skill 带脚本也不能执行；允许运行一个脚本，也不自动允许安装依赖、修改源码或连接生产数据库。

为什么 Skill 里已经写「禁止读取凭据」，还要 Runtime 和 Sandbox？ 文字提醒能降低模型误用概率，却无法保证模型不被恶意注释诱导，也无法限制进程真实的文件与网络访问。三层防御增加配置与审计成本，但把「意图约束」「授权决策」「操作系统可达范围」分别落实；任何一层都不被当成另外两层的替代品。

在 Agent 平台中，这意味着新 Skill 仍应接既有 Runtime 的工具策略、身份、预算和审计，不另开一条「Skill 专用执行通道」。disable-model-invocation 适合减少自动暴露，不适合承担敏感能力保护。

6. 四类验证：选对、做对、说对

测试类型输入预期行为主要防止
正例订单审查，规则与入口完整选择目标方法，逐项取证该用却漏选、漏做
负例只润色订单文档不因「订单」关键词误选代码审查描述过宽、误用方法
缺输入缺少查询上限查当前权威规则；仍缺则保留未知把一般经验冒充项目规则
执行失败路径错误或脚本接口不匹配报告受阻，不改规则、不伪造通过把执行错误写成业务结论

每类都使用干净会话，保存任务、实际配置、Skill 版本或内容指纹、工具记录和最终报告。自动选择有波动，重要任务要重复观察。选对、做对、说对是三道独立门：读了方法但没运行必要动作是执行问题；动作做了却把静态观察夸大为实测是陈述问题。

还可以做「无 Skill / 有 Skill」对照：固定模型、项目、任务、权限和预算，比较有效发现、遗漏、误报、耗时与输入量。报告更长不是收益；一次变好也不证明稳定提升。多次 Trial 与新旧版本回归将在 0026 展开。

7. 五步提炼与 Skills-as-Code

  1. 选择值得复用的任务：反复出现、容易漏规则、需要统一输出或共享工具。简单任务也可能值得封装。
  2. 分开方法与现场：稳定步骤写入 Skill；当前路径、规则、版本和权限由任务提供。
  3. 写成条件、动作和证据：不要只写「注意性能」，而要写「发现循环逐单查询时记录查询方式；允许执行时统计 SELECT，与当前上限比较」。
  4. 确定事实给脚本，报告组织给模板：脚本输出检查项、实际值、错误与退出码；模板保留范围、证据与未知，示例数值必须标明。
  5. 用失败修改方法并复测：漏选、漏做、夸大、接口不匹配分别修复；重跑受影响任务，也检查原正例、负例、缺输入和失败场景没有退化。

幂等检查也可同样具体化：初始库存 10，同一业务编号与参数预占 2，连续提交两次，核对最终库存 8、有效预占记录 1 及响应契约。没有执行权限则只报告静态风险和未验证部分。

为什么需要领域所有权和发布机制？ 同一份 Skill 被多人使用后，旧版滞留、私自放宽规则和边界无人确认会变成维护事故。Owner 负责业务判断，PR/CI 控制修改质量，运行指纹证明实际生效。代价是需要持续评测和兼容管理；因此先围绕高价值任务做小规模闭环，而不是一次把所有提示词都平台化。

学习笔记推荐从 Superpowers、Matt Pocock skills 和社区整理的 andrej-karpathy-skills 观察方法组织。第三个不是 Karpathy 本人编写。本课只把它们作为阅读方向，不把仓库热度、作者身份、安装渠道或命令可用性当作本机已验证事实；安装前阅读实际方法、脚本与依赖，并在自己的固定任务上验证。

8. 代码解剖：本机做到哪一步

组件当前真实行为不能外推成
setup_demo.py新建工作目录、复制 fixture、生成 v1/v2 简化 Skill、模板和角色笔记中的完整 check_orders 脚本或自动项目安装
skill_manifest.py递归哈希文件，拒绝符号链接，生成 package_sha256语义评审、权限执行、宿主已加载或新版已生效
probe_orders.py真实 SQLite 返回与 SELECT 计数，判断隔离和查询上限读取当前 docs 的通用规则引擎；上限在代码中固定为 2
skill_selection.py正/负/缺输入三例，从已完成 read 工具路径找 SKILL.md精确目标判断、显式展开识别、完整做对/说对评分
graders.py课程固定字段、字面证据、静态诚实性和只读状态检查通用语义 Judge 或缺输入/所有失败场景验收
pi_runner.py启动真实 pi、保存事件、记录 SKILL.md 哈希与本地进程状态无 pi 时模拟回答、整包版本证明、全局费用或任务成功

8.1 选择检测器的具体盲区

read_skill_paths(events)
  └─ 只遍历 analyze(events)["completed_tools"]
     └─ 只接受 toolName == "read"
        └─ 只检查 args.path 中是否含 "SKILL.md"

本机合成 Trace 实测：

  • 显式展开但没有 read 工具：[]，会漏报；
  • 读取目标 Skill：能返回路径；
  • 读取另一份 unrelated/SKILL.md：也返回路径，会把非目标读取算作 did_select；
  • 用 bash 读取：不识别；读取只有 start 没有 end：不入选，同时 trace_analysis 留下 unfinished_tool_calls。

此外，脚本三个案例都传了 --skill，每次启动新进程，但没有在结果里显式断言「会话历史为空」。正式验收应记录会话与历史状态、比对规范化后的目标绝对路径和内容指纹，再分别评价选择与执行。

8.2 版本与运行记录也不是一回事

skill_manifest.py 的包指纹覆盖 SKILL.md 与参考文件；pi_runner.py 的 skill_sha256 只记录 SKILL.md，项目快照只遍历 app/tests/docs，不会覆盖 .pi/skills。所以「项目 snapshot 没变」不能证明 Skill 材料没变，「frontmatter 版本改了」也不能证明运行加载了它。

仓库附带的 _smoke/runs-sel/ 是历史运行材料，不是本机实测：pi 1.2.0 + deepseek-chat 的记录中，正例和缺输入均为漏选、负例为正确未选，三条 task_success 都是 null。它们恰好说明 status=exited 只说明进程结束，不说明选对或任务通过。

8.3 显式提示词材料有一个换行陷阱

仓库 prompts/skill-explicit.txt 在 /skill:order-list-review 后直接换行。固定版 _expandSkillCommand 用第一个普通空格分隔名称和参数；按这段源码模拟解析，名称会包含后续换行与文字，不能匹配 order-list-review。本机没有运行 pi，这不是 live 失败回执；但可选实验会使用新建的单行提示词，避免把材料格式问题混入加载验证。其他 pi 版本须重新核对实际解析。

为什么要把这些实现边界写进课件？ 因为本节最容易把「有脚本」误读成「有完整平台」。指纹只证明内容，Trace 只证明观察到的动作，硬编码 grader 只覆盖固定题；把这些边界说清，才能知道下一次该补目标路径校验、动态规则输入、干净会话证明还是语义与行为验收，而不是笼统增加更多文件。

9. 面试视角：两分钟主链

我会先把 Tool、Prompt、Skill、Agent、Subagent 分开：Tool 执行动作，Prompt 表达本次目标，Skill 保存稳定方法与材料，Agent 处理当前任务，Subagent 提供独立委托执行。写 Skill 时把方法与当前路径、业务规则、版本和权限分开。加载先走显式入口，核对宿主展开后的真实输入，再用干净会话验证模型能否根据目录自动读取正文。程序发现文件不等于模型看到全文，渐进披露仍要算输入预算。Skill 和材料文字都不扩权，宿主工具治理与 Sandbox 继续执行。验收分正例、负例、缺输入、执行失败，每类都看选对、做对、说对。最后用 Owner、PR、Review、CI 和确定版本发布管理，运行记录保存实际生效版本或内容指纹，并用固定任务做对照和回归。

常见追问链

  1. 「不就是 Prompt 文件吗？」——普通 Prompt 也能保存；Skill 进一步约定发现、选择、加载、配套材料和复用。是否需要它取决于重复与维护收益。
  2. 「程序启动时明明读过全文，为什么说模型没看到？」——磁盘读取、程序对象与本轮模型请求是三个事实；目录通常只含名称、描述和位置。
  3. 「没有 read SKILL.md，怎么证明显式加载？」——固定版 pi 可由宿主直接展开；检查展开后的实际请求与诊断，而不是只找一条工具调用。
  4. 「description 写好却仍失败，怎么查？」——先分未加载、漏选、漏做、夸大，再看正文、工具行为与报告，不把所有问题都归因描述。
  5. 「disable-model-invocation 能否保护敏感 Skill？」——不能，它只控制自动目录可见性；文件访问仍由路径策略、工具权限和 Sandbox 决定。
  6. 「frontmatter 改成 v2 能否证明升级完成？」——不能；还要发布到实际入口、核对运行版本或包指纹，并重跑正例、负例、缺输入、失败与旧能力回归。
