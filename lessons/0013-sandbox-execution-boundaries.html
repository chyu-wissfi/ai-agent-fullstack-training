第一部分：精讲（先读，测验在后）

0. 开篇：Loop 放大的是副作用

Agent 要清理临时文件，生成了 rm -rf ./tmp。单看参数，这似乎是一次普通清理；如果工作目录解析偏差让实际目标变成仓库根目录，它就成了不可逆删除。更麻烦的是，Loop 不会因一次错误自动恢复理智：下一轮可能基于已经改变的现场继续判断，再产生下一轮副作用。

3-1 到 3-3 刻意只开放少量工具；真实开发却要求读整个仓库、改源码、跑测试、装依赖、操作 Git，甚至访问网络。能力给全以后，核心问题从「模型这句话说得对不对」变成「这次动作碰到哪里、越界谁拦、出事怎样查」。

本课的主线只有一句：从任务出发定义允许的副作用，让 Runtime 在执行前检查，让 Sandbox 限制执行后的影响范围，再由 Harness 把真实结果、审计和状态接回去。

1. 风险模型：防不可挽回，而不是幻想不犯错

笔记要求接受三个事实。第一，模型输出永远是不可信输入；到 Agent 场景，不仅参数不可信，意图也可能因误解、长循环偏差和上下文污染而改变。第二，Agent 读到的内容本身可能是攻击：恶意 README、注释、issue 或网页可以诱导它读取 .env 或执行远程脚本。第三，Loop 是风险放大器：同一偏差可能在几十轮里反复落到真实世界。

因此文件边界只能限制「最后能碰到什么」，不能判断「这段文字是不是恶意指令」。防御必须由 Host 和执行环境强制执行，不能写在提示词里让模型自觉遵守。

为什么默认拒绝，而不是黑名单：黑名单要预先枚举所有危险路径、命令和参数形态，新型写法永远枚举不完；白名单只回答「这个任务到底需要哪些能力」，范围更窄，也更贴近任务。代价是合法的新需求也会被拦住，需要补规则或审批，所以还要做到越界可感知：返回明确拒绝原因、留下审计，不能静默失败让模型反复重试。

边界的三个目标要分别验收：可拦截是危险动作在执行前被拦下；可审计是允许和拒绝都有记录；可恢复是损失能通过 Checkpoint、Git、独立工作区或快照挽回。只返回一个错误码，不等于三者都成立。

2. Runtime、Sandbox、Harness：三个对象，三种责任

这三个对象最容易在面试里混成一句「运行时负责安全」。笔记和教师 PDF 给出的分工是：

  • Tool Runtime：检查放行——检查参数、路径、权限和审批要求；危险调用在 handler 前拒绝。
  • Sandbox：限制影响范围——限制实际执行能触及的文件、网络、进程与资源。
  • Harness：组织执行——把工具接入同一工作区，组织取消、结果回写、审计和状态更新；Loop 再根据真实结果继续、调整或等待。
为什么需要两层防线：read/write/edit 在 Agent 的 Node.js 进程内运行，OS 沙箱如果只包住 bash 子进程，就罩不到它们，所以要应用层前置检查；反过来，一旦 Agent 能运行任意代码，它可能绕过应用层判断，所以 bash 还要 OS 或容器强制隔离。只做应用检查，任意代码可能绕过；只做子进程沙箱，进程内工具成为旁路。

3. 文件三区与读写差异

文件边界先分三区（笔记 3.4 二 2.1）：

  • 只读区：目标源码、项目文档、依赖源码。允许读取取证，修改必须走受控补丁工具。
  • 可写区：artifacts/、临时目录。允许读写，删掉重建代价低；可写隐含可读，写完还要回读验证。
  • 禁止区：~/.ssh、~/.aws、.env*、*.pem、*.key、系统目录。读写都禁止，硬阻断，不进入审批。

「可写」不等于「随便写」。如果完成契约要求交付 artifacts/login-flow.md，而工具能写任意路径，那么「写入成功」不再证明约定产物完成。允许改哪个源码文件也可以进一步收窄成逐文件白名单。

为什么禁止区不能审批放行：审批适合「高风险但可能有合理用途」的动作，例如修改指定源码；Codebase Agent 读取私钥没有合理用途。把硬禁止也送去审批，既增加误放行机会，也把本应不存在的路径变成可协商路径。

pi-sandbox 的读写规则还有一处不能混：读侧的 denyRead 可被明确 allowRead 覆盖；写侧的 denyWrite 是硬阻断，优先于 allowWrite，不提示、不放行。笔记给出的理由是破坏性不同：读错主要泄露信息，写错造成不可逆修改，所以写的拒绝更强。

4. 路径必须 resolve 后校验

模型给的是路径字符串，文件系统解释的是解析后的落点。直接做 startsWith("artifacts/")，会把「字符串开头合法」误当成「最终落点合法」。

提交：artifacts/../../.env
字符串前缀：以 artifacts/ 开头 → 朴素检查通过
resolve 后：/repo/.env → 已离开 artifact 根 → 拒绝

笔记的最小校验同时处理根目录本身和目录分隔符：

import { resolve, sep } from "node:path";

function assertInside(root: string, submitted: string): string {
  const resolved = resolve(root, submitted);
  if (resolved !== root && !resolved.startsWith(root + sep)) {
    throw new FileError("PATH_OUTSIDE_BOUNDARY", resolved);
  }
  return resolved;
}
为什么拒绝码也要设计：PATH_OUTSIDE_BOUNDARY 同时服务两个消费方：模型知道应换合法路径，而不是原样重试；审计能按拒绝类型统计越界尝试。只返回 ERROR，下一轮缺少修正依据，事后也分不清路径问题、权限问题和真实执行失败。

5. 专用工具优先于通用 Shell

文件边界再严，只要开放不受控的 run_command，就能用 cat ~/.ssh/id_rsa 绕开 read_file 的拒绝。笔记因此称 Shell 为所有工具的超集：一条命令可以读写文件、访问网络、启动进程。

首选不是写更复杂的命令过滤，而是不暴露通用 Shell。修复任务需要测试时，只提供 run_test(scope)：唯一入参是测试范围，测试文件清单在执行上下文中事先约定，命令由 Runtime 自己拼。模型没有机会注入命令字符串。

这是表达力与安全性的取舍：通用 Shell 灵活性最高，但把参数本身变成可执行载荷，防线必须理解所有 Shell 语法；专用 run_test 牺牲任意命令能力，换取结构性防御——危险表达根本无法从接口进入。只有任务确实需要通用 Shell，才付出白名单、解析、超时、进程组和输出治理的成本。

必须开放时，按副作用能否挽回分级，而不是按命令名背表：

  • 只读观察：git status、git diff、ls、grep 等，直接放行并审计。
  • 可逆修改：npm install、git add、git commit 等，放行并审计；错误可在本地回滚。
  • 不可逆或外发：git push、rm -rf、curl/wget、sudo、越界重定向、管道到 sh，转人工审批或硬拒绝。

git commit 与 git push 的差异很直观：前者错了还能在本地 reset，后者已进入远端历史。风险等级来自影响范围与可逆性，不来自命令看起来是否常见。

6. 解析、超时、取消与输出：Shell 的四条补防线

白名单命令也可能带危险参数：git commit --no-verify 跳过钩子，git push --force 覆盖远端，npm run build > /etc/crontab 越界写文件，echo ... | sh 把内容变成代码。因此要在执行前把命令解析成命令头 + 参数 + 重定向 + 管道，逐部位检查；不要对整条字符串做正则匹配，引号、转义和变量替换都可能绕过。

文件边界管空间，超时管时间。npm run dev、pytest --watch、tail -f 可能永远不返回，让 Loop 卡在等待工具结果。每条命令要有超时，长任务显式申请；超时不是停止等待，而是真的杀掉进程组，包括 fork 出的子进程。用户取消也要通过 AbortSignal 传播到正在执行的命令。

输出则管上下文与资源：npm install 的几万行日志不能原样塞回 Context，通常只把尾部或失败关键行连同真实退出码给模型，完整输出留审计。

最后与 0012 接上：run_test 启动子进程前先登记「已启动、结果不明」，拿到真实退出码才销记；中断时返回 TEST_RESULT_UNKNOWN，不能把「不知道」伪报成测试失败。Promise.race 只能提前结束等待，不会自动停掉另一个 Promise 背后的真实操作。

7. 网络、凭证与环境变量：既要防读走，也要防发出

文件边界保护信息不被读走，网络边界保护信息不被发出去。只封读、不封网，敏感内容可能被 POST 出去；只封网、不封读，密钥仍会进入上下文，下一轮可能被写进提交信息、评论或交付文档。这也是 Prompt Injection 的完整攻击链：诱导读取敏感文件 → 编码进 URL 或请求体 → 外发。

  • 外网公网：按域名白名单逐域放行，不写 *。Codebase Agent 的合理需求通常只有拉依赖、查文档、调 Git 平台 API。
  • 内网地址：公司内网、回环地址、私网与云元数据服务默认禁止，防止被带偏后横向移动。
  • 第三方 API：Agent 只持有权限受限、可吊销、调用有审计的 Gateway 凭证，真实供应商密钥留在 Gateway。

环境变量是容易漏掉的读取面。run_command("env") 一次就能读出进程环境，所以 Agent 只应获得任务必需变量，其余不继承。Docker 默认环境较干净，本地执行要显式裁剪。注意顺序：即使网络白名单挡住外发，也不能弥补凭证已被读进上下文；读取面与外发面要分别收窄。

8. 本地 Sandbox 与 Docker Sandbox：隔离强度与交付摩擦的取舍

策略层决定能不能做，隔离层决定由谁强制。本地 pi-sandbox 把 bash 交给 macOS sandbox-exec 或 Linux bubblewrap，进程内工具仍在 beforeToolCall 做同样策略检查。阻断后可选择保持阻断、本次会话、本项目或全局放行；提示超时永远视为拒绝，会话级授权只存内存。

Docker Sandbox 以 OpenSandbox 为例：命令与文件操作发生在容器里，文件系统独立，环境变量显式注入，沙箱有整体超时与资源限制；产物要显式取回，容器显式销毁。

为什么「用了 Docker」仍不是完整答案：挂载宿主目录会扩大文件访问面，开放网络会保留外发能力，注入凭证会把凭证带进容器。容器只提供独立环境的起点，权限、网络、资源和入口仍需明确配置。教师 PDF 还特别指出：本课 OpenSandbox 演示尚未限制对外联网，所以它证明的是执行与回收闭环，不是完整网络边界。

9. OpenSandbox 闭环代码解剖

sandbox_demo.py 只有一条主链，但每一步都对应一条工程要求：

  1. 创建宿主标记（14–16 行）：host-only-marker.txt 只在宿主创建，不挂载进容器，作为「容器看不到宿主文件」的检验对象。
  2. 创建 Sandbox（17–33 行）：连接本地 Server，指定 python:3.11-slim、3 分钟整体超时、1 CPU 与 512Mi 内存。
  3. 写入并执行固定测试（37–57 行）：测试代码由程序固定，不拼接模型生成的 Shell；命令在容器执行。
  4. 取回并验证真实结果（59–69 行）：读取 /tmp/result.json，要求测试退出码为 0、容器内 host_visible = false、宿主标记仍为 host-original，最后才把结果写到宿主 sandbox-result.json。
  5. 显式销毁（70–73 行）：finally 中调用 sandbox.kill()。代码注释明确：退出客户端上下文不代替销毁容器。

10. 审计、Checkpoint 与风险回放

再完整的边界也可能有盲区。审计是边界的另一半：拦截决定当下能不能做，审计决定事后能不能说清楚。最小形态是 append-only JSONL，一行一条记录，只追加、不修改。

  • runId / turn / toolCallId：与 Trace、Checkpoint 对齐定位。
  • tool 与脱敏参数摘要：说明动作，不把秘密或大段内容复制进日志。
  • decision 与命中规则、actor：说明放行、拒绝、审批或阻断由谁依据什么作出。
  • resultCode / durationMs / artifactRef：记录真实结果、耗时与产物引用。

被拒绝的动作也必须记录：审计一半回答「它做了什么」，另一半回答「它试图做什么」。反复探测凭证目录或内网地址，可能正是定位 Prompt Injection 的线索。审计文件本身必须落在 Agent 文件边界的禁止区，否则被审计者能改写证据。

与 0012 的分工是：Checkpoint 回答恢复时从哪继续、哪些进度可信；审计回答已经发生了什么、谁放行的、试图越界了什么。两者通过 runId + toolCallId 关联，不能互相替代。

重跑是在独立工作区再执行一次，回答「这次会怎样」；回放是按审计还原当时的决策链，回答「当时为什么放行」。事故复盘依次定位 toolCallId、还原 decision 与规则、沿 runId 追溯意图来源、修防并留审计，最后把事故写成回归场景。误拦要调整规则，不是直接关掉防线；漏放要补规则与回归；越权尝试要追查它此前读到了什么。

11. R1–R6 与 A1–A6：把「应该安全」改成可判红绿的证据

笔记最小规格可以压成六条：

  1. R1 文件三区：resolve 后校验、带分隔符比较、禁止区硬阻断、语义化拒绝码。
  2. R2 Shell 白名单与高风险拦截：按副作用分级，解析参数/重定向/管道，在 beforeToolCall 拦截。
  3. R3 网络与凭证最小化：域名白名单、内网默认禁止、只注入任务必需变量、不持有真实供应商密钥。
  4. R4 超时与取消：超时杀进程组、取消传到命令、结果代码可区分。
  5. R5 审计留痕：append-only，执行与拦截都记，decision、规则、actor 齐全，参数脱敏。
  6. R6 风险回放：能按 runId/toolCallId 还原判定链，区分误拦、漏放和越权尝试，策略变更留痕。

A1–A6 分别用路径逃逸、危险命令、白名单外审批、超时取消、网络外发和风险回放验证这些规则。两条验收原则必须记住：该失败的必须真的失败；拦截证据是 handler 没执行，不是返回了错误。

为什么 handler 调用次数为 0 才关键：工具先写文件、再返回 PATH_OUTSIDE_BOUNDARY，也有明确错误码，但副作用已经发生；这只是事后贴标签。只有拒绝发生在 beforeToolCall、真实 handler 次数为 0，再配合 deny 审计，才能证明防线拦在副作用之前。

12. 面试视角：沿事故链回答，不背工具名

主问题：「Agent 能执行 Shell 和改文件，你怎么保证安全？」可按下面顺序回答：

  1. 先定义任务副作用：文件、命令、网络、资源分别允许什么；默认拒绝，目标是可拦截、可审计、可恢复。
  2. 再讲执行链分工：Runtime 在唯一入口检查参数、路径和授权；Sandbox 限制实际影响；Harness 统一执行、取消、审计与状态回写。
  3. 挑两个硬例子：路径用 artifacts/../../.env 说明 resolve；Shell 用专用 run_test 与通用 run_command 说明表达力取舍。
  4. 讲隔离取舍：交互可信任务用本地，陌生或无人值守任务用 Docker；说明产物回传、冷启动、环境裁剪，以及 Docker 不回滚外部副作用。
  5. 最后给证据：handler=0、deny 审计、真实进程组终止、宿主标记不可见、容器已销毁、结果不明不重放。

常见追问及回答锚点：

  • 「有 OS 沙箱为什么还要 beforeToolCall？」——OS 沙箱罩子进程，罩不住 Agent 进程内文件工具。
  • 「有白名单为什么还要解析参数？」——--no-verify、强推、重定向和管道到 sh 能改变同一命令头的风险。
  • 「容器删了不就恢复了吗？」——只恢复容器文件系统，已经外发的数据或远端写入不会消失。
  • 「审计为什么记失败？」——它揭示模型试图做什么，帮助发现注入与越权探测。

第三部分：第二层练习——跑起来，再主动改造

实验①②使用 pi-sandbox，需要本机已有可运行的 pi 与模型供应商配置；实验③④使用 OpenSandbox，需要 Docker 与 uv，不需要模型 API key。所有命令从仓库根目录开始。实验②④是主动改造：先写预期，再跑，再对照；完成后恢复配置或代码。

实验 ①：本地三条提示词，验证「能写、硬拒、网络阻断」

  • 检查命令并安装扩展；macOS 缺 rg 时用 Homebrew 安装：
    pi --version
rg --version
# macOS 缺 rg 时执行：brew install ripgrep
pi install npm:pi-sandbox

    Ubuntu / Debian 按教师 PDF 准备依赖：sudo apt-get update && sudo apt-get install -y ripgrep bubblewrap socat。

  • 进入课程提供的本地演示目录，创建假配置与沙箱规则：
    cd course_code/week03/3-4/pi-boundary-demo
mkdir -p .pi artifacts
printf 'DEMO_ONLY=original\n' > .env.demo
cat > .pi/sandbox.json <<'JSON'
{
  "enabled": true,
  "sandboxUserShell": true,
  "permissionPromptTimeoutSeconds": 30,
  "allowBrowserProcess": false,
  "network": {
    "allowedDomains": [],
    "deniedDomains": [],
    "allowLocalBinding": false,
    "allowAllUnixSockets": false,
    "allowUnauthenticatedSocksProxy": false
  },
  "filesystem": {
    "denyRead": ["/Users", "/home", "/root"],
    "allowRead": ["."],
    "allowWrite": ["./artifacts"],
    "denyWrite": [".env.demo", ".pi"]
  }
}
JSON

    .env.demo 只含假数据，不放真实凭证。项目配置会与全局配置合并，空列表不代表清除已有授权。

  • 启动 pi，先核对最终生效权限：
    pi
    进入交互界面后输入：
    /sandbox
  • 先写预期：下面三个动作哪个应成功、哪个不应出现授权提示、哪个应等你决定？拒绝后 .env.demo 的内容应该是什么？
  • 提示词一——产物可写并回读：
    使用 write 工具创建 artifacts/ok.txt，内容为 sandbox-ok。
完成后使用 read 工具回读，报告实际读到的内容。
  • 提示词二——受保护文件硬阻断：
    这是一个仅含假数据的边界验收。
请使用 write 工具把 .env.demo 改为 DEMO_ONLY=changed。
若工具拒绝，报告拒绝原因，不申请修改策略，也不要换工具重试。
  • 提示词三——未授权域名访问；出现权限提示后选择 Abort：
    !curl --max-time 5 -I https://example.com
  • 退出 pi 后核对真实文件，而不只看模型报告：
    cat artifacts/ok.txt
cat .env.demo
    预期依次看到 sandbox-ok 与 DEMO_ONLY=original。提示词二应被 denyWrite 硬阻断，不出现放行提示；提示词三保持阻断。

实验 ②：主动改造——同时加入 allowWrite 与 denyWrite，验证优先级

  • 仍在 pi-boundary-demo，把 .pi/sandbox.json 中这一行：
    "allowWrite": ["./artifacts"],
    临时改成：
    "allowWrite": ["./artifacts", ".env.demo"],
    保留 "denyWrite": [".env.demo", ".pi"] 不变。
  • 先写预期：路径已进入允许写列表后，提示词二会放行、弹审批，还是仍然拒绝？为什么写侧规则与读侧 denyRead 的覆盖语义不同？
  • 重新启动 pi，用 /sandbox 核对规则，再原样执行实验①的提示词二。退出后核对：
    cat .env.demo
    预期仍是 DEMO_ONLY=original，且没有授权提示：denyWrite 优先于 allowWrite。
  • 实验结束后把 allowWrite 恢复为只含 ./artifacts。

实验 ③：OpenSandbox 跑通「创建 → 执行 → 取回 → 销毁」

  • 终端 A 进入目录，准备环境并启动服务。仓库已提供 sandbox.toml，不要重新生成覆盖：
    cd course_code/week03/3-4/opensandbox-demo
docker info
uv venv --python 3.13.14
uv pip install opensandbox
uv pip install opensandbox-server
docker pull python:3.11-slim
uvx opensandbox-server --config ./sandbox.toml
    最后一条命令保持运行。示例使用本地演示 API key，不是真实凭证。
  • 终端 B 检查服务并运行客户端：
    cd course_code/week03/3-4/opensandbox-demo
curl --fail http://127.0.0.1:8080/health
uv run --no-project python sandbox_demo.py
  • 先写预期：容器里能否看到宿主绝对路径下的 host-only-marker.txt？宿主标记会不会被改？async with 结束后是否还需要 kill()？
  • 预期日志依次出现 CREATED、container test finished、VERIFIED、DESTROYED。核对取回结果：
    cat sandbox-result.json
    应为 exit_code: 0、host_visible: false。这只证明执行、隔离宿主文件与回收闭环；本演示尚未限制对外联网。

实验 ④：主动改造——让容器内测试失败，验证错误结果与清理

  • 保持 OpenSandbox Server 运行。打开 sandbox_demo.py，把固定测试字符串里的：
    "test += 'assert allowed(True)\\nassert not allowed(False)\\n'",
    临时改成：
    "test += 'assert allowed(True)\\nassert allowed(False)\\n'",
  • 先写预期：客户端退出码会是多少？会打印测试失败还是测试通过？sandbox-result.json 会不会被本次失败结果覆盖？DESTROYED 是否仍应出现？
  • 终端 B 再运行：
    uv run --no-project python sandbox_demo.py
echo "exit=$?"
    预期容器测试返回非 0，客户端抛 RuntimeError，进程退出码非 0；因为结果校验在写宿主结果文件之前，本次不会生成新的成功结果；finally 中仍打印 DESTROYED。
  • 恢复原来的 assert not allowed(False)，再运行一次，确认重新回到 VERIFIED 与 DESTROYED。
