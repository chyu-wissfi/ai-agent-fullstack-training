1. 这个项目要证明什么

综合场景选 Codebase Agent，不是为了展示模型会写多少代码，而是因为文件、Shell、测试和外部服务同时存在，能直接暴露执行边界、超时、审批、审计和 Loop 终止问题（笔记原话）。项目要回答的核心工程问题（PDF 开场列的三问）：

  • handler 完全忽略 AbortSignal 时，Runtime 能否按时返回 TOOL_TIMEOUT？
  • 超时后，重试和降级从哪里接上？
  • Trace 能否还原整个执行过程？

2. 复用阶段一 Gateway

Agent 不直接持有供应商 Key，也不重复实现模型重试和路由——只依赖平台逻辑模型名 agent-default，把请求发给第一章的 OpenAI-compatible Gateway（本章用 LiteLLM 组合 FastAPI，业务逻辑与第一章实现相同）。平台模型名与真实供应商模型分离后，Gateway 可以在不修改 Agent Prompt、工具或 Loop 的情况下切换底层端点；供应商 Key 留在 Gateway，Agent 进程只持有访问 Gateway 的受管凭证。三条工程纪律（PDF）：

  • LiteLLM max_retries=0——重试的唯一负责方是 Gateway，工具重试由 Runtime 负责，两层不共用车计数；
  • 流式响应首段发出前允许切换模型，之后中断返回 STREAM_INTERRUPTED，不中途换模型；
  • 预算用价格上界配置，LoopGuard 在风险发生前停止——不能等最终账单出现才发现超支。

3. 注册三合一：内部命名、模型投影、能力快照

Registry 中的完整元数据（ToolMetadata）一次声明：internalName、risk（read/write/high）、permissions、requiresConfirmation、timeoutMs、maxRetries、idempotent、source（local/python/mcp）。三个动作同时完成：

  • 内部命名保留领域语义：order.get_status、ticket.create、mcp.my-coffee.query_order；
  • 模型投影：Provider 不接受点号就投影为 order__get_status，注册时维护 internalName 和 modelName 两个索引，双向映射可逆、可预测、不自动截断——名称碰撞直接启动失败，不带病运行；
  • 能力快照：模型能看到的 Tool Schema、Runtime 能执行的具体版本、风险和治理配置一起冻结进 Run Snapshot，按用户、Agent、租户、模式过滤；模型请求与后续 Runtime 不能各自重新查全局 Registry。

4. Schema 单一来源

Python 业务服务用 Pydantic 定义输入模型（extra="forbid" + strict=True），再通过 model_json_schema() 导出给 Node 侧读取（python -m app.export_schemas 生成 config/schemas/*.json，CI 检查 diff）。不要手工维护 Python 与 TypeScript 两份 Schema——两份契约独立演进后，模型按一份生成参数，业务服务却按另一份拒绝。关键句：单一来源不等于只校验一次。仍然保留两道校验：① Pi/Runtime 边界尽早拒绝模型生成的非法调用；② Python 服务入口再次校验——因为业务服务不能假设所有调用方都来自当前 Agent。两道校验使用同一份契约事实。

5. 审批设计成可恢复状态

审批不是对话布尔值：持久化 approval_id、参数摘要（canonicalJson + SHA-256，绑定 trace_id、tool_call_id、tool_name、user、tenant、args）和等待状态。pi-agent-core 通过 shouldStopAfterTurn 检测待审批，停止 Loop 返回 AWAITING_APPROVAL。人通过 CLI 或 API 处理（list / decide / execute）。执行审批时重新完整校验：工具存在且名称映射未变、参数仍符合当前 Schema、用户权限和租户范围未变、参数摘要与批准时一致——然后原子领取（SQL UPDATE approvals SET status='executing' WHERE id=? AND status='approved' AND expires_at>?，防并发双执行）。状态流转：pending → approved → executing → consumed（或 rejected/failed）。恢复的三重含义全部落地：恢复同一任务而不是让模型假装完成、重新检查权限与启停、原子消费审批。

6. 硬超时与重试

执行入口用 runWithDeadline 包住 handler。实现是 Promise.race + controller.abort()——分工必须背准（PDF 明确点名的关键命中）：

  • 真正保证按时返回的是 Promise.race：deadline Promise 到时 reject，无论 handler 是否响应；测试用故意忽略 signal 的 handler 验证（超时 15ms、断言错误码和返回时间）；
  • AbortController 负责通知合作型下游取消——但 Runtime 不能假设所有 handler 都会响应；本地超时不代表远端副作用停止。

重试只有一个 owner：Tool Runtime 只恢复明确瞬时故障，Agent Loop 负责重新规划，两者都消费 Run 的统一预算。重试条件是 ToolRuntimeError.retryable 且工具声明 idempotent，maxAttempts = idempotent ? maxRetries + 1 : 1。写操作超时返回 TIMEOUT_UNKNOWN，保留 Trace，用幂等键查询或人工核对——不自动重放。降级（fallbackHandler）同样经过 deadline helper，成功码是 FALLBACK_OK；降级返回明确的不确定性（如 status: "unknown"），不能伪装成正常成功。

7. MCP 工具进同一条治理链

远端工具发现后（mcp.my-coffee.*，streamable HTTP，Token 从环境变量读取、缺失直接失败），每个远端工具转为内部 ManagedTool 再进入 Registry、Snapshot、Policy、Approval 和 Runtime。两个易错点：① trusted: true 只表示 Server 来源经过配置，不表示其中每个工具都可以无条件执行——远端工具仍是默认 high 风险、要权限和确认；② 取消信号传递给 MCP SDK，MCP 结果做归一化、限长和脱敏。验收标准（笔记原话）：不止要成功列出远端工具，还得验证本地 Tool、Python 服务和 MCP Tool 都无法绕过同一个 invoke()。

8. Audit 与 Trace 怎样分工

一次 Run 的形状（笔记原文）：

trace_id = tr_01
└── run_id = run_01
    ├── step_01：LLM Call
    ├── step_02：Tool Call / order.get_status
    ├── step_03：LLM Call
    ├── step_04：Tool Call / filesystem.read_file
    ├── step_05：Tool Call / bash.run_tests
    └── step_06：Final Answer

Trace 用来还原调用链、时间和依赖；Audit 用来记录身份、策略与业务动作。所有事件共享关联 ID，但保存范围不同、分表存储、保留周期不同。四条纪律：① 脱敏必须发生在日志写入之前，而不是事后清洗（配置敏感字段 + 通用正则）；② 即时失败事件也要进入 Trace，不能只记录成功调用；③ 审计写入异常单独告警，不能把已成功的业务动作改写成失败并触发重试；④ 查看用 npm run cli -- trace <trace-id>，策略拒绝、成功、失败均记录。pi 已实现的 tool_execution_start / update / end 事件是优秀参考实现。

9. LoopGuard 为什么属于 Harness

为什么不能交给模型：模型可能每一步都合法，却始终重复调用工具——终止条件不能交给模型，它也无法自动增加限制。所以 Harness 至少限制六个预算（工具调用前和每轮结束后检查）：

max_turns: 8              # 轮数
max_tool_calls: 12         # 工具调用总数
max_repeated_call: 2       # 相同调用重复次数
max_total_tokens: 30000    # Token 预算
max_cost_usd: 0.25         # 成本预算
max_duration_ms: 120000    # 总时限

三个设计细节：① 重复调用判断用「工具内部名 + 规范化参数摘要」，而不是只看工具名称（signature = toolName + ":" + canonicalJson(args)）；② 等待审批期间任务进入显式暂停状态，不继续消耗模型调用预算；③ 分工句（必背）：Tool Runtime 决定一条调用能否执行；LoopGuard 决定整个 Run 是否还能继续。两者都属于 Harness 的确定性控制，不能只写进 System Prompt。

10. 阶段二最终验收清单 + 面试视角

笔记 2.5 九的三层验收，也是 Week02 的结业标准：

  • 口头：画出 Gateway → Model → Tool Call → Snapshot → Runtime → Policy / Approval → Handler / MCP → Tool Result → Loop，说清 Function Calling（模型选工具生成参数）、MCP（外部能力发布发现调用）、Runtime（单次调用校验执行收口）、Handler（业务动作本体）的边界；
  • 代码：模型无法伪造身份/租户/审批；模型与 Runtime 使用同一 Run Snapshot；所有入口共用 invoke()；写操作无幂等保证时不因超时自动重试；本地/Python/MCP 工具经过相同治理链；成功与失败都保留 tool_call_id；Tool Result 和日志写入前完成脱敏；审计与 Trace 能关联模型调用、工具调用和业务结果；
  • 审查（面对 AI 生成代码能发现）：权限发生在副作用之后；SDK、Runtime 和 Loop 同时重试；超时被错误解释为写操作失败；原始异常、Token 或客户数据进入模型和日志；测试只检查错误文本没有检查副作用；Tool Result 丢失原始调用 ID。

面试收尾句（本章总结）：第二章完成的不是「给模型注册几个函数」，而是建立了一条从不确定模型输出到确定性业务执行的边界——模型负责理解、选择和生成候选参数，工程师负责协议、可信边界、风险、失败语义和验收证据。真正的标准是：错误动作能否在副作用前停止，失败能否被恢复，结果能否被追踪，系统能否用测试证明自己的行为。
