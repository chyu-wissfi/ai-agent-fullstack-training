第一部分：精讲（先读，测验在后）

0. 开篇：任务结束后，什么值得留下

登录修复结束了。回头看工作记忆里的信息：「正在准备补丁」通常已经没用；但模块位置、项目边界要求、测试入口和核验过的修复经验，下次增加退出登录还会用到（笔记行 911）。不保留这些，新任务就要重新搜索，用户也可能再次说明同一条约定（行 913）。

这正是 0018 生命周期最后一环「归档：筛选后续有用知识」的展开。长期记忆，是跨会话、跨任务保存并复用信息的能力——程序从外部记录取回相关知识，再放进模型输入，没有修改模型参数（行 917）。本课路线：选出值得存的 → 用 OKF 组织成文件 → 用 pi 插件维护与召回 → 上下文丢失后怎样恢复。

1. 短期与长期：按用途区分，不按存储介质

为什么按用途而不是按「存哪里 / 存多久」分？ 按介质分（内存=短期、数据库=长期）会误判：持久化的工作记忆仍服务当前任务，任务结束就该归档筛选；按时间分（超过一天=长期）同样误判。用途口径直接决定维护责任：服务当前任务的记录随任务归档，服务后续任务的记录才需要来源、适用范围与失效规则。长期记忆≠模型参数更新（没改参数，只是外部记录进输入），也≠向量数据库（向量库只是可选检索组件，文件/普通数据库同样能组织记忆）——这是复习 Q13 的核心。

2. 写入前三问，与要求/事实/推断/证据四种性质

写入前问三件事（行 935–941）：以后哪类任务还会用到它？来源能不能核对？什么变化会让它失效？模块和测试入口有明确用途，可以保留；「退出登录可能与缓存有关」只能作为推断；已删除的临时打印通常留在本次日志即可（行 943）。凭证、登录令牌、密码和完整用户请求载荷，不作为本案例的长期知识（行 945）。

为什么分性质保存，而不是统一存「结论」？ 因为四种性质的使用方式完全不同：要求要遵守（但先核对提出者权限与适用范围），事实要重核（版本变了就失效），推断只能当排查线索（不能直接定根因），证据用来支持核对。混存的事故：错误推断被写成确定结论，反复影响后续排查（行 982）；一次任务的临时限制被当成全项目永久规则。这与 0018 临时事实五性质、你熟悉的 de-test fact 族输出协议同构——先定性质与来源，再谈检索与使用。

3. 生命周期：写入、检索、更新、失效

写入后，新任务还必须真正读取（行 968–974）：几天后输入变成「退出登录任务 + 项目标识」，程序检索相关记录、装配进请求，模型才能据此读当前源码、确认测试、再实施功能。只看到回答提及熟悉文件名，不足以证明记忆被读取——要看工具回执或确定性加载记录（行 974）。

为什么冲突不能「新的覆盖旧的」？ 时间更新不等于更可靠：新消息可能来自模型建议，也可能属于另一个分支（行 988）。按时间覆盖的事故：把另一分支的入口约定覆盖到当前项目，或把模型推断覆盖掉维护者要求。当前方案是四问顺序——先核范围（不同范围分别保留、各自标注），再比来源（要求看权限、事实看证据），同样可靠却矛盾就查配置或问维护者，不替用户编结论（PDF p6）。为什么过期≠删除？ 「旧版本用 <=，改 < 后测试通过」有历史追溯价值，保留并标失效范围；「当前源码仍用 <=」在修改后就不能当现行事实。删除活动记忆也不自动证明备份和缓存都已清除（行 1004）。

4. OKF：先解决知识组织，再选择检索技术

长期记忆不等于向量数据库——保存、分类、来源、更新和使用规则，不能由向量相似度替代（行 1010）。OKF（Open Knowledge Format）用 Markdown 目录树组织知识，顶部 YAML 保存元数据，链接连接相关概念，index.md 提供目录，log.md 记录更新（行 1012）。v0.2 规范中概念文件的 type 始终必填；~/.pi/agent/okf-memory 是路径约定，实际跨项目隔离仍要确认配置的根目录，不能只靠标签（行 1014）。工作顺序：先读索引，再读当前任务相关概念，不必把整套知识全文自动塞进请求（行 1016）。

材料与快照的口径差（已核对）：笔记 4.1 与 PDF p8 展示的原稿文件是另一份（Python 味，app/session.py、source: session），它的 description 直接写「实现在 app/session.py」，正文却承认原相对路径未找到——摘要比正文更确定，这是需要核对的信号（行 1036）。仓库 okf/ 快照是 TS login_demo 版（generated/verified 成对），描述与正文一致。两份不是同一文件：原稿作警示案例，快照作正面样本，实验①会对照。

为什么先组织、再谈检索？ 规则写在笔记、入口写在临时文件、经验藏在聊天记录里——下次任务开始时 Agent 不知道有哪些记录、哪条是当前规则，只能重翻或问用户（PDF p7）。OKF 先解决「有哪些、什么性质、谁来源、何时更新」，检索技术（向量/BM25/文件读取）只是在此之上的取用方式。替代方案「直接上向量库」的代价：相似度找不到「哪条是当前有效规则」，也无法表达失效与权限。格式通过（/okf-validate）只证明结构合规，不证明业务结论正确（行 1090，复习 Q15）——与 0018「工具正常返回≠业务验证通过」同构。

5. pi 插件：「自动记忆」的真实路径

两个插件分工（行 1052）：pi-okf 辅助建立和维护项目知识；pi-okf-memory 在对话中让模型调用工具保存与召回。原稿提醒两套插件声明的 OKF 版本不同，不能直接混写，以对应插件支持的格式与实际回执为准（行 1054）。终端安装（pi install npm:pi-okf@0.4.0）与会话命令（/okf-init、/okf-validate、/okf-update）分开；笔记保留原稿版本，命令是课程操作记录，不代表最新发布版本（行 1070）。

全新会话验证外部读取（行 1094–1108）：关闭旧会话，在同一项目启动新会话，要求先读索引、再读会话与测试概念、最后读当前源码。原稿记录中索引 → 概念 → 源码三步都出现在工具回执，可以确认外部知识进入了新会话；此时只完成定位与核对，没有实现退出登录，也没有运行建议命令。

为什么「自动记忆」要强调「模型在指引下选工具」？ 误解一：后台无条件保存每句话——那会把噪声、凭证、推断全存进去，违反写入筛选。误解二：每次任务确定性读入全部记忆——那等于完整历史直发，预算与污染问题回来（0017）。真实路径是适配层注入纪律与目录摘要，模型按需 search/read/remember，是否实际写入、召回或删除，看回执（行 1145–1147）。这与 0016「状态≠结论只认审计」同构：能力声明不等于执行事实。图谱（/okf graph）显示关联，也不能直接证明因果（行 1157）。

6. 恢复边界：长期记忆不是进度存档

不能只查长期知识就宣布恢复（行 1163）。长期记忆能告诉模型模块在哪里、曾用什么办法；当前任务到底应用补丁没有、审批是否有效、测试对应哪个版本，仍要读工作记忆、Checkpoint 和执行回执，再核对现场（行 1165）。

为什么不能把这几类信息混在一次相似度检索里？ 相似度只回答「语义相近」，不回答「这是进度还是经验、是当前事实还是历史」。混检索的事故：模型把历史故障经验当成当前约束，把旧版本测试当成当前通过结果（行 1174）——0018 的 stale 问题在记忆层重演。当前方案按信息性质分入口：精确状态走工作记忆/Checkpoint，线索经验走长期记忆召回，细节走执行记录引用，现场走实际读取。分入口的代价是装配更复杂，收益是每类信息的证明力不被混淆。

7. 记忆策略：四种取舍，与本项目先采用的组合方案

策略可能收益需要承担的代价
无记忆简单，没有记忆查询开销重复搜索和重复询问
完整历史细节多输入增长，夹带旧状态，可能超限
摘要记忆输入集中可能漏约束、改条件；生成有开销
按需检索控制输入规模查询、维护成本与漏召回风险

笔记强调：这些是取舍，不是本项目已测出的性能结果——不能只因接了插件就宣布成功率提高或延迟降低（行 1187）。本项目先采用组合方案（行 1189）：精确状态走工作记忆和 Checkpoint，必要约定按项目读取并强制检查，经验按需检索，完整日志留引用。比较时固定任务与起点，记录完成率、总 Token、费用、查询耗时和端到端耗时，再检查失败原因（行 1191）。

为什么是组合方案而不是单选？ 四种策略各怕一件事：无记忆怕重复、完整历史怕丢约束与超限、摘要怕失真、按需检索怕漏召回（PDF p15）。组合方案让每类信息走最适入口，把单一策略的弱点用另一入口补上。代价是系统复杂度与装配责任上升。比较口径与你的 benchmark 工作完全一致：固定任务与起点、统一指标、再查失败原因——「接了插件」是配置变化，不是性能结论。

8. 面试视角：两分钟主链 + 追问链

两分钟主链（不看稿讲清）：短期长期按用途分（服务这一次 vs 服务下一次），长期记忆是外部记录进输入、没改参数、不等于向量库 → 写入前三问（复用价值/来源/失效）+ 四性质分开（要求/事实/推断/证据），凭证不存 → 生命周期四动作，更新定位原记录、冲突先核范围再比来源、过期≠废弃≠删除 → OKF 先组织（目录树+YAML+index+log），格式通过≠事实正确 → 自动记忆是模型在指引下选工具，看回执；新会话读取要三步回执证明 → 长期记忆不能恢复全部进度，四类信息四个入口 → 策略是取舍不是测出的结果，组合方案 + 固定口径比较。

长期记忆
├── 是什么：跨会话跨任务复用；外部记录进输入（≠参数更新 ≠向量库）
├── 存什么：前三问筛选 + 四性质（要求/事实/推断/证据）；凭证不存
├── 怎样维护：写入→检索→更新→失效；冲突四问；过期/废弃/删除三分
├── 怎样组织：OKF 目录树 + YAML + index + log；格式≠事实
├── 怎样发生：适配层注入指引 → 模型选工具 → 回执为准
├── 怎样证明读了：新会话三步回执（索引→概念→源码）
└── 边界：不恢复进度（四入口分工）；策略是取舍，组合方案

面试官追问链：

  • 「记忆为什么不直接 fine-tune 进模型？」→ 外部记录可核对、可更新、可删除、可按项目隔离；参数更新做不到这些治理动作。
  • 「怎么防止模型把推断当事实存进去？」→ 写入前三问 + 分性质保存 + 无执行证据标待验证；快照里「token 永久有效」就标了待验证。
  • 「两条记忆冲突你信哪条？」→ 先核范围再比来源：要求看谁有权提出，事实看证据是否适用；不只看时间新旧。
  • 「怎么证明新会话真用了外部记忆？」→ 不继承旧聊天的新会话 + 索引→概念→源码三步工具回执 + 内容进本轮请求；回答提及文件名不算。
  • 「上下文丢了，查长期记忆能恢复任务吗？」→ 不能只查长期知识：进度走工作记忆/Checkpoint，现场走实际读取，长期记忆只给线索。

实验 ①：快照结构与元数据——type 必填，描述与正文一致

  • 读索引与五个概念的元数据：
    cd course_code/week04/4-3/okf
head -12 index.md
grep -n "^type:\|^status:\|^generated:\|^verified:" sessions/*.md testing/*.md

实验 ⑥：设计练习——写入筛选分类 + 冲突四问（纸面，附参考要点）

  • 分类：把下面 8 条信息分成「保存/不保存」，保存的标性质（要求/事实/推断/证据）与失效条件——① 会话模块在 utils/token.ts 与 middleware/auth-middleware.ts（实读确认）；② 项目约定「恰好到期必须无效」（维护者规定，仅限本教学项目）；③ 「退出登录可能与缓存有关」（模型猜测）；④ 本次为排查临时加的 console.log（已删除）；⑤ 用户登录令牌原文；⑥ grep 无到期词的回执（exit 1）；⑦ 「旧版本用 <=，改 < 后边界测试通过」（有版本范围）；⑧ 「文件应该在 session 目录」（用户随口一说，未核对）。
    参考要点：①事实（核对当前文件，迁移即失效）；②要求（核对提出者权限，范围仅本项目，规则正式变更才更新）；③推断（只作线索，标待验证）；④不存（留本次日志）；⑤不存（凭证红线）；⑥证据（支持①的负向结论）；⑦事实/经验（标版本范围，退出当前事实但保留历史价值）；⑧推断/待核对线索（不能当事实）。
  • 冲突四问：旧记忆「pytest tests/ -q」，新说明「python -m pytest tests/ -q」。按顺序走：同项目同对象同环境吗？→ 来源是否适用（新说明来自维护者还是模型建议？是否另一分支？）→ 谁有权调整入口？→ 决定替换。
    参考要点：两条可能都能运行，差别在入口约定与环境；不能只因新消息更晚就覆盖；确认维护者调整后更新原记录、旧命令留历史；同样可靠却矛盾就查配置或问维护者，不替用户编结论。
