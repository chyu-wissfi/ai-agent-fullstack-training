第二部分：精讲（测验后再读）

1. 一条主链：Gateway 是模型调用的收口，不是 HTTP 转发

1-6 的定义：LLM Gateway 的价值不是多转发一次 HTTP，而是把模型调用变成一项统一、可校验、可降级、可观测的平台能力。1-7 的演进不是推翻 1-6，而是把已验证的边界从单文件原型升级为可配置、可部署、可测试的服务：

Agent / Planning / RAG
        ↓ LLMRequest（统一契约）
FastAPI 入口：鉴权、限流、请求校验（extra="forbid"）
        ↓
Prompt 装配：模板名 + 版本 + 变量（StrictUndefined）
        ↓
模型路由：白名单 + 能力检查（Router 产出可解释 RouteDecision）
        ↓
Adapter / Provider：协议转换与归一化（SDK max_retries=0）
        ↓
普通调用：JSON 解析 + Schema 校验 / 流式调用：增量 + SSE
        ↓
临时故障：有限重试（次数+截止时间+错误类型）-> 能力等价 fallback
        ↓
Trace：Model / Prompt / Token / Cost / TTFT / Latency / Attempts
        ↓
LLMResponse 或稳定错误回到 Harness

贯穿 1-7 的核心原则：Gateway 统一模型执行语义；Agent Loop 决定任务怎样推进；Harness 管理状态、预算、权限、取消和完成条件。Gateway 可以返回模型输出，但不能因为模型说「任务已经完成」就修改 Agent 的真实终态。

2. 分层职责（本课第一张必背表）

层负责混用后的故障
Gateway统一平台协议、调用治理、恢复、留痕吞掉 Agent 任务逻辑，变成所有业务的中心
Provider / Adapter吸收供应商通信差异，归一化响应差异泄漏进 Harness，换模型要改 Loop
Harness / Loop任务状态、上下文、工具、多轮决策适配每家 SDK，业务代码跟随供应商变化
模型根据输入生成候选结果被当成确定性组件，硬边界交给概率

重试散落在 SDK、Provider、Gateway 和 Loop 四层时，调用预算就会失控（Gateway 最多四次 × Loop 三轮 = 一步任务十二次调用）。另外两个 ID 纪律：`request_id`/`call_id` 标识一次模型调用，不能代替 `trace_id`/`run_id`（一次 Agent Run 可含十次 Gateway 请求）；业务 ID（工单号）与供应商 Response ID 也各有用途不能互换。

工作对应：你在 OpenViking 做的 vectordb adapters（default / local / VikingDB）正是「Adapter 只适配协议、不制定策略」的活例子--local 与 VikingDB 两后端能被公平对比，前提就是差异被收敛在 adapter 层，上层检索语义不随后端漂移。这就是 1-6 表格里那行「OpenAI Compatible 不保证能力和错误完全相同」的镜像版。

3. 契约与装配：入口处拒绝，好过出口处收拾

  • extra="forbid"：Message/LLMRequest 拒绝未声明字段--否则某 Agent 依赖供应商 A 的私有字段，表面统一了 URL，实际没有统一契约。
  • stream + response_schema 组合在入口拒绝：没有增量 JSON 解析能力时，放行会导致已向客户端发送半段 JSON 后才发现不合法--既不能撤回内容，也不能改回普通 HTTP 错误。
  • PromptSelection 只传模板名 + 版本 + 变量：不让调用方上传完整 System Prompt，否则绕过模板发布、版本记录和审查流程；缺变量在模型请求之前失败--模板校验是确定性客户端错误，不该靠重试解决（同一份缺变量请求会重试四次仍失败）。
  • 逻辑模型名：上层只说 `general-primary` / `agent-structured`，Gateway 解析成真实模型、地址、密钥与能力。部署换模型不改 Agent Loop。

4. 四层成功 + 校验：HTTP 200 只覆盖第一层

层级成功条件失败示例
TransportHTTP 请求完整返回DNS、超时、连接中断
Provider供应商接受并执行请求429、5xx、认证失败
Protocol响应能映射到内部协议缺少 choice、未知事件
Semantic输出满足 Schema 与业务规则JSON 合法但工具参数越权

所以即使 Provider 声称支持原生 Structured Output，Gateway 仍要做本地两层校验（json.loads 语法 + jsonschema 字段）。`json_schema` 是 API 原生约束，`json_object` 只保证 JSON 格式、Schema 靠 Prompt 传递--两种模式不能讲成同一种保证。流式的对应边界：连接正常关闭不等于输出完整，只有 `response.completed` 才算成功；流中错误必须成为流协议的一部分（1-7 用 compare_and_set 保证 completed / failed / cancelled 唯一终态）。

5. 恢复：重试、fallback 与它们的不适用清单（第二张必背表）

失败类型处理为什么
连接失败、超时有限重试可能是短暂传输故障
限流（429）等待后有限重试供应商暂时没有容量
认证 / 配置 / 未知模型 / 模板缺失不重试相同配置不会自行恢复
非法 JSON、Schema 失败有限修复（非网络重试）模型已正常返回，是格式问题
内容安全拒答不换模型绕过策略拒绝不是故障

四条恢复纪律：① max_retries=0 关闭 SDK 隐式重试，attempts 才对应真实上游调用数；② 退避受三重约束--次数、总截止时间（deadline）、错误类型，三次超时可能已远超 Run 剩余预算；③ fallback 先做能力检查--切到不支持 Structured Output 的备模型，只是把基础设施故障变成协议故障；④ 流式以首块为界--首块前可重试可切换，首块后只能发 failed 并保存部分输出，透明重生成会造成重复文本、风格混合、Token 与内容无法对账。Fallback 的不适用清单还包括：请求非法、认证/租户权限失败、结构化业务校验失败却无修复策略。

6. 预算与追踪：证据要能回答问题，还不能泄密

预算从 Run 传播到 Call：Gateway 的重试和 fallback 必须消费上层 Run 的剩余预算，否则每次单调用都「没超」，完整 Run 却无限消耗。追踪链是四级：trace_id -> run_id -> step_id -> call_id / tool_call_id--Gateway 负责 call_id 内部细节，Harness 负责把它放进完整 Run 的因果链。延迟不能只记一个数字（total_latency 拆成 queue / render / route / connect / TTFT / generation），TTFT 以第一个有业务意义的 delta 为准。Trace 九个维度（关联、路由、Prompt、用量、延迟、弹性、结果、错误、成本）里，requested_model 与 resolved_model 必须同时保留--日志只看到「请求了默认模型」，就无法知道实际切到了哪个版本。不要默认把完整 Prompt 和输出写进日志：内容采样、脱敏、保存期限和访问权限是独立的数据治理决策。

7. 1-7 服务化：Router、Prompt Bundle 与修复边界

  • OpenAI Compatible 是外部接口，不是内部领域模型：外部协议在 API Layer 终止；禁止业务层写 `if provider == ...`，差异全部收敛到 Adapter。「兼容」也不等于复制全部字段--未知字段立即拒绝，而不是静默忽略。
  • Router 产出可解释的 RouteDecision：候选、拒绝原因、理由都进 Trace，否则费用或质量变化时无法回答「为什么选中了这个端点」。路由不是挑最强模型：能力过滤 -> 租户预算/区域/数据策略/健康过滤 -> 优先级排序。
  • Prompt 是 Bundle 不是字符串：模板 + 输入输出 Schema + Few-shot + 模型参数 + Eval 集 + content_hash 绑定成一个可发布版本；hash 能暴露「文件名没变但内容被改」的不可追踪修改。灰度分流基于稳定键（租户/用户/Run 的 sha256 bucket），版本选定后固定到 RunState--同一 Run 内 v1/v2 混用，行为变化无法归因。
  • 修复调用有边界：计入同一 Run 预算、新 call_id 关联原调用、最大修复次数、失败返回明确错误--不退回未经校验的自然语言。这与 1-5 的 repair loop 是同一条纪律在 Gateway 的复现。
  • 并发限制比 QPS 重要：模型请求持续时间长，只限每秒请求数仍会堆积大量并发连接；需要全局并发、每供应商并发、每租户 QPS 与并发、每模型 Token/分钟多层限制。幂等键能避免 Gateway 重复建调用记录，但不能假设供应商不执行两次--不重复计费没有保证。

8. 测试与验收：证明「不允许发生的行为确实不会发生」

一份「能返回 200」的实现不算掌握。有证明力的断言是：未知模型 / 非法请求 / 缺模板变量时 Provider 调用次数为零；一次失败一次成功时 attempts == 2；非法 JSON 不产生 parsed；流式首块后失败不调用备用模型；Trace 不含 API Key、Python 堆栈和完整敏感 Prompt；取消传播后只有一个 cancelled 终态、用量只落一次。重试测试注入时钟与随机数（不让测试真的等待几秒），Streaming 测试覆盖 UTF-8 跨 chunk、断连、Backpressure。Fake Adapter 不是废代码：Router、Loop、Eval 和故障注入测试都依赖它稳定复现成功、限流、超时、流中断和非法输出。

开发顺序同样重要：先自己画主链和伪代码（只标边界与顺序）→ 把确定的接口、字段、失败语义交给 AI 补实现 → 自己做故障注入（缺密钥、未知模型、非法 JSON、首 Token 后断流、客户端取消、预算耗尽）。把「帮我写一个 Gateway」直接丢给 AI，得到的是能运行却无法解释的代码。

工作对应：你做 local vs VikingDB 对比时，Trace 字段设计直接决定结论可信度--requested/resolved model、Prompt 版本 hash、TTFT 分段、attempts 不记全，50 次 find 的延迟分布就无法归因；「Adapter 契约测试」（每个 Adapter 过同一组用例）也正是两个后端公平对比该有的形态。你接入过的 MCP proxy 插件（lib/servers 统一入口）则是「收口成平台能力」的小型同构。
