0. 开篇：结课项目组装了什么

笔记「本章总结」把全章主线压缩成七句话，项目三就是这七句话的落地（行 3970–3978）：

3.1 让任务能继续
3.2 让系统知道做到哪一步
3.3 让进度能跨进程恢复
3.4 把真实执行限制在安全边界内
3.5 把模型、工具、状态、上下文和环境装配成完整系统
3.6 用显式图编排分支、并行、人工中断和循环
3.7 用两类真实仓库任务完成项目闭环
为什么结课课不学新机制？ 因为工程能力的标志不是「会多少机制」，而是「机制之间的连接是否真的有效」。笔记 3.7 八 8.2 的四类失败案例全部指向同一个问题：程序记录的状态，是否与实际执行事实一致。参数错了 handler 有没有提前跑？测试失败了状态有没有变成完成？审批中断后会不会错用旧授权？文件改了结果没保存怎么办？——每一问都不是单个模块的知识，而是连接处的验收。替代方案是「再做一个更大的 Demo」，代价是机制更多、断点更多；当前约束下选「两类小任务 + 逐项验收」，因为验收密度比功能数量更能证明掌握程度。

1. 两类任务与十件工具

项目用两类任务验收（笔记 3.7 一）：

  • 任务一 · 代码理解：「帮我找出该项目的登录逻辑，并生成 Markdown 说明文档。」——搜索认证代码、阅读模块、梳理调用链、输出文档并给出真实路径。样本：samples/1_login_demo。
  • 任务二 · 测试与修复：「读取登录会话模块的失败测试与日志，修复源码并复测，不修改现有测试。」——样本预置 7 条测试、4 过 3 红，缺陷在 src/auth/session-policy.ts（到期比较只比到「哪天」）。新增测试只能写 tests/generated/。样本：samples/2_bug_fix/demo-app。

十件仓库工具：list_files、search_code、read_file、read_directory（读侧四件）；write_file、apply_patch（写侧两件）；run_test、run_command（执行侧两件）；git_diff、git_status（Git 两件）。容易混淆的三处（笔记 4.1）：read_directory 看一层目录、list_files 按范围找文件；run_test 优先用任务配置允许的测试目标，run_command 能力更宽要单独查命令与审批；搜索结果为空和搜索失败必须区分。

阶段二 Runtime 的复用方式（笔记 1.2）：ToolRegistry 注册十件工具、JSON Schema 做参数校验、权限与风险分级区分读/写/执行、人工确认拦高风险、超时重试降级按错误类型决定、审计与 Trace 记录调用。复用的是治理边界和工程原则，不是把客服项目代码原样搬过来。

两个编号不能混（笔记 1.3，README 也专门强调）：trace_id 标识本次运行（给 audit --trace-id 用）；pending_approval_id 标识某一次待批准操作。一个任务可能产生多次审批——本机实测任务二一趟就有 3 张单。

为什么验收重点是系统行为而不是模型输出？ 笔记 1.1 的十项可验收能力全部落在「运行了什么测试、收到什么结果、做了什么修改、最终验证证据是什么」。模型的自然语言总结可以编（README 记录了真实事故：pi 入口的模型在补丁被拦后自己宣布审批已通过，而文件没落盘）；审计是 Runtime 写的，模型改不动。所以交付判定只认审计——这条纪律会在第 8 节的 deliverable.ts 里变成代码。

2. 按职责切分：pi Loop × LangGraph 审批图

笔记 7.1 的模块职责表，对应到代码就是八个组件：任务装配（platform.ts + tasks.ts）、计划管理（任务 brief + 决策脚本）、模型与决策适配（pi/provider.ts + pi/decider.ts）、Tool Runtime（runtime.ts）、仓库工具（tools/）、上下文处理（context-budget.ts）、状态与 Checkpoint（store.ts + hitl 存档）、完成检查与评估（deliverable.ts + eval.ts）。

决策器三档（README「切回离线」）：--decider real（默认，直连 DeepSeek；没设 DEEPSEEK_API_KEY 时按任务脚本降级并在开头说破）/ auto（离线优先）/ mock（只准离线，没脚本直接报 SCRIPT_REQUIRED）。三种口径都会把「这一趟是谁在决策」打在开头，并写进 decider.selected 这笔账。离线脚本可以检查工具与审批路径，但两类任务的模型能力验收要以真实模型运行结果为准（笔记 1.3）。

为什么不把整个系统画成一张大图？ 0015 已经给过判断：图的价值在显式状态与迁移，代价是 State 契约与装配成本。代码任务的主体是「下一步依赖上一步真实结果」的开放探索——路径无法提前枚举，画图反而把灵活性锁死；审批则是「提单 → 资格门 → 等人 → 答复门 → 终局」的固定形状，且必须跨进程恢复，正是图的主场。按职责切分后，两边各自可独立测试：TS 侧 121 条单测不依赖 HTTP 服务，hitl 侧 25 条 pytest 不依赖 Node。替代方案「全图」的代价是每次模型决策都要过一遍 State 序列化；「全 Loop」的代价是审批恢复要自己写存储——当前约束下各取所长。

3. 任务差异放配置，新能力扩代码

真实岗位任务会增加。如果每加一个任务都要在 Loop、工具函数和审批模块里改一遍，成本会失控（笔记 3.7 三）。项目的回答是 config/tasks.yaml：任务目标、允许范围、检查范围、输出路径、预算和审批要求写进配置；具体读哪个文件、下一步做什么，仍由模型决定。src/ 下任何 TypeScript 文件都不出现任务名——tasks.ts 只是解释器。

任务条目门口 gate裁定 via名单 approvers关键约束
understand（任务一）auto（工具自带确认要求）local（本地表）maintainer交付物 artifacts/login-flow.md；唯一写操作是文档
fix_tests（任务二）[run_test]（点名追加）http（LangGraph 图）maintainer、tech_leaddeny_write_extra: tests/** + allow_write_extra: tests/generated/**
debt_audit（任务三）none（一个都不拦）local—纯配置新增：一次检索、一份报告，TS 一行未改

三个键是正交的（tasks.yaml 注释原话）：gate 管「要不要过人」，via 管「谁来裁定」，approvers 管「谁批算数」。关掉门口不等于放开审批，换成图也不等于门口开着。环境变量 HITL_MODE 这一层永远大过 tasks.yaml 的 via，但它只换裁定人，不动门口：HITL_MODE=disabled 退到本地表后，审批门口=[run_test] 照旧生效，第一次 run_test 仍被拦下（本机实测）。

两处「失败关闭」值得记住：① 名单清空不是「谁都能批」，而是图在第一道门就把单子弹回（NO_APPROVER_CONFIGURED），连人都不会惊动；② gate=none 的任务每次放行都单独留一条 APPROVAL_GATE_OFF 审计——「没人看着」和「没记录」是两件事（runtime.ts prepare 里的专门分支）。

为什么 debt_audit 是这条原则的论据？ 判断「任务差异写错位置还是引擎缺通用能力」的试金石：如果接新任务必须在多个模块追加 if (taskType === "docs_audit")，就要停下来检查。debt_audit 用「一次检索 + 一份新报告 + 一次 git_status」全部由已有工具完成，所以它只加了一个 YAML 条目和一份决策脚本。替代方案「每类任务一个专用 Agent」的代价是治理链分叉——0007 的 MCP 教训（治理不分叉）在这里同样适用：入口可以多个，护栏必须一套。

4. 工具契约：两层定义、四层检查

模型决定读取登录入口，却传来坏参数——应该在 handler 执行前被拦下，并把具体错误反馈给模型（笔记 3.7 四）。项目把契约分成两层（contract.ts 头注）：

  • 第一层 · 声明式边界：直接写在每件工具的 TypeBox 参数定义里（minimum / maximum / minLength / description）。模型只看得到这份 Schema——它既是说明书，也是上游校验器的依据，所以能写在这里的边界一定要写在这里。
  • 第二层 · 语义规则：Schema 表达不了、又注定办不成事的参数——绝对路径（CONTRACT_PATH_MUST_BE_RELATIVE）、目录当文件读（CONTRACT_PATH_IS_DIRECTORY）、以 / 开头的 glob（CONTRACT_GLOB_NEVER_MATCHES）、编译不出来的正则（CONTRACT_PATTERN_NOT_REGEX）、整批空操作补丁（CONTRACT_PATCH_NO_CHANGES）、空白命令（CONTRACT_COMMAND_BLANK）。统一 CONTRACT_ 前缀，审计里一眼分得清是哪层拦的。

参数错误怎样反馈（笔记 4.3）：返回结构化失败，保留原 toolCallId，并说清 execution.started: false——后续处理需要知道这次操作有没有实际发生。模型修正参数后重新提交，新调用再次经过参数、权限、预算和 Sandbox 完整检查。参数错误通常不能靠原样重试解决：path 传成数字，重复十次仍然是数字；连续提交相同无效参数会撞上循环预算与 REPEATED_TOOL_CALL 护栏。项目的回喂文案比笔记示例更进一步：把整份契约贴给模型（「合格长什么样」），并警告重发后果——被拒之后模型拿到的是下一步，不是一句不行（kg_contract.test.ts 原话）。

⚠️ 材料与实现不一致（本课核对发现，以代码和测试为准）：笔记 4.3 举例 {"path": 42} 应返回 INVALID_ARGUMENT 且 started: false。但本机实测：pi-ai 的 validateToolArguments 会先执行 Value.Convert 做类型折叠——42 被折成字符串 "42"，通过 Schema，handler 真的去读了文件（报 ENOENT）。这不是 bug 而是上游的设计，单测明确写着「类型写错由上游顺手纠正，我们不再造第二个校验器」（limit: "2" 折成 2 后成功读取）。所以「handler 调用次数为 0」的关键证据要用折叠不掉的错误来验证：缺必填字段（write_file 缺 content）、超范围（limit 99999）、多余字段（additionalProperties: false）——本机实测这三类都在 handler 前被拦，账上只有 policy_decision。延续 0014/0015 的纪律：设计文档与实现不一致时，以代码和测试为准。

契约还要自检：verifyContracts 在装配阶段检查「每件工具的 Schema 有没有 description、limit 有没有上下界、additionalProperties 是否为 false、语义规则指向的工具与字段是否真实存在」。为什么不等模型跑到第 5 轮才发现？因为契约写错与规则失效都是「看起来一切正常、真要拦时一句都没拦住」的故障（contract.ts 注释）。cli contract 命令把模型视角摊开打印——交付前先对一遍「模型能看到什么」。

5. 上下文与预算：两笔账分开记

代码任务的特点：用户输入很短，工具输出却可能很长（笔记 3.7 五）。「帮我修复登录问题」一句话，后面跟着几十条搜索结果、几百行源码、多轮测试日志和 Diff。如果每轮都带全文，输入持续增长，旧日志还会淹没当前失败。预算分两层：

  • 单次上下文预算：这一轮最多给模型多少输入，还要为输出留空间；
  • 任务累计预算：整个任务最多消耗多少 Token、费用、工具调用和时间（loop-guard.ts：max_turns / max_tool_calls / max_total_tokens / max_cost_usd / max_duration_ms）。

压缩只减少后续请求输入，已经发生的消耗仍计入任务预算。系统提示词、工具定义和当前用户要求也占空间，检查时要一起算。

为什么不用 pi 自带的 compact()？context-budget.ts 头注给了理由：它要调一次模型生成摘要，摘要文字每次跑都不一样；离线跑（脚本决策器）根本没有可用的摘要模型，课后复现和评估器对账都无从下手。这里的压缩纯按规则裁剪，同一份输入永远得到同一份输出。这是「确定性摘要先行，再考虑让模型参与」的工程化（笔记 5.2 末段）。

三类证据绝不能丢（笔记 5.2，复习问题 Q17）：① 尚未解决的失败——错误位置、表现、日志引用；② 操作是否真的发生——等待审批、已应用、结果不明是三种状态；③ 验证结果对应哪个版本——测试通过后代码又变了，旧结果只能说明修改前状态。其余完整源码、日志、Diff 保存引用，需要时再读回。压缩后的记录要回答四件事：做过什么、得到什么结果、依据在哪里、还有什么没确认；「已确认」和「当前判断」要分开，避免猜测下一轮变成结论。消息协议要求 Tool Call 与结果配对，压缩时不能删掉调用只留无编号结果。

测试日志的截断顺序（笔记 5.1）：保留退出码和超时状态 → 提取可识别的失败信息 → 剩余空间展示片段 → 提取失败时保留有限首尾 → 提供完整日志位置。不能只留前几百行——真正的失败可能在中间或末尾。模型看到 truncated: true 就知道观察不完整，需要时按引用补查。

为什么审计要存哈希而不是全文？ 审计回答「发生过什么」，不是「全文是什么」。全文塞进数据库会让账本膨胀、查询变慢，而且脱敏后的文本也未必适合长期保存；但只存截断版又无法证明完整性。截断 + 全量哈希是取舍后的中间态：平时翻账看头部，争议时拿哈希对哈希。替代方案「全文入库」的代价是存储与泄漏面，「只存摘要」的代价是不可对账——当前约束（课堂可复现、事后可复核）下选哈希。

6. HITL：审批与执行分离

审批机制在第二章已经存在，本节把它放进具体任务流程，回答三个问题（笔记 3.7 六）：哪里设确认点、确认时给人看什么、批准后由谁执行。

哪里设确认点：代码理解任务里，list_files / read_directory / search_code / read_file 在授权范围内自动执行（仍要过参数校验、权限检查和沙箱）；在产物目录报告满足预授权条件时自动执行；文档要展示差异后确认；改动业务源码按任务权限拒绝或另行授权。不能仅按工具名放行所有 write_file——新建报告和覆盖源码影响完全不同，审批策略要结合任务类型、目标路径和写入方式。任务二把 run_test 点名进门口，因为它实际执行的是仓库里的 npm script——审批人要看最终解析出的命令，不是工具名。

给人看什么（笔记 6.3）：用户目标、失败证据、目标文件与补丁、当前验证状态、影响范围、操作编号与有效期。审批摘要要分清事实与推断：「三条测试失败」来自工具结果，「可能与日期粒度有关」是当前诊断，「补丁能修复」在复测前仍是未验证。批准只表示允许执行，执行后的验证才决定任务是否完成。

批准后由谁执行（笔记 6.2）：本地审批路径由显式执行动作（approvals execute）领取并执行获批操作；HTTP 审批路径由等待中的任务收到批准后继续（Loop 每 250ms 轮询，最长等 120 秒）。同一张审批单只能被一条路径领取，重复点击不能重复写入。拒绝、过期、服务不可达也要有明确结果。

图的两道门（hitl/graph.py）：check_eligible 在提单时判「这单有没有人够格批」——名单为空回 NO_APPROVER_CONFIGURED，发起人角色与名单无交集回 NO_ELIGIBLE_APPROVER，都不必打扰人；check_approver 在答复后判「批的人对不对」——action 必须是 approve/reject、审批人不能是发起人本人（SELF_APPROVAL_DENIED）、角色必须落在名单里（APPROVER_ROLE_DENIED）。本机实测：用名单外的 developer 角色批单，图回 rejected，跑 agent 的终端当场收口，收口码就是图给的那一个，样本仓库一字未动。

获有效批准后还要复核（笔记 7.3 + executeApproval 代码）：审批单里的参数是从数据库读回来的，没有任何上游校验器看过它——所以参数指纹比对、一次性领取（claimApproval）、契约与策略全部重跑一遍。批「往 src/a.ts 写」不等于批「往任何地方写」，也不等于批「这个参数本身合法」。等待期间文件被改、配置变化，旧批准就不能用于新现场（复习问题 Q18）。

中断恢复的五种情况（笔记 7.3 表）：等待审批 → 查询原审批状态，核对有效期和待执行内容；已批准未执行 → 重新检查执行条件再领取；操作可能已发出、结果未保存 → 先核对文件或进程现场；结果已持久化、计划未更新 → 根据已有结果补齐状态，不再执行；补丁已应用未复测 → 继续验证当前内容。Checkpoint 保存任务状态，不能撤销已经写入的文件；审批通过也不代表补丁已经成功应用。LangGraph 审批自身的 Checkpoint 能恢复审批流程，但整个代码任务还需要计划、工具调用、工作区信息和验证证据——两者通过运行编号和审批编号连接。

为什么 decide 和 execute 必须是两个动作？ 批准是一个授权决定，执行是一个副作用事实——两者之间隔着时间，现场可能变化。合成一个动作（批了就写）意味着授权时的快照就是执行时的现场，等待期间文件被改也照写不误；分开之后，execute 前才有机会重核指纹与策略。替代方案「审批即执行」省一条命令，代价是把 0012 的「恢复前核对现场」和 0008 的「allow ≠ 成功」全部推翻。图不可达时的两条失败路（HITL_KEY_MISSING / HITL_UNREACHABLE）也遵循同一原则：一律当成「没有人批准」，绝不能当成「批过了」——失败关闭。

7. 完整执行链：六步走一遍

笔记 7.2 把测试修复任务的完整执行链写成六步。对照代码逐步落点：

  1. 接收任务并建立运行上下文：CLI 收目标、任务类型、工作目录，加载平台配置与任务配置，检查工作区，生成 Run ID，确认决策器来源（cli.ts → platform.ts）。平台和任务约束共同形成有效策略。
  2. 建立计划并准备模型输入：计划层记录步骤和验收条件；上下文模块组装目标、限制、计划、近期观察和必要历史，检查输入预算再交给模型（context-budget.ts renderContext）。
  3. 接收工具调用，进入 Runtime：按本轮工具定义校验参数，检查权限、预算和审批要求；需要审批时保存待执行操作并进入等待；获有效批准后还要确认操作内容和执行条件仍然一致（runtime.ts prepare / gateForPi）。
  4. 在执行边界内调用工具：仓库工具在 Sandbox 范围内读取、打补丁或运行进程；结果保留退出码、错误类型、是否超时，以及文件或日志引用（tools/ + sandbox.ts）。
  5. 保存结果并更新进度：结果与原调用编号关联，记录审计，更新计划证据和任务状态，保存恢复所需信息；给模型的结果经过长度控制进入下一轮（store.ts + runtime success/reject）。测试命令执行结束可能只意味着「已取得失败基线」，是否代表「修复已通过」要看测试结果和当前阶段。
  6. 检查继续还是结束：模型可以提出继续或结束；结束时由完成检查核对产物、当前测试结果和改动范围；证据不足时在剩余预算内继续，或停止并报告未完成（loop-guard.ts shouldStop + deliverable.ts）。

四项能力怎样协作（笔记 7.3）：人工确认回答「这次具体操作是否获得授权」；Sandbox 回答「操作实际发生时能访问和影响什么」；Checkpoint 回答「暂停后继续执行需要哪些状态」；审计回答「提出、批准和执行了什么，结果如何」。以一次补丁为例：保存待修改路径、补丁内容、目标文件状态和审批编号 → 等待人工决定 → 批准后重新核对权限、补丁和目标文件状态 → 通过沙箱边界执行 → 结果写入审计，更新任务状态与 Checkpoint。统一关联信息四件套：Run ID 标识任务、调用编号标识动作、审批编号标识授权、产物引用指向日志或 Diff。

为什么「测试执行结束」不等于「修复完成」？ 这是 0014「一个结果两个消费者」在结课项目里的再现：run_test 的退出码 1 对模型是「还有三条红用例要修」，对状态是「已取得失败基线」——同一个事实，两种解读，取决于当前阶段。如果程序把「进程正常结束」当成「任务完成」，就会在失败基线刚拿到时宣布修复成功。笔记 8.2 案例二给了排查顺序：模型没看到失败日志 → 查回写/截断/组装；看到了但计划标完成 → 查完成条件；模型提结束程序直接通过 → 查完成检查；修改后沿用旧通过结果 → 查证据与版本关联。先找断链，不先改 Prompt。

8. 验收与评估：状态 ≠ 结论

两类任务各跑一次，自动评估报告要回答的关键区分（笔记 6.4）：执行状态（完成 / 失败 / 待审批 / 取消 / 预算耗尽）与验收结果（交付条件是否通过）分开记：

  • Agent 正常结束但报告文件不存在 → 验收失败；
  • 测试全通过但改了禁止改动的文件 → 不能通过；
  • 代码理解文档非空 ≠ 解释准确，还要对照源码；
  • 任务仍在等审批 → 不能计为完成。

deliverable.ts 把这条纪律写成代码：delivered 只看审计——任务声明的交付物路径与审计里成功的写入对上账才算；model_claims（最终回答提到交付物路径）单列，不参与 delivered；两者不一致就是 claim_without_evidence（说了但没做）。注释里记录了真实事故：模型在 PATCH_CONTEXT_NOT_FOUND 之后写下「复跑全绿」。被门口拦下的尝试（等审批、被契约拒）也进 attempts——评估器要看「它试了几次、每次卡在哪」，只看跑成功的那次等于没看。

eval.ts 的三条纪律：① 每次评估用独立工作副本与独立账本（.eval-runs/<时间>-<任务>/）——上一趟修好的代码不能替下一趟背书；② 待审批就是待审批：评估全程退到本地表裁定但绝不代人批准，自动生成报告不等于自动批准；③ 报告只写证据：产物路径、审批次数、用量都取自审计与 Trace。报告落 artifacts/eval_report.md 与 .json 两份，工作副本、账本路径与 Trace 编号都写进去，便于逐条复核。

四类失败案例（笔记 8.2，验收必做）：① 参数错误——工具有没有提前执行？（handler=0 + 文件原样 + 修正后重新全检）② 测试失败——有没有把执行结束当成任务完成？③ 审批中断——恢复后会不会错用旧授权？（重复提交批准、批准后再次 execute 都不能重复写入）④ 文件已改、结果未保存——恢复逻辑读当前文件，区分「确认已应用 / 确认未应用 / 无法判断」，无法判断就保留现场转人工。重点证明系统没有盲目重放；即使不能自动恢复，也要说清不确定在哪里。

为什么评估要「不代人批准」？ 如果评估器自动 approve，报告里的「完成」就混进了一个不存在的人工授权——它证明的只是「脚本能跑完」，不是「治理链有效」。把待审批照实记为待审批，反而让报告能区分三种能力：工具路径通不通（调用次数与审计）、治理拦不拦得住（审批次数与停止码）、交付有没有账（delivered）。替代方案「全自动批完跑到底」适合演示，不适合验收——验收要看的恰恰是「该停的地方停没停」。

9. 已知边界与工程复盘

笔记 8.3 的已知边界，逐条都是面试时「结论范围」的表述训练：

边界应怎样说明
样本覆盖两类样本通过，只能证明对应任务与环境下的表现
新增测试可写 tests/generated/；新用例是否有效仍需独立证据（eval 报告明确标「未覆盖」）
配置化已有工具能完成的任务可复用配置；新能力仍需扩展代码
模型输出同一目标可能产生不同操作顺序和消耗，按结果与约束验收
上下文压缩可能省略细节，必须保留关键事实和补查入口
中断恢复结果不明的写操作需核对现场，部分情况需人工接管
Sandbox保护范围取决于实际执行机制，路径检查不能代替进程层隔离
自动评估文件、测试、Diff 可自动核对；解释准确性仍需人工复核

真实模型的一次成功只是样本证据，不能推导稳定成功率。要讨论稳定性，需要固定任务集合、记录每次成败，再按数据判断（笔记 8.3 末段）——这正是你工作中 benchmark 的方法论。

AI 可以外包什么，工程师必须把关什么（笔记 8.4）：AI 可以整理流程、生成适配代码、编写 Schema、实现审批流、生成用例；工程师必须把关交付目标与完成条件、是否绕过关键检查、授权绑定什么与何时失效、状态是否符合现场、用例是否验证目标、修复是否处理真正原因。让 AI「加入断点恢复」，它可能生成一套能保存和读取 JSON 的代码——你还要追问：补丁执行后、结果保存前崩溃怎么办？审批过期怎么办？恢复时文件被别人改了怎么办？

一条连续三课的工程纪律：0014 发现作业设计文档与实现不一致（恢复范围、digest 口径），0015 发现 README 的 CLI 旧写法与固定 ticket 复用旧存档，本课发现笔记 4.3 的 path: 42 示例与上游类型折叠不一致。三课的处理方式相同：以代码和测试为准，把差异标出来，并用实验拿到现场证据。这不是「材料不可信」，而是工程世界的常态——文档会漂移，行为不会说谎。

掌握程度三层（笔记 8.4）：能解释（Loop、Runtime、Harness、Sandbox、Checkpoint 各自负责什么）→ 能追踪（沿一次任务找到输入、决策、校验、执行、回写和完成检查）→ 能修复并验证（发现未校验执行、旧审批复用、错误结果丢失或写操作误重放，并用测试证明修复有效）。结课要求至少到第二层，第三层是工作里的持续修炼。

本章六条判断（笔记「本章总结」，结课必须能脱稿复述）：① Loop 成立的条件不是能循环，而是 Tool Result 能真实驱动下一轮；② Planning 的核心不是列步骤，而是子目标有完成标准、依赖和证据；③ Checkpoint 的核心不是保存聊天，而是恢复业务现场并能核对现实；④ Sandbox 的目标不是不犯错，而是把影响限制在可拦截、可审计、可恢复的范围内；⑤ Harness 的核心不是又多一层封装，而是保证同一事实能正确进入模型、状态、审批和完成检查；⑥ LangGraph 的价值在于把复杂流程的状态和迁移显式化，不在于所有 Agent 都必须画图。最终的项目验收不是看模型说「完成了」，而是看：参数是否经过校验、副作用是否在授权与边界内发生、测试结果是否对应当前版本、中断后能否找回进度并避免重复写入、交付物、Diff、Trace 和审批记录能否互相印证。

10. 面试视角：两分钟主链 + 结课复习地图

如果面试官问「介绍一下你的 Agent 项目」，不要从框架讲起，按这条链讲：

  1. 目标与形状：两类真实仓库任务（代码理解 / 测试修复），十件仓库工具；主体是 pi Loop 的开放探索，审批这一段交给 LangGraph 图——按职责切分，不追求整系统一张大图。
  2. 契约与检查：工具参数两层定义（Schema 声明式边界 + 语义规则），四层检查各答各的问题；参数错误在 handler 前拦下，错误带调用编号和「合格长什么样」回喂模型；handler=0 用审计证明。
  3. 预算与证据：单次上下文与任务累计两笔账；确定性压缩不请模型帮忙，三类证据（未解决失败 / 操作是否发生 / 证据对应版本）绝不丢；审计存截断 + 全量哈希，可对账。
  4. 审批与执行：decide 只授权、execute 才落盘；批准绑定参数指纹，执行前重核契约与策略，一次性领取防重复写入；图的两道门管资格与答复，失败关闭。
  5. 验收：执行状态与验收结论分开；交付判定只认审计不认模型自述；评估用独立副本、不代人批准；四类失败案例逐一构造反例。
  6. 边界：一次成功只是样本证据；新增测试能力标未覆盖；结果不明的写操作核对现场，必要时转人工。

常见追问与回答方向：

  • 「模型说修好了，能信吗？」→ 不能；deliverable 只看审计里最后一次成功写入，model_claims 单列，claim_without_evidence 就是抓「说了没做」的。
  • 「怎么防死循环？」→ loop-guard 的轮数/调用数/Token/费用/时长五道预算 + 相同工具与参数的重复护栏（canonicalJson 指纹）。
  • 「审批通过后为什么还要再查文件？」→ 批准绑定的是那一次具体操作与当时现场；等待期间文件可能变了，executeApproval 重核指纹、重跑契约与策略。
  • 「中断以后怎么恢复而不重放副作用？」→ 五种中断位置五种处理；结果不明先核对现场；Checkpoint 不能撤销已写入的文件。
  • 「为什么不全用 LangGraph？」→ 开放探索路径无法提前枚举；图只用在状态迁移可枚举、需要跨进程恢复的审批段。

实验 ⑤：契约探针——用 invoke 绕过模型但不绕过 Runtime

  • 五发探针，每发先写预期再跑（都在 v2 目录）：
    node --import tsx src/cli.ts invoke read_file '{"path": "README.md", "limit": 99999}'
node --import tsx src/cli.ts invoke write_file '{"path": "artifacts/probe.md"}' --task understand
node --import tsx src/cli.ts invoke read_file '{"path": "/etc/passwd"}'
node --import tsx src/cli.ts invoke read_file '{"path": "../../outside.txt"}'
node --import tsx src/cli.ts invoke read_file '{"path": 42}'
    预期（本机实测）：① INVALID_ARGUMENT（超上界，回喂文案含「≤ 2000」与「只改点名字段」）；② INVALID_ARGUMENT（缺 content，文件未创建）；③ CONTRACT_PATH_MUST_BE_RELATIVE（语义契约层）；④ PATH_OUT_OF_WORKSPACE（类型正确但被 Sandbox 拒——层级不能混）；⑤ 注意：不是 INVALID_ARGUMENT——上游 Value.Convert 把 42 折成 "42"，handler 真的去读文件并报 ENOENT（TOOL_EXECUTION_FAILED）。这是笔记 4.3 示例与实现的不一致处，以代码和单测为准。
  • 用审计证明「handler=0」：
    node --import tsx src/cli.ts audit --trace-id <探针①的 trace>
    预期：账上只有 policy_decision:INVALID_ARGUMENT，没有 tool_execution——拦截发生在副作用之前；而探针⑤的账上有 tool_execution:error——它真的执行了。「返回了错误」不等于「拦住了执行」，差别就在这一条记录。
  • 沙箱两条线（任务二口径）：
    node --import tsx src/cli.ts invoke write_file '{"path": "tests/login-flow.test.ts", "content": "x"}' --task fix_tests
node --import tsx src/cli.ts invoke write_file '{"path": "tests/generated/probe.test.ts", "content": "x"}' --task fix_tests
    预期（本机实测）：前者 PATH_DENY_WRITE（已有测试禁写）；后者 confirm · APPROVAL_REQUIRED（allow_write_extra 单点放开，但仍要过人）——「允许例外」不是「免审批」。产生的待批单不用管，它留在本地账本里（v2/data/ 已 gitignore）。
