1. 这一课为什么存在：四类典型事故

课程 PDF（2-4.pdf）用一组真实感极强的事故开场：把六个核心 API 封装成 Agent 工具直接暴露给模型之后——查询接口遇到瞬时故障被盲目重试三次，下游收到三笔订单，用户被锁三笔钱；模型在参数里伪造 user_id 说「帮我查 user_123 的订单」，B 用户看到了 A 的订单；订单五分钟前已被取餐，取消请求照样发向下游，模型拿到报错也不知道下一步该干什么。归成四类典型故障：

  • 权限逃逸——身份和授权事实由模型参数传递，而不是服务端上下文；
  • 参数篡改——approved=true 这类字段被塞进参数伪造授权；
  • 幂等缺失——读操作和写操作使用相同重试策略，非幂等写被盲目重放；
  • 绕过规则——规划阶段的试探性写操作产生了真实副作用。

本质一句话（PDF 原话）：模型只产生「候选动作」，系统却错误地将候选动作当成了「执行许可证」。工具治理解决的就是：当前这一次调用，有没有资格进入真实世界——协议连通 ≠ 安全边界建立。

2. 治理的目标与主链

笔记定义句（本课第一句必背）：工具治理的目标，是让应该执行的动作成功，让不该执行的动作在副作用发生之前停止，并为每次放行、拒绝和失败留下可解释证据。主链压缩为七步（笔记原文）：

不可信 Tool Call
  → Pydantic 参数校验
  → 业务预检查
  → 白名单 / RBAC / 资源权限 / 审批
  → 受控执行与恢复
  → 输出投影 / 脱敏 / 限长
  → 审计与稳定 Tool Result

对照 tool_governance_demo.py 的 invoke()：这条链就是 prepare（before_tool_call）→ execute（_execute）→ finalize（after_tool_call）三段的展开。2-2 学过的骨架没变，这一课填进去的是每一格放什么判断、顺序为什么不能换。

3. 第一阶段：谁可以申请什么动作

工具分级：只读（权限与资源范围检查，可有限重试）、写入（更严格权限，要求幂等与审计）、高风险（显式确认、最小权限、强审计与隔离）。风险判断一定不能由模型临时判断，也不能由 Prompt 中一句「请谨慎」代替——它属于 ToolPolicy，由工程师根据可逆性、金额、数据敏感度和失败成本定义（demo 里 ToolPolicy(effect, risk, permission, requires_approval, max_retries, idempotent...) 就是这张策略表）。

四控制层，各回答一个不同的问题：

控制层回答的问题典型结果
工具白名单当前 Agent 和本轮任务能否看到或调用这个工具不可见或 TOOL_NOT_ALLOWED
RBAC当前登录主体是否具备该业务权限PERMISSION_DENIED
资源级授权当前主体能否操作这一个订单、文件或租户资源RESOURCE_FORBIDDEN
人工确认这次具体高风险动作是否获得确认APPROVAL_REQUIRED

RBAC 不等于资源授权：客服拥有 order:read，不表示可以读取任何租户的订单——Runtime 还要根据可信 tenant_id 和业务资源归属做二次检查。白名单要查两次：发现阶段一次（不盲目把工具交给模型），执行时重新检查一次（阻止旧 Tool Call、缓存消息或其他入口改变、伪造、放大工具权限，绕过发现层的限制）——这正是 0006 学过的「发现时检查 + 执行前复查」在白名单上的复用。

身份必须来自可信上下文：ExecutionContext（trace_id / user_id / tenant_id / permissions / allowed_tools / mode / approval_id）由登录态、服务间身份或 Harness 创建。模型只能提供订单号、金额、原因等候选业务参数，不能提交「我是管理员」「当前租户是另一家公司」「已经审批」这类授权事实。demo 的实现是 Pydantic extra="forbid"：参数里塞 user_id、approved 直接 INVALID_ARGUMENT，handler 零调用。

三态决策：只有 True/False 无法表达「用户有资格执行该工具，但必须暂停并等待人工确认」——所以是 allow / deny / confirm。门禁按固定优先级排布，一张梯子图记住（谁都不能翻越上面的层）：

硬 deny 规则            ← 任何模式、任何主体都翻不过
  ↓
plan 模式拒绝写和 Shell   ← 规划阶段零副作用
  ↓
执行期白名单             ← 旧 Tool Call / 缓存消息也拦
  ↓
RBAC                   ← 主体资格
  ↓
业务预检查              ← 资源归属、状态、额度
  ↓
一次性参数绑定审批        ← 高风险具体动作
  ↓
受控的普通 allow 规则     ← 兜底放行

bypassPermissions 最多只能减少普通交互确认，不能绕过硬拒绝、租户边界和高风险业务审批（demo 里 BYPASS 模式下 create_refund 仍返回 APPROVAL_REQUIRED——requires_approval 是强制审批，bypass 跳过的只是 requires_confirmation）。

审批必须绑定参数。不能是模型参数里的布尔值，也不能靠上下文临时记住「用户刚才说过可以」，它必须是可持久化、可恢复的状态，绑定 user_id、tenant_id、tool_name、规范化参数的 SHA-256 摘要、过期时间和一次性使用状态：

digest = sha256(
    canonical_json({
        "user_id": context.user_id,
        "tenant_id": context.tenant_id,
        "tool_name": call.name,
        "arguments": validated_args,
    }).encode()
).hexdigest()

为什么绑参数：常见攻击是在批准退款 100 元之后，通过对话诱导把参数改成 399 元——旧审批必须失效（摘要不匹配）。同一审批成功执行一次后也必须重新审批，哪怕只是重放。人工确认的完整流程（PDF 链路原文）：

Tool Call
  → PermissionEngine 返回 confirm
  → Agent Loop 暂停（等待状态，不是让模型假装完成）
  → 可信界面展示动作
  → 用户确认并生成 approval_id
  → 原参数重新进入 Runtime
  → 审批完全匹配才 allow

4. 第二阶段：允许执行以后，怎样避免失控

Schema 正确不等于业务正确。四层校验各管一段（v1 代码里就是 ValidationLayerGuide）：

层判断失败例子
Schema字段、类型、格式和范围金额为负、未知字段、订单号格式错
业务预检查资源归属、状态、额度、依赖事实订单不属于当前租户、已退款、可退金额不足
权限当前主体是否有资格申请普通客服没有退款权限
审批用户是否确认当前具体动作审批后金额改变、审批过期、审批已使用

SQL 和 Shell 不能原样交给模型：run_sql(sql) 的危害远大于业务任务，Prompt 写「不要执行危险命令」只能降低概率，不能形成安全边界。收窄优先级（笔记原文）：① 更窄的业务 Tool（query_order_status(order_id)）→ ② 参数化查询、只读账号、允许表与操作白名单 → ③ Shell 固定命令和参数枚举，必要时解析 AST → ④ Sandbox、中间目录和最小权限身份 → ⑤ 网络、文件系统、CPU、内存和时间边界 → ⑥ 无法确定安全性时 fail closed。

Sandbox 与权限治理不能混淆：权限治理解决「这次是否应该执行」（业务正当性），Sandbox 解决「即使执行了，也不会造成真实系统影响，降低爆炸半径」（技术失控范围）。两个问题、两套手段，互不替代。

重试语义按副作用区分。Runtime 重试解决外部系统明确瞬时故障，保持工具、参数和业务意图不变；Loop 重新决策处理计划错误、参数错误或业务条件变化，允许模型换工具、改参数或询问用户。demo 的实现一行看懂：retries = policy.max_retries if effect is READ or policy.idempotent else 0——只读或真幂等才允许重试。非幂等写超时意味着状态未知：返回 TIMEOUT_UNKNOWN，让 Loop 查询真实业务状态，禁止直接重放。硬超时不能只发取消信号后继续等：Runtime 自己必须与 deadline 竞争，按时返回（asyncio.timeout 包住 handler）；若 handler 仍在后台产生副作用，还要靠进程隔离、任务取消、下游幂等或状态对账解决。

原始结果不能同时发给模型、用户和日志。三类消费者需要不同视图：模型要完成下一步决策所需的最小结构化事实；用户要可理解、符合授权范围的业务结果；审计与运维要经过脱敏的决策、耗时、错误码和定位信息。键名包含 token、secret、password、authorization 的字段不应进入普通日志或 Context；Python traceback、数据库连接串和内网地址也不能直接返回模型。demo 的 redact() 递归脱敏 + project_for_model() 限深限宽限长，就是这层的实物。

Prompt 注入最终靠 Tool 边界兜底：注入检测和 Prompt 分区只能降低模型被诱导的概率，不能证明攻击永远失败。最坏情况下，即使模型被诱导生成危险 Tool Call，Runtime 仍要通过白名单、RBAC、资源范围、审批和 Sandbox 阻止副作用。所以安全验收不能只看模型回答是否礼貌，而要检查 handler 调用次数、数据库记录和外部请求是否保持为零——注入动作真的没被执行过。

5. 第三阶段：编排（了解即可）

先识别三种关系再谈编排：独立查询可有限并行；数据依赖必须显式串行（查店、搜品、预览、等待确认、下单，每一步结果是下一步的前提，顺序本身错误就该拒绝）；同一资源上的写操作按资源键排队，并结合数据库约束或幂等机制（demo 的 _execute 对写操作按 canonical_target 取 asyncio.Lock）。两个工程细节：排队时间也要进入总 deadline；一次生成一百个只读调用不等于可以启动一百个协程，需要全局、按工具和按租户的并发限制。不要提前复杂化——只有任务存在稳定的多步骤依赖、分支、补偿和长时间等待时，才需要 DAG 或工作流引擎。

6. 第四阶段：审计——怎样证明系统为什么这样决定

定义句（本课第二句必背）：审计不是打印完整 Prompt、参数和结果，而是在不扩大泄漏面的前提下，保存足以重建决策与副作用的证据。一条最小审计记录：trace_id、run_id 和 tool_call_id；工具内部名称、版本和来源；用户、租户和 Agent；决策阶段与执行阶段；allow / deny / confirm / executed / failed；规则来源、稳定错误码、重试次数和耗时；经过脱敏的参数摘要和业务对象 ID（demo 只记 argument_keys，不默认保存参数值）。

决策审计与执行审计必须分开：allow 只表示策略允许进入 handler，不表示业务已经成功；TIMEOUT_UNKNOWN 也不能证明业务失败。分开记录，才能同时回答「为什么放行」和「真实发生了什么」。Trace 与 Audit 不能互相替代：Trace 回答一次 Run 中模型、工具、队列和下游调用如何流动；Audit 回答谁以什么身份、依据什么规则触发了什么业务动作。最后一条纪律：审计写入失败不能覆盖真实业务结果——否则会把一次已经成功的退款伪装成失败并诱发重试；生产上用可靠事件或告警处理审计故障，并明确哪些高风险动作在无法审计时必须 fail closed。

7. 八项安全测试：证明治理有效

测试不能只断言返回了某个中文错误文本，还要断言副作用没有发生。八项与 demo 测试文件的对应：

测试要证明的硬性要求对应测试函数
deny-first宽松模式不能覆盖硬拒绝test_unallowed_tool_is_denied_before_execution
plan 模式只读规划阶段不能产生写副作用test_plan_mode_denies_write_before_approval_and_handler
严格 Schema模型不能伪造身份、租户和确认test_schema_rejects_forged_identity_and_approval
RBAC权限不足时 handler 零调用test_rbac_denial_keeps_handler_at_zero_calls
审批改参批准 100 元后改成 399 元，旧审批失效test_approval_rejects_amount_changed_after_confirmation
结果边界敏感字段脱敏，结果仍保留调用关联test_result_is_redacted_but_audit_keeps_tool_call_id
双重白名单模型不可见，旧 Tool Call 在执行时也被拒绝test_discovery_and_execution_both_enforce_whitelist
一次性审批首次成功后不能用同一审批重复执行test_one_time_approval_cannot_be_replayed

一条有证明力的关键断言（笔记原文）：

result = await runtime.invoke(snapshot, call, unauthorized_context)

assert result.code == "PERMISSION_DENIED"
assert refund_gateway.calls == 0
assert result.tool_call_id == call.id

第一条只证明返回协议正确；第二条才证明真实副作用没有发生；第三条保证 Agent Loop 还能把失败关联回原调用。这就是 0005 学过的「有证明力的断言」在治理场景的标准形态。

8. 面试视角：这一课怎么被问

  • 开放题：「讲讲你的工具治理体系」——用定义句开场（该执行的成功、不该执行的停在副作用之前、留下可解释证据），然后走门禁梯子，最后落到「所有调用走唯一 invoke() + 八项副作用测试」收尾。
  • 追问链 1：「模型伪造身份怎么办？」→ 可信上下文：身份来自 ExecutionContext，模型参数只允许业务候选字段，extra="forbid" 拒绝授权字段。
  • 追问链 2：「退款重复执行怎么办？」→ 非幂等写不重试、超时返回 TIMEOUT_UNKNOWN 查状态、审批绑定参数摘要 + 一次性核销、按资源键排队。
  • 追问链 3：「Prompt 被注入怎么办？」→ Prompt 分区降概率，Tool 边界兜底；验收看 handler 零调用，不看模型回答是否礼貌。
  • 追问链 4：「bypassPermissions 是不是后门？」→ 不是：它只跳过普通低风险确认，硬拒绝、租户边界、强制审批一条不少。
  • 反向题（审查岗）：「给你一段 AI 写的治理代码，你查什么？」→ 五查：身份是否可从参数传入；门禁顺序是否可交换（deny 是否够前）；审批是否绑定参数摘要；结果是否原样回灌三方；测试是否只断言错误码不断言副作用。
