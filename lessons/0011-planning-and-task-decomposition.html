Planning 与任务拆解

本课定位：Week03 第二课。0010 让 Agent「循环起来」并停得住；这一课回答循环之上的新问题——任务由哪些可验收的子目标组成、当前允许开始哪一步、哪一步真的完成了。Loop 保存的是消息历史，它知道模型读过什么、说过什么，不知道任务还差哪几步。本课给 Loop 加一层计划状态：子目标 + 依赖 + 证据 + 完成契约，底层循环一行不改。
材料定位：course_code/week03/第三章-学习笔记.md 3.2 节（行 719–1192，学生版学习笔记，本课术语以此为准）+ course_materials/week03/3-2.pdf（31 页教师 PDF）
代码定位：course_code/week03/3-2/planning_agent_demo/（实验组：计划层完整版）；对照组 course_code/week03/3-2/codebase_agent_demo/（无计划层，但 Runtime、契约同等加强——两者唯一差别是计划层）。核心新文件 src/plan-store.ts（471 行，计划状态与确定性规则）、src/planning-prompt.ts（运行提示词与计划快照）
预计用时：精讲 30 分钟 + 测验 25 分钟 + 第二层动手练习 30 分钟
本课验收标准（笔记「本节重点与验收」）：能判断——一个任务该用 Workflow、Loop 还是显式计划；一份计划为什么不能只写动作；什么情况只是改参数、什么情况必须修订计划；怎么证明计划规则不是提示词里的摆设。

怎么用这一课

先讲后测，五五开：第一部分精讲先把地图建好，读的时候每节自问「这解决了什么事故」；第二部分 19 题测验检验留存，前 4 题是 0010 四个薄弱点的换形式间隔重测（判定顺序、缺失项列表、拦截证据、停止原因不可覆盖——0010 测验 78%，这四题是对那次诊断的兜底），做完页面底部自动生成诊断报告。

这一课在三层学法里的位置：第一层建地图——精讲第 3 节的组件分工表和第 9 节的 Hook 接线表是本课两张「必须能默画」的图；第二层跑代码——实验①–④全部离线可跑、不需要任何 API key（测试用脚本化模型响应）；第三层工程师级——精讲贯穿两个问法：「这条规则如果不由程序守住，模型会怎么绕」「这个错误码出现时，文件系统里到底发生了什么」。

就业面试视角：Planning 是 Agent 岗位面试的分层题——「Plan-and-Execute 和 ReAct 什么时候用哪个」只是入场券；真正的区分题是「模型说这一步做完了，你怎么验」（证据四项检查 + StepVerifier）和「计划要改，谁能改、怎么改才不失控」（版本对齐 + 原子修订 + 不能降标准）。答得出「模型提、程序查」的分工，就把「用过 LangChain Planner」的候选人甩在身后。

第一部分：精讲（先读，测验在后）

0. 开篇：任务变了，Loop 不够用了

0010 的 Codebase Agent 已经能完成代码理解：搜索登录逻辑、读文件、写 artifacts/login-flow.md。这类任务输入明确——找什么、写哪里都说清了。换成一个修复任务，性质就变了（笔记 3.2 开篇）：

请修复登录模块的会话过期边界问题：先定位登录和会话相关代码，复现失败测试，分析根因，只修改必要源码，然后运行目标测试、边界测试和回归测试，最后把根因、改动和验证结果写入 artifacts/login-fix.md。

提示词只说了「会话过期边界」，没说错在哪。可能是日期粒度截断、时区语义、边界是否包含到期时刻——哪一条成立，只能靠工具结果证实或推翻。当工具结果推翻当前判断时，Loop 无法回答三个问题（PDF p2）：哪一步的结论作废了？哪些跑过的验证要重做？手上这份改动到底能不能交？

本章地图推进一格：3.1 解决「怎样继续、何时停止」，3.2 解决「先完成什么、还缺什么、什么时候改变路径」——计划层。后续 3.3 的 Checkpoint 会把这份计划状态持久化，3.7 的 Codebase Agent v2 会把它用到真实仓库任务上。

1. 要不要计划：先判断，再动手

计划会增加调用、等待和状态维护成本，不是所有任务都该上 Planner（笔记 1.3）。判断标准不是「任务听起来复杂」，而是现有工具调用或固定流程能不能把事情管住。一次查询、固定字段抽取、审批流程由制度定死、特别在意响应速度、高风险操作不允许模型临时增删步骤——这些都不必急。

四种执行方式按两个问题选（笔记 1.4、PDF p9–p10 的决策树）：

拿到一个任务
 ├─ 一次明确操作就能完成？……………… 直接 Tool Calling（查一个订单状态）
 ├─ 步骤与异常分支能提前写清？………… 固定 Workflow（固定规则的数据导入）
 ├─ 下一步取决于执行中获得的信息？…… Agent Loop（调查登录测试为什么失败）
 └─ 还要持续追踪多子目标、依赖与验收？ 在 Loop 中加入显式计划（跨模块修复+分层验证）

两个易混点：① Workflow 不是只能从头到尾——它也可以有分支、重试，甚至某一步调用模型；② 有计划能力不等于单独建一个 Planner Agent。几种方式还能混用：排查故障先用 Loop 调查，需要追踪多子目标时加计划，修复完成准备发布时交给固定 Workflow。

一次性计划 vs 动态计划（笔记 1.5）：一次性计划的主要步骤在开始时就能列清（代码理解：搜索入口→读实现→整理调用关系→写文档）；动态计划开始时只能定「先查清、再修复、再验证」，具体怎么改要等证据。一次性计划与 Workflow 的区别在步骤由谁定：模型根据本次任务临时列出步骤是一次性计划；每次都做同一套操作、步骤和分支由工程师事先写好是 Workflow。允许调整不等于每次都要调整——真实运行可能计划 v1、修订 0 次，模型读到源码就找到了问题，后面步骤继续可用。

2. 组件与分工：模型提，程序查

计划层落在组件上（笔记 1.2、PDF p5–p6）。这张表是本课第一张必默画图：

对象            主要职责
──────────────────────────────────────────────────────────────
Planner         提出子目标、依赖、下一步和修订建议（模型的活）
Plan / PlanStore 保存步骤、状态和修订历史；检查依赖与状态转换（程序的活）
pi Agent Loop   调用模型、处理 Tool Call、回写 Tool Result 并继续（3.1 已有）
Harness         装配模型、工具和计划组件，在执行接缝上落实约束（3.5 展开）
Tool Runtime    参数校验、权限检查、超时与工具执行（第二章已有）
Verifier        检查实际证据是否满足当前验收条件（程序的活）
──────────────────────────────────────────────────────────────
一句话锚点：模型负责提下一步，程序负责检查能不能做、做完算不算数。

对照代码：plan-store.ts 里的 PlanStore（依赖检查、证据校验、原子修订、修订预算全部收口在这里）+ EvidenceStore（可信证据的唯一来源）+ PlanningSession（一次 Run 的计划容器，Loop、计划工具、完成契约通过它读写同一份计划与证据）就是表中三个程序侧对象的实体。注意 pi 完全不知道计划的存在——计划层全部是应用代码，pi 继续提供 Loop 与 Hook（plan-store.ts:2-4 注释原文）。

Why（为什么这个分工是本课的灵魂）：0010 已经证明「模型说做完了不能信」（FINAL_REJECTED）；本课把同一原则推到每一步——模型说「这一步完成了」同样不能信，要证据；模型说「我可以开始这一步了」不能信，程序算 ready；模型要改计划，程序验版本、控预算、守标准。整个计划层就是给模型的自由裁量权配上程序化的护栏。

3. 计划写成什么样：从动作改成可验收结果

列出「分析、修改、测试」不够——模型要知道每步做到什么程度，程序要有办法检查做没做完。方法是把模糊动作改写成可验收子目标 + 可接受的证据（笔记 2.1）：

模糊动作      可验收子目标                              可接受的证据
────────────────────────────────────────────────────────────────────
复现失败  →   在 scope=target 上拿到退出码 1，         命令、退出码、失败断言
              并保留失败断言的期望值与实际值            的期望值与实际值
修一下    →   产生当前代码版本上、允许修改范围内的      受控 Diff、修改理由
              最小 Diff
跑测试    →   target、boundary、regression 三个        三个范围各自的
              范围的退出码都为 0                       退出码与测试范围

写一个步骤时多问两句（笔记 2.1 收尾）：① 做完以后，我应该知道什么、拿到什么？② 拿什么来证明？答得出来，这一步才有办法验收。课程给了一个完整的六步修复计划示例（笔记 2.4、PDF p15）：s1 确认入口与允许修改范围 → s2 复现失败 → s3 按证据确认根因 → s4 最小修复 → s5 三个测试范围全过 → s6 交付说明。注意「一个步骤不一定只调一次工具」——s5 就可能包含三个测试范围的三份证据。

4. 计划至少保存什么：PlanStep 字段逐个 why

三个对象：Plan 保存整份计划，PlanStep 保存一步，Evidence 保存工具执行留下的证据（plan-store.ts:33-53）。字段为什么这么分（笔记 2.2）：

PlanStep {
  id               步骤标识
  objective        完成后系统应产生的新事实——不能只写「分析一下」
  dependsOn[]      前置步骤；决定谁先谁后
  successCriteria[] 事前定义的完成标准 ──┐ 两个字段必须分开：
  evidenceIds[]    执行后记录的证据编号 ──┘ 标准不能事后挪，结果不能自封
  status           六个值，见下
  attempts         尝试次数
  lastError?       最近一次失败原因
}
Evidence {
  stepId / toolCallId   归属：属于哪一步、由哪次调用产生
  artifactVersion       产生该证据时的代码版本（本课关键，第 6 节展开）
  kind                  "tool" | "test" | "diff" | "inspection"
  summary / payload     人读的摘要 + 机器查的载荷
}

status 的六个值（plan-store.ts:11-17）：pending 等依赖、in_progress 执行中、completed 证据已过验收、blocked 权限/预算/外部条件阻塞、skipped 被替换或明确放弃、failed 失败待修订。Why 不能只有完成/未完成两个值：阻塞和失败需要不同的处理路径（等外部条件 vs 等修订）；skipped 不等于 completed——尤其验证步骤，跳过不等于验证过（第 7 节展开）。另外两个全局字段：constraints 保存任务约束（实际限制仍由执行检查落实），maxRevisions 限制修订次数——避免一直改计划却不结束任务。

5. 标准在事前，证据在事后：两层验收

本课最重要的认识论：不能看到退出码 0 就把所有步骤算完成，也不能看到非零就全算失败。同一条证据在不同步骤意义不同（笔记 2.3）：

证据                                能证明                    不能证明
──────────────────────────────────────────────────────────────────────
scope=target 退出码 1                复现步骤完成，原问题存在   修复完成
scope=target 退出码 0（版本为当前）  修复验证完成              边界与回归也通过
三个范围退出码都为 0（版本为当前）   本次修复在约定范围内可交付 仓库其它区域没有回归

模型申请完成某一步（complete()，plan-store.ts:223），程序先做四道结构检查：① 证据非空；② 引用的证据存在；③ 证据的 stepId 与当前步骤一致；④ test/diff 类证据的 artifactVersion 等于当前代码版本。这四项只回答「证据拿对了没有」——第 ⑤ 道 StepVerifier 才判断证据够不够满足完成标准（不够则 PLAN_COMPLETION_REJECTED，步骤留在 in_progress）。

Why artifactVersion 是灵魂字段（PDF p12、笔记行 4141 的总纲）：测试通过后又修改了文件，旧证据就失效——「测试记录只对当时受测的代码版本有效……最新失败不能被更早的成功掩盖」。引用旧版本通过结果申请完成会得到 PLAN_EVIDENCE_STALE。这是把「代码变了要重验」这条工程常识变成机器可执行的规则。

最后分清两层验收：步骤验收回答「这一步能不能算完成」；任务级 CompletionContract 回答「整个任务能不能交付」。步骤全勾上不等于任务完成——整体还要检查当前版本 Diff、三类测试通过记录和交付说明（对照 0010：完成契约从 LoopGuard 硬编码升级为可注入，同一套 Loop 跑理解任务和修复任务只差换一个契约）。证据的铁律贯穿两层：证据来自真实工具执行，模型只能引用编号——模型自己写一句「测试通过了」不构成证据。

6. 依赖决定谁先谁后：ready 由程序计算

依赖回答一句话：「这一步要开始，前面必须先拿到什么？」六类依赖（笔记 2.5）：前置（没复现不该动代码）、数据（判断根因要错误栈和检索结果）、权限（写文件前过策略和审批）、验证（改完必须跑目标测试）、汇合（目标和边界都过才能进回归）、互斥（多个候选方案只能一个进写操作）。

ready 由程序计算，不由模型声明（plan-store.ts:189）：

readySteps(): PlanStep[] {
  return this.plan.steps.filter((step) =>
    step.status === "pending"
    && step.dependsOn.every((id) => this.requireStep(id).status === "completed"));
}

注意 filter 的条件：skipped 和 failed 都不满足依赖。所以 skip() 会先查有没有别的步骤在等它（plan-store.ts:277）：有下游依赖就直接 PLAN_SKIP_REQUIRES_REWIRE——必须先说明为什么不需要、下游改成等谁，通过一次修订一起处理，不能直接把跳过当完成。最后一条边界：依赖就绪不等于没有资源冲突——两步都 ready 但都要改同一个文件，仍然不能并行；依赖检查只回答前置条件齐不齐，不能替代并发资源检查。

7. 计划怎样变化：先分流，再修订

执行后发现的偏差，先记录发生了什么、判断影不影响原安排，再决定处置（笔记 3.1 的分流表、PDF p18）：工具参数拼错→改正参数，不修订；目标文件不存在→先搜索实际位置，路径变了局部修正、模块结构变了才修订；短暂超时→受控重试；测试断言指向到期边界→先补证据再判断假设是否被推翻；用户中途补充约束→检查计划与已有 Diff，让冲突步骤和相关验收失效；权限拒绝或预算耗尽→记录阻塞，不能靠改计划绕过。

测试失败还要先分类（PDF p19）：assertion（到达业务断言但没满足——检查实现、预期或根因假设）、environment（缺依赖，断言根本没执行——先恢复测试条件）、timeout、infrastructure。非零退出码本身不够：缺依赖时测试没跑到原断言，不能叫复现成功。

什么才算一次修订（笔记 3.2）：不要数「失败了几次」，要问「按现在拿到的信息，原来安排的步骤、依赖和后续路径还合不合适」。路径拼错改参数重跑——目标和步骤没变，不占修订预算；证据推翻根因判断，原修改步骤不该继续做，要替换步骤、调整依赖——这才是修订。重复一次动作不等于修订，补一条当前步骤能用的证据也不等于换了一份计划。

8. 原子修订：六项检查与三条程序守住的底线

修订申请（RevisionRequest，plan-store.ts:68）至少带 expectedVersion、reason、evidenceIds 和变更内容。程序收到后六步（revise()，plan-store.ts:290，PDF p22 的流程图）：

1. 版本对齐    expectedVersion ≠ 当前版本 → PLAN_VERSION_CONFLICT
2. 预算        revisionCount ≥ maxRevisions → PLAN_MAX_REVISIONS_EXCEEDED
3. 依据        reason 非空；evidenceIds 非空且都真实存在
4. 应用变更    在「候选副本」上：旧步骤标 skipped、新步骤插入、下游依赖自动改接
5. 整体校验    ID 唯一、依赖存在、依赖图无环（有环 → PLAN_DEPENDENCY_CYCLE，
               整次修订被拒，原计划不变）
6. 提交        版本 +1、修订计数 +1、追加一条修订记录

Why 三件事必须由程序守住（笔记 3.3 的表格）：版本对齐防「基于旧版本的申请覆盖新计划」；原子提交（候选副本四字是关键，PDF p23）防中间状态——旧步骤已跳过而新步骤还没接上时，别处看到的计划是残缺的；预算上限防「失败循环里无限修订，永远不收敛」。旧步骤不会消失——它留下被替换记录，回头看修订历史才知道当时准备做什么、后来为什么换方向。

修订只能改路径，不能改标准（笔记 3.4）：回归测试一直不过，模型不能把「回归测试通过」改成「运行过回归测试」然后给自己打勾——用户要的结果没变，验收底线不能由模型自行降低。反过来，用户补充新约束（如「不要修改公共 API」）也不能只把这句话加进提示词：要记下新约束、检查已有 Diff、暂停冲突步骤、修正不合要求的改动并重新验证；已发出通知等不可直接撤销的操作，把事实说清楚交给人处理——改掉计划里的文字，不等于现实里的操作也撤销了。全节一句话锚点（值得背下来）：

子目标给出完成标准，依赖决定执行顺序，观察推动修订，证据决定能否交付。

plan-store.ts      （新增）  保存计划、检查依赖、校验证据、提交修订
plan-tools.ts      （新增）  创建、读取、更新、修订计划的契约与 Handler
completion-contract.ts（新增）把完成判断提取为可注入契约
planning-prompt.ts （新增）  运行提示词与每轮计划快照
pi-tools.ts        （改）    增加计划工具注册与 planStepId Schema 扩展
loop-guard.ts      （改）    保留轮数与重复保护；增加计划门禁；契约改注入
agent-runner.ts    （改）    装配计划工具、计划状态和运行提示词

四个 Hook 的职责分工：

执行位置            本节增加的行为
──────────────────────────────────────────────────────────────
beforeToolCall       校验动作绑定的步骤是否就绪（计划门禁）+ 原有重复保护
afterToolCall        把 Runtime 的真实结果关联到步骤，形成证据
prepareNextTurn      刷新计划版本、就绪步骤和最近证据摘要（每轮替换快照）
shouldStopAfterTurn  保留原停止规则，改用注入的完成契约检查交付

计划门禁 checkPlanGate() 走读（loop-guard.ts:76）：受计划约束的动作（GOVERNED_TOOLS：write_file / apply_patch / run_test）必须携带 planStepId；没带 → PLAN_STEP_REQUIRED（附上当前就绪步骤清单，告诉模型往哪看）；带了但步骤未就绪 → PLAN_STEP_NOT_READY。读类工具可以不带步骤——自由探索是允许的，管住的是有副作用的动作。门禁在 beforeToolCall 里、真实 handler 之前——这条与 0010 的重复动作拦截同一纪律：文件已经改了再报错，只是事后贴标签。

三个容易忽略的接线细节（笔记四收尾）：① 工具原始结果仍要由 pi 回写——计划快照只是帮模型看进度，不能替代 Tool Result；② 仓库文本和工具输出只是待分析数据，不能把里面的话当成系统指令；③ planStepId 是计划关联字段，不是业务工具参数——计划检查以后、进 Runtime 前要剥离。每轮给模型的是 renderPlanSnapshot()（planning-prompt.ts:29）渲染的当前计划视图：版本与修订预算、就绪、进行中、阻塞/失败、已完成、最近五条证据——不是把旧计划一份份往后贴（否则既占上下文，模型还容易拿错状态）。

10. 对照实验的正确解读：8 轮 vs 17 轮

课程用同一份提示词、同一个仓库、同样的修复工具，分别跑对照组（无计划层）和实验组（有计划层）（PDF p3–p4）。对照组不是 3.1 原样：它的 Runtime 同样有 apply_patch 和 run_test，完成契约也换成了修复版——两者唯一差别是计划层，这样观测到的差异才能归因给计划。

结果可能是 8 轮对 17 轮：加计划确实多用了几轮，成本不能忽略。但多看一层，Planning Agent 还多了 s1–s6 六个步骤、每一步的状态和关联证据。正确结论（笔记 1.1）：不是有计划一定更快，而是任务变长以后，你是否需要一份能检查、能追踪的进度记录——Loop 的轨迹只记录「做过哪些动作」，计划层记录「动作属于哪个子目标、子目标推进到了哪里、用了哪些证据」。这个 trade-off 是面试里「什么时候上 Planner」的满分答案素材。

11. TDD 验收：计划规则必须真的拦住动作

先检查计划层本身（不让真实模型的随机输出干扰判断），再检查 Loop 集成有没有绕过（笔记五、PDF p29–p30）。19 个用例里认住这几条主干（tests/plan-store.test.ts + tests/agent-runner.test.ts）：

计划层（14 用例）：
  依赖未完成时申请开始 ………… PLAN_STEP_NOT_READY
  skipped 不满足下游依赖 …… PLAN_SKIP_REQUIRES_REWIRE，必须修订改接
  没有证据 / 证据不存在 / 证据不属于本步骤 / 旧版本证据 ………… 全部拒绝
  替换步骤 ………………………… 旧步骤 skipped + 下游依赖原子改接（changes 里两条记录）
  有环的修订 …………………… 整体拒绝，原计划不变（候选副本的意义）
  缺理由缺证据 / 旧版本发起 / 超预算 ………… 各自的拒绝码
Loop 集成（5 用例）：
  完整闭环 ………………………… 计划 v1→v2，源码真实改写，交付说明落盘
  缺 planStepId …………………… PLAN_STEP_REQUIRED，apply_patch handler 调用次数为 0
  绑定未就绪步骤 ……………… PLAN_STEP_NOT_READY，run_test handler 调用次数为 0
  引用不存在证据 ……………… 申请完成被拒，步骤不完成
  证据不足时 Final …………… 注入 FINAL_REJECTED，直到预算上限 MAX_TURNS_EXCEEDED

关键断言并不仅是「返回了错误」，而是 handler 调用次数为 0（笔记五原文）。这是 0010「有证明力的断言」在计划层的复现：错误码可以打印出来骗人，真实执行次数伪造不了。另外注意最后一个用例的深意：FINAL_REJECTED 逼模型继续，但预算兜底——计划层不能让「永远差一点」的 Run 无限跑下去。

12. 面试视角：这一课怎么被问

  • 「什么时候需要显式计划，什么时候 Loop 就够？」——两个问题定位：下一步是否取决于执行中的信息（是→Loop 能解决）；是否还要持续追踪多个子目标、依赖和验收（也是→加计划）。追问「计划会不会拖慢」→ 8 vs 17 对照实验，成本真实存在，换来的是可检查可追踪的进度记录。
  • 「模型说这一步做完了，你怎么验？」——四道结构检查（非空/存在/归属/版本）+ StepVerifier（够不够）；证据只来自真实工具执行、模型只能引用 id；同一证据在不同步骤意义不同（退出码 1 在复现步骤=成功、在验证步骤=没修好）。追问「测试通过后又改了代码」→ artifactVersion，PLAN_EVIDENCE_STALE，最新失败不被更早成功掩盖。
  • 「计划要改怎么办？」——先分流（参数错改参数不占预算）；真修订走 revise_plan 六项检查：版本对齐、预算、理由证据、候选副本、整体校验、提交。追问「模型能不能把验收标准改松」→ 修订只能改路径不能改标准。
  • 「怎么证明计划层不是摆设？」——门禁落在 beforeToolCall、handler 之前；断言 apply_patch / run_test 的 handler 调用次数为 0，而不是断言错误码出现。与 0010「handler 恰执行 2 次」同一口味。
