0. 开篇：一条发布流水线，六个机制

先看本节要编排的业务流程：

开发者提交上线工单，系统自动跑完构建、单测、安全扫描、依赖审计，按变更风险分成 L / M / H 三级审批，再进入预发、10% 灰度、50% 灰度、100% 灰度，并在该停的地方停下来等人批准。

这个流程覆盖 LangGraph 的六个核心机制：State / 节点 / 边、条件分支与循环、ToolNode 并行、interrupt 人工审批、Checkpoint 跨进程恢复、Mermaid / 流式 updates / 状态快照 / langgraph dev 可视化。

先把生态里的角色分清（笔记 3.6 一 1.1）：

工具解决什么不解决什么
LangGraph用状态、节点、边编排分支、循环、中断和恢复不帮你写 Prompt，也不做模型抽象
LangChain模型客户端、消息类型、工具接口统一封装不负责复杂多步流程调度
LangSmith / Langfuse记录调用输入、输出、耗时和 Trace不参与执行，不能让任务具备恢复能力
Dify / AgentScope可视化工作流 / 另一套多 Agent 框架不是 LangGraph 插件，定位不同

两条判断先记住。第一，Trace 记录发生过什么，Checkpoint 保存接下来怎么继续；装观测 SDK 不等于能恢复任务。第二，用 LangGraph 不要求装 LangChain 全家桶；模型客户端和消息类型可以用少量组件，状态图靠 LangGraph 本体。

为什么要把流程显式画成图？ 当分支、并行、人工暂停和循环散落在代码里时，你只能靠读 if/else 还原流程，事故复盘时也很难回答「工单现在停在哪、下一步是谁」。图把这些迁移变成可枚举、可渲染、可存档的对象；代价是多了一层 State 契约和装配代码，简单直线流程反而更啰嗦。所以本课的判断不是「图更高级」，而是流程复杂到值得显式表达时，图比散落的条件分支更好检查（笔记 3.6 九）。

1. 映射：业务概念 → 图对象

LangGraph 的第一动作不是写节点，而是把业务词翻译成图词：

  • 工单，贯穿全流程的共享数据 → State，一个随流程传递的字典；
  • 每个业务步骤（受理、分级、审批、部署、灰度、报告）→ 节点，一个 Python 函数；
  • 步骤依赖关系 → 边，add_edge 或 add_conditional_edges；
  • 流程总装 → StateGraph，最后由 compile() 得到可运行图；
  • 等待人工输入 → interrupt() + Command(resume=...)；
  • 跨进程暂停恢复 → Checkpointer，例如 SqliteSaver；
  • 调用外部工具 → ToolNode。

2. P1 主线：State、Node、Edge

第一步只搭最直的一条路，不含分支、不含中断：

START → intake → deploy_staging → smoke_test → canary_10 → canary_50 → canary_100 → finalize → END

State 用 TypedDict 声明预期字段。它方便编辑器和静态检查发现错误，但本身不会在运行时拦截额外字段（笔记 3.6 二 2.1）——这是常被误解的一点。顶层的 ReleaseState 还把「闭世界」写进注释：任何节点不得引用这里未声明的字段；验收测试 AC-7 会检查最终 State 没有多出未声明键。

class ReleaseState(TypedDict):
    ticket_id: str
    service: str
    version: str
    patch_diff: str
    revision_count: int
    rollback_count: int
    max_revisions: int
    max_rollbacks: int
    canary_cursor: int
    messages: NotRequired[Annotated[list[AnyMessage], add_messages]]
    checks: NotRequired[list[CheckResult]]
    approvals: NotRequired[Annotated[list[Approval], add]]
    change_level: NotRequired[Literal["L", "M", "H"]]
    outcome: NotRequired[Literal["released", "rejected", "rolled_back", "blocked", "incomplete"]]

节点接收整个 State，只返回自己改了什么：

def deploy_staging(state: ReleaseState) -> dict:
    return {"current_stage": {...}}
为什么节点只返回增量，而不是处理完再返回完整对象？ 普通 pipeline 同一时刻只有一个步骤在改对象；LangGraph 的节点可以并行、可以回头重跑、每步都要存档。增量让框架能按字段的 reducer 合并并行结果，也让 Checkpoint 只记录变化。代价是：节点作者必须理解每个字段的合并语义，不能把 State 当普通可变对象随便改。

构建器与编译：

builder = StateGraph(ReleaseState)
builder.add_node("intake", nodes.intake)
builder.add_edge(START, "intake")
...
graph = builder.compile(checkpointer=InMemorySaver())

StateGraph 是构建器，compile() 才得到可调用对象。compile() 会做结构检查（孤立节点、缺失边），但不检查业务规则。即使 P1 没用到中断，也先传 Checkpointer——后面 interrupt() 依赖存档，没有 checkpointer 时 Command(resume=...) 会直接报错（笔记 3.6 二 2.3）。

P1 的四条验收：主流程跑完 outcome == "released"；阶段顺序为 ["staging","smoke","canary_10","canary_50","canary_100"]；前置检查 checks_passed == 4；报告文件存在且能加载。

3. Reducer：节点只报增量，框架负责合并

Reducer 是多个节点先后或并行写同一字段时的合并规则。 默认没有 reducer 就是「后写覆盖」（last-write-wins）。发布图里有三种字段，三种语义，不能统一：

字段Reducer为什么
messagesadd_messages按消息 ID 追加和去重；ToolNode 要追加 4 条 ToolMessage，后续 fanout 还要用新 ID
checks默认覆盖只代表本轮四项检查结果；修订后旧通过不能继续满足新一轮
approvalsoperator.add审批是审计轨迹，H 级两次审批必须都留下，不能被后一条覆盖
为什么不能所有字段都用 add？ 因为三种事实的生命周期不同：消息是历史，要累积；检查是当前轮的结论，旧结论必须失效；审批是责任链，永远不能丢。统一成一种语义，要么让旧检查污染新一轮（误放行），要么让后一次审批覆盖前一次（审计断链）。字段的 reducer 应该由「这个事实代表什么」决定，而不是由方便决定。

4. P2 条件路由：只读状态选路

改一行 README 和改 auth 模块不能走同一条审批路径。课程先用规则分级：diff 含 auth / payment / password / token 判 H；len(diff) > 800 判 M；其余判 L。注意代码里的顺序：先看检查失败与高风险关键字，再看长度（nodes.py 的 _rule_level），所以 samples/patch.diff 即使不长，也会因为路径里有 auth 被判 H——这是实验③会亲眼看到的事实。

等级路由审批人数
Ldeploy_staging（跳过 M/H 审批，但仍要 SRE 灰度确认）0 次发布审批
Mapproval_m → 批准后部署1（tech_lead）
Happroval_h_lead → approval_h_security → 部署2（tech_lead + security）
def route_by_level(state: ReleaseState) -> Literal["L", "M", "H"]:
    return state["change_level"]

builder.add_conditional_edges("classify_change", route_by_level, {
    "L": "deploy_staging",
    "M": "approval_m",
    "H": "approval_h_lead",
})

add_conditional_edges(source, path_fn, path_map) 三个参数：source 是分叉点；path_fn 只读 State、返回路名；path_map 把路名翻译成实际节点名。返回类型用 Literal[...] 而不是 str：它不仅用于类型检查，也让 Mermaid 渲染器知道分支边的标签（实验⑥会看到 approve / revise / reject 出现在图上）。

为什么路由函数不能修改 State？ 路由函数不是节点，不参与「节点执行 → 产生增量 → 存档」这条链；它如果在选路时顺手改状态，这次修改既不会被当作节点更新，也不会出现在 Checkpoint 的增量里，恢复时容易丢失或与真实执行不一致。把状态修改放回节点，路由只做纯函数判断——这样图才是可重放、可检查的。

分支汇合：三条分支各自连一条边到同一节点，就形成汇合。汇合与 ToolNode 的并行不是一回事：ToolNode 是一个节点内部并发执行多个工具，图上看仍是一个普通节点。

5. P3 ToolNode：四路并行

构建、单测、安全扫描、依赖审计互不依赖，可以并行。LangGraph 提供 ToolNode 作为现成执行器。关键契约：一条 AIMessage 携带四个 tool_calls，每个调用有唯一 id。

def intake(state: ReleaseState) -> dict:
    fanout = AIMessage(content="", tool_calls=[
        {"name": "build_service", "args": {...}, "id": "call_build"},
        {"name": "run_unit_tests", "args": {...}, "id": "call_unit"},
        {"name": "security_scan", "args": {...}, "id": "call_scan"},
        {"name": "dependency_audit", "args": {...}, "id": "call_audit"},
    ])
    return {"messages": [fanout]}

ToolNode 不看图，只看 state["messages"] 末尾那条 AIMessage；它自动并发执行对应工具，把结果包成 ToolMessage 追加到 messages。之后 collect_checks 读取 ToolMessage，整理出 checks。messages 保留不删，便于审计。

为什么 messages 一定要 add_messages？ ToolNode 追加 4 条结果，后续节点若再写 messages，没有 reducer 就会覆盖整个列表：模型看不到工具结果，collect_checks 也读不到。反过来，add_messages 按 ID 追加和去重，既保留审计历史，也避免同一条消息被重复写入。每个新 fanout 都必须生成新的 tool_call id，否则去重会把它们当成同一条。

检查不通过时的路由：route_after_checks 在没有结果或任一 passed 为 false 时返回 blocked，直接去 finalize，部署与灰度一个都不执行。这与前面课程「门禁拒绝压过放行」同构：一项失败就整体不放行，而不是让模型解释一下继续。

6. P4 interrupt：暂停不是停在那一行

现实里的审批不是 return {"approver_count": 1}。流程要停下来，把待批 diff 摆到审批人面前，进程可以退出，审批人几小时后点「同意」，再从断点继续。

def approval_m(state: ReleaseState) -> dict:
    decision = interrupt({
        "kind": "approval",
        "interrupt_id": "INT-1",
        "role": "tech_lead",
        "ticket_id": state["ticket_id"],
        "diff": state.get("patch_diff", ""),
        "actions": ["approve", "reject", "revise"],
    })
    return {"approvals": [_as_approval(decision, "tech_lead")]}

interrupt(payload) 第一次执行时抛出特殊信号，让图停下；payload 是给审批人看的可 JSON 序列化数据；那一行 return 第一次不会执行。恢复时，interrupt() 这一行不再抛信号，而是返回 Command(resume=...) 传入的人工决定。

最重要的心智模型（笔记 3.6 五 5.1）：interrupt() 不是「暂停在这一行等」，而是「这一次执行到此为止，下一次从头再来到这一行」。 LangGraph 保存的是 State 和执行检查点，不保存 Python 调用栈。恢复时，包含 interrupt() 的节点函数会从头执行：

恢复 → 重新读 State → 重新构造 payload → 再次执行到 interrupt() → 拿到 resume 值 → 继续往下
由此得到一条绝对规则：interrupt() 之前不能放任何有副作用的操作。 如果暂停前已经发请求、部署、写文件或扣款，每次 resume 都可能重复一次。正确路径是：① 补丁内容在前一个节点生成并写入 State；② 审批节点只展示并收决定；③ 真正写入、部署或切流量放在审批后的受控节点；④ 无法避免重试的外部请求使用幂等键。教学环境里的 print 可以观察重跑，生产代码不能把「多执行几次也没关系」当安全策略（笔记 3.6 八 8.1）。

Checkpointer 与 thread_id：要让人工审批生效，compile() 必须传 checkpointer，调用时必须带 thread_id。thread_id 不是操作系统线程，它是 LangGraph 给一次独立任务的编号，相当于存档文件名；同一个 thread_id 下的存档属于同一次任务。但thread_id 只是查找键，不是权限——谁能批准、批的是哪一版补丁，仍要在入口校验（笔记 3.6 五 5.3）。

Command(resume) 与审批记录：恢复要用 Command(resume=...)，不是把原始任务消息再提交一遍；后者会创建新的执行路径，旧中断仍在，可能重复副作用。这段必须写在收到人工决定的入口，不能紧跟 submit 自动批准。恢复前先 get_state 检查 snap.next：没有待审批节点就说明工单没在等待。H 级两次审批都往 approvals 追加，任一 reject 条件路由到 finalize，后面灰度一个都不跑。

顶层工程用 AsyncSqliteSaver 的 open_checkpointer()；demo 04 用同步版 SqliteSaver，CLI 演示更简单。两者的共同点：数据库文件是跨进程恢复的关键，进程内 InMemorySaver 只能做单进程演示。

7. P5 循环与预算：回边是普通边

发布流程除了往前走，还需要两类回头：① 审批人选择 revise，回到 intake 重新检查与审批；② 灰度指标不健康，回到同一个灰度阶段重试。LangGraph 不需要 loop 专用 API：指向已经走过的节点就是回边。节点写状态，路由读状态，每一圈计数器变大，路由在合适时机不再选回边。

builder.add_edge("begin_revision", "intake")

builder.add_conditional_edges("monitor_window", route_after_monitor, {
    "advance": "canary_step",
    "unhealthy": "auto_rollback",
    "released": "finalize",
})
builder.add_conditional_edges("auto_rollback", route_after_rollback, {
    "retry": "canary_step",
    "abort": "finalize",
})
为什么业务预算不能交给 recursion_limit？ recursion_limit 是框架安全阀，触发会抛 GraphRecursionError——这是运行错误，不是正常业务收尾。业务上「修订两次没通过就返回 incomplete」「回滚两次就停止」必须自己写成路由，让图主动走到 finalize。否则一次正常的「审批人反复要求修改」会被当成系统崩溃，报告、计费和审计都拿不到终态（笔记 3.6 六 6.2）。

循环里的局部变量：canary_step 里 cursor = state["canary_cursor"] + 1。恢复时节点从头重跑，cursor 会不会每恢复一次多一档？不会——cursor 只是局部变量，只有 return 时才写回 State；恢复重跑读到仍是旧游标，所以重算得到同一个目标阶段（笔记 3.6 六 6.3）。前提仍是：interrupt() 之前不能有真正部署、写文件等外部副作用。

8. P6 调试：图、流、快照

图变长以后，靠眼睛看不清工单停在哪里、还差几次审批。P6 不改业务图，只加四个观察入口：

  • Mermaid：graph.get_graph().draw_mermaid() 从已经 compile 的图对象生成，改一条边、加一个节点、调一下路由，图自然变化，不需要手维护。条件边标签来自路由函数的 Literal[...] 返回类型——这就是 P2 强调不要用 str 的原因。PNG 导出可能走在线渲染，离线会失败；先落地 .mmd，PNG 失败也不丢文本。
  • stream_mode="updates"：事件形状是 {节点名: 状态增量}。当节点触发 interrupt() 时，它不会作为正常 key 出现，而是 emit {"__interrupt__": [...]}。所以日志里「没看到 approval_m」不代表节点没执行，多半是执行到 interrupt() 就停了（笔记 3.6 七 7.2）。
  • get_state：StateSnapshot 三个重要字段——values（当前完整 State）、next（接下来要执行的节点元组）、tasks（待执行任务，含 interrupts 列表）。这是跨进程查看「工单停在哪、待批载荷是什么」的主要办法。异步服务用 aget_state() 并记得 await。
  • langgraph dev：读取 langgraph.json 找到图入口，注入内存 checkpointer。studio_graph.py 可以调用 build_graph(None)，核心图代码不变，只是把「用哪个 checkpointer」交给宿主。

同步 I/O 与异步节点：同步文件 I/O 节点应定义成普通 def，让 LangGraph 在线程池运行；如果写成 async def，阻塞 I/O 会卡事件循环，blockbuster 会拦截（笔记 3.6 七 7.3）。顶层 finalize 就是 sync 节点：它内部用 os.mkdir + Path.write_text，代码注释明确说明这一点。

9. 三个实际工程坑

笔记 3.6 八把三个最容易在真实工程里翻车的问题单列。它们是本课最值得背成「现象 → 原因 → 避免」三段式的部分：

坑现象原因避免
恢复时审批节点从头执行恢复后请求、部署、写文件又发生了一次保存的是 State，不是 Python 调用栈副作用放到审批后的独立节点；外部请求用幂等键
复用旧 checkpoint 污染测试单独跑通过，重复跑/并行跑状态异常，如 canary_cursor 停在上轮Checkpointer 按 thread_id 保存；测试复用数据库文件与 thread ID每个测试会话用干净数据库；不同用例不同 thread_id；清理 Checkpoint 与报告目录
异步节点里执行阻塞 I/O命令行正常，接 langgraph dev 后 finalize 被 blockbuster 报错async def 节点跑在事件循环，同步 I/O 占住线程短小同步操作写成普通 def（线程池）；必须异步的改用异步 I/O；CLI/测试/服务分别验证

本课实验会亲手撞上前两个：实验④在 approval_m 开头加一行 print，跑 submit + approve，你会看到它执行两次；实验⑤把 approvals 的 add 改成覆盖，两条验收测试立刻变红。测试文件里的 session 级 fixture 会先删掉 test-checkpoints.sqlite，正是为了不踩第二个坑。

为什么这些坑在「图能跑通」之后才暴露？ 因为 compile() 只检查结构，不检查业务规则，更不检查恢复语义。图能跑到 released，不代表恢复时不会重放副作用、测试之间不会互相污染、服务环境不会阻塞事件循环。真正的验收必须覆盖失败场景：跨进程、旧存档、服务模式、异常指标——这也是笔记六步阅读顺序的最后一步「用失败场景验证这些连接是否真的生效」。

10. 什么时候用 LangGraph

场景选择
直线流程，步骤固定且无人工暂停普通函数或固定 Workflow 更简单
单一 Agent 在未知路径中探索Agent Loop 足够
多分支、并行节点、人工中断、跨进程恢复LangGraph 的价值明显
业务人员可视化搭流程，逻辑不复杂Dify 一类平台可能更合适

还有一个实践信号：3-7 项目三只把 LangGraph 用在审批服务（hitl/graph.py），主体 Agent 仍是 pi 循环。这说明「用 LangGraph」不是全有或全无——可以把需要显式迁移的那一段用图，把开放探索留给 Loop。这种按职责切分比「整个系统都画成一张大图」更符合工程成本。

11. 面试视角：两分钟主链

如果面试官问「你什么时候会用 LangGraph，怎么保证它能恢复」，不要从 API 讲起，按这条链讲：

  1. 业务形状：发布审批有 L/M/H 分支、四项并行检查、三处人工审批、修订与灰度两个循环，步骤和异常路径能提前枚举——这类流程值得显式编排。
  2. 映射：工单是 State（TypedDict 闭世界），每个步骤是节点（不等于一次模型调用），依赖是边，总装是 StateGraph，人工等待是 interrupt，跨进程是 Checkpointer，外部调用是 ToolNode。
  3. 合并语义：节点只返回增量；messages 用 add_messages 追加/去重，checks 默认覆盖代表本轮，approvals 用 add 保留审计链。
  4. 并行与分支：一条 AIMessage 携带四个 tool_calls，ToolNode 并发执行；条件路由只读 State、返回 Literal，分支标签才能进 Mermaid。
  5. 暂停与恢复：interrupt() 是「本次执行到此为止」，恢复时节点从头重跑；所以副作用必须在 interrupt 之后；thread_id 只是存档查找键，不是权限；恢复用 Command(resume)，先 get_state 确认在等待。
  6. 循环与预算：回边是普通边；修订/回滚靠业务计数器主动走到 finalize；recursion_limit 只是异常安全阀。
  7. 工程验收：跨进程恢复、旧 checkpoint 隔离、异步节点阻塞 I/O 三处都要用失败场景验证；能说清什么时候不用 LangGraph。

常见追问与回答方向：

  • 「模型说完成了，能信吗？」→ 回到 0010/0014 的完成契约：只认当前最新事实，不看模型自述。
  • 「恢复会不会重放副作用？」→ 会重跑 interrupt 之前的代码；所以副作用后移 + 幂等键，并用真实产物证明只执行一次。
  • 「Checkpoint 和 Trace 有什么区别？」→ 前者保存接下来怎么继续，后者记录发生过什么；装 Trace 不等于能恢复。
  • 「thread_id 能当权限吗？」→ 不能，它只是查找键；谁能批、批哪一版补丁要在入口校验。
  • 「为什么不用一个大 Agent 全做完？」→ 发布流程的价值在可审计、可审批、可恢复；开放探索才交给 Loop。按职责切分，别为了图而图。

实验 ③：跨进程人工审批——M 与 H 各走一遍

  • 先读 CLI 签名，不要照抄 README 的旧写法：当前 app.py 的 submit 是位置参数，--diff-file 是选项；README §2 的 --ticket 写法与代码不一致，照抄会报 No such option。以代码为准：

    先写预期：应停在哪个节点、interrupt_id 是什么、next 是什么？

    预期：停在 approval_h_lead 的 INT-2A；批准后再停在 approval_h_security 的 INT-2B；任一 reject 直接 finalize，不再部署。

实验 ④：主动改造——证明审批节点会从头重跑

  • 先跑一条 M 级流程，记住第一次 submit 时 approval_m 没有被打印（日志里只有 __interrupt__）。
