1. 一条主线：输出侧要同时管「过程」和「结果」

非流式接口里，一次模型调用对用户和系统都是黑盒：2 秒出第一个 Token、十几秒出全文，接口只在最后返回 JSON。Streaming 把这个过程变成可观察、可取消、可恢复的事件流；Structured Output 把最终结果变成可验证、可拒绝、可恢复的业务协议。两条主链分别是：

【Streaming 主链】                          【Structured Output 主链】
Client 创建 Run                             工程师定义协议（Pydantic）
      ↓                                           ↓
Agent Loop 请求 Model Adapter               生成 JSON Schema 发给模型
      ↓                                           ↓
Provider chunk -> ModelStreamEvent           模型生成候选结构化结果
      ↓                                           ↓
Agent Loop -> RunEvent                      服务端解析并校验（三层）
      ↓                                           ↓
Event Store 按 run_id + seq 保存             ├─ 通过 -> 交给下游
      ↓                                           └─ 失败 -> 反馈错误 -> 有限修复
SSE Gateway 编码推送                                  ├─ 成功 -> 交给下游
      ↓                                              └─ 失败 -> 合格缓存降级或明确终止
Web / CLI 按事件类型消费

取消信号沿 Streaming 主链反向传递，最终写入唯一的 run.cancelled 终态。

2. Streaming 改善什么、不改善什么（本课第一张必背表）

Streaming 主要改善感知延迟和过程可见性，不会自动让模型推理更快。要区分三个指标：

指标含义主要受什么影响
TTFT请求开始到第一个可显示 Token排队、网络、输入长度、Prefill
Generation Time首 Token 到模型输出结束输出长度、模型解码速度
End-to-End Latency用户发起任务到 Run 最终完成模型、多轮 Loop、工具、存储

Streaming 也不能解决：模型本身慢、Prompt 过长、工具阻塞、Context Window 不足；也不会自动保存事件、停止后台任务、恢复崩溃 Worker。这些分别属于 Cancellation、Event Replay、Checkpoint 的职责。特别地：长文本超出单次输出上限要拆任务 + checkpoint，Streaming 突破不了 Context Window。

3. 分层术语：七个不能混用的数据单位

名称准确含义不能当成什么
Token模型内部生成与计费的文本单位一个汉字或一个网络包
Provider chunkSDK 从供应商流中读到的增量对象稳定业务协议
ModelStreamEventAdapter 归一化后的模型事件SSE 文本帧
RunEventHarness 对外发布的运行事实只有文本 delta
HTTP chunk网络层一次读写到的字节一条完整 SSE event
SSE frameevent/data/id 组成的文本帧模型 Token
Checkpoint可恢复的任务执行状态保存每个网络包

三个关键事实：一次 Provider chunk 可能没文本也可能含多个 Token；一次网络读取可能只有半个 SSE frame 也可能粘着三条 frame（客户端要「增量解码 -> 按空行切 frame -> 按类型分发」三层处理）；一次 SSE frame 可能对应多个模型事件也可能只是心跳。TTFT 记录在第一个非空 text.delta 到达时，不是响应头也不是首个 chunk。

为什么要 ModelStreamEvent 这一层：供应商 chunk 是协议细节，直接转发给前端，换模型就要 Web、CLI、日志、Trace、重连逻辑全链路修改--这是主题课 1「Adapter 收敛差异」在流式场景的复现。

4. 终态与取消：断开连接 ≠ 停止生成

  • 唯一终态：客户端只有收到 run.completed / run.failed / run.cancelled 三者之一才能确认 Run 已终止；同一个 Run 只能产生一个终态（完成与取消同时发生时要测试竞态，最终只保留一个）。
  • cancelling 中间态：取消请求被接受时资源可能还没释放，直接显示 cancelled 会让用户误以为成本和副作用已停止。
  • 创建 Run 与订阅 Run 分离：页面刷新不会自动创建第二次模型请求；客户端断线只中断订阅，不等于取消业务 Run。
  • 部分输出：应保留（partial_text、last_seq、当前 step、工具状态、usage、cancel reason），但不能自动当成最终业务结果--被截断的 JSON、SQL、补丁不能直接进下游执行器。
  • run_id + seq：客户端去重、Event Store 排序、重连确认位置、Trace 还原，四个用途共用这一对字段。断线续传是重放已保存事件（按 Last-Event-ID 从 Event Store 查询），不是重新调用模型。

5. 失败分阶段：重试还是重放（本课第二张必背表）

失败阶段示例正确动作
建立流之前连接超时、429、503有界重试
已连接未产生业务事件上游提前关闭按策略有限重试
已发出 text.delta网络中断不盲目重跑并拼接
工具调用已开始执行器失联先查询工具状态
已产生终态但客户端掉线ACK 丢失重放事件，不重跑任务

三个不能混的概念：Model Retry（重新推理）、Transport Replay（重发已保存事件）、Task Resume（从 checkpoint 继续）。核心纪律：一旦向下游产生不可重复的业务事件，就停止自动重新生成。伪流式的三个来源（代码层面看不出）：先收集完整文本再 yield、同步 SDK 阻塞事件循环、Nginx/CDN/压缩层缓冲响应--所以验收要从客户端实测首事件时间，不能只看代码里有没有 StreamingResponse。

工作对应：你在 OpenViking 日常处理的 MCP 工具流式结果与 Claude Code 插件的上下文注入，走的都是这条「内部事件 -> 对外协议」的分层路子；「通知可以丢，事实事件不能丢」也是你做 benchmark 跑批时的同款约束。

6. Structured Output：四层术语一句话收束

JSON 解决「能不能解析」，Schema 解决「长什么样」，Pydantic 解决「Python 程序怎样定义和验收」，业务代码解决「这个结果能不能用」。

自然语言、关键词、正则解析没有稳定边界：「暂时不要转交」仍然包含「转交」，解析器不报错却选了错误分支。即使 Prompt 强调「只返回 JSON」，{"action":"route","team":123} 也是合法 JSON 却不符合协议。Agent 不应猜测一句话大概是什么意思，只接收通过明确协议校验的对象。Prompt 约束行为倾向，Structured Output 把结果变成协议对象，两者不能互相替代。

字段设计从下游消费方出发，不从模型能生成什么出发：字段名面向业务接口（action/team/question），不面向模型思考过程（model_thought/thought_2 迫使调用方再次猜测）。Pydantic Model 是协议的单一来源：model_json_schema() 发给模型描述结构，model_validate_json() 验收实际返回，两端共享同一份定义不漂移。注意 model_validator 的业务组合关系不一定能完整投影成 Schema，所以即使 Provider 支持原生 Structured Output，服务端仍要保留统一验收入口（跨 Provider 稳定边界 + 业务组合规则 + 完成状态都靠它）。

7. 校验三层 + 修复循环五检查点

一次校验区分三类错误：JSON 语法（无法解析）、字段结构（缺失/类型/枚举/额外字段）、业务组合（字段单独合法但整体不可用，如 route_to_team 却没有 team）。错误不能只是一句「不合法」，要归一化成带 path/code/message 的 ValidationIssue 列表--日志能统计失败原因，修复循环才知道改什么。全有或全无：不能从失败对象取 team 再给 action 补默认值，那会伪造一份模型没作出的决策。

有边界的 repair loop 五个检查点：

  1. 所有调用共用同一份 Schema（生成端 = 校验端）；
  2. 每次返回都重新校验，第二次也不绕过；
  3. 只有 valid=True 才返回类型对象，失败对象不进下游；
  4. 上一份输出 + 具体错误进入下一轮--让模型修复已有结果，不是重新猜一次（修复提示三要点：指出哪里错、限制只修协议问题、只返回 JSON）；
  5. max_repairs 有限预算（默认修复 2 次、总调用最多 3 次），用完抛 StructuredOutputFailure。

只有输出协议错误适合交给模型修复；网络超时归 Provider 调用层退避重试、认证失败立即终止修配置、权限不足归业务策略。宽泛的 except Exception 把所有错误都送回模型，是本课审查题的标准答案之一。

8. 失败收口：三种状态与缓存四条件

最终失败也要有稳定协议：DecisionResult 返回 ok / degraded / failed，其中 failed 状态下 decision 必须为空--系统不能为了流程继续而伪造一个团队，也不能从最后一次错误输出拼半成品。处理顺序固定：先有限修复，修不好再查合格缓存，缓存不可用就明确失败。缓存成为降级结果的四个条件：同一输入、同一协议版本、有效期内、历史上通过校验；是否允许用缓存仍是业务决定（快速变化的订单状态、权限判断、写操作不能因为结构合法就复用旧结果）。处理顺序固定之外还有个纪律：只捕获 StructuredOutputFailure，不要把程序 Bug 或数据库故障伪装成输出格式问题。

工作对应：你在 de-test 里 fact 族（entities/events/preferences）的输出协议，就是这条「定义协议 -> 校验 -> 定向修复 -> 失败收口」链路的真实实例--模型产出的记忆字段必须过校验才能落盘，落错了不改旧文件、新增修正，正是「非法结果不进下游」的变体。
