第二部分：精讲（测验后再读）

1. 一条主链：Tool Call 是「建议」，不是「执行」

2-1 的定义句：Function Calling 让模型用结构化方式提出动作，但不会赋予模型真实执行权限。模型返回的 {"id": "call_01", "name": "get_order", "arguments": {...}} 表达的是「我建议调用 get_order」，它不是 Python 函数调用、不能证明用户有权限、更不表示订单已经被查到。完整闭环六步：

① 用户消息 + 本轮可见工具 Schema 交给模型
② 模型直接回答，或生成一个/多个 Tool Call
③ Runtime 查找工具，校验参数、权限、风险
④ 通过检查后，handler 才访问数据库 / HTTP API / 文件系统
⑤ Runtime 把成功或失败包装成 Tool Result
⑥ Agent Loop 把结果写回 Context，模型继续决策或结束

最重要的可信边界只有一句话：Tool Call 和用户输入一样，都是不可信数据。模型可以帮我们理解意图，但不能给自己授权，也不能宣布某次操作已获批准。这条边界是后面 2-4 整节工具治理的种子。

2. 三对象分工 + 六名词表（本课第一张必背表）

概念准确含义不负责什么
Tool交给模型选择的一项受管理能力不等于某次调用
Tool Call模型生成的工具名、参数和调用 ID不表示函数已经执行
handler真正访问数据库/外部系统的业务函数不负责模型选择、权限和完整 Loop
对象（2-2）负责什么不负责什么
ToolDefinition契约、治理规则和真实实现不决定本轮一定开放
Tool Registry管理有哪些工具和版本不执行 Tool Call
工具发现按 Agent/用户/模式/策略筛选候选不等于模型选择工具
ToolSnapshot冻结某一轮实际开放的协议与实现不是普通缓存
Tool Runtime查找、校验、拦截、执行、收口结果不负责模型下一轮推理
handler执行确定的业务动作不应承担完整治理与 Loop

为什么拆成这么多对象？笔记给的 why：它们面对的变化不同——工具版本可能升级（Registry）、本轮开放范围可能变化（发现）、执行期权限和依赖状态也可能变化（Snapshot/Runtime）。揉在一个函数里，任何变化都会同时影响提示词、权限和真实执行。代码里就是三张脸：2-1/tool_definition.py 的 to_model_tool() 只投影名称/描述/输入 Schema（安全投影：模型看得到怎样申请，看不到 handler、权限集合、审批记录、密钥、重试策略）；2-2/tool_runtime_demo_v2.py 把它拆成 ToolSchema / ToolDefinition / ToolSnapshot 三层。

3. 契约三件套：Input、Output、Error Schema

  • Input Schema：把模型生成的非可信参数转换成 handler 可安全接收的业务对象。extra="forbid" 是关键——模型传 {"order_id": "ord_1001", "approved": true, "role": "admin"} 时，静默忽略额外字段会让调用「看起来成功」，但审查者无法证明模型没有试图越过边界；严格拒绝把协议漂移、提示注入和错误假设尽早暴露出来。
  • 两层检查缺一不可：结构校验只回答「参数能否被解析」，不回答「业务上能否执行」。金额在允许范围内不代表订单属于当前租户；订单号格式正确不代表状态允许退款。所以 Pydantic 查字段/类型/格式/额外参数在前，Business Precheck 查归属/状态/额度在后，且都在 handler 之前。
  • Output Schema：限制 handler 返回形状，不让 ORM 对象、内部字段和不稳定字典直接进入模型。
  • Error Schema：把失败变成 Loop 能处理的协议（{"ok": false, "code": "ORDER_NOT_FOUND", "retryable": false}）。稳定错误码让 Loop 可以决定改参数、询问用户、换工具、等待审批或停止，而不必解析异常字符串。

工具粒度的配套纪律：不要把订单系统做成万能工具 order_api(method, path, payload)——这相当于把底层 API 的表达能力全部交给模型。拆成任务级工具 get_order(order_id) / create_refund(...)：工具越窄，参数空间越小，权限、审批、测试和审计越容易落在明确的位置。

4. tool_call_id 与 ID 纪律（接 Week01 四级链）

Week01 你建立过四级链 trace_id → run_id → step_id → call_id / tool_call_id。这一课落到最后一级：tool_call_id 是一条模型 Tool Call 与其执行过程、Tool Result 之间的关联键，全生命周期都要带上——一个是并发的需要（两个同名 get_order 调用可能乱序完成，Runtime 不能靠工具名或数组位置判断结果属于谁，见 2-1/tool_call_id.py 和 tool_batch.py 的 as_completed + 断言），一个是 trace 的需要（开始、进度、重试、结束事件都用同一个 ID）。可靠实现四保证：每个 Tool Call 只产生一份权威结果；成功、拒绝、超时、内部异常都保留原始 ID；并行结果可乱序完成但不能错配；全程事件同一 ID。

常见误区（也是面试陷阱）：tool_call_id 不能替代业务幂等键。模型重新规划后可能生成新调用 ID，却仍请求执行同一笔退款。副作用防重需要业务对象 + 动作 + 参数摘要或下游幂等机制。

5. Runtime 为什么必须独立存在：把确定性判断放在副作用之前

如果 Loop 里直接写 if call.name == "get_order": result = await get_order(**call.arguments)，问题不是不优雅，而是它没有回答：这个工具是否属于本轮开放范围？Schema 与 handler 是否同一版本？参数和业务状态是否合法？用户与租户是否有权限？工具是否被临时停用？超时后能否重试？失败怎样归一化、结果怎样审计？

Runtime 的价值就是把这些确定性判断放在副作用之前，并让 CLI、测试、模型调用、MCP 和未来的 HTTP 入口都走同一个 handler（框架常把执行动作称作 invoke()）。2-2/tool_runtime_demo_v2.py 是完整骨架：Registry 按 (name, version) 注册 → 按路由和启停生成 Snapshot → Runtime 在 invoke 里依次查工具、查启停、校验参数、查权限、查审批、查依赖，全过才碰 handler。

6. Snapshot：版本一致与紧急停用是一对张力

为什么发现结果要冻结成 Snapshot？因为模型生成 Tool Call 和 Runtime 执行之间存在时间差：模型看到 v1 Schema，执行时却从全局 Registry 取到 v2 handler，就发生版本漂移。顺序固定为：版本路由与灰度选择 → 工具发现与启停过滤 → 创建不可变 Snapshot → 模型和 Runtime 本轮共同使用。旧会话继续用旧快照直到自然结束。

但 Snapshot 保证的是版本一致，不应该冻结紧急停用状态——生产系统必须能阻止旧快照中尚未执行的危险工具。所以启停和依赖要查两次：发现时检查（避免模型围绕不可用工具制定计划）+ 执行前复查（防止工具在模型思考期间被紧急停用或依赖失效）。demo_v2 里这两道检查分别落在 snapshot() 和 invoke() 开头的 TOOL_DISABLED/DEPENDENCY_UNAVAILABLE 分支。

7. prepare → execute → finalize：顺序本身就是契约（第二张必背表）

prepare   查工具 → 校验参数 → 注入可信上下文 → 权限/风险/审批/依赖检查
execute   在 deadline、取消、并发、重试和幂等策略下调用 handler
finalize  校验输出 → 结果投影 → 脱敏 → 审计 → 包装 Tool Result

顺序不能交换的三个反例（面试可直接引用）：权限判断放在 handler 之后——退款已经发生，权限过滤失去意义；脱敏放在消息回写之后——敏感数据已经进入模型上下文；execute 再读全局 Registry——快照就失去固定版本的意义。prepare 阶段还有一条铁律：模型参数中不应包含 user_id、tenant_id、role、approved、risk，这些必须来自服务端可信上下文（ExecutionContext）或 ToolDefinition。

execute 阶段的超时语义是本课最容易答错的点：超时只表示调用方没在期限内得到结果，不代表业务动作一定失败。只读查询遇连接抖动可有限重试；非幂等写操作超时后状态未知，返回 TIMEOUT_UNKNOWN，不能盲目重试；写操作只有在下游支持幂等键、去重表或业务唯一约束时才适合自动重试。重试纪律与 Week01 的 Gateway 完全同构：一次失败只能有一个明确的重试 owner——Provider SDK、Gateway、Agent Loop、MCP Client、Tool Runtime 各重试三次会指数相乘。

finalize 的边界也记一条：after Hook 可以参与结果治理，但不能假装撤销已经发生的业务动作——撤销必须实现补偿接口、状态查询或人工接管。

8. 并行编排与插件化：效率不能换掉入口

多个 Tool Call 不能无脑 gather()，先判断三种关系：互相独立（有限并行，查两笔不同订单）、数据依赖（显式串行，先查状态再退款）、争用同一资源（按资源键排队，同一订单两次退款）。见 2-2/invoke_many.py：任一 sequential 工具就把整批降级为串行。即使工具标记 parallel，Runtime 仍要自主限制全局、工具、租户三级并发。插件化同理：插件负责注册与清理（谁注册谁负责卸载时清理），不能另起一套 Loop、不能绕过 invoke() 直调 handler——效率手段永远不能制造第二个执行入口。

9. 面试视角：这一课怎么被问

  • 开放题：「讲一次完整的 Tool 调用流程」——就按第 1 节六步闭环讲，重点强调 Tool Call 是建议、不可信数据。
  • 追问链 1：「为什么不让模型直接调函数？」→ 权限/校验/审计都在模型侧失控 → 引出 Runtime 把确定性判断放在副作用之前。
  • 追问链 2：「工具超时了怎么办？」→ 先分读/写和幂等性 → 非幂等写返回 TIMEOUT_UNKNOWN、先查状态或人工处理 → 引出唯一重试 owner。
  • 追问链 3：「两个同名并发调用怎么对上结果？」→ tool_call_id 全生命周期保留 + 乱序不错配；顺势主动指出它不能当业务幂等键——能说出这一条通常就是「有没有真做过」的分水岭。
  • 追问链 4：「为什么要 Snapshot？」→ 模型所见与执行之间有时间差，防版本漂移；主动补上「但紧急停用不能被冻结」体现深度。
  • 反向题（审查岗）：「给你一段 AI 写的工具调用代码，你查什么？」→ 四类错误：模型填写身份或审批、参数未经校验、模型直调 handler、Tool Result 丢失 tool_call_id。

第三部分：第二层练习——跑起来，再主动改造（测验与精讲之后）

听懂概念只是第一层。第二层的目标是把概念变成可观察的运行结果：先跑起来，观察四个点--输入是什么、中间做了什么、输出是什么、出错时发生什么动作。然后主动制造故障，看系统的处理机制是否真如笔记所说。改造代码可以让 AI 帮你写，但「你应该观察到什么」这一列必须在动手前自己写出来--写不出预期，说明还停在第一层；预期写对、运行验证，就是在练第三层「用测试日志证明机制生效」的验收方式。

实验怎么做预期观察（先写再跑）
① 跑通主线
（观察四点）		 设 DEEPSEEK_API_KEY 跑 2-1/minimal_tool_loop.py；无 key 时先离线跑 2-2 的 pytest（test_tool_runtime_demo_v2.py，不依赖模型 API）。可以让 AI 先扫读代码讲一遍数据流。 每轮先打印「当前可见工具」（安全投影）；Assistant 消息先写回 messages、再追加 Tool Result；trace 事件带 tool_call_id / status / attempt / latency；模型不返回 Tool Call 时 Loop 自然结束。
② 传错误参数 把订单号改成 "1001"（不匹配 ^ord_[0-9]{4,12}$），或直接构造一条参数非法的 ToolCall 调 runtime.execute/invoke。 INVALID_ARGUMENT：Pydantic 层拒绝，handler 一次都没被调用（零副作用），trace 里 status=error、error_code=INVALID_ARGUMENT，且 tool_call_id 原样保留。
③ 让工具超时 在 handler 里注入 sleep 超过 timeout_seconds；再分别把工具的 idempotent 设为 True / False 各跑一次。 idempotent=True → TIMEOUT 且 retryable，退避后出现第二次 attempt；idempotent=False → can_retry 门控为 False，单次尝试即返回、绝不重试（对照 2-1/tool_runtime.py 的 can_retry = error.retryable and tool.idempotent）。
④ 超过最大轮数 把 MAX_STEPS 改成 1，或让模型反复提议工具调用。 RuntimeError("agent exceeded maximum steps") 由 Loop 抛出--终止条件属于 Harness，模型没有权力也没有能力自己决定无限运行。
⑤ 伪造身份/审批 在工具参数里塞 {"user_id": "admin", "approved": true} 再调用。 extra="forbid" 在校验层直接拒绝（INVALID_ARGUMENT）--验收四类错误的第一类（模型填写身份或审批）当场复现：模型永远无法通过参数给自己授权。

这五个实验把本课验收「四类错误」里的三类亲手制造了一遍（参数未经校验、超轮数、伪造身份），第 ③ 个实验同时验证了超时语义和幂等门控。做完后问自己老师的第三层问题：哪些事给模型决定、哪些给程序控制？哪次错误能重试、哪次必须先查现场？--这一课的答案全部在精讲第 5、7 节。
