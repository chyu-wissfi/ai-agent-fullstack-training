第一部分：精讲（先读，测验在后）

0. 开篇：五件事，不是两个工具

前面几节分别解决输入、任务记录、长期知识、检索和知识维护。项目四把其中长期记忆与 RAG 接回 project4/v2（笔记行 2260；笔记沿用旧称 project3/v2，实际目录是 project4/v2，见回读指引口径提醒）。分工一句话：长期记忆帮助复用之前核对过的项目知识；RAG 帮助从资料库查当前任务需要的业务规则（行 2262）。两者为动作提供依据，真正读取、修改和测试仍走既有 Loop、Runtime 与 Sandbox——不能再写一条绕过治理的执行路径，也不能把检索答案直接当成代码已修改的结果（行 2264）。

为什么收敛成五件事而不是「功能清单」？ 功能清单（加了 recall/remember/rag_query 三个工具）回答的是「做了什么」，五件事回答的是「凭什么算装好」——每件都对应一类可拿出的证据（读取记录、预算报告、性质标注、恢复回执、引用与 Trace）。取舍在于：按功能验收容易把「函数能返回」当完成（行 2510 明确反对）；按目标验收则必须把前五课的装配、记录、筛选、校验能力一起拉进来陪跑。代价是验收面变宽——这正是结课课的意义：信息能力要回到同一个 Agent、同一条治理链。

1. 接长期记忆：六处修改各管什么

接长期记忆不是「加一个工具」，是六处修改一起补（行 2284–2293）：配置开关、记忆模块、工具暴露、启动装配、使用指引、单元测试。启动摘要与按需读取配合使用：摘要帮助发现相关知识，具体结论还要读全文和当前源码（行 2295）。

为什么是六处而不是两处（模块+工具）？ 只加模块和工具，会缺四件事：平台不能明确启停（配置）、本次运行拿不到知识入口（装配）、模型不知道「先召回核对再应用」（指引）、接入无法用反例检查（测试）。每处隔离一种变化：开关变化不动代码、组织变化不动工具、指引变化不动装配——与第三章「一个对象管一种变化」同构。另一条红线：记忆文本进系统提示词≠记忆里的指令成为宿主授权（行 2297），这与 0021「access_policy 字段不是鉴权」、0008「提示词不是边界」是同一条不变量的三个现场。

2. 两件工具走 Runtime：治理链不分叉

memory_recall（risk=read）与 memory_remember（risk=write）与十件仓库工具一样，注册进 ToolRegistry，经过白名单、RBAC、参数契约和 ToolRuntime，留下审计（行 2303–2308）。记忆写入不是修改业务源码，但仍然是持久副作用——原稿操作中需要审批，批准只针对对应写入（行 2310）。代码核对：recall 权限 memory:read、免确认、timeout 5000ms、可重试；remember 权限 memory:write、requireConfirmation 来自配置（platform.yaml 为 true）、maxRetries=0（非幂等不自动重试）。rag_query 同样只读也要 rag:read（行 2409）。

为什么读记忆、查资料这种「无害操作」也要走全链？ 取舍是性能换治理：直调 fs.readFile 或 subprocess 确实更快，但白名单/RBAC/审计全部失效——reviewer 能读不该读的项目、写入不经审批、事故复盘拼不出证据链（0008 审计两阶段的原话）。Q32 的答案就是这条：写记忆要检查参数、路径、权限和审批，读资料也要检查访问范围；统一经过 Runtime，才能执行治理、回写结构化结果并留下审计。代码里还有一个细节：rag.ts 的外层 timeoutMs = rag.timeoutMs + 15000（L79–83 注释「外层余量」）——后端超时先报结构化错误，外层兜底防挂死，两层超时各管一段。

3. RAG 独立后端与 rag_query 契约

RAG 查询要先确认索引、答案和引用都正确，再接 Agent——失败时能分清是后端检索问题，还是工具适配与结果回写问题（行 2365）。后端职责：ingest.py 入库建索引写 storage；query.py 管查询模式/Top-K/生成开关/JSON 输出；rag/ 内 hybrid（jieba+BM25+向量+RRF）、local_embed（BGE 中文 512 维，行 2378）、answer（编号证据装配）、llm（MiniMax 适配）。入库与查询分开执行（行 2382–2394）：查询使用已有存储，避免每次提问重复向量化整套资料；--no-llm 只观察检索结果和引用，不把它说成已由回答模型综合生成结论。

为什么先保留独立查询入口，而不是直接接进 Agent？ 取舍是「多一个入口」换「失败可归因」：直接接入后一旦答案不对，分不清是检索没找到、适配层格式化丢了引用，还是模型没调用——0020 的归因六步在跨进程场景下第一步就断了。独立入口先验证索引/答案/引用，再把 query.py 封装成只读工具，后端问题与适配问题各有现场。--overwrite 只用于明确重建的实验，不是日常查询的前置动作（行 2394）；本机 storage/ 已建好，实验④直接查询不重新入库。另一条边界：无 key 时 LLM 失败优雅降级——query.py L120–127 返回 answer=null + llm_error，引用追溯不受影响；「检索到了」与「生成了」是两个事实，不混写。

4. 验证方法：先写入，再新进程召回

笔记保留原稿 CLI 操作（行 2316–2337）：invoke memory_remember 写入 → 从回执取审批 ID → approvals decide 批准 → approvals execute 执行 → 新进程 invoke memory_recall 读取 + npm test。要核对的结果：概念文件真实落盘、索引和日志同步、新进程取得同一记录。CLI 召回证明跨进程读取；业务新会话是否自动加载，还要检查实际模型请求（行 2339）——这句是本课最重要的证明边界之一。单元测试至少覆盖五条（行 2345–2353）：写入合法 OKF 内容相符、index/log 同步、query/ID 召回、路径穿越写入前拒绝、新进程能读持久记录；再结合第三章验收：拒绝或未批准不写入、错参数不执行 handler、写结果保留调用关联、开关关闭行为符合配置（行 2355）。

为什么必须「新进程」召回，而不是同一进程里再读一次？ 同一进程读取可能命中内存缓存，证明不了持久化；新进程不继承任何运行时状态，读到才证明「文件真实落盘 + 启动回读路径可用」。但注意证明的边界（行 2339）：CLI recall 走的是工具路径，业务 Run 走的是「renderSystemPrompt 启动摘要 + 模型按需 recall」——前者成立不自动推出后者成立，后者要查实际模型请求（Debug Report/Trace，0017 四位置定位法）。这与 0019「回答提及文件名不算证明读了」、0016「状态≠结论只认审计」是同一条纪律：每层证明只覆盖那一层。真实 Run 同理：--decider real 只表示让真实模型决策，仍要靠 Trace 证明本次走了查询工具（行 2441）。

5. 冲突裁决：四来源各证明什么

例子：RAG 规则写 30 分钟，源码实际计算为 20 分钟（行 2451）。不要让模型直接选择看起来更权威的一份，更不能靠更新文档掩盖代码问题（行 2453）。先指出差异，再读取当前规则状态、代码和相关测试，判断是记忆过期、资料滞后，还是实现不符合规则（行 2462）。

为什么不能「选更权威的一份」或「改文档让它一致」？ 四来源证明的对象不同：规则是应然、源码是现状、测试是指定版本的行为、记忆是过去。选一份覆盖其余，等于把「实现不符合规则」这个真问题抹掉——改文档迎合源码更是用知识资产造假掩盖代码缺陷（0021「不能改原文迎合结论」的同构现场）。取舍：保留差异并分别标注，回答会「显得不一致」，但这才是诚实且可行动的输出——工程师据此决定是修代码（需授权+测试）还是走规则变更流程。模型没有这个裁决权：修复代码仍需用户目标、当前证据、授权和修改后测试（行 2468）。

6. 五目标验收、七类反例与工程师/AI 分工

五个目标分别拿什么证据（行 2474–2480）：找得到——新会话召回+真实 Run 查询，读取或工具调用记录、相关来源进入请求；装得下——总请求受控、关键证据保留、必须项超限停止；记得准——混入推断/旧入口/另一项目记录时性质与范围明确；恢复得了——修改后未测试时暂停再恢复，找回状态、核对现场、继续当前版本验证；解释得清——引用编号、原文位置、版本和 Trace 对应。

工程师负责什么，AI Coding 可以承担什么（行 2502–2508）：

工作AI 可以辅助工程师必须核对的证据
信息结构与模块边界编写模块和接口数据样例与真实链路
上下文与记忆策略实现装配、压缩和存储Debug Report、更新与恢复结果
检索方案接索引、混合与重排固定问题集的对照结果
来源、版本与权限实现过滤和维护引用核对、版本与拒绝用例
最小规格与验收编码、补测试和修复测试报告、Trace 和失败分析
为什么正向验收之外还要主动制造七类反例？ 正向用例只证明「能成功」，治理的价值恰恰在「不该成功时不成功」：未批准不写入、穿越被拒、失败不伪装成空结果成功。只跑正向路径，审批闸口和错误码可能从未被触发过——第三章 handler=0 的验收思路在这里原样复用。分工表的共同结构是：AI 的产出是建议与实现草稿，工程师用可执行证据决定是否接受——与 0014 Harness「模型建议、程序把关」、0021「模型整理内容，程序管理草稿、有效条件与发布」同构。取舍：让 AI 直接「宣布完成」更快，但测试报告、Trace 和失败分析才是交付判断的依据（行 2508）。

面试官追问链：

  • 「rag_query 只读，为什么不让所有人随便查？」→ 只读≠任何人可读：资料有项目与权限范围，RBAC 检查 rag:read，后端结果仍受输出预算与审计控制（行 2409）。

  • 「接完之后你怎么验收？」→ 五目标各拿证据 + 主动制造七类反例；真实 Run 沿 Trace 找第一个断点；报告三分（已实现/已验证/尚未证明），无 key 的真实 Run 如实标待验证。
