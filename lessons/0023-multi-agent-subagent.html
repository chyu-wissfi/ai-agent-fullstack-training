Multi-Agent 与 Subagent——该拆才拆，拆了还要管得住

本课定位：Week05 第一课。Week04 让一个 Agent 获得足够、适用、可核对的信息；本课开始解决任务怎样分给合适的执行者。主线不是「多开几个角色」，而是：独立工作与不同视角带来收益，交接、隔离、预算、取消与冲突处理带来成本，收益超过协调成本才值得拆。
材料定位：第五章 学习笔记.md 5.1 节（行 75–268，本课第一材料）+ 章首学习预期（行 31–59）+ 本章复习 Q1–Q8（题干行 2349–2365，答案行 2479–2511）+ 教师 PPT 5.1 PPT.md 与 PDF 5-1.pdf。

预计用时：精讲 45 分钟 + 测验 20 分钟 + 第二层实验 45 分钟
本课验收标准（笔记行 260–268）：① 用三个问题解释为什么拆或不拆；② 区分 Multi-Agent、Subagent 与并行命令；③ 说清 Supervisor、Planner/Executor、Reviewer 的职责与证明边界；④ 按依赖排并行，用程序落实三层隔离、局部与全局预算及取消；⑤ 面对冲突回到范围、版本和行为证据；⑥ 从真实工具记录证明 pi 委托发生，而不是只看回答。

0. 开篇：先问该不该拆

第五章把前四章能力继续向外组织：

5-1 该不该分工？              → 分工方式、依赖关系、运行边界
5-2 怎样交清楚并验收回来？    → 任务契约、结构化结果、聚合出口
5-3 好方法怎样反复使用？      → 可发现、可加载、可验证的 Skill
5-4 改动是否真的更好？        → 题集、Trace、评分器、采用决定
5-5 怎样落进真实交付？        → Skills + Subagent + Eval 平台

先比较两个订单任务。「补上当前用户过滤并验证」围绕同一处代码，读取、修改、测试紧密依赖；拆成读源码、修改、测试三个 Agent，只会增加版本与结果交接。「综合审查可维护性」则可以把架构、测试、权限、性能作为不同调查线，各自产出发现，再按统一规则汇总。文件多不等于可并行：沿路由、Service、数据访问层解释一条调用链，仍可能只是同一条调查线（笔记行 92–110）。

为什么不是「任务复杂就拆」？ 多 Agent 的收益是独立调查并行、压缩主历史、增加单独检查视角；代价是重复装配上下文、额外模型调用、结果合并、版本对齐、失败传播与复核。拆得不好时，这些成本真实发生，独立产出却不存在。当前任务只是补一个过滤条件，因此单 Agent 的短链路更合适；综合审查才出现值得比较的独立工作。材料没有给统一的收益阈值，工程师要用实际耗时、Token、发现质量与协调失败记录判断。

1. 概念与收益：委托不等于并行

Multi-Agent 描述多个 Agent 协作的形态；Subagent 强调主 Agent 委托子 Agent 的关系（笔记行 112–120）。主 Agent 保留整体目标，决定拆什么、等什么、怎样汇总、是否补查；子 Agent 在自己的任务状态与工具循环中，根据观察继续选择动作。同一个模型可以运行多个子 Agent；同一次模型调用换几个角色名称，不会自动形成多个 Agent。三个并行命令也只是三个确定任务，除非每个执行单元有自己的观察—决策循环。

Subagent 不要求并行。主 Agent 只委托一个子任务并等待返回，仍然是委托。它可能为了让子 Agent 阅读大量测试、把中间搜索留在自己的历史里，只交回覆盖项、缺失项与来源位置；也可能为了获得只读 Reviewer 的单独视角。收益要和额外调用与复核成本一起比较。

子任务上下文要够用而不扩权：当前需求、源码与测试入口、当前规则、快照标识；主 Agent 的猜测可标为待核对线索，但不必附上全部历史讨论。即使框架支持继承历史，也要按任务选范围——独立检查的一部分价值，正是减少未经复核结论的锚定（笔记行 136–140，承接 0017 的「本轮适用性」）。启动前至少能说清：检查哪些对象、回答什么问题、可用什么工具、交回什么证据、何时停止。

为什么「只交回摘要」不是丢信息？ 它是有意的上下文分工：大量 grep、阅读与试错留在子历史，主 Agent 只接收带来源的覆盖项、缺失项和待验证事项，避免主历史被中间搜索淹没。代价是主 Agent 不再天然拥有全部细节，所以摘要必须保留来源，关键结论仍能回读原文；不能为了短而只剩「已检查、无问题」。

2. 三种模式：统筹、执行与复核

模式解决的问题订单案例中的交付不能自动证明
Supervisor拆分、调度、收集、冲突识别、补查问题 / 证据 / 影响 / 优先级 / 验证方式四份报告拼起来就已复核
Planner / Executor计划与实际执行衔接，按事实修订当前步骤、实际结果、后续计划变化计划写完就等于按现场调整
Reviewer按独立标准复核当前产物有支持的结论、遗漏、待验证项独立会话就必然正确
为什么 Reviewer 不能当最终裁判？ 独立会话减少执行者先前结论的干扰，这是收益；但同模型可能重复相同错误，不同模型也可能共同误解业务规则。让它只看「已经修好」的叙述会进一步削弱独立性，因此要提供当前代码、真实 Diff、规则与测试证据，并把发现接回程序检查、行为测试和必要人工判断。多一层意见增加了检查机会，不等于创造一个绝对正确的真相源。

3. 并行与写入：依赖决定调度

谁能并行，由数据依赖决定，不由角色数量决定（笔记行 174–192）。架构与测试静态检查可读同一冻结快照；报告依赖专家结果，必须等待；修复后的测试依赖补丁成功，也必须等待。把「同时启动」当目标，会制造旧代码测试、新补丁报告这种版本错位。

多个 Agent 确实需要修改代码时，使用独立工作目录或工作树，各自保留补丁与被测快照，再按顺序集成并验证。工作树隔离的是文件版本，不自动隔离进程、网络、凭据和系统资源；写入范围仍要由执行机制控制。不要让修改 Agent 与测试 Agent 在同一个可变目录里一边改一边测，再把两份「完成」拼成验收结论。

为什么冻结快照比「大家都读最新文件」更可靠？ 后者看似减少同步，实际让不同角色在同一任务中看到不同输入，证据无法指向同一版本。冻结快照牺牲一点获取最新改动的灵活性，换来发现可比较、结果可复现。确实需要新改动时，应显式创建新快照、使旧证据失效并重验，而不是让文件在调查期间悄悄变化——与 0017 的 revision、0019 的旧证据失效同构。

4. 三层隔离：提示词不是权限

隔离至少分三层（笔记行 182–192）：

  • 上下文隔离：各自消息历史，交接使用带来源的结果摘要；不要把其他角色未复核结论默认当事实。
  • 工具隔离：每个角色只获得任务需要的读取、搜索、测试或写入工具；没有 write 工具是能力收窄。
  • 权限隔离：执行时检查实际路径、命令、网络、身份和写入范围；即使工具有写能力，也只能在授权范围内生效。
为什么有了工具白名单还要执行时权限？ 工具白名单减少可达动作，但同一个 write 或 bash 工具仍能接受不同路径、命令和参数；测试命令也可能写缓存、访问网络或加载插件。把检查放进 Prompt，依赖模型自觉遵守；放进 Runtime/Sandbox，才能把实际副作用拦在边界上。代价是策略与运行环境更复杂，但这是从「能力收窄」走向「后果受控」必须付的成本，与 0008/0013 的门禁和 Sandbox 同构。

5. 预算与取消：局部合规仍会全局超限

每个子任务要有时间、模型调用、工具调用与 Token 上限；主任务还要有全局预算，包含 Supervisor、所有专家、报告、重试与复核（笔记行 196–202）。并行可能缩短等待，不保证减少 Token：每个角色都要装配上下文、调用模型、输出结果，主 Agent 还要读取与整理结果。

局部检查：每个 child_usage ≤ child_limit
全局账目：Supervisor + Σ(children) + Report + Retries + Review ≤ global_limit

时间：由依赖图关键路径、排队与协调成本共同决定
Token / 费用：各次真实调用累计；不能用并行后的墙钟时间代替求和

证据不足时可以返回未完成和缺失材料，不能持续搜索耗尽全部预算。全局预算需要调度层真正记账与执行停止；只在 JSON 里写 limits 或提示词里写「节约 Token」不构成限制生效（5-2 会继续展开任务契约）。

为什么预算与取消要放在同一节？ 预算决定「还能继续多少」，取消决定「超过以后是否真的停下」。只有阈值没有取消传播，超限后子进程仍运行；只有本地 kill 没有全局账，也无法判断其他角色、重试和复核是否继续消耗。两者共同保证系统能可靠结束。代价是必须维护父子运行关联和部分结果状态，而不是简单 Promise.all 等所有任务。

6. 冲突仲裁：测试绿与越权可同时成立

Test Agent 说「现有测试通过」，Security Agent 说「没有用户过滤」，两者并不必然矛盾：现有测试可能根本没有跨用户场景。本课 fixture 正是这样：test_list_not_empty 只断言列表非空；真实 SQLite 探针却返回用户 10 和 20 的订单，查询次数从 4 增至 7。性能角色提出 N+1 风险，也要用 SELECT 计数独立验证，不能拿用户隔离探针代替性能检查（笔记行 210–216）。

为什么冲突处理不是「让 Supervisor 再判断一下」？ 多一次模型判断仍可能误读同一材料，投票更会把证据问题变成人数问题。先拆范围与版本，可以识别「两个结论其实都成立」；再做行为探针，可以把静态猜测变成实际观察；权威规则仍不清时，升级给有权确认的人。代价是增加定向验证与等待，但避免把冲突悄悄压成一份貌似一致的报告。

7. pi 实现：独立进程、并发与取消

课程材料给了两种入口：PPT 使用 pi install npm:pi-subagent-extension，学习笔记使用 pi -e "$PI_SOURCE/.../subagent/index.ts"。本课实际核对的是官方源码示例，不是据此推断所有同名 npm 包或旧版本行为。固定阅读版本：earendil-works/pi@9c465268。官方 README 明确：每个子 Agent 是独立 pi 进程，具备独立上下文、流式输出与取消支持；parallel 为最多 8 项、同时 4 项。

源码位置（固定版本）本课需要理解的职责不要误读成
runSingleAgent组装 --mode json -p --no-session、角色工具与模型参数，启动并收集一个子 Agent只是同一会话里换 system prompt
spawn 与 abort独立子进程；取消先 SIGTERM，5 秒未退出再 SIGKILL；保留状态与错误停止等待就等于所有远端工作停止
mapWithConcurrencyLimitworker 数量受上限约束，结果按输入下标写回，保持结果顺序最多 8 项就等于同时跑 8 项
Limitations每项输出有 50 KB 上限；子用量展示在 details，不自动加入父会话 usage示例已经实现完整全局预算与 Sandbox

因此图 6 的全局账在示例上仍要由 Harness 补：父会话 usage 不包含子任务总量，必须关联父子运行、读取各子任务 usage 后统一累计。当前源码还显示：未指定模型时子 Agent 继承调度会话模型与 thinking level；项目级角色默认不加载，启用时需注意仓库提示词来源与确认机制。角色文件里的 tools: read, grep, find, ls 是工具范围，不是操作系统 Sandbox。

主 Agent 的模型调用
  └─ subagent 工具调用（真实事件，不是文字计划）
      └─ parallel: tasks = [task A, task B]（最多 8 项）
          └─ mapWithConcurrencyLimit（同时最多 4 项）
              └─ runSingleAgent → spawn 独立 pi 子进程
                  ├─ 独立任务状态、消息历史与工具循环
                  ├─ AbortSignal → SIGTERM → 5s 后 SIGKILL
                  └─ 返回各自状态、结果、错误与 usage
  └─ 主 Agent / Harness 复核：来源、冲突、未完成、全局预算

怎样证明委托确实发生？ 至少看三处（笔记行 244–254）：① 实际记录出现 subagent 工具调用；② 参数以 tasks 数组传入两项任务；③ 返回结果分别保留两项检查，并能关联各自执行。模型说「我会并行」只是计划。若没有工具调用，先查扩展注册、加载错误与工具可见性，不把普通回答当演示成功。这次演示只证明委托与结果返回；没执行测试就不能宣称业务验收通过。

为什么要从实现确认「独立状态」？ 界面同时出现两个角色卡片，可能只是同一模型输出排版；源码中每个任务启动独立 pi --no-session 子进程，才为这份示例的独立上下文提供机制依据。相反，独立进程并不自动提供业务正确、全局预算或操作系统隔离。阅读实现的目的不是背 API，而是把每个宣传词落到具体机制与未覆盖边界。

8. 面试视角：两分钟主链 + 追问链

两分钟主链（先脱稿，再对照）：

我会先判断任务是否值得拆，而不是先选多 Agent 框架。筛选看三点：子任务能否独立产出可验收结果、信息或视角是否明显不同、结果能否按统一规则合并；最后还要比较并行、上下文压缩和独立检查的收益是否超过交接成本。Subagent 是主 Agent 委托具有独立任务状态和工具循环的子 Agent，不要求并行，同一个模型也能跑多个子 Agent。模式上，Supervisor 管拆分、依赖、汇总与补查，Planner/Executor 让计划随执行事实调整，Reviewer 复核当前产物，但独立意见仍要接回程序和行为验证。调度看依赖 DAG，隔离分上下文、工具、权限三层，写任务用独立工作树与快照。预算同时记局部和全局两本账，取消传到模型流、工具和子进程，并保留远端未知。冲突不投票，先核对范围与版本，再用真实行为探针补证。最后在工具记录里确认 subagent 调用、tasks 参数和各自结果，而不是相信一句「已并行」。

面试官可能继续追问：

  1. 「文件很多，为什么不直接拆？」——文件数量是阅读范围，数据依赖才决定并行；一条调用链仍可能适合单 Agent。
  2. 「只起一个 Subagent 有什么意义？」——可以隔离大量中间历史或提供单独检查视角，但要算额外调用与复核成本。
  3. 「Reviewer 独立了，为什么还要测试？」——独立减少锚定，不消除共同误判；最终发现仍需规则、程序校验和真实行为支持。
  4. 「每个子 Agent 都限 1000 Token，为什么还会超？」——父 Agent、所有子项、报告、重试和复核是另一本全局账。
  5. 「你已经 cancel，为什么结果仍 unknown？」——本地等待或进程停止，不证明远端请求、已发写操作和费用状态都确定。

实验 ③：依赖调度与并发上限——改 2 为 1，变化的是速度不是依赖（必做）

  • 先写预期：limit=2 与 limit=1 的 peak 各是多少？report 能否在任一专家结束前开始？结果顺序会不会随完成先后变化？
  • python3 -I - <<'PY'
from concurrent.futures import ThreadPoolExecutor
from threading import Lock
from time import monotonic, sleep

TASKS = {
    'freeze': ([], 0.02),
    'architecture': (['freeze'], 0.12),
    'test': (['freeze'], 0.16),
    'security': (['freeze'], 0.10),
    'report': (['architecture', 'test', 'security'], 0.03),
}

def schedule(limit):
    active = peak = 0
    lock = Lock()
    started = monotonic()
    timeline = {}
    def run(name):
        nonlocal active, peak
        with lock:
            active += 1
            peak = max(peak, active)
        begin = monotonic() - started
        sleep(TASKS[name][1])
        end = monotonic() - started
        with lock:
            active -= 1
        timeline[name] = (round(begin, 3), round(end, 3))
        return name + '-result'
    remaining = set(TASKS)
    results = {}
    while remaining:
        ready = [name for name in TASKS if name in remaining
                 and all(dep in results for dep in TASKS[name][0])]
        assert ready, '依赖图存在环或缺失节点'
        with ThreadPoolExecutor(max_workers=min(limit, len(ready))) as pool:
            for name, value in zip(ready, pool.map(run, ready)):
                results[name] = value
                remaining.remove(name)
    assert timeline['report'][0] >= max(timeline[n][1] for n in ('architecture', 'test', 'security'))
    return {'limit': limit, 'peak': peak, 'elapsed': round(monotonic() - started, 3),
            'report_start': timeline['report'][0], 'result_order': list(results)}

print(schedule(2))
print(schedule(1))
PY
    本机一次实测：limit 2 → peak 2、约 0.287 秒；limit 1 → peak 1、约 0.454 秒；两种情况下 report 都等三类检查结束，result_order 都按 DAG 定义顺序。这个脚本只是本地教学调度器，不是 pi 实现：它演示依赖与上限，不证明模型子进程治理已经完整。

from pathlib import Path
import tempfile

root = Path(tempfile.mkdtemp(prefix='isolation-0023-'))
target = root / 'tests' / 'test_orders.py'
target.parent.mkdir()
target.write_text('original')

# 只有提示词「只读」，宿主仍给了可直接写文件的能力。

def guarded_write(tools, root, relative, content):
    if 'write' not in tools:
        return 'TOOL_NOT_GRANTED'
    path = (root / relative).resolve()
    if not path.is_relative_to(root):
        return 'PATH_DENIED'
    path.write_text(content)
    return 'WRITTEN'

escape_result = guarded_write({'write'}, root, '../outside.txt', 'blocked')
usage = {'supervisor': 400, 'architecture': 600, 'test': 500,
         'security': 400, 'report': 200, 'review': 100}
local_limit = 800
global_limit = 2000
children = ['architecture', 'test', 'security']
local_ok = all(usage[name] <= local_limit for name in children)
total = sum(usage.values())
print({'prompt_only_test_changed': prompt_only_changed,
       'scout_write': scout_result, 'escape_write': escape_result,
       'each_child_within_800': local_ok, 'total_tokens': total,
       'global_within_2000': total <= global_limit})

assert scout_result == 'TOOL_NOT_GRANTED'
assert escape_result == 'PATH_DENIED'
