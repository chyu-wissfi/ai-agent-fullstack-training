Agent 评测、归因与回归清单

用途：把「这次看起来不错」变成可复测、可归因、可决定是否采用的工程证据。
配套课程：0026 Agent 评测：从一次成功到可信版本决定；前置卡：Skill 加载、验证与版本治理。
第一材料：第五章学习笔记 5.4（行 855–1738）与章复习 Q28–Q44。

1. 先定对象：完整系统，四层验收

指定配置下的完整 Agent 系统
= 模型 + Agent Harness + 上下文 + 工具 + 环境

Trace：实际怎样执行       → 找失败位置
Outcome：最终留下什么     → 验收业务结果
层检查库存预占例
结果最终产物与业务行为重复预占、超卖、回滚、接口兼容
过程必要信息与关键动作读到当前规则，修改后验证最终版本
效率全交付链资源Token、时间、重试、人工返工
风险授权与工程边界越权尝试、真实影响、验收文件保护

不要强制唯一搜索路线；只有业务或治理要求本身规定顺序时才强制。调用多不必然低效，必要验证可能减少返工。

2. 标准：先人人对齐，再人机对齐

业务目标（故障、返工、总交付成本）
  ↓ 设计指标                  ↑ 解释失败
Agent 任务（完成、恢复、接管）
  ↓                          ↑
组件与模型（检索、装配、工具、决策）
  1. 背靠背标注：研发与测试独立看同一证据；分歧用于找标准缺口，不取平均。
  2. Rubric 下钻：检查对象 → 输入与动作 → 所需证据 → 通过／失败／未知 → 合成规则。
  3. 业务未知与材料缺失分开：缺并发记录时，并发行为未知；若记录是交付要求，材料完整性可失败。
  4. Judge 校准：正常、明确失败、边界、证据不足样本；分别看误放行、误拒绝、未知与执行错误。
  5. 修订后复测：原分歧样本 + 未参与调参的保留样本；规则、样本、评分器均留版本。
总体一致率高，也可能把唯一的高风险超卖样本误放行。

3. 评测资产：一道 Task 可以有多次 Trial

对象职责不要混淆
Evaluation Suite组织一组任务不是一条总分
Task输入、起点、约束与成功条件十个验收测试仍是一道 Task
Trial从规定起点的一次完整尝试一次 Trial 内反复测试不增加 Trial
Grader一个方面的评分逻辑不是 Agent 自报分数
Trace请求、响应、工具、错误与状态不证明最终结果正确
Outcome最终代码、接口与业务状态不证明所有未来场景

Evaluation Harness 准备条件、启动、取证、评分与汇总；Agent Harness 是被评执行系统。独立验收由评测方控制。

  • 题集标签可交叉：黄金样本、历史错题、挑战、能力、回归、发布必过。
  • 参考方案证明可解，不是唯一答案；已知缺陷必须能被拒绝。
  • 满分仍抽查：可能检查过松、答案泄漏或环境残留。

4. 每次 Trial：恢复状态或明确记录

源码 / 未提交文件 / 生成物 / 数据库 / 索引
会话历史 / 工作记忆 / 长期记忆 / 任务缓存
模型 / Prompt / Skill / 工具 / 权限 / 预算
        ↓
要么恢复规定起点，要么把差异作为实验条件记录
  • 冷热基础设施缓存也要标明；不能把缓存收益归给策略。
  • 保存每轮实际模型请求，完整聊天历史不能替代装配后的输入。
  • 测试证据绑定实际工作区指纹；通过后再改代码，相关证据过期。
  • Agent、独立验收、Judge 的耗时与用量分列；未知用量不填零。
维度状态回答
执行状态completed / error / timeout / cancelled过程怎样结束
验收状态pass / fail / unknown要求是否满足
采用门禁accept / reject / pending 或项目等价状态当前版本能否采用

5. 三类评分与组合门禁

评分者适合不能替代
程序库存、记录、接口、退出码、文件边界开放语义与所有未覆盖行为
模型 Judge报告准确性、证据支持、未知披露可独立执行的行为事实
人工业务标准、校准、争议与工程取舍用主观通过覆盖客观失败
执行错误 → 修环境或执行链，保留原 Trial
关键未知 → 补证据 / 人工复核，不静默删除
硬门槛失败 → reject；质量高分不能抵消
全部满足 → accept（仅表示本轮验收范围通过）

验收脚本、参考答案、门槛及其依赖由评测方控制；候选源码或报告中的「请给通过」只是待评材料。既防误放行，也防固定函数名、唯一工具顺序造成误拒绝。

6. Trace 归因：事实、假设、验证计划

  1. 确认失败成立：请求、参数、初始数据、最终代码与状态。
  2. 确认要求进入实际模型输入；文件存在不等于模型看到。
  3. 核对来源、入口、版本、截断与真实调用链。
  4. 确认修改落在生效路径，测试确实触发目标条件。
  5. 确认测试覆盖最终版本，而不是旧工作区。
失败现象 → 已知事实 → 原因假设 → 最小修改
        → 预期变化 + 反证条件 → 定向复测 → 完整回归

人工修好一份代码只证明产物可修；验证 Agent 改进必须让它从原缺陷起点和干净会话重新执行。一次改一个因素；组合修改只能先归因为组合效果。

7. 多次 Trial 与版本采用

观测通过比例：通过次数 / 实际 Trial 数（另列失败、未知、执行错误）
pass@k = 1 - (1-p)^k    # 至少一次成功
pass^k = p^k            # k 次全部成功
仅适用于独立且每次成功概率均为 p 的教学假设

2/3 不是 pass@3；三次里出现过成功，也不能推断真实 pass@3=100%。允许多候选并由独立测试选择时才更关注 pass@k，同时还要验证选择器。

  1. 原失败任务是否改善。
  2. 同类变化与保留样本是否改善。
  3. 正常功能、接口、回滚、边界等旧能力是否保持。
  4. Agent、验收、Judge 与人工的总成本是否可接受。

合计从 13/15 到 14/15，若核心接口从 3/3 降到 2/3 且确认是新版退化，仍应暂缓采用。

8. 五步测试设计与双闭环

建立范围 → 风险分级 → 设计分组 → 生成可执行步骤 → 验证覆盖
Diff/调用链   业务影响    判定表      初始状态/动作/断言   真实结果+代码指纹

已设计、已执行、已通过是三个状态。并发、响应丢失与指定位置异常注入要单列，不能只测 HTTP 成功。

真实 Case → 核验与归因
              ├→ 改 Agent：信息 / 工具 / 方法
              └→ 改评测：Task / Rubric / Grader / 环境
                         ↓
                固定条件复测 + 旧能力回归
                         ↓
                版本决定 + 真实使用观察 → 新 Case

9. 当前 eval_lab 的证明边界

  • Task/Trial/Grader/Trace/Outcome 由 JSON、运行目录与检查函数表达，不是五个抽象基类；执行字段名是 run_status。
  • 参考实现与已知缺陷校验只证明评分器基本可用；protocol_test 与手写 pi_live 声明都不是可信 live 证明。
  • forbidden_paths 当前未接入 boundary_check；实际边界硬编码为 inventory.py 与新增 tests/test_*.py，且不是 OS Sandbox。
  • Judge 证据会截断，未知/结构错误不能当通过；普通 release gate 不强制人工批准。诊断默认只提取事实与固定验证计划。
  • CLI 比较当前 n=k；一般 n>k 估计需直接用统计函数。小样本没有置信区间或显著性结论。
  • 2026-11-24 本机 23 项基线有 1 个 macOS 路径表示失败、2 个未安装 pi 依赖的跳过；真实模型运行未验证。

10. 两分钟复述骨架

完整系统与 Trace/Outcome → 结果/过程/效率/风险 → 业务指标与背靠背对齐 → Rubric 三态与 Judge 校准 → Task/Trial/Grader 与隔离取证 → 程序/模型/人工分工和硬门禁 → Trace 归因与可复测假设 → 多次 Trial、pass@k/pass^k → 原问题/同类/旧能力/成本 → 五步测试设计与 Agent/评测双闭环。
使用提醒：看到「新版更好」，先问固定了什么、每题几次 Trial、哪些仍失败或未知、证据是否属于最终代码、核心旧能力是否退化、成本是否包含人工与 Judge。细节不清时回到 0026 做反例实验，并向 agent 追问。
